Why EKS?

  • Container Image 구동 시

  • Pod가 생성

  • K8s의 Self-Healing등의 관리는 안 됨

  • Replica, Deployment 생성

  • 감시 기능이 필요 → Running 개수 유지

  • 배포 전략, Rollback 관리

  • Pod는 다음과 같은 순서로 생성

  • 명령어로 확인해 보면

  • Deployment를 생성하고

  • Replica를 생성

  • Pod를 생성

  • K8s Cluster 구조

  • Component 들

  • Component의 Watch 메커니즘

  • watch는 Pub/Sub 패턴의 subscribe와 유사

  • API 서버는 etcd를 watch 하고 있는데 API 서버에서 변경사항이 발생하면 etcd로 업데이트

  • etcd에서 변경사항이 발생하면 watch하고 있는 대상에게 알림을 보냄

  • API 서버도 watch하고 있는 Component에 알림을 보냄

  • 다음과 같이 watch가 됨

  • kubectl run nginx —image=nginx

  • Deploy 과정을 살펴 보면

  • Component는 API 서버를 watch 하고 있음

  • kubectl로 run 하면

  • Node 선정 방법

  • Kubelet에는 docker에서 사용되는 c-advisor가 경량화 되어 탑재

  • c-advisor는 node metric data를 수집하여 전송

  • 그 외에 affinity (어떤 node가 오면 좋겠다), taint (어떤 node는 오지 않으면 좋겠다) 설정을 확인

  • 우선 순위에 따라 Pod 할당 순서가 결정

  • kubelet이 Pod를 생성

  • 만약 API 서버에 장애가 발생하면

  • 다른 component들은 Pod로 구성되어 있어 장애가 발생해도 Pod가 재 실행되어 영향을 주지 않지만

  • API 서버 장애가 발생하면 전체 서비스에 영향을 주게 되어 HA를 구성해야 함

  • etcd에 장애가 발생한다면

  • etcd에 cluster의 모든 data가 저장되기 때문에 HA를 유지해야 함

  • etcd는 내부적으로 consensus 알고리즘인 Raft를 사용

  • 과반수 투표를 통해 결정하기 때문에 홀수로 HA 구성

  • Amazon EKS가 위의 복잡한 과정을 관리

  • Worker Node는 보통 EC2 instance에 구성하여 사용자가 관리하게 되는데 Amaozn EKS에서 Node Group을 통해 생성 관리를 해 줌

Network

  • Docker network - docker0

  • net option으로 container의 network를 공유

  • K8s에서는 network 공유를 위해 Pause라는 container를 만들어 사용

  • Pod를 만들면 그 안에 여러개의 container를 생성하게 되는데 동일한 IP를 부여 받음

  • Host를 추가 하면

  • Router가 traffic을 분배

  • 만약 container가 동일한 IP를 가지고 있다면 어디로 routing을 해야 하는가?

  • Container별로 다른 IP를 할당

  • 이 방법을 Overlay Network 이라고 함

  • K8s에서는 plug-in 으로 제공

  • AWS에서는 AWS CNI를 사용

  • 다른 plug-in은 가상 IP를 할당 받음

  • AWS CNI는 가상 IP가 아닌 실제 VPC IP를 받음

  • IP Range에 대한 고려 필요 - Pod 생성 실패할 수 있음

  • ENI 제한으로 Pod 생성 실패할 수 있음

  • IPAM - ENI의 IP를 Pod에 할당해 주는 AWS CNI에 포함된 demo set, IP manager

  • ENI에서 할당 할 수 있는 IP의 개수를 초과하면 추가적으로 ENI를 생성
