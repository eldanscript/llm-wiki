DHCP

  • domain-name : ap-northeast-2.compute.internal

  • domain-name-server : AmazonProvideDNS

DNS

  • DNS IP 4개 까지 지정 하거나 AmazonProvidedDNS 사용

  • NTP 및 NetBios name server도 4개 까지 지정 가능

Subnet

  • VPC Subnet은 항상 하나의 AZ에 연결

CIDR (Classless Inter Domain Resolution)

  • Subnetworking을 위한 표시 규약

  • Subnet mask는 NID bit와 HID bit로 구분

  • NID (Network Identifier)

    • Netmask : NID bit 크기

    • 10.0.0.0/16 → Netmask는 16 bit : 10.10.x.x

  • HID (Host Identifier)

    • 32bit - NID bit

    • 10.0.0.0/16 → HID 16bit로 2^16개의 Host를 가질 수 있음

  • Subnet Block address

    • 10.0.0.0/16

    • 1st Block : 10.0.1.0/24 → 2^8 (10.0.1.0 ~ 10.0.1.255) 개의 IP 주소를 가짐

    • 2nd Block : 10.0.2.0/24 → 2^8 (10.0.2.0 ~ 10.0.2.255) 개의 IP 주소를 가짐

Reserved IP

  • CIDR example : 10.0.0.0/16

  • 총 5개의 주소가 예약

  • Network address (Subnet ID) : 10.0.0.0

  • VPC Router : 10.0.0.1

  • DNS : 10.0.0.2

  • Future Use : 10.0.0.3

  • Broadcast Address : 10.0.255.255

    • VPC에서는 브로드캐스트를 지원하지 않으므로, 이 주소를 예약하여 사용

VPC Peering

  • Private IP 주소를 사용하는 direct route를 통해 한 VPC를 다른 VPC에 연결

  • 연결된 instance가 동일한 network에 있는 것처럼 동작하도록 구성

  • 동일 region, cross region, cross account 실행 가능

  • Transitive peering 미 지원 → Star Topology 유사 구조로 peering

  • VPC Peering으로 많은 지점 연결 시 관리 overhead를 피하기 위해 AWS Transit Gateway를 사용

NAT Gateway

  • Private Subnet의 instance에 Internet access를 위해 사용

  • IP header를 수정하여 packet의 IP 주소를 다시 mapping

  • Private Subnet의 NAT 서비스 방법

    • NAT Gateway : AWS의 Managed 서비스

    • NAT Instance

  • NAT Gateway는 SG과 연결되지 않음

  • RT내 route 추가

  • AZ에 span (걸쳐있음) 되지 않음 → 고 가용성을 위해 리전별로 최소 2개의 AZ에 NAT Gateway 설정 필요

💡

The point here is that a subnet can only span one AZ anyway, so your question is kind of meaningless. If one AZ is down, all subnets associated to that AZ is down. If you have high availability, you would have multiple subnets spanning multiple zones - each zone’s private subnets would point to a NAT Gateway in that zone’s public subnet, with separate routing tables for each zone. That gives you the high availability

  • IPv6 미 지원 → 송신 전용 IGW 사용

IGW

  • VPC당 하나의 IGW 연결

RT

  • Main RT에는 두 개의 routing이 AWS에 의해 생성

    • IPv4 subnet 용

    • IPv6 subnet 용

NACL & SG

  • AWS에서 생성하는 기본 NACL은 모든 inbound와 outbound traffic을 허용

  • 사용자 정의 NACL은 모든 inbound와 outbound traffic을 거부

  • 모든 Subnet은 한 번에 하나의 NACL과 연결

  • 단일 NACL은 여러 Subnet과 연결

  • 번호가 가장 낮은 규칙부터 평가

    • 규칙에 일치하는 트래픽이 있으면 이와 모순되는 상위 규칙이 있더라도 적용

    • 100의 배수로 규칙 번호 사용 권장

  • Asterisk 기본 규칙은 패킷이 다른 어떤 규칙과도 일치하지 않을 경우에 거부되도록 되어 있음

  • NACL은 특정 IP 주소 차단이 가능하지만 SG에서는 불가능

  • NACL은 SG보다 먼저 평가

  • NACL은 모든 port에 대해 inbound와 outbound traffic을 명시적으로 허용해야 함

  • NACL은 Subnet level, SG은 instance level의 가상 방화벽 역할

  • SG은 허용 규칙만 지정

  • NACL은 Stateless

  • SG는 Stateful

    • Inbound traffic은 SG 최초 생성 시 규칙이 없음 → 다른 host에서 instance로 가는 inbound traffic 허용되지 않음

    • Inbound 요청을 허용하면 outbound 규칙과 관계없이 outbound로 요청에 응답이 허용

    • outbound traffic은 SG 최초 생성 시 모두 허용하는 규칙 포함 → 규칙 제거하여 특정 outbound traffic만 허용 가능

    • Instance에서 요청 보내는 경우 (outbound 전송) 이에 대한 응답은 inbound 규칙에 관계없이 허용

VPC Endpoint

  • VPC에서 지원되는 AWS 서비스에 비공개로 연결 → public IP 주소 불 필요

  • VPC Endpoint는 일종의 고가용성 가상 장치

  • AWS PrivateLink로 구동

Interface Endpoint

  • 지원되는 서비스에 traffic을 허용하는 Private IP가 있는 ENI → traffic 진입점

  • API Gateway, CloudWatch, Config, KMS 등 20여개 서비스 가능

Gateway Endpoint

  • NAT Gateway와 같이 Pirvate IP가 없음

  • S3, DynamoDB

Gateway Load Balancer Endpoint

  • Subnet IP 주소 범위에서 IP 주소를 사용하는 ENI

VPC Flow Log

  • VPC간 IP traffic capture

  • CloudWatch log 또는 S3 bucket에 게시

  • Allow 또는 Deny traffic 선택 기록

  • VPC level, Subnet level, NIC level 등으로 생성 가능

  • Flow log 구성은 생성 후 변경 불가

  • Monitoring 불가능 traffic

    • VPC의 reserved IP 주소 traffic

    • DHCP

    • Instance metadata query : 169.254.169.254

    • Instance를 통해 Amazon DNS 연결 traffic

    • Window license activation traffic
