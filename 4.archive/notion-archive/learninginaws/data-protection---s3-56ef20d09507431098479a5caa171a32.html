AWS 지원 기본 ACL : Canned ACL

  • private, public-read, public-read-write

  • aws-exec-read, authenticated-read

  • bucket-owner-read, bucket-owner-full-control

  • log-delivery-write

  • API 호출 시 x-amz-acl request header를 사용하여 ACL 지정 가능

Summary

  • S3 객체는 생성시 계정 소유자 외에는 접근 권한이 없음

  • 기본 ACL은 리소스 소유자 (계정 소유자)에게 모든 권한을 부여하고 다른 모든 사용자에게 아무것도 허용하지 않음

  • ACL은 권한 부여만 가능하고 접근을 거부할 수 없음

  • ACL은 XML 형식으로 표현

  • ACL은 IAM policy 혹은 bucket policy 중 하나를 사용하는 것이 좋음 (?)

    • ACL은 각 자원에 따라 지정

    • Bucket 혹은 IAM policy는 bucket과 하위 경로로 지정

  • ACL 사용 Case

    • Bucket 소유자가 소유하지 않은 객체에 대한 접근을 허용 : 계정 사용자가 객체를 다른 계정의 bucket에 업로드 한 경우 등

    • S3 log delivery group에 권한을 부여하는 데 사용

    • 다양한 객체에 고유한 권한을 부여 → Bucket policy도 가능 하지만 ACL 관리 하는게 더 효율적

Process

  • 계정 B에서 계정 A bucket에 file upload

  1. 계정 B의 canonical id가 bucket write를 할 수 있는 ACL을 생성한 후 계정 A의 bucket ACL에 업데이트

  2. 계정 B에 계정A의 bucket에 s3:PutObject 및 s3:PutObjectAcl을 수행할 수 있는 정책을 생성한 후 계정 B의 사용자 그룹에 정책을 연결

  3. 계정 B에서 계정 A bucket에 upload test

  4. 계정 B에서 계정 A bucket의 ACL을 수정하여 권한 추가 : PutObjectAcl 허용으로 가능해 짐

  5. ACL 대신 Bucket policy를 생성하여 동일 절차 진행 가능

    1. Principal에 IAM 사용자 추가

Additional

계정 B에 접근 권한 부여

1-1. 계정 A 관리자가 Bucket policy 혹은 ACL을 통해 계정 B에 접근 권한 부여

  • A의 S3 bucket에 접근 policy를 생성하는데 여기에 계정 B의 Canonical ID에 대해 명시

1-2. 계정 B 관리자는 계정 B 사용자에게 부여된 접근 권한을 위임

  • 계정 B IAM 사용자 또는 사용자 그룹에 policy를 추가

  1. 계정 A 관리자가 Bucket policy로 계정 B 사용자에게 바로 접근 권한 부여

    • A의 S3 bucket에 접근 policy를 생성하는데 여기에 IAM User로 계정 B 사용자를 명시

3-1. 계정 A 관리자는 S3 bucket에 대한 접근 권한이 있는 역할을 생성하고 Trust relationship에 계정 B를 추가

3-2. 계정 B 관리자는 계정 B 사용자에게 부여된 접근 권한을 위임

  • 계정 B IAM 사용자 또는 사용자 그룹에 policy를 추가

추가 시나리오

  1. 계정 A bucket에 AllUsers에 대한 PutObject ACL 권한 부여

    1. A 관리자로 부터 사용자 policy에 추가 되지 않은 (접근 권한이 없는) A 사용자가 bucket에 파일 업로드가 가능한가? → Yes

    2. 사용자 policy에 추가 되지 않은 (접근 권한이 없는) 다른 계정 사용자가 bucket에 파일 업로드가 가능한가? → No

    3. 사용자 policy에 추가 되지 않은 (접근 권한이 없는) 다른 계정 관리자가 bucket에 파일 업로드가 가능한가? → Yes

  2. 계정 A bucket에 계정 ID를 사용해 계정 B에 PutObject ACL 권한 부여

    1. 사용자 policy에 추가 되지 않은 (접근 권한이 없는) 계정 B 사용자가 bucket에 파일 업로드가 가능한가? → No

      1. 계정 B 사용자는 B 관리자로 부터 접근 권한을 위임 받아야 함 (my opinion)

    2. 계정 B 관리자가 bucket에 파일 업로드가 가능한가? → Yes

  3. 계정 B는 계정 A에 교차 login 할 수 있는 권한으로 파일을 업로드 했지만 ACL은 없음

    1. S3를 소유하고 있는 계정에서 정책이 추가되지 않은 권한 없는 사용자가 해당 파일에 접근 가능한가? → No

    2. S3를 소유하고 있는 계정에서 관리자가 해당 파일을 읽을 수 있는가? → No

    3. S3를 소유하고 있는 계정에서 관리자가 해당 파일을 삭제 할 수 있는가? → Yes

  4. 계정 A에 bucket을 생성하고 bucket policy를 통해 계정 B 사용자 testuser에게 PutObject 권한을 직접 부여

    1. 계정 B testuser가 추가 권한 없이 계정 A bucket에 파일 업로드 할 수 있는가? → No

      1. 계정 B 사용자는 user policy를 통해 권한을 위임 받아야 함

    2. 관리자 권한으로 계정 B에서 계정 A bucket에 파일 업로드가 가능한가? → No

  5. 계정 B 관리자가 계정 A가 부여한 것 보다 더 많은 접근 권한을 사용자에게 위임할 수 있는가? → Yes

    1. 부여된 권한을 통해 계정 A에서 권한이 재평가되어 권한 오류가 발생하거나 다른 영향이 없음

  6. ACL 사용을 bucket policy로 강제로 사용하게 할 수 있는가? → Yes

    1. Policy condition 항목을 통해 s3:x-amz-acl 조건 키 값을 확인하도록 하여 사용할 수 있음 : bucket-owner-full-control 값 확인 등

Encryption method

Server-side encryption

  • 파일 암호화에는 대칭키 사용

  • 파일 전송에는 비대칭키 사용

  • SSE-S3

    • S3 관리 키 사용

    • Envelop encryption 사용

    • 각 객체는 고유 파일로 암호화 → 객체별로 다른 암호화 키 존재(?)

    • AES-256

    • 데이터 키는 Master 키로 암호화 → 주기적으로 교체

    • 사용 요금 미 발생

  • SSE-KMS

    • KMS 키 사용

    • Envelop encryption 사용

    • S3 외에 여러 서비스에서 키 공유 가능

    • Master 키 생성 및 교체 / 비활성화, 데이터 키 생성 등을 효과적으로 제어 가능

    • AES-256

    • 객체 업로드 시 암호화에 사용할 키 선택 가능

    • CloudTrail로 KMS API 호출 모니터링 가능하여 Audit에 활용

    • 사용 요금 발생

  • SSE-C

    • 고객이 키를 관리

    • 고객은 데이터와 함께 키를 제공하고 S3는 키를 암호화 하거나 삭제하는데 사용

    • 복호화를 위해 반드시 키를 제공해야 함

    • 대칭키를 업로드하기 때문에 업로드하는 동안 HTTPS 사용

    • Envelop encryption 미 사용

    • AES-256

    • 사용 요금 미 발생

Example Case

  • 버전 관리 활성화 후 동일 객체를 2번 PUT 할 경우 몇 개의 객체 version을 사용할 수 있는가? → 3개

  • 버전 1을 활성화하고동일 객체를 2번 PUT 해 버전1, 버전2 두 가지 버전을 생성. 그 후 버전 3를 비활성 (vesion suspending)화하고 동일 객체를 다시 PUT해 버전 3를 생성하고 나중에 객체를 삭제해 봤다. 이 객체를 복원할 수 있는가? 그렇다면 어떤 버전이 최신 버전인가? → 객체 2가 최신 버전이 된다

Cross Region Replication

  • Bucket 데이터가 다른 리전의 bucket에 비동기적으로 복사 됨

    • 데이터 내구성 향상과 DR 지원을 위해 사용

    • Compliane 또는 latency 개선을 위해 사용

  • S3에 대상 bucket에 복제할 수 있는 권한이 필요

  • IAM Role

Summary

  • Cross region replication은 SSL을 통해 구성

  • CRR 활성화 후 추가되는 파일부터 적용

  • 소스 bucket 소유자에게 객체 읽기 권한이나 ACL 읽기 권한이 없는 경우 복제 되지 않음

  • 소스 객체의 ACL이 복제되지만 대상 bucket 소유권이 변경되지는 않는다

  • SSE-C 암호화 사용 객체는 복제 되지 않음

  • SSE-KMS 객체를 복제하려면 S3가 KMS 키를 제공해야 한다. 이럴 경우 KMS 요청 제한이 초과될 수 있음

  • 하위 리소스 변경에 대한 복제는 지원하지 않음

  • 대상 bucket에서 파일을 복제할 수 없음

  • 소스 bucket에서 버전을 삭제해도 대상 bucket의 버전은 삭제되지 않음
