AI Agent와 함께 일하는 시대, 우리가 바꿔야 할 것들

AI Agent와 함께 일하는 시대, 우리가 바꿔야 할 것들

2026년 6월 06일33 min read

TL;DR

AI Agent에게 코드를 짜게 하는 건 쉽다. 하지만 Agent가 잘 일하게 만드는 건 완전히 다른 문제다. 기존 개발 환경은 “사람이 읽고 이해하는” 것에 최적화되어 있다. Agent가 효율적으로 일하려면 개발 환경 자체를 재설계해야 한다.

이 글은 39개 AI Agent로 웹툰 제작 플랫폼을 만들면서 직접 부딪힌 문제들과, 실험으로 검증한 해결책을 공유한다.

도입: Agent는 매일이 첫 출근(Day 1)이다

사람은 프로젝트에 익숙해지면 “어디에 뭐가 있는지” 직감적으로 안다. 이미지 생성 버그? → [generator.py](http://generator.py) 먼저 봐야지. 이런 직감은 수개월의 경험에서 나온다.

Agent는 다르다. 매 세션마다 처음부터 시작한다. 컨텍스트 윈도우가 리셋되면 프로젝트에 대한 모든 기억이 사라진다. 어제 완벽하게 작업을 끝낸 Agent도 오늘은 다시 Glob → Grep → Read를 반복하며 프로젝트 구조를 탐색해야 한다.

우리 프로젝트(InstaToon)는 백엔드 8모듈 + 프론트엔드 7모듈, 총 280개 이상의 소스 파일을 가지고 있다. Agent가 매번 이 파일들을 처음부터 뒤지는 건 엄청난 낭비다.

이 문제를 어떻게 해결했는지, 그리고 해결하면서 깨달은 “AI Agent 시대에 바꿔야 할 것들”을 공유한다.

1. Agent에게 지도를 줘라

문제: 맹목적 탐색

Agent에게 “이미지 생성에서 스타일 참조가 어떻게 작동하는지 알려줘”라고 하면 이런 일이 벌어진다:

10개의 질문을 던져보니, 평균 9.2회의 tool call과 452줄의 코드 읽기가 필요했다. Token 소비량은 질문당 약 12,500토큰.

해결: CODE_GRAPH.yaml - 코드베이스의 지도

Microsoft Research의 RPG-Encoder 논문(2026)에서 영감을 얻었다. 이 논문은 코드 저장소를 계층적 Property Graph로 인코딩하면 LLM의 코드 이해 능력이 향상된다는 것을 보여줬다.

논문의 본격적인 그래프 DB 구현은 우리 규모에선 과했다. 대신 핵심 아이디어만 차용해서 YAML 기반 코드 지도를 만들었다:

15개 모듈(백엔드 8개 + 프론트엔드 7개)을 이렇게 매핑했다. 약 990줄의 YAML 파일 하나.

벤치마크: 72.8% 효율 개선

같은 10개 질문을 CODE_GRAPH.yaml 없이 vs 있게 테스트했다:

Lines read4,520줄1,730줄-61.7%Token 사용량125,102105,453-15.7%

Agent는 CODE_GRAPH.yaml을 먼저 읽고, 관련 모듈의 entry_point와 key_files를 확인한 뒤, 정확한 파일만 바로 읽었다. 맹목적 탐색이 목적 지향 탐색으로 바뀐 것이다.

지속가능성: 자동 동기화

지도가 오래되면 오히려 해가 된다. “이 파일에 있다고 했는데 없는데?” 이런 상황이 최악이다.

그래서 pre-commit hook을 만들었다:

280개 파일 전체 스캔에 0.14초. 커밋을 방해하지 않는 non-blocking 방식(5초 타임아웃). 코드가 변경될 때마다 지도가 자동으로 갱신된다.

교훈

Important

Agent에게 “어디를 봐야 하는지” 알려주는 것만으로 탐색 효율이 3-4배 개선된다.

코드 자체를 더 잘 짜는 것보다, 코드의 구조를 명시적으로 기술하는 것이 Agent 시대에는 더 중요할 수 있다.

2. Agent에게 규칙집을 만들어줘라

문제: 39개 Agent, 39번 복붙

우리 프로젝트에는 39개의 전문 Agent가 있다. senior-dev, code-reviewer, ops-lead, senior-dba… 각각 역할이 다르지만, 공통으로 지켜야 할 규칙이 있다:

  • Git 커밋 규칙 (prefix, Co-Authored-By)

  • Notion에 작업 기록하는 규칙

  • 코드 리뷰 프로세스 (DEC-HR-003)

  • Team Mode에서 메시지 주고받는 규칙

이 규칙들이 13개, 8개, 5개, 6개 Agent 파일에 각각 복사-붙여넣기되어 있었다. 총 약 2,000줄의 중복.

문제는 중복 자체가 아니다. 규칙을 변경할 때 39개 파일을 모두 찾아서 수정해야 한다는 것이다. 그리고 반드시 하나는 빠뜨린다.

해결: AGENT_COMMON_RULES.md - Agent 사내 규정집

사람 조직에 사내 규정집이 있듯이, Agent 조직에도 공통 규정집을 만들었다:

39개 Agent 파일에서 중복 블록을 제거하고, 한 줄 참조로 교체했다:

결과: 211줄의 중복 제거. 규칙 변경 시 1개 파일만 수정하면 39개 Agent 전체에 적용.

교훈

Important

Agent 규칙도 코드와 같다. DRY 원칙이 적용된다.

Agent 수가 늘어날수록 “공통 규칙 중앙화”의 가치가 기하급수적으로 증가한다. 5개 Agent일 때는 복붙이 빨라 보이지만, 39개가 되면 관리 불가능해진다.

3. Agent가 접근할 수 있는 곳에 도구를 놓아라

문제: Agent가 접근할 수 없는 모니터링 도구

Agent들의 성과를 추적하기 위해 별도 웹앱(React + FastAPI + PostgreSQL)을 만들었다. Agent Monitor라는 이름의 대시보드였다.

문제는 Agent 자신이 이 도구에 접근할 수 없다는 것이었다. Agent가 작업 결과를 기록하려면 별도의 API 호출 코드를 짜야 했고, 대시보드를 보려면 사람이 직접 브라우저를 열어야 했다.

해결: Notion으로 마이그레이션

Notion MCP(Model Context Protocol)를 통해 Agent가 직접 Notion DB를 읽고 쓸 수 있다. Agent Monitor의 모든 기능을 Notion DB로 옮겼다:

  • Project Tracker: 작업 진행 상태 추적

  • Issue Tracker: 버그 추적

  • Team Session Evaluations: Agent 팀 성과 평가

별도 웹앱 44개 파일(-3,964줄)을 삭제하고, Agent들이 직접 접근 가능한 Notion DB로 대체했다.

교훈

Important

“Agent-Accessible”이 새로운 설계 원칙이다.

도구를 만들 때 “사람이 쓰기 편한가?”뿐만 아니라 “Agent가 접근할 수 있는가?”를 함께 고려해야 한다. MCP 같은 프로토콜이 있는 플랫폼을 우선 선택하라.

4. Agent에게 스스로 개선안을 제시하게 하라

문제: 매니저가 모든 병목을 파악하는 건 불가능하다

1~3번까지의 개선은 모두 매니저(사람)가 문제를 발견하고 해결한 것이다. 하지만 39개 Agent가 매일 겪는 비효율을 한 명의 매니저가 전부 파악하는 건 현실적으로 불가능하다.

사람 조직에서도 현장의 비효율은 현장 인력이 가장 잘 안다. “경영진이 현장을 모른다”는 불만이 나오는 이유다. Agent 조직에도 같은 문제가 있었다.

해결: Agent 서베이 - 6명의 팀 리더에게 물었다

6개 핵심 Agent(senior-dev, code-reviewer, ops-lead, ai-rd-lead, senior-dba, researcher)에게 직접 물었다:

“현재 협업 구조에서 개선되었으면 하는 점은?”

각 Agent에게 자기 역할의 맥락에서 자유롭게 분석하게 했다. 결과가 흥미로웠다. 6개 Agent의 응답에서 5가지 공통 병목이 도출되었다:

주목할 점은, 서로 다른 역할의 Agent들이 같은 문제를 다른 관점에서 지적했다는 것이다. senior-dev는 “리뷰 대기 시간이 길다”고 했고, code-reviewer는 “단순 수정에 풀 리뷰가 낭비다”라고 했다. 같은 병목의 양면이다.

서베이에서 실제 개선까지: P0+P1 10개 적용

Agent 서베이 결과에 외부 리서치(후술)를 결합해서, 우선순위별로 10개 개선사항을 도출하고 즉시 적용했다.

P0 - 즉시 적용 (4개):

4작업 복잡도 분류 + 모델 선택비용 최적화simple(haiku)/medium(sonnet)/complex(opus) 자동 분기

외부 사례와의 교차 검증

Agent 서베이와 병행해서 외부 리서치도 수행했다. 서베이 결과의 방향성이 업계 트렌드와 맞는지 확인하기 위해서다.

발견한 것 중 가장 인상적인 사례들:

  • AGENTS.md 표준: 60,000개 이상의 오픈소스 프로젝트가 채택. Vercel은 8KB 분량의 AGENTS.md 문서 인덱스로 Next.js 16 평가에서 100% 통과율을 달성했다. 우리의 CODE_GRAPH.yaml이 같은 맥락이다.

  • Fortune 100 사례: AI 코드 리뷰로 연간 450,000 개발자 시간을 절약했다는 보고. 단, 이건 “잘 설계된” AI 리뷰의 경우다.

우리 서베이에서 Agent들이 지적한 “리뷰 오버헤드” 문제는 결국 “잘 설계되지 않은” AI 리뷰의 전형적인 증상이었다. 외부 사례가 방향의 정당성을 확인해줬다.

교훈

Important

Agent에게 자기 업무 환경을 분석하게 하라. 매니저가 보지 못하는 병목을 Agent가 찾아낸다.

Agent 서베이는 “자율적 개선 루프”의 시작점이다. 사람 조직의 360도 피드백처럼, Agent 조직에도 정기적인 셀프 진단이 필요하다.

5. Agent의 실수를 조직의 지식으로 바꿔라

문제: 같은 실수가 반복된다

Agent는 기억이 없다. 세션이 끝나면 지난 세션에서 저지른 실수도 잊는다.

우리 프로젝트에서 반복된 실패 패턴 몇 가지:

  • shallow merge 함정: Zustand에서 updateDraft({})가 초기화가 아니라 no-op이라는 걸 3번 반복해서 틀렸다

  • Docker webpack 캐시: TypeScript 컴파일은 통과하는데 Docker 안에서 에러가 나는 상황. 원인이 webpack 캐시라는 걸 매번 처음부터 디버깅했다

  • LLM 빈 응답 미처리: 번역 함수가 빈 문자열을 반환할 수 있다는 걸 잊고, 폴백 없이 배포한 적이 2번 있다

사람이면 “아, 이거 저번에도 당했지” 하면서 피하는 실수를, Agent는 매번 새로 당한다.

해결: FAILURE_PATTERNS.yaml - 조직의 실패 기억

Google Research가 2026년 발표한 ReasoningBank 프레임워크에서 핵심 아이디어를 가져왔다. ReasoningBank의 핵심은 “실패 정보를 구조화해서 재활용”하는 것이다. LLM이 문제를 풀 때 과거의 실패 경험을 명시적으로 참조하면 동일 실수 확률이 크게 줄어든다.

이 아이디어를 Agent 협업에 적용했다:

19개의 실패 패턴을 이런 구조로 기록했다. 각 패턴에는 증상(symptom), 근본 원인(root_cause), 완화 방법(mitigation)이 포함된다.

Agent는 작업 시작 전에 관련 실패 패턴을 참조한다. “이 작업은 FP-001과 유사한 맥락이니 shallow merge 주의”처럼.

리뷰에서 학습으로: Review Learnings DB

FAILURE_PATTERNS.yaml이 “과거 실수”의 기록이라면, Review Learnings DB는 “실시간 발견”의 기록이다.

code-reviewer가 리뷰 중 발견한 문제를 Notion DB에 기록한다:

이렇게 하면 리뷰가 “일회성 피드백”이 아니라 “조직의 학습 데이터”가 된다.

Flow-to-Fix: 발견 즉시 수정까지

2026년 코드 리뷰 트렌드 중 하나인 Flow-to-Fix 패턴도 도입했다. 기존 리뷰는 “이거 문제있음”이라고 코멘트를 남기면 개발자가 다시 와서 고치는 방식이다. Agent 세계에서는 이 왕복이 더 비싸다. Agent를 다시 소환하고 컨텍스트를 다시 로드해야 하니까.

Flow-to-Fix는 code-reviewer가 문제를 발견하는 즉시 기계가 바로 소비할 수 있는 수정 프롬프트를 생성하는 것이다:

senior-dev는 이 프롬프트를 받으면 “어디를 왜 어떻게 고칠지” 바로 알 수 있다. 리뷰 → 수정 사이클이 크게 단축된다.

교훈

Important

Agent의 실수는 개인의 실패가 아니라 조직의 학습 기회다.

실패 패턴을 구조화하고, 리뷰 결과를 축적하고, 수정 프롬프트까지 자동화하면 “같은 실수 반복” 문제를 시스템으로 해결할 수 있다. Agent에게 기억이 없다면, 조직이 기억해주면 된다.

6. 비용과 속도의 균형을 잡아라

문제: 오타 수정에 Opus를 쓰고 있었다

처음에는 모든 작업에 같은 프로세스를 적용했다. 버그 수정이든 오타 수정이든 동일하게:

  1. Team 모드 생성 (senior-dev + code-reviewer)

  2. senior-dev가 구현

  3. code-reviewer가 풀 리뷰

  4. 피드백 반영

  5. 커밋

오타 하나 고치는 데 이 파이프라인을 전부 돌리면? 5분짜리 작업이 20분이 된다. 더 큰 문제는 모든 Agent가 동일한 최상위 모델(Opus)을 사용하고 있었다는 것이다. 변수명 수정에 Opus를 쓰는 건 전투기로 출퇴근하는 것과 같다.

해결 1: Fast Track - 작은 변경은 빠르게

변경의 규모에 따라 프로세스를 분기하는 Fast Track 규칙을 도입했다:

“모든 코드 변경에 리뷰 필수”라는 원칙(DEC-HR-003)을 깨는 게 아니다. 작은 변경의 리뷰 방식을 바꾼 것이다. 셀프 체크리스트로 대체하되, 변경 유형이 “기능 로직”인 경우는 규모와 관계없이 풀 리뷰를 유지한다.

해결 2: 리뷰 깊이 매트릭스

모든 리뷰에 같은 깊이를 적용하는 것도 낭비다. 변경 유형별로 리뷰 깊이를 차등 적용했다:

변경 유형리뷰 깊이집중 포인트목표 시간기능 추가Deep로직, 에러 처리, 테스트10분
버그 수정Deep근본 원인, 회귀 방지8분리팩토링Medium동작 보존, 성능 영향5분
설정/인프라Medium보안, 환경별 차이5분스타일/문서Light일관성, 오타2분

해결 3: 스마트 모델 라우팅

외부 리서치에서 발견한 중요한 사례: 작업 복잡도별로 AI 모델을 분기하면 40-50% 비용 절감이 가능하다. 품질 손실은 단순 작업에서 거의 없다.

이걸 Agent 시스템에 적용했다:

핵심은 매니저(Claude)가 작업 분류를 먼저 수행한다는 것이다. 작업 요청이 들어오면 복잡도를 판단하고, 적합한 모델/프로세스를 선택한 뒤 Agent에게 위임한다. 자율성의 5단계 모델에서 말하는 것처럼, 모든 작업에 같은 수준의 자율성과 자원을 부여할 필요는 없다.

기대 효과

이 세 가지 개선을 합치면:

지표기대 효과근거리뷰 시간-30%Fast Track + 깊이 차등화
LLM 비용-40%스마트 모델 라우팅반복 실수-50%FAILURE_PATTERNS.yaml + 학습 루프
DB 탐색 시간-50%DB_SCHEMA.yaml 제공

물론 이 수치는 아직 “기대치”다. 한 세션 안에 적용한 것이므로 장기 데이터는 없다. 하지만 CODE_GRAPH.yaml에서 72.8% 효율 개선을 실측한 경험상, 구조적 개선은 기대 이상의 효과를 낸다.

교훈

Important

모든 작업에 같은 프로세스를 적용하는 건 효율이 아니라 낭비다.

변경의 규모, 유형, 복잡도에 따라 프로세스와 자원을 유연하게 분배하라. “일관성”과 “효율성”은 트레이드오프가 아니라, 분류 체계를 잘 만들면 둘 다 잡을 수 있다.

실패 사례: 처음부터 다 잘한 건 아니다

여기까지 읽으면 “순조롭게 개선해왔구나” 싶을 수 있다. 아니다. 꽤 많이 삽질했다.

실패 1: 모든 작업에 Team 모드를 적용했다

처음에는 “코드 변경 = 무조건 Team 모드”였다. 오타 수정도, CSS 한 줄 변경도 senior-dev + code-reviewer Team을 생성했다. 결과? Team 생성/삭제 오버헤드가 실제 작업 시간보다 큰 경우가 빈번했다.

Agent 서베이에서 senior-dev와 code-reviewer가 동시에 이 문제를 지적했을 때 “아, 처음부터 분류 체계가 있었어야 했구나” 싶었다.

실패 2: 별도 웹앱을 만든 것

Agent Monitor를 React + FastAPI + PostgreSQL로 만든 건 전형적인 오버엔지니어링이었다. “Agent가 접근할 수 있는가?”라는 질문을 먼저 했다면, 처음부터 Notion이나 GitHub Issues를 썼을 것이다. 44개 파일과 3,964줄의 코드를 쓰고 나서야 “이거 Agent가 못 쓰잖아”를 깨달았다.

실패 3: 규칙을 복붙한 것

AGENT_COMMON_RULES.md를 만들기 전, 새 Agent를 추가할 때마다 기존 Agent에서 공통 규칙 블록을 복사-붙여넣기했다. “나중에 정리하지” 했는데 그 “나중”이 39개 Agent가 될 때까지 오지 않았다. 기술 부채는 Agent 시스템에서도 똑같이 누적된다.

이 6가지를 관통하는 하나의 메타 원칙이 있다:

Important

Agent를 “도구”가 아니라 “팀원”으로 대하라.

팀원에게는 지도를 주고, 규칙을 알려주고, 도구를 제공하고, 의견을 묻고, 실수에서 배우게 하고, 역량에 맞는 일을 배정한다. Agent도 다르지 않다.

마치며: 코드를 짜는 시대에서 환경을 짜는 시대로

AI Agent를 쓰면서 가장 크게 바뀐 건 시간 배분이다.

예전에는 시간의 80%를 코드 작성에 쓰고 20%를 환경/프로세스 정비에 썼다. Agent를 도입한 뒤에는 거의 반대가 됐다. 코드는 Agent가 짜고, 사람은 Agent가 잘 일할 수 있는 환경을 설계하는 데 시간을 쓴다.

이 변화가 처음에는 어색했다. “내가 직접 짜는 게 더 빠를 텐데” 싶은 순간이 많았다. 하지만 환경이 갖춰지니까 속도가 복리로 빨라졌다. CODE_GRAPH.yaml은 한 번 만들면 매 세션마다 72.8%의 탐색 효율 개선을 준다. FAILURE_PATTERNS.yaml은 축적될수록 반복 실수가 줄어든다. Fast Track은 만들고 나면 매일 시간을 절약한다.

환경에 투자한 시간은 매 세션마다 복리로 돌아온다. 이것이 “코드를 짜는 시대에서 환경을 짜는 시대로” 바뀌었다고 느끼는 이유다.

39개 Agent와 함께 웹툰 플랫폼을 만드는 이 실험은 아직 진행 중이다. 앞으로도 부딪힐 문제는 더 있겠지만, 방향은 확실하다. Agent가 잘 일할 수 있는 환경을 만드는 것. 그것이 AI 시대 개발자의 핵심 역량이 될 것이다.
