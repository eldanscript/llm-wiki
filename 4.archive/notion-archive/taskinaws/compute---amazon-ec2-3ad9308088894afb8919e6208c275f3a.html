Hypervisor

Role

  • 물리적 하드웨어와 BIOS를 보호

  • CPU, 저장소, 네트워킹을 가상화

AWS Nitro System

https://aws.amazon.com/ko/blogs/korea/amazon-ec2-update-additional-instance-types-nitro-system-and-cpu-options/

https://www.wwt.com/article/security-benefits-of-aws-nitro-based-architecture

  • AWS가 개발한 infrastructure 가상화 platform : 다양한 방식으로 조립할 수 있는 수많은 구성 요소 (Building Block)를 모은 컬렉션

  • Nitro Hypervisor로 Host 하드웨어에 대한 컴퓨팅, 메모리 리소스에 대한 성능 향상 : bare metal launch 속도로 최적화

  • Nitro Card를 통해 네트워킹, 고속 EBS, I/O 가속

  • Nitro Security Chip으로 보안 기능을 전용 하드웨어 및 소프트웨어로 off load

Bare-metal

  • AWS 인프라의 물리 서버에서 직접 OS 시작이 가능

  • 가상화된 환경에서 사용할 수 없거나 완전히 지원되지 않는 저수준 하드웨어 기능(예: intel VT)에 액세스해야 하는 워크로드

  • 라이선스 또는 지원을 위해 가상화되지 않은 환경이 필요한 애플리케이션

  • Instance size : metal

EFA (Elastic Fabric Adapter)

  • HPC 혹은 ML application의 속도 향상을 위한 Network device

  • Libfabric 1.7 이상과 통합

  • HPC application : Open MPI 3.1.3, MPI 2019 지원

  • ML application : NCCL (Nvidia Collective Communication Library) 지원

Key pair

  • Linux AMI : SSH (Secure SHell) 접속을 위해 사용

    • Public Network 에서의 안전한 통신을 위해 사용 : 데이터 전송, 원격 제어

    • Key Pair : Asymmetric

      • RSA, ED25519 (Elliptic Curve Cryptography) Algorithm

        • ED25519는 Curve25519 곡선을 사용하며 DSA (Digital Signing Algorithm)을 구현한 EdDSA (타원 곡선 기반 전자 서명 알고리즘)

      • Private Key Format

        • OpenSSH : .pem

          • X.509 v3 file 형태 (Privacy Enhanced Mail) : Base64로 인코딩된 ASCII text file

        • PuTTY : .ppk

      • Public Key : AWS 저장, Prvate Key : User 저장

  • Windows AMI : Log in password를 얻기 위해 사용

    • Computing Savings Plans

      • EMR, ECS, EKS 클러스터, Fargate, Lambda 인스턴스에 적용 가능

      • Instance Family, Size, AZ, Region, OS, Tenancy에 관계업이 사용량에 적용

      • C4 → M5, EU Ireland → EU London, Fargate → Lambda

      • Convertible RI와 동일 수준 할인률 : 최대 66%

    • EC2 Instance Savings Plans

      • 리전 내 특정 instance family에 대한 사용량 약정 : N.Virginia M5 usage

      • Instance size, OS, Tenancy에 관계없이 사용량에 적용

      • Standard RI와 동일 수준 할인률 : 최대 72%

  • Reserved Instance

    • Convertible RI (Region RI)

      • 약정 기간 동안 속성 변경 가능한 예약 인스턴스

      • Instance Type, OS, Tenenacy 변경 가능 → Region 고정, Converitible RI 총액 유지 변경 가능

    • Standard RI

  • Spot Instance

    • AWS cloud에서 미 사용되는 EC2 용량을 활용. 최대 90% 할인 금액

    • AWS에서 2분 전 공지하고 instance 종료

Placement group name

https://docs.aws.amazon.com/ko_kr/AWSEC2/latest/UserGuide/placement-groups.html

  • EC2 서비스는 모든 인스턴스가 기본 하드웨어 전반에 분산되도록 하여 상호 관련 오류의 위험을 줄임

  • Cluster plancement : Instance를 AZ안에 서로 근접하게 패킹, HPC application에서 긴밀하게 결합된 node간 통신에 낮은 지연 시간의 네트워크 성능 필요시 적용 가능

  • Partition placement : Instance를 Logical partition으로 분산 하여 다른 Partition group과 기본 HW를 공유하지 않게 하는 방법. Hadoop, Cassandra, Kafka 등의 대규모 분산 및 복제 workload에 필요

  • Spread placement : 소규모 instance group을 다른 HW로 분산하여 상호 관련 오류를 감소 시킴

Instance Storage

Instance Store

  • 블록 수준의 임시 스토리지를 제공

    • Host Compute에 물리적으로 연결된 disk에 위치

    • NVMe, SATA 기반 SSD : High random I/O performance

  • 자주 변경되는 정보의 임시 storage : Buffer, Cache, Scratch data, Temporary contents

  • 여러 instance에 복제되는 data : Load가 분산된 web server pool

  • Instance store volume : ephemeral 0 ~ 23

  • Low latency, short-term storage, 지속이 필요하지 않은 데이터의 경우 적합

EBS (Elastic Block Store)

  • 블록 수준 스토리지 볼륨을 제공 하며 instance 수명과 관계없이 지속

  • 데이터에 빠르게 access하고 장기간 지속해야 할 경우 적합

Type

  • General Purpose (gp2 or gp3)

    • 다양한 transaction workload를 위한 가격 성능 균형

    • Boot volume, Instance Database, 개발 및 테스트 환경

  • Provisioning IOPS SSD (io1 or io2)

    • Storage 성능에 민간함 I/O 집약적 workload → 일관된 IOPS 속도 제공 ( ~ 수만 IOPS)

    • Volume 내구성 : io2

  • Throughput Optimization HDD (st1)

    • 처리량으로 성능 정의하는 저비용 magnetic storage

    • EMR, ETL, DW, Log processing 등의 대용량 순차 workload

  • Cold HDD (sc1)

    • 데이터에 자주 액세스할 필요가 없고 비용을 절약해야 할 경우

    • HTTP connection과의 차이는 연결이 지속된다는 것이며 long-lived connection을 위해 Idle Connection Timeout을 60초 이상으로 설정 (default 60s)

Listener Rule Routing

https://docs.aws.amazon.com/ko_kr/elasticloadbalancing/latest/application/load-balancer-listeners.html#rule-condition-types

  • Host header : 호스트 이름을 기반으로 routing

  • HTTP header : HTTP header를 기반으로 routing

  • HTTP request method header : HTTP request method를 기반으로 routing

  • Path pattern : URL 경로 패턴을 기반으로 routing

  • Source IP : 각 request의 source IP 주소를 기반으로 routing

Authentication Flow

https://docs.aws.amazon.com/ko_kr/elasticloadbalancing/latest/application/listener-authenticate-users.html#authentication-flow

  1. 사용자는 Application Load Balancer 뒤에 호스팅되는 웹 사이트에 HTTPS 요청을 보냅니다. 인증 작업이 포함된 규칙에 대한 조건이 충족되면 로드 밸런서는 요청 헤더에서 인증 세션 쿠키를 확인합니다.
  2. 쿠키가 없는 경우 로드 밸런서는 IdP가 사용자를 인증할 수 있도록 사용자를 IdP 권한 부여 엔드포인트로 리디렉션합니다.
  3. 사용자가 인증된 후 IdP는 권한 부여 코드를 사용하여 사용자를 로드 밸런서로 다시 전송합니다.
  4. 로드 밸런서는 IdP 토큰 엔드포인트에 권한 부여 코드를 제공합니다.
  5. 유효한 권한 부여 코드를 받으면 IdP가 Application Load Balancer에 ID 토큰 및 액세스 토큰을 제공합니다.
  6. 그런 다음 Application Load Balancer가 액세스 토큰을 사용자 정보 엔드포인트로 전송합니다.
  7. 사용자 정보 엔드포인트는 사용자 클레임을 액세스 토큰으로 교환합니다.
  8. Application Load Balancer는 AWSELB
    인증 세션 쿠키를 사용하는 사용자를 원래 URI로 리디렉션합니다. 대부분의 브라우저는 쿠키 크기를 4K로 제한하기 때문에 로드
    밸런서는 크기가 4K를 초과하는 쿠키를 여러 쿠키로 샤드합니다. IdP에서 수신한 사용자 클레임과 액세스 토큰의 총 크기가 11K
    바이트를 초과하면 로드 밸런서는 클라이언트에게 HTTP 500 오류를 반환하고 ELBAuthUserClaimsSizeExceeded 지표를 증가시킵니다.
  9. Application Load Balancer가 쿠키를 검증하고 사용자 정보를 X-AMZN-OIDC-* HTTP 헤더 세트의 대상으로 전송합니다. 자세한 정보는 사용자 클레임 인코딩 및 서명 확인을 참조하십시오.
  10. 대상은 Application Load Balancer에 응답을 전송합니다.
  11. Application Load Balancer가 최종 응답을 사용자에게 전송합니다.

  • First 연결 : 1 ~ 11

  • 후속 연결 : 9 ~ 11
