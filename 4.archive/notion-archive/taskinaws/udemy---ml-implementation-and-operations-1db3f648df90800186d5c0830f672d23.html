Udemy - ML Implementation and Operations

SageMaker’s Inner Details and Production Variants

SageMaker와 Docker 컨테이너의 상호작용에 대해 더 자세히 살펴보겠습니다.

SageMaker에서 모든 기계 학습 모델 및 배포는 ECR(Elastic Container Registry)에 등록된 Docker 컨테이너 안에 호스팅되어야 합니다.

이 Docker 컨테이너에는 다양한 것들이 포함될 수 있습니다.

사전 구축된 딥러닝 모델, scikit-learn 또는 Spark ML 모델, 사용자가 TensorFlow, MXNet, Chainer, PyTorch 등의 프레임워크로 직접 구현한 코드 등이 Docker 컨테이너에 담겨질 수 있습니다. SageMaker는 이러한 다양한 기술이 담긴 Docker 컨테이너를 자동으로 지원합니다.

다만 TensorFlow의 경우 다중 머신 분산 처리가 자동으로 되지 않으므로, Horovod나 parameter server 등의 기법을 사용해야 합니다.

Docker 이미지는 Docker 파일을 통해 빌드되고, 이 이미지는 ECR에 저장됩니다.

SageMaker는 이 ECR에서 이미지를 가져와 학습 및 추론에 사용합니다.

학습 시에는 S3에 저장된 데이터를 활용하고, 학습 결과 모델은 다시 S3에 저장됩니다. 이 모델은 추론 코드가 담긴 별도의 Docker 컨테이너에서 활용됩니다.

Docker 컨테이너의 구조에 대해서도 설명했습니다.

/opt/ml 디렉토리에 입력, 코드, 출력 등이 구조화되어 있고, 이를 활용하도록 Dockerfile이 작성됩니다.

또한 SageMaker의 production variant 기능을 소개했습니다. 이를 통해 새로운 모델 버전을 실제 트래픽에 일부만 적용하여 점진적으로 확대할 수 있어, 리스크를 줄일 수 있습니다.

주요 내용 요약:

  • SageMaker는 ECR에 등록된 Docker 컨테이너 기반으로 동작

  • Docker 컨테이너에는 다양한 기계 학습 프레임워크의 모델/코드 포함 가능

  • TensorFlow의 경우 다중 머신 분산 처리를 별도로 구현해야 함

  • Docker 이미지는 Dockerfile로 빌드되며, ECR에 저장됨

  • 컨테이너 내부 구조 (/opt/ml 디렉토리 등)를 이해해야 함

  • Production variant를 통해 새 모델 버전을 점진적으로 배포할 수 있음

  • 다중 머신 분산 처리

    TensorFlow의 경우 다중 머신 분산 처리가 자동으로 지원되지 않기 때문에 별도의 기법을 사용해야 합니다.

    Horovod와 Parameter Server는 TensorFlow의 분산 처리를 지원하는 대표적인 기법입니다:

    • Horovod: TensorFlow, Keras, PyTorch 등의 분산 학습을 지원하는 라이브러리입니다. 여러 머신의 GPU/CPU를 효과적으로 활용할 수 있게 해줍니다.

    • Parameter Server: 모델 학습을 위한 파라미터를 여러 대의 서버에 분산 저장하고 관리하는 방식입니다. 이를 통해 대규모 데이터를 병렬로 처리할 수 있습니다.

    이와 달리 PySpark나 MXNet은 다중 머신 분산 처리를 보다 자동화된 방식으로 지원합니다:

    • PySpark: Spark 클러스터를 통해 자동으로 데이터를 분산 처리합니다. 코드 수정 없이 손쉽게 병렬 처리가 가능합니다.

    • MXNet: 내장된 분산 학습 기능을 활용하면 여러 GPU/CPU를 활용한 병렬 학습이 가능합니다. 별도의 추가 기법 없이 자동화된 분산 처리가 가능합니다.

    즉, TensorFlow는 분산 처리를 위해 별도의 라이브러리 사용이 필요하지만, PySpark와 MXNet은 보다 자동화된 분산 처리 기능을 제공한다고 볼 수 있습니다.

SageMaker Security : Encryption at Rest and in Transit

먼저, 일반적인 AWS 보안 모범 사례부터 살펴보겠습니다.

IAM(Identity and Access Management) 서비스를 최대한 활용해야 합니다. IAM을 통해 서로 다른 서비스 간의 권한을 제한할 수 있고, 사용자 계정의 권한도 최소 권한 원칙에 따라 설정할 수 있습니다. 예를 들어 SageMaker 노트북 생성 권한만 부여하고 다른 권한은 제한할 수 있습니다.

또한 가능한 한 다중 인증(MFA)을 사용해야 합니다. 관리자 계정과 루트 계정에는 반드시 MFA를 적용해야 합니다. 이를 통해 비밀번호 추측 공격을 방지할 수 있습니다.

SSL/TLS를 통해 모든 연결을 암호화해야 합니다. EMR을 제외하고는 대부분의 경우 이를 적용하기 어렵지 않습니다.

CloudTrail 서비스를 사용하여 API 호출 및 사용자 활동을 기록해야 합니다. 이를 통해 보안 사고 발생 시 감사 추적이 가능합니다. CloudTrail과 CloudWatch의 차이점을 알고 있어야 합니다.

데이터 암호화도 중요합니다. 개인 식별 정보(PII)와 같은 민감한 데이터는 반드시 암호화해야 합니다.

SageMaker에서의 암호화에 대해 좀 더 자세히 알아보겠습니다.

우선 저장 데이터 암호화의 경우, KMS(Key Management Service)를 사용할 수 있습니다. SageMaker의 모든 작업, 노트북, 아티팩트 등에 KMS 키를 제공하여 암호화할 수 있습니다.

전송 데이터 암호화의 경우, SageMaker 내부의 모든 트래픽은 TLS/SSL을 사용하여 암호화됩니다. 또한 훈련 노드 간 통신도 선택적으로 암호화할 수 있습니다.

IAM을 사용하여 SageMaker의 권한을 최소 권한 원칙에 따라 설정해야 합니다. 즉, SageMaker가 접근해야 할 데이터와 리소스에 대해서만 권한을 부여해야 합니다.

요약하면 다음과 같습니다.

  • IAM을 통한 권한 관리 및 최소 권한 원칙 적용

  • MFA 사용을 통한 보안 강화

  • SSL/TLS를 통한 데이터 전송 암호화

  • CloudTrail을 통한 감사 기능 활성화

  • KMS를 통한 저장 데이터 암호화

  • 훈련 노드 간 통신 암호화 (선택적)

SageMaker Security : VPC’s, IAM, Logging and Monitoring

SageMaker를 사용할 때의 VPC 관련 특별한 고려사항들:

  • SageMaker에서 학습 작업을 실행할 때 항상 가상 프라이빗 클라우드(VPC) 내에서 실행됩니다. 보안성을 높이기 위해 프라이빗 VPC를 사용할 수도 있습니다.

  • 그러나 SageMaker는 학습 데이터를 가져오고 학습된 모델 결과물을 가져오기 위해 S3에 접근할 수 있어야 하므로, VPC와 S3 간에 연결성을 확보해야 합니다. 이를 위해 S3 VPC 엔드포인트를 설정해야 합니다.

  • SageMaker 노트북은 기본적으로 인터넷에 접속이 가능한데, 이는 보안상 문제가 될 수 있습니다. 따라서 노트북의 인터넷 접속을 차단할 수 있지만, 그럴 경우 S3에 대한 접근을 위해 PrivateLink 또는 NAT 게이트웨이를 별도로 구성해야 합니다.

  • SageMaker의 학습 및 추론 컨테이너 또한 기본적으로 인터넷에 접속이 가능한데, 이를 차단할 경우 S3 접근이 불가능해지므로 이 부분도 해결책을 마련해야 합니다.

SageMaker에 대한 IAM 권한 설정:

  • SageMaker에서 사용자별로 세부적인 권한 설정이 가능합니다. 예를 들어 학습 작업 생성, 모델 생성, 엔드포인트 생성, 하이퍼파라미터 튜닝 작업 생성, 노트북 생성 등의 권한을 세분화할 수 있습니다.

  • 미리 정의된 SageMaker 권한 정책(읽기 전용, 완전 접근, 관리자 권한, 데이터 과학자 정책 등)을 활용할 수도 있습니다.

SageMaker 로깅 및 모니터링:

  • CloudWatch를 통해 SageMaker 엔드포인트의 호출, 지연시간, CPU/메모리 사용량 등을 모니터링할 수 있습니다.

  • CloudWatch를 통해 Ground Truth의 작업자 수, 처리량 등을 모니터링할 수도 있습니다.

  • CloudTrail을 통해 사용자, 역할, 서비스의 SageMaker 관련 활동을 감사할 수 있습니다.

주요 내용 요약:

  • VPC 내 SageMaker 사용 시 S3 접근 허용, 노트북/컨테이너 인터넷 차단 시 대체 방안 필요

  • IAM을 통해 사용자 권한 세분화 가능, 미리 정의된 정책 활용 가능

  • CloudWatch, CloudTrail을 통한 SageMaker 리소스 모니터링 및 감사 가능

SageMaker Resource Management : Instance Types and Spot Training

SageMaker의 리소스 관리

  • GPU 기반의 딥러닝 알고리즘의 경우 P3 인스턴스나 g4dn 인스턴스 타입이 가장 적합합니다.

  • 추론(inference) 작업의 경우 상대적으로 리소스 수요가 낮아서 C5 인스턴스 등의 저렴한 인스턴스 타입으로도 충분할 수 있습니다.

  • 딥러닝이 아닌 일반적인 ML 알고리즘의 경우에는 M5 인스턴스 같은 범용 인스턴스가 적합할 수 있습니다.

  • GPU 인스턴스는 비싸므로 꼭 필요한 경우에만 사용해야 합니다. 그러나 단일 GPU 인스턴스가 여러 개의 CPU 인스턴스보다 더 효율적일 수 있습니다.

Managed Spot Training

  • EC2 Spot 인스턴스를 사용하면 온디맨드 인스턴스 대비 최대 90%까지 비용을 절감할 수 있습니다.

  • 그러나 Spot 인스턴스는 언제든 중단될 수 있기 때문에, S3에 체크포인트를 저장하는 등의 추가 작업이 필요합니다.

  • Spot 인스턴스 사용으로 인해 트레이닝 시간이 늘어날 수 있는데, 이는 Spot 인스턴스를 기다려야 하기 때문입니다.

  • 비용 절감이 최우선 과제라면 Spot 인스턴스 활용을 고려해볼 수 있지만, 복잡성과 시간 지연 문제를 해결해야 합니다.

주요 내용 요약:

  • GPU 인스턴스 타입 선택 시 딥러닝/추론 작업 특성을 고려해야 함

  • 비용 절감을 위해 Spot 인스턴스 활용 가능하나 중단 위험 및 시간 지연 문제 해결 필요

SageMaker Resource Management : Automatic Scaling, AZ’s

SageMaker 내부 구조 및 프로덕션 버전

SageMaker에서 추론 모델을 배포할 때는 프로덕션 버전을 사용할 수 있습니다. 프로덕션 버전은 모델의 여러 버전을 관리하고 트래픽을 각 버전에 동적으로 라우팅할 수 있게 해줍니다. 이를 통해 새로운 모델 버전을 점진적으로 테스트하고 배포할 수 있습니다.

프로덕션 버전은 다음과 같은 이점을 제공합니다:

  • 모델의 여러 버전을 관리할 수 있습니다.

  • 트래픽을 각 버전에 동적으로 라우팅할 수 있습니다.

  • 새로운 모델 버전을 점진적으로 테스트하고 배포할 수 있습니다.

또한 SageMaker에는 자동 스케일링 기능이 있습니다. 이 기능을 통해 트래픽 변화에 따라 inference 노드를 자동으로 추가하거나 제거할 수 있습니다. 이는 비용을 절감할 수 있는 좋은 방법입니다.

자동 스케일링 기능은 다음과 같이 작동합니다:

  • CloudWatch를 통해 inference 노드의 성능을 모니터링합니다.

  • 사용자가 설정한 스케일링 정책에 따라 inference 노드의 수를 동적으로 조절합니다.

  • 개별 프로덕션 버전별로 스케일링을 수행하므로 각 버전의 트래픽 변화에 유연하게 대응할 수 있습니다.

자동 스케일링 기능을 사용할 때는 테스트 환경에서 정책을 사전에 확인하는 것이 중요합니다. 그렇지 않으면 과도한 용량 증가나 부족 등의 문제가 발생할 수 있습니다.

마지막으로 SageMaker는 가용성 영역(AZ)을 고려하여 인스턴스를 배포합니다. 하나의 AZ에 장애가 발생할 경우에도 다른 AZ의 인스턴스로 서비스를 계속 제공할 수 있습니다. 이를 위해서는 최소 2개 이상의 인스턴스와 VPC 구성이 필요합니다.

주요 내용 요약:

  • SageMaker의 프로덕션 버전 기능

  • 자동 스케일링을 통한 비용 절감

  • 가용성 영역(AZ)을 고려한 인스턴스 배포

  • 자동 스케일링 정책 사전 테스트의 중요성

SageMaker Serverless Inference and Inference Recommender

서버리스 추론(Serverless Inference)은 SageMaker의 새로운 기능으로 2022년에 도입되었습니다. AWS에서는 가능한 한 서버리스 아키텍처로 전환하려는 추세인데, 이는 그 연장선상에 있는 기능입니다.

서버리스 추론의 핵심 아이디어는, 사용자가 자신의 컨테이너와 컨테이너의 메모리 요구 사항 및 동시성 요구 사항만 지정하면 AWS가 실제 하드웨어 용량을 자동으로 프로비저닝하고 확장하는 것입니다. 이 기능은 추론 모델에 대한 트래픽이 불규칙하거나 예측하기 어려운 경우에 매우 유용합니다. 트래픽이 없을 때는 용량을 0까지 줄여 비용을 최적화할 수 있고, 트래픽이 늘어나면 자동으로 용량을 늘릴 수 있기 때문입니다.

SageMaker에는 이를 모니터링할 수 있는 CloudWatch 지표들이 있습니다. ModelSetupTime 지표를 통해 새로운 추론 모델을 배포하는 데 걸린 시간을, invocations 및 오류 invocations 지표를 통해 트래픽 패턴을, memory utilization 지표를 통해 컨테이너 메모리 사용량을 확인할 수 있습니다. 이를 통해 서버리스 추론에 제공한 컨테이너 요구 사항이 적절했는지 확인할 수 있습니다.

또 다른 새로운 기능인 SageMaker Inference Recommender는, 사용자가 직접 추론 인스턴스 유형을 선택할 때 도움을 줍니다. 사용자가 SageMaker 모델을 모델 레지스트리에 등록하면, Inference Recommender가 다양한 엔드포인트 구성을 벤치마크하고 결과를 분석하여 최적의 인스턴스 유형을 추천합니다. 이때 latency, throughput, cost 등의 지표를 고려하여 사용자의 요구 사항에 맞는 추천 결과를 제공합니다.

Inference Recommender에는 두 가지 모드가 있습니다. 하나는 인스턴스 추천 모드로, 약 45분 안에 추천 결과를 제공합니다. 다른 하나는 엔드포인트 추천 모드로, 사용자가 직접 테스트할 인스턴스 유형과 트래픽 패턴을 지정할 수 있고 약 2시간이 소요됩니다. 전자는 빠른 답변을, 후자는 사용자 요구 사항을 더 잘 반영한 결과를 얻고자 할 때 사용합니다.

이처럼 SageMaker에는 추론 배포를 자동화하고 최적화하기 위한 다양한 기능들이 있습니다. 수동으로 직접 설정하는 방식부터, 완전 서버리스 방식, 그리고 중간 단계의 자동 스케일링 등 다양한 선택지가 제공됩니다.

주요 내용 요약:

  • 서버리스 추론(Serverless Inference): 컨테이너 정보만 지정하면 AWS가 자동으로 하드웨어 용량을 프로비저닝하고 확장하는 기능

  • CloudWatch를 통해 모델 배포 시간, 트래픽, 메모리 사용량 등을 모니터링할 수 있음

  • SageMaker Inference Recommender: 최적의 인스턴스 유형 추천, 인스턴스 추천 모드와 엔드포인트 추천 모드 제공

  • SageMaker에는 수동 설정부터 완전 자동화까지 다양한 추론 배포 옵션이 존재

SageMaker Inference Pipelines

우리는 이전에 추론 노드에 도커 이미지를 배포하는 것에 대해 이야기했습니다. 기본적으로 ECR에서 가져온 미리 패키징된 도커 이미지를 사용하여 학습된 모델로 런타임에 추론을 수행하게 됩니다.

그러나 **하나 이상의 컨테이너를 사용하고 추론 파이프라인을 통해 이를 연결**할 수도 있습니다. 사전 학습된 내장 알고리즘이나 자체 알고리즘을 호스팅한 도커 컨테이너를 어떤 조합으로든 사용할 수 있습니다.

2개에서 15개 사이의 이러한 컨테이너를 연결하여 협력하는 선형 순서를 만들 수 있습니다. 전처리, 예측, 예측 결과의 후처리 등을 서로 다른 컨테이너에서 처리한 뒤 추론 파이프라인으로 연결할 수 있습니다.

Spark ML 또는 scikit-learn의 컨테이너도 이 파이프라인의 일부로 사용할 수 있습니다. Spark ML의 경우 Glue나 EMR에서 실행할 수 있으며, 결과는 MLeap 형식으로 직렬화됩니다.

추론 파이프라인은 실시간 추론과 일괄 변환 모두에 사용할 수 있습니다. 우리는 실시간 추론에 더 집중해 왔지만, 대량의 데이터에 대한 일괄 변환에도 추론 파이프라인을 활용할 수 있습니다.

요약하면, 추론 파이프라인은 여러 추론 컨테이너를 하나의 결과 처리 파이프라인으로 연결하는 방법입니다.

핵심 내용 요약:

  • 추론 노드에 도커 이미지 배포 외에 추론 파이프라인 사용 가능

  • 2-15개의 컨테이너를 선형 순서로 연결하여 협력하도록 구성 가능

  • 전처리, 예측, 후처리 등을 각기 다른 컨테이너에서 처리하고 파이프라인으로 통합

  • Spark ML, scikit-learn 컨테이너도 파이프라인의 일부로 사용 가능

  • 실시간 추론과 일괄 변환 모두에 추론 파이프라인 활용 가능

MLOps with SageMaker, Kubernetes, SageMaker Projects, and SageMaker Pipelines

머신러닝 운영(MLOps)은 초기 AWS 인증 머신러닝 시험 출시 이후 크게 발전했습니다. 그러나 시험은 이에 아직 맞추어가지 못하고 있습니다.

MLOps는 머신러닝 모델의 구축, 테스트, 배포 등 전체 워크플로우를 관리하는 것입니다. SageMaker는 이를 위한 몇 가지 솔루션을 제공하고 있습니다.

예를 들어 Amazon SageMaker Operators for Kubernetes는 Kubernetes에서 SageMaker 작업을 네이티브로 실행할 수 있게 해줍니다.

Kubeflow Pipelines의 SageMaker 구성 요소들도 Kubeflow 기반 MLOps 워크플로우에 SageMaker를 통합할 수 있게 해줍니다.

한편 SageMaker Projects와 SageMaker Pipelines는 Kubernetes나 Kubeflow 없이도 SageMaker 내에서 MLOps를 가능하게 합니다.

SageMaker Projects는 CI/CD를 포함한 MLOps 기능을, SageMaker Pipelines는 데이터 처리, 모델 학습, 평가, 등록 등의 단계를 정의하는 기능을 제공합니다.
