Dojo Study Guide

Common Scenario

Organization Complexity

Q) 여러 계정을 관리, 각 계정은 사용 하기로 된 자원만 사용 해야 함. 간단하고 재 사용이 가능한 방법은?

  • AWS Organization

    • 대량의 계정 관리와 제어를 간단하게 함

    • Resource control

      • CF Stackset : 스택 지정과 리소스 생성에 제한을 줄 수 있음 (blog link)

        • stack sets with service-managed permissions

        • StackSets가 사용자를 대신하여 각 멤버 계정에 IAM 역할을 생성 (AWS IAM 역할을 생성할 필요가 없음)

        • 나중에 조직에 추가되는 계정에 자동 배포를 활성화하기도 가능

      • Service Catalog : product 구성과 CF stack을 지정하고 개발자가 배포를 자유롭게 할 수 있음

        • Service Catalog를 사용하면 AWS에서 사용이 승인된 IT 서비스 카탈로그를 생성하고 관리

        • 조직 내 포트폴리오 공유와 제품 복사가 간소 : 공유 시 OU별

    • Permission control

      • IAM policy와 SCP (Service Control Policy)를 조합하여 사용

Q) CF stack을 Service Catalog로 업로드 하여 다른 계정들과 공유. 최소 권한으로 제품과 포트폴리오를 접근하는 방법은?

  • AWSServiceCatalogEndUserFullAccess / AWSServiceCatalogEndUserReadOnlyAccess

    • 추가로 IAM role을 전달할 수 있는 permission을 CF에 부여하여 CF stack이 필요한 리소스를 launch 할 수 있도록 해야 함

Q) 다른 계정의 사용자에게 리소스 접근 권한을 공급하는 방법은?

  • 계정간 (cross-account) IAM role을 사용하고 리소스 접근 권한을 attach

Q) 두개의 네트워크를 공유하거나 연결하는 방법은? 네트워크가 public internet 접근이 안 될 경우는 어떻에 연결하는가?

  • VPC / VPN / Strict Network

    • VPC : VPC sharing, VPC peering, Transit GW

    • VPN : S2S VPN

    • Strict Network : shared VPC endpoint (blog link)

Q) RI를 직접 구매했었는데 이제는 단일 중앙 계정에 구매를 요청해야 한다. 가장 안전한 방법은?

  • All AWS account를 AWS Organziation에 있어야 함 → SI 구매가 가능한 rule을 거부하는 SCP를 생성 ( ec2:PurchaseReservedInstancesOffering , ec2:ModifyReservedInstance ) → SCP를 각 OU에 연결 (attach)

Q) 여러개의 VPC를 다른 계정에 연결하고 CIDR를 겹치게 할 수 있는지? 그럴 경우 Route table은 어떻게 관리할 수 있는가?

  • CIDR이 겹쳐도 VPC를 연결할 수 있음 (blog link) : LPM

    • AWS에서는 longest prefix matching을 사용하여 traffic이 제대로 전달될 수 있도록 하고 있음

Q) IAM user를 생성하지 않고도 AWS console에 대한 long-term access를 제공할 수 있는지?

  • 온프렘의 SAML 2.0 호환 자격 공급자를 사용 (IdP)

    • AWS SSO endpoint를 통해 AWS console에 접근할 수 있도록 허용

Q) 하나의 계정에서 나머지 멤버들의 계정에 대한 API 동작을 모니터링 할 수 있는지? 그 방법은?

  • AWS CloudTrail로 모든 계정의 모든 event를 log하는 trail을 생성

    • 이 trail은 조직에 속한 모든 AWS 계정에 생성되며 CloudTrail 접근 권한이 있는 계정은 이 trail을 볼 수 있음

    • 멤버 계정은 이 organization trail을 삭제나 수정 할 수 있는 권한이 없음

    • Organization trail을 생성하거나 CloudTrail을 Organization의 Trusted Service로 enable 시키면 AWSServiceRoleForCloudTrail 이라는 service-linked role이 logging 작업을 수행할 수 있는 권한을 사용자 계정에 생성

Q) 50개의 계정이 있는 AWS Organization에서 네트워크 복잡도를 줄이기 위해 중앙의 내부 DNS 솔루션을 사용하고자 한다. 현재 각 계정은 각자의 VPC에서 private DNS 솔루션을 사용하고 있다. 가장 복잡하지 않은 네트워크 아키텍처는?

  • Shared service VPC를 생성하고 여기에 private hosted zone을 구성한다

    • 다른 VPC는 모두 Shared service VPC에 연결하고 (VPC peering 이나 Transit Gateway를 사용)

    • Shared service VPC에 Amazon Route53에 private hosted zone을 구성하고 필요한 도메인과 서브 도메인을 추가

Q) 다른 AWS region에 기본 infrastructure를 배포 하고자 한다. 이때 launched된 infrastructure는 동시에 최적화를 한다고 하면 가장 쉽게 배포 할 수 있는 방법은?

  • 다른 region 배포에 CF Stackset을 사용 (blog link)

    • Stack을 admin 계정으로 배포하고 개발자가 assume 할 수 있는 IAM role을 생성하여 infrastructure를 최적화 할 수 있게 한다.

    • IAM role에는 CF에서 생성한 리소스 삭제를 deny 할 수 있어야 한다.

Q) 여러개의 VPC가 회사 DC에 연결되는 동일한 DX line을 사용하고 있음. 이 구성은 네트워크 회선 장애 대책이 되어 있지 않다. 이 때 가용성을 늘릴 수 있는 방법은? VPC가 여러 region에 걸쳐 있다면 어떻게 할 것인가?

  • VPC와 DC간에 S2S VPN을 활용하고 Virtual private gateway에서는 VPN tunnel을 termination → BGP routing 구성

    • 동일한 네트워크 성능을 유지해야 한다면 → 다른 DX 회선을 다른 location에 추가 (추가 비용이 발생)

    • VPC가 여러 region에 걸쳐 있을 때는 Direct Connect Gateway를 사용할 수 있음

Design for New Solutions

Q) 동일 계정에 Prod, Dev가 있음. 개발자가 실수로 Prod instance를 중지, 종료 시키는 경우가 있는데 이것을 막는 방법은?

  • Resource tagging 후 명시적으로 개발자가 production tag 리소스를 중지, 종료 시키는 것을 Deny

Q) 사전 승인된 AMI만 사용을 허용. 인증되지 않은 AMI 실행을 막고 사용을 알리기 위한 방법은?

  • AWS Config를 사용하여 AMI compliance를 모니터하고 SNS는 구성하여 승인되지 않은 AMI 사용시 알림

    • EventBridge를 사용하여 각 RunInstance event를 모니터 → Lambda 함수로 launch configuration을 cross check하고 미 승인 AMI 사용시 SNS로 notification : instance를 시작하는 사용자 등과 같은 추가 정보를 제공

Q) 완전 자동화 된 Call center를 구축한다면?

  • Amazon Connect, Amazon Lex, Amazon Polly, AWS Lambda

Q) 다수의 비디오 파일을 보유하고 있으며 로컬에서 안면 인식 AI 애플리케에션에서 처리 됨. 장기간 보존을 위해 tape library에 보존. Metadata와 timestamp는 MongoDB에 저장. 기존 프로세스 동작에 최소의 영향을 주며 AWS로 이전하는 방법은?

  • Storage Gateway Tap Gateway 사용하여 video file을 S3에 저장. Lambda 함수로 video file을 Tape Gateway에서 추출하여 Amazon Rekognition으로 전달하고 안면 인식 수행. Rekognition 수행 완료되면 Lambda 함수로 인식된 정보를 DynamoDB에 저장

Q) 애플리케이션 연결에 HTTPS를 사용해야 함. 애플리케이션 성능에 대한 영향을 줄이고 싶어서 SSL/TLS를 offload 하고 싶은데 사용하고 있는 region에서 AWS ACM을 지원하지 않음. 대안은?

  • ACM (AWS Certificate Manager)은 regional service 이기 때문에 ACM을 다른 region에서 사용할 수 없음. 사용자 인증서를 생성하고 AWS IAM에 upload. Load Balancer에 import한 인증서를 연결 (associate) (blog link)

Migration Planning

Q) 온프렘에 RDS에서 지원되지 않는 database를 사용하고 있는데 AWS로 migration 하는 방법은?

  • DMS (Database Migration Service)와 SCT (Schema Conversion Tool) 사용

    • 대상 database 정보를 모으고 SCT로 schema와 database code를 변환 (사용 가능 list)

    • Conversion이 완료 되면 RDS database를 실행하고 변환된 schema를 적용

    • DMS를 사용하여 안전하에 migrate

Q) 온프렘에 수천개의 애플리케이션이 있는데 AWS로 migration 하고자 함. 애플리케이션이 서로 얽혀 있어 의존성이 제대로 매핑되지 않으면 이슈가 예상됨. 가능한 처리 방법은?

  • AWS Application Discovery Service로 서버 활용 데이터와 의존성 매핑을 수행

    • 결과를 AWS Migration Hub로 전송하여 발견된 서버의 migration을 주도 (initiate)

Q) 수 TB의 데이터를 S3로 migration. 500Mbps DX를 보유. 1Gbps 인터넷 연결을 보유하는데 migration mode는?

  • Snow hardware를 사용하여 migration을 수행

    • DX 속도가 500Mbps 이어서 S3 Transfer 가속을 enable 시키고 가용한 bandwidth를 데이터 전송에 전담 시킴

Q) 사용자 애플리케이션을 migration 하는데 클라우드 최적화를 위해 애플리케이션 재 작업을 위한 비용과 맨 파워가 없음. 가능한 migration 전략은?

  • Rehost → 최적화 작업이 없음, Re-architecting → 예산과 맨 파워가 필요, Replatform이 가능한 옵션 → scaling과 load balancing

Q) 짧은 RTO, RPO를 만족해야 하는 offsite backup을 위한 비용 효율적인 솔루션은?

  • Hybrid 아키텍처에는 AWS Storage Gateway 사용 가능

    • 짧은 RTO, RPO를 유지하기에는 File Gateway가 적합

Q) 수백개의 EC2 Linux가 동시에 local NAS로 접근. 통시은 AWS DX와 IPsec VPN을 통해 private하게 진행. NAS가 충분이 EC2 인스턴스를 서비스 하지 못하고 있고 이로 인해 많은 속도 저하가 발생하고 있음. AWS Storage service로 migration 하는 것을 대안으로 생각한다면 가능한 서비스는?

  • Amazon EFS, EFS로 migration 하기 위해 AWS DataSync 사용 가능

    • EFS에 대한 VPC endpoint를 만들어서 DX를 통해 migration을 빠르고 안전하게 수행

Q) 클라우드로 옮기고 싶은 몇 개의 SW가 있음. Re-architect를 위한 맨 파워는 부족하지만 예산은 있음. 클라우드의 장점을 활용하기 위한 다음 best option은?

  • AWS Marketplace에서 유사한 도구를 확인 : Repurchasing 전략

Cost Control

Q) EMR cluster를 구동하고 있는데 이용이 불규칙하고 task 처리 시간이 늘어가고 있음. 비용을 최소로 유지할 수 있는 방법은?

  • Task node를 추가 하지만 instance fleet을 사용

    • Master node는 On-Demand를 사용

    • Core와 task node는 On-Demand와 Spot instance를 사용

Q) Organization에 다수의 계정이 존재. AWS cost를 추적하고 예산을 초과하면 alert를 보내고자 함

  • Cost Explorer를 사용하여 각 계정 비용을 모니터링

    • AWS Budget에서 각 OU별로 그룹화된 연결 계정에 대해 예산 설정하고 초과되면 SNS로 notification

Q) Mobile 애플리케이션을 위한 Serverless stack을 구동. 온프렘 환경의 SQL database와 통신하는 네트워크 지연으로 Lambda 함수 실행 시간이 길어지고 비용이 증가. VPN 솔루션이 VPC와 온프렘을 연결하고 있는데 비용을 감소할 수 있는 방법은?

  • 가능하다면 database를 AWS로 migration하여 low latency를 유지

    • Database migration이 안된다면 VPN을 DX로 구성

    • 빈번한 조회에 대해서는 API Gateway의 Cache를 고려

Q) LB와 ASG에 연결된 여러개의 EC2 인스턴스가 있고 인스턴스는 RDS database에 연결 된다. VPC는 NAT gateway를 사용하는 인스턴스를 포함하고 있고 주기적으로 패치를 수행. 모두 회사 네트워크에서 액세스 가능하다면 비용을 최소화하는 방법은?

  • Production 워크로드 : RI 사용

    • Production이 아니라면 Scale-in, out 적용

    • NAT instance → NAT Gateway

Q) 데이터는 끊임없이 일정한 비율로 file storage로 전달. Storage는 증가에 맞춰 충분한 용량을 가져야 한다. 데이터는 추출되어 worker node에서 동작되어야 한다. 이 작업은 mission-critical workload가 아니어서 interrupt 및 재 처리가 가능하며 저녁에만 동작이 필요

  • Amazon Kinesis Firehose를 사용하여 S3로 끊임없이 스트리밍. AWS Batch로 worker node에 spot pricing을 적용. CloudWatch Event로 작업을 저녁에 수행하도록 설정

Continuous Improvement for Existing Solutions

Q) AWS partner DC와 온 프렘 DC간 DX가 구성. Web 서버는 EC2 인스턴스에서 구동되고 온 프렘의 database/warehouse로 다시 연결 된다. 연결의 안전성을 증가 시키려면?

  • Redudancy를 위해 추가 DX를 구성

    • IPSec VPN 연결을 public internet 망을 통해 구성

Q) NLB에 연결된 다수의 인스턴스가 있는데 DDoS로 부터 인스턴스를 보호 하려고 하려면?

  • WAF는 NLB와 통합되지 않기 때문에 NLB를 origin으로 하여 CloudFront를 구성하고 WAF를 CloudFront에 생성

    • AWS Shield Advanced를 활성화하여 DDoS에 대한 모든 기능을 사용

Q) 한개 region에 critical한 prod 워크로드가 있음. RTO는 5분, RPO는 15분 이라면 가장 비용 효율적인 DR 옵션은?

  • Warm standby : Route53을 사용해 immediate failover

Practice Test

Organization

Q) Prod 계정이 여러 사업 조직간 공유. 단일 사업 조직은 prod 계정에 리소스들을 가지는 한개 이상의 계정들로 되어 있음. 특정 사업 조직의 개발자들이 EC2 인스턴스를 종료 시키는 사고가 빈번하게 발생하고 있어 EC2 인스턴스와 AWS 리소스를 소유한 **특정 사업 조직만이 그들의 리소스를 종료**할 수 있도록 구성해야 함

A) AWS Organization을 사용하여 중앙에서 계정을 관리해야 함. 특정 사업 조직에 속한 계정을 OU로 그룹화. Prod 계정에는 **리소스 단위permission policy가 포함된 IAM role을 생성** (특정 사업 조직이 소유한 인스턴스를 종료 할 수 있는). OU에 속한 **모든 멤버 계정에 대해 cross-account 접근과 IMA policy를 제공**

Tip)

  • AWSServiceRoleForOrganizations service-linked role은 AWS service에 대한 service-linked role 생성을 허락하는 role 이며 모든 Organization에 존재하며 특정 OU에만 한정되지 않음.

  • SCP는 단순히 보안 주체가 수행할 수 있는 행동에 대한 guardrail을 정의한 것. Organization의 계정에 대한 접근을 허락하는 용도로 사용하기에는 부족함

  • SCP는 OU에 적용되는 permission이고 IAM policy는 principal level에 적용되며 SCP가 IAM policy에 우선한다.

Domain - Organization Complexity

Organization Units

Cross-Account Roles

  • 다른 계정의 사용자에서 리소스에 대한 접근 권한을 제공하는 IAM role

  • 각 계정에 전담된 IAM user를 생성하고 관리하는 지루한 작업을 감소 시킴

Service Control Policies

  • 계정에서 어떤 동작이 가능한지를 정의 한다 → IAM Policy와는 다르게 실제 permission을 위임 받지 못한다

  • 계정 범위로 적용 되며 IAM User와 IAM Role에 영향을 줌

  • Resource-based나 Service-linked role에는 영향을 주지 못함

  • SCP는 개별 계정이나 OU에 연결 가능하며 cascade 됨 → Root account에 연결된 SCP는 하위 OU에 영향을 줌

  • Explicit deny → Explicit allow → Implicity deny

  • Blackisting

    • FullAWSAccess SCP에 적용 → 기재된 특정 API에 대해 filtering

  • Whitelisting

    • Modify S CPto be more restrictive in allow permission : 허가를 더 제한하기 위해 SCP를 수정

    • IAM policy가 모든 동작을 허용해도 whitelist에 기재된 권한만 가능

Shared Directory Services

  • AWS Managed Microsoft AD Direcoty

    • Direcotry를 다른 VPC와 계정과 공유 가능. 단 동일한 Region 이어야 함

    • VPC간 networking이 필요 : VPC Peering, DX, Transit Gateway, VPN, …

  • AWS Organization 사용 시

    • 공유할 계정 선택 → Directory 선택

    • 외부 계정과 공유할 경우 handshake request를 initiate 하고 recipient가 request를 수락해야 함

  • External AD 사용 시

    • AWS 계정에 대한 인증 방법이 필요 : SAML Federation

    • Id로 부터 Auth token을 수락

      • AWS SSO

      • IAM Id : OIDC, SAML 2.0 OIDC 호환

      • Third-party SAML solution

S3 Requester Pays

  • 버킷 소유자 대신 요청자가 데이터 다운로드 및 요청 비용을 지불

  • 데이터 저장 비용은 항상 버킷 소유자가 지불

  • 버킷을 요청자 지불 버킷으로 구성하면 요청자가 x-amz-request-payer를 요청의 헤더에 포함하거나 (DELETE, GET, HEAD, POST 및 PUT 요청의 경우) 파라미터로 포함하여 (REST 요청의 경우) 요청 및 데이터 다운로드에 대한 요금 부과를 인지했음을 표시

Multi-Account Infrastructure Management

  • AWS Organization, AWS CloudFormation StackSet, AWS Service Catalog

AWS CloudFormation StackSet

  • CF Stack 기능의 확장으로 여러 계정과 리전에 걸쳐 Stack 생성, 업데이트, 삭제를 할 수 있도록 함

  • Admin 계정에서 AWS CF template을 정의 및 관리 → Template을 base로 지정된 계정 혹은 리전으로 Stack provisioning

  • Admin 계정과 배포할 계정간의 trust relationship이 필요

    • 배포 계정이 AWS Organization에 포함되어 있지 않을 경우 각 계정에 IAM Role을 생성하여 trust relationship을 형성

      • 배포 계정 : AWSCloudFormationStackSetExecutionRole (Admin 계정을 trust)

    • AWS Organization에 포함 되어 있는 계정은 trust access를 활성화

      • StackSet이 필요한 IAM Role을 생성

Service Catalog

  • What you see is what you get

  • AWS 계정에서 사용이 승인된 서비스 포트폴리오를 생성

  • 공통적으로 배포되는 서비스에 대한 중앙 관리 및 컨텐츠 거버넌스 확보, compliance 요구 만족

  • Catalog admin은 CloudFormation template으로 product을 정의 할 수 있음

  • Product에 버전을 적용하여 update를 자동으로 배포하거나 사용자가 필요한 버전을 선택할 수 있음

  • Share portfolio

    • Account-to-account sharing : import portfolio by getting URL from the admin

    • Organziational sharing via AWS Organization : single OU, organization account, whole organziation

    • Deploying catalogs using CloudFormation StackSet

  • Pros and Cons

    • StackSet

      • Pros : CloudFormation template이 준비되어 있다면 좋은 옵션으로 여러 계정과 리전에 배포가 가능

      • Cons

        • 사용자의 목적이 다를 수 있기 때문에 표준화가 어려울 수 있음

        • CF가 배포된 후 수정이 될 수 있어 compliance 모니터링이 이슈가 있음

    • Service Catalog

      • Pros : EC2, RDS와 같은 기본 서비스에 어떤 제약이 있다면 좋은 도구가 됨. 설계된 구성으로만 배포가 되기 때문

      • Cons

        • Regional, 여러 리전을 사용하는 여러 계정이 있다면 관리가 어려움

        • CI/CD pipeline 생성을 고려할 수 있는데 추가적인 overhead가 발생

        • 유연성이 떨어짐

    • StackSet + Service Catalog

      • Pros : 여러 리전의 여러 사용자에 대한 거버넌스 확보, 사용자는 필요한 파라미터만 선택하여 customizing

      • Cons : 사용자가 Product 구성에 대해 잘 알고 있어야 함

Domain - Multi Account Network Complexity

Multi-VPC Connection and Routing

VPC Peering

  • 2개의 VPC간 양방향 통신

  • 동일 region, 다른 region, 다른 계정간

  • Not transitive : VPC를 타고 넘어갈 수 없음

  • Route table은 LPM (longest prefix matching)을 사용하여 어떤 목적지로 traffic을 보내야 하는지 파악

Transit VPC

  • Hub and spike 모델을 구축 → BGP over IPsec을 이용하여 VPN 연결을 생성 (VPN overlay)

  • VPN appliance 없이 hub and spike 모델을 구축할 수 있는 것이 AWS Transit Gateway

  • 여러 VPC를 동시에 연결하는 것 외에 VPN 솔루션이나 DX도 연결 가능

  • Regional 서비스 이므로 여러 리전에 걸쳐 구성할 경우 각 리전의 Transit Gateway를 peering

  • 다른 VPC의 SG를 참조할 수 없음 → IP 주소나 주소 대역으로 rule 구성해야 함

  • DX 연결이 이미 구성이 되어 있는 경우 물리적 연결을 여러개의 논리적 연결로 분리하여 각 VPC를 연결할 수 있음

  • 여러 리전의 AWS DX location을 기 구축한 WAN provider에 연결하여 WAN backbone network을 구축할 수 있음

Hybrid Environment

  • 온프렘의 VPN appliance와 managed AWS VPN 서비스를 사용하여 온프렘과의 통신을 구성

  • AWS DX line을 IPsec VPN과 사용하여 traffic이 public internet으로 routing 되지 않도록 구성

  • AWS Transit Gateway에서 Site-to-site VPN을 위한 IPsec termination을 지원 : Transit Gateway에 연결된 VPC와 VPN간 연결 구성

  • EC2 instance를 실행하고 VPN을 인스턴스에서 termination

  • One-to-one connectivity to VPC : Virtual Private Gateway (VGW)를 provision 하여 사용 가능. VPC의 개수가 많아 지면 Transit Gateway가 적합

Hybrid - Dedicated line

  • VPC 내부의 리소스에 대해 접근할 때 Private Virtual Interface (VIF)를 생성하여 VGW에 연결할 수 있음 : 최대 50개 VIF 가능 (50개 VPC)

  • 여러 리전에 VPC가 있다면 Private VIF를 여러개의 VGW가 있는 Direct Connect Gateway에 생성

  • Direct Connect Gateway에 Transit Gateway를 연결 : VIF당 3개의 Transit Gatewy 연결 가능

  • AWS의 public endpoint (S3, DynamoDB)에 접근할 경우에는 Direct Connect public VIF를 통해 Transit Gateway와 VPN 연결

Configuring DNS Resolution

Backgroun

  • 대규모 조직에선 사용자, 컴퓨터, 정책등에 대한 관리를 위해 Active Directory를 사용

  • AD는 다른 group과 도메인으로 분리되고 여기에 GPO (Group Policy Object)를 적용 → 보안 및 관리 정책

  • 도메인에 속해 있는 컴퓨터는 private network를 통해 서로 통신 하기 때문에 도메인 컨트롤러가 도메인 사용자를 위해 DNS provider가 되도록 구성해야 함

  • 많은 컴퓨터에 대한 DNS 서버 구성을 동시에 관리하기가 쉽지 않기 때문에 VPC의 DHCP option set을 생성한다

DHCP set

  • 기본이 아닌 VPC에서 private 인스턴스를 생성할 경우 인스턴스는 AWS에서 resolve 되지 않는 hostname을 받게 됨

  • 인스턴스에 소유한 도메인 이름을 할당 (4개 까지) → VPC의 DHCP option을 지정

  • DHCP option은 DNS 서버에서 도메인 이름을 resolve 할 수 있게 해줌 → VPC에서 provisioning 되는 모든 EC2 인스턴스에 적용

  • DNS Server 구성

    • domain-name-servers=AmazonProvidedDNS

      • Amazon Route53 Resolver server

      • VPC의 Internet Gateway 필요

    • domain-name-servers=domain-name-for-your-region

AppStream
