Exam Readiness: AWS Certified ML - Specialty

Domain 1 : Data Engineering

  • Page Script

    도메인 1.1: 머신 러닝을 위한 데이터 저장소 생성

    머신 러닝 분야 전체가 데이터를 중심으로 돌아갑니다. 깨끗한 데이터를 가지고 있다면 중요한 비즈니스 통찰력을 얻을 수 있습니다. 데이터를 통해 전략적 비즈니스 의사결정에 있어 반응적이기보다는 선제적일 수 있으며, 고객을 더 깊이 이해할 수 있습니다.

    그러나 이 모든 데이터를 저장하는 것은 어려운 과제입니다. 데이터를 중앙 집중화된 저장소에 보관할 수 있는 방법이 필요합니다. 데이터 레이크가 이 과제를 해결하는 핵심 솔루션입니다. 데이터 레이크를 통해 구조화된 데이터와 비구조화된 데이터를 모두 저장할 수 있습니다.

    AWS Lake Formation과 Amazon S3는 데이터 레이크 솔루션입니다. AWS Lake Formation은 데이터 레이크 솔루션이고, Amazon S3는 AWS에서 데이터 과학 처리를 위한 선호되는 저장 옵션입니다.

    Amazon S3 스토리지 클래스를 활용하여 데이터 저장 비용을 절감할 수 있습니다. 각 클래스의 차이점을 확인해 보세요.

    하지만 Amazon S3는 모델 학습을 위한 유일한 저장 솔루션은 아닙니다. Amazon S3와 Amazon SageMaker를 함께 사용하거나, Amazon FSx for Lustre, Amazon EFS 등의 다른 파일 시스템을 사용할 수 있습니다. 파일 시스템 선택 시에는 학습 부하 시간을 고려해야 합니다.

    도메인 1.2: 데이터 수집 솔루션 식별 및 구현

    ML에 이 데이터를 사용하려면 Amazon S3와 같은 서비스로 수집해야 합니다. 데이터 레이크 솔루션의 핵심 이점 중 하나는 다양한 유형의 데이터를 신속하고 쉽게 수집할 수 있다는 것입니다. 때로는 데이터가 Amazon S3 데이터 레이크 솔루션 외부의 데이터베이스, 온프레미스 저장소 플랫폼, 데이터 웨어하우스 등에 있을 수 있습니다. 이 데이터를 ML에 사용하려면 Amazon S3와 같은 저장 서비스로 수집해야 합니다.

    일괄 처리와 스트림 처리는 두 가지 데이터 수집 방식입니다.

    일괄 처리는 주기적으로 소스 데이터를 수집하고 그룹화합니다. 이에 비해 스트림 처리는 데이터가 생성되거나 인식되는 즉시 데이터를 처리하고 로드합니다. 실시간 예측이나 실시간 분석 대시보드와 같은 경우 스트림 처리가 적합합니다.

    Amazon Kinesis는 AWS의 스트리밍 데이터 플랫폼으로, 빠르게 움직이는 데이터를 캡처하고 수집하는 데 사용됩니다.

    도메인 1.3: 데이터 변환 솔루션 식별 및 구현

    수집된 원시 데이터는 ML 준비가 되어 있지 않습니다. 데이터 중복 제거, 불완전한 데이터 관리, 속성 표준화 등의 데이터 변환 및 정리 작업이 필요합니다. 또한 데이터 구조를 OLAP 모델로 변경하여 데이터를 쉽게 쿼리할 수 있도록 할 수 있습니다.

    이를 위해 MapReduce, Apache Spark과 같은 분산 컴퓨팅 프레임워크를 사용할 수 있습니다. Amazon EMR은 Apache Spark을 관리형으로 제공하여 대량의 데이터를 처리할 수 있습니다.

    데이터 변환을 위한 핵심 단계 중 하나는 데이터셋 파티셔닝입니다. 데이터베이스 웨어하우스, IoT 스트리밍 입력, 데이터 레이크 등에서 가져온 ML 애플리케이션용 데이터셋을 Amazon S3에 저장할 수 있습니다. Amazon Athena, AWS Glue, Amazon Redshift Spectrum과 같은 ETL 처리 서비스를 활용하여 Amazon S3에 저장된 데이터셋을 사전 처리할 수 있습니다.

    이처럼 데이터를 한 곳(Amazon S3)에 저장하고 다양한 서비스를 활용하여 분석하는 접근법을 통해 데이터 중복을 피할 수 있습니다.

도메인 1.1: 머신 러닝을 위한 데이터 저장소 생성

  • 데이터가 비즈니스 통찰력과 의사결정의 핵심

  • 모든 데이터를 저장하는 것이 어려운 과제

  • 데이터 레이크가 해결책

    • AWS Lake Formation과 Amazon S3가 데이터 레이크 솔루션

  • Amazon S3 스토리지 클래스로 비용 절감

  • Amazon S3 외에도 Amazon SageMaker, Amazon FSx, Amazon EFS 등 활용 가능

  • 파일 시스템 선택 시 학습 부하 시간 고려

도메인 1.2: 데이터 수집 솔루션 식별 및 구현

  • 머신 러닝을 위해 데이터를 Amazon S3 등으로 수집

  • 일괄 처리와 스트림 처리 두 가지 방식

    • 일괄 처리: 주기적 데이터 수집 및 그룹화

    • 스트림 처리: 실시간 데이터 처리 및 로드

  • Amazon Kinesis를 통해 빠르게 움직이는 데이터 캡처 및 수집

도메인 1.3: 데이터 변환 솔루션 식별 및 구현

  • 수집된 원시 데이터는 ML 준비가 되어 있지 않음

  • 데이터 변환 및 정리 필요(중복 제거, 불완전 데이터 관리, 속성 표준화 등)

  • MapReduce, Apache Spark 등 분산 컴퓨팅 프레임워크 활용

  • Amazon EMR로 관리형 Apache Spark 제공

  • 데이터셋 파티셔닝이 핵심 단계

  • Amazon S3에 데이터를 저장하고 다양한 서비스로 분석하여 데이터 중복 피하기

키워드 분석 결과:

  • “from various sources” - 다양한 소스에서 데이터를 수집한다는 의미

  • “streamed” - 실시간 스트림 데이터 처리를 의미

  • “Amazon EMR instances” - 대량의 데이터 처리를 위해 Amazon EMR을 사용한다는 의미

이를 바탕으로 생각한 답변:

데이터 수집 솔루션으로는 Amazon Kinesis를 사용하는 것이 가장 적절해 보입니다. Amazon Kinesis는 실시간 스트리밍 데이터를 수집하고 처리할 수 있는 서비스이며, 다양한 소스의 데이터를 수집할 수 있습니다. 또한 대량의 데이터 처리를 위해 Amazon EMR을 활용할 수 있습니다.

답변 선택지 검토:

A. Amazon Kinesis Firehose - 이 서비스는 스트리밍 데이터를 Amazon S3나 Amazon Redshift와 같은 대상으로 전송하는 역할을 하므로, 데이터 수집 솔루션으로는 적절하지 않습니다.
B. Amazon Kinesis Data Streams - 이 서비스는 스트리밍 데이터를 실시간으로 수집하고 처리할 수 있어, 생각한 답변과 일치합니다.
C. Amazon DynamoDB Streams - DynamoDB Streams는 DynamoDB 테이블의 변경 사항을 캡처하는 데 사용되므로, 데이터 수집 솔루션으로는 적절하지 않습니다.
D. AWS Glue - AWS Glue는 ETL(Extract, Transform, Load) 작업을 자동화하는 서비스이므로, 데이터 수집 솔루션으로는 적절하지 않습니다.

따라서 B. Amazon Kinesis Data Streams가 가장 적절한 답변으로 보입니다.

도메인 2.1: 모델링을 위한 데이터 정리 및 준비

데이터를 수집, 변환, 중앙 집중식 저장소에 저장했지만 여전히 정리되지 않고 완전히 이해되지 않는 경우가 많습니다. 데이터에는 누락, 노이즈, 편향, 불균형 등의 문제가 있을 수 있습니다. 따라서 ML 모델을 효과적으로 학습시킬 수 있도록 데이터를 정리하고 정제해야 합니다. 이 서브 도메인은 이를 수행하기 위한 전략에 대한 것입니다.

  • 데이터를 더 잘 이해하기 위해 기술 통계 사용

    • 상관관계 파악: 모델 성능에 영향을 줄 수 있음

    • 산점도: 수치 변수 간 관계 시각화

    • 상관 행렬: 변수 간 선형 관계 정량화

데이터 정제 방법:

  • 언어와 문법 표준화

    • 알고리즘이 요구하는 언어로 통일

    • 대소문자 통일 등

  • 데이터 스케일 맞추기

    • 서로 다른 단위의 데이터 통일

  • 단일 열에 복수 특징 포함된 경우 분리

  • 이상치 처리

    • 이상치는 모델 성능에 부정적 영향 가능

  • 누락 데이터 처리

    • 열/행 제거, 평균값 대체 등

도메인 2.2: 특징 엔지니어링 수행

특징 엔지니어링은 모델의 예측 성능을 높일 수 있습니다.

데이터 정리 후에도 원시 특징이 여전히 부족할 수 있습니다. 원하는 예측을 하기 위해서는 원래 특징에서 새로운 특징을 만들어야 합니다. 이를 통해 모델의 예측 성능을 높일 수 있습니다.

특징 엔지니어링 방법:

  • 차원 축소: PCA, t-SNE 등

  • 숫자 특징 변환: 제곱, 세제곱, 곱셈 등

  • 범주형 특징 인코딩

    • 순서형: 숫자로 매핑

    • 명목형: 원-핫 인코딩

숫자 특징 스케일링도 중요합니다. 스케일 차이가 큰 경우 일부 특징의 영향력이 커질 수 있기 때문입니다.

자주 사용되는 스케일링 기법:

  • 평균-분산 표준화

  • MinMax 스케일링

  • Maxabs 스케일링

  • Robust 스케일링

  • Normalizer

도메인 2.3: ML을 위한 데이터 분석 및 시각화

시각화를 통해 특징과 특징 간 관계를 더 잘 이해할 수 있습니다.

  • 산점도: 두 변수 간 관계 시각화

  • 히스토그램: 개별 변수의 분포 파악

이를 통해 데이터 정제 및 특징 엔지니어링 필요성을 파악할 수 있습니다.

기타 관련 시각화 기법:

  • 박스 플롯

  • 산점도 행렬

  • 상관 행렬

  • 히트맵

  • 혼동 행렬

이 문제에서 주요 키워드는 다음과 같습니다:

  • “XGBoost algorithm”: 의사결정 트리 기반의 강력한 ML 알고리즘

  • “merge the customer application data with demographic and location data”: 고객 데이터와 인구통계, 위치 데이터를 병합

  • “dimension of the data is really large”: 데이터의 차원이 매우 크다는 것

  • “only keep the features that are most relevant”: 가장 관련성 높은 특징만 유지

이를 종합해 보면, 이 문제는 데이터의 차원이 매우 크기 때문에 특징 선택이나 차원 축소가 필요한 상황으로 보입니다.

답변지를 검토해 보면:

A. **Dropout은 과적합 방지를 위한 신경망 모델의 정규화 기법**이지만, 차원 축소와는 직접적인 관련이 없습니다.
B. 주성분 분석(PCA)은 차원 축소에 효과적인 기법입니다.
C. AWS Glue에는 feature_tokenizer 함수가 없으므로 이 선택지는 제외할 수 있습니다. → feature_tokenizer는 텍스트 데이터를 토큰화하고 피처로 변환하는 기능을 제공하는 Scikit-learn의 함수
D. 순차적 특징 선택은 관련성이 높은 특징만 선택하는 방법으로, 차원 축소에 도움이 됩니다.

따라서 이 문제의 정답은 B. 주성분 분석(PCA)과 D. 순차적 특징 선택이 될 것 같습니다.

**t-SNE**(t-Distributed Stochastic Neighbor Embedding)는 **데이터의 차원을 축소하는 비선형 차원 축소 기법**입니다.

t-SNE의 주요 기능은 다음과 같습니다:

  1. 고차원 데이터를 **저차원 공간으로 임베딩**하여 시각화할 수 있게 해줍니다.

  2. 데이터 간의 유사도를 보존하면서 **저차원 공간으로 투영**합니다.

  3. 군집 구조를 효과적으로 드러내어 데이터의 내재적 구조를 파악할 수 있게 해줍니다.

즉, t-SNE는 고차원 데이터를 저차원 공간에 효과적으로 매핑함으로써 데이터의 구조와 특성을 시각적으로 표현할 수 있게 해줍니다. 이를 통해 데이터를 더 잘 이해하고 분석할 수 있게 됩니다.

t-SNE는 주로 데이터 탐색, 차원 축소, 군집 분석 등의 용도로 사용되며, 특히 이미지, 텍스트, 유전체 데이터 등 다양한 유형의 고차원 데이터 시각화에 활용됩니다.

정답 설명:
LSTM은 순서를 고려하는 순환 신경망(RNN) 모델로, 입력으로 숫자 시퀀스를 받습니다. 따라서 원문 문장을 숫자 시퀀스로 변환해야 합니다. 또한 **LSTM은 입력 길이가 일정**해야 하므로, 문장의 길이를 고정하기 위해 패딩(padding)이 필요합니다. 따라서 2번 선택지가 가장 적절한 답변입니다.

오답 설명:
1번 선택지는 문장을 숫자 시퀀스로 변환하는 것은 맞지만, 패딩 작업이 누락되어 있습니다. LSTM 모델은 입력 길이가 동일해야 하므로, 이 선택지는 적절하지 않습니다.

요약하면, LSTM 모델을 사용하기 위해서는 문장을 숫자 시퀀스로 변환하고, 길이를 일정하게 맞추기 위한 패딩 작업이 필요합니다. 따라서 2번 선택지가 가장 적절한 답변입니다.

    도메인 3.1: 비즈니스 문제를 ML 문제로 프레이밍하기

    ML을 적용할 적절한 문제인지 먼저 확인해야 합니다.

    ML은 데이터에서 숨겨진 패턴을 식별하는 것입니다. 따라서 ML은 다음과 같은 경우에 적합합니다:

    • 규칙을 코딩하기 어려운 경우

    • 규모를 키워야 하는 경우

    반면 단순한 규칙이나 계산으로 해결할 수 있는 문제라면 ML이 적절하지 않습니다.

    ML 알고리즘에는 지도학습(분류, 회귀)과 비지도학습(군집화, 이상치 탐지) 등 다양한 유형이 있습니다. 비즈니스 문제를 적절한 ML 문제로 정의하는 것이 중요합니다.

    도메인 3.2: ML 문제에 적합한 모델 선택하기

    Amazon SageMaker에는 다양한 내장 알고리즘이 있습니다:

    • 분류: 선형 학습기, XGBoost, K-평균 군집화 등

    • 회귀: 선형 학습기, XGBoost 등

    • NLP: BlazingText, Sequence2Sequence, Object2Vec 등

    • 컴퓨터 비전: 이미지 분류, 객체 감지, 의미 분할 등

    또한 직접 개발한 알고리즘을 Docker 이미지로 사용하거나, AWS Marketplace에서 구독할 수도 있습니다.

    도메인 3.3: ML 모델 학습시키기

    학습, 튜닝, 평가는 반복적인 과정입니다.

    데이터를 훈련, 검증, 테스트 세트로 분할하는 것이 중요합니다. K-겹 교차 검증 등의 기법으로 모델 성능을 평가할 수 있습니다.

    Amazon SageMaker에서 학습 작업을 생성하면 Amazon S3에 모델 산출물이 저장됩니다.

    도메인 3.4: 하이퍼파라미터 최적화 수행하기

서브 도메인: 도메인 3.3 - ML 모델 학습시키기

핵심 문제: 데이터 과학자들이 빠르게 모델을 실험할 수 있도록 해주는 솔루션

문제 식별자:

  • 데이터 과학자들이 빠르게 모델을 실험하고 싶어함

  • 데이터 로딩 시간이 오래 걸리는 문제

답변 선택지 검토:
A. 훈련 작업 생성 시 증분 학습 활성화 - 데이터 과학자의 빠른 실험을 지원하지 않음
B. **로컬 모드에서 개발 및 실험 - 데이터 로딩 없이 빠른 실험이 가능**하므로 적절한 답변
C. 훈련 데이터를 Amazon S3에 저장 - 데이터 과학자의 빠른 실험을 지원하지 않음
D. 훈련 작업 생성 시 **Pipe 모드 사용 - 데이터 스트리밍으로 로딩 시간을 줄일 수 있지만, 여전히 데이터 로딩 시간이 소요**됨

따라서 이 문제의 정답은 B. 로컬 모드에서 개발 및 실험이 가장 적절합니다.

이 문제의 경우, 머신러닝 알고리즘으로 이미지 세그멘테이션(image segmentation)을 사용해야 하므로, 정답은 2번 선택지입니다.

정답 설명:
이 문제는 주변 환경에서 사람, 차량, 교통 표지판 등의 **다양한 객체를 감지하고 라벨링**해야 하는 자율 주행 차량 문제입니다. 이는 이미지 내에서 개별 객체를 구분하고 식별해야 하는 문제이므로, 이미지 세그멘테이션 알고리즘이 적절합니다.

**이미지 세그멘테이션**은 이미지를 **의미 있는 여러 부분(객체)으로 분할**하는 기술로, 각 픽셀을 특정 클래스(사람, 차량 등)에 할당합니다. 따라서 이 문제에 가장 잘 부합하는 머신러닝 알고리즘이라고 볼 수 있습니다.

오답 설명:
1번 선택지인 이미지 분류(**image classification**)는 전체 이미지를 **하나의 클래스(사람, 차량 등)로 분류하는 기술**입니다. 이 경우 이미지 내 **개별 객체를 구분하고 식별할 수 없으므로**, 이 문제에 적합하지 않습니다.

따라서 이 문제의 정답은 2번 선택지인 이미지 세그멘테이션입니다.

배치 정규화(Batch Normalization)는 딥러닝 모델의 성능 향상을 위해 사용되는 기술입니다.

배치 정규화의 주요 기능은 다음과 같습니다:

  1. 입력 데이터 표준화:

    • **각 배치(batch)의 입력 데이터를 평균 0, 분산 1로 표준화**합니다.

    • 이를 통해 **입력 데이터의 스케일 차이로 인한 문제를 해결**할 수 있습니다.

  2. 내부 covariate shift 감소:

    • 네트워크 내부 층의 입력 분포가 변화하는 현상을 ‘internal covariate shift’라고 합니다.

    • 배치 정규화는 이러한 **분포 변화를 감소시켜 모델 학습을 안정화**합니다.

  3. overfitting 방지:

    • 배치 정규화는 **regularization 효과가 있어 모델의 과적합을 방지**할 수 있습니다.

  4. 학습 속도 향상:

    • 입력 데이터 표준화로 학습 속도가 빨라집니다.

    • 이를 통해 epochs 수를 줄이고 수렴 속도를 높일 수 있습니다.

이처럼 배치 정규화는 모델 학습의 안정성과 성능 향상에 매우 유용한 기술입니다.

정답:
2. 배치 정규화 추가
3. 이미지 정규화

이유:

  1. 배치 정규화 추가:

  • 배치 정규화는 모델의 성능 향상에 도움이 될 수 있습니다.

  • 이미지 정규화와 함께 사용하면 모델 수렴 속도와 오차 진동 문제를 해결할 수 있습니다.

  1. 이미지 정규화:

  • 이미지의 픽셀 값을 표준화하여 모델 학습을 용이하게 합니다.

  • 모델 수렴 속도를 높이고 오차 진동 문제를 해결할 수 있습니다.

나머지 답변들은 문제 해결에 적절하지 않습니다:

  1. **가중치 감쇄 감소: 과적합 방지**에 도움이 되지만, 핵심 문제를 해결하기 어렵습니다.

  2. **배치 크기 증가: 수렴 속도는 높일 수** 있지만, 오차 진동 문제를 해결하기 어렵습니다.

따라서 이 문제의 정답은 2번과 3번 선택지입니다.

이미지 정규화(Image Normalization)는 **이미지의 픽셀 값을 특정 범위 내로 변환하는 작업**입니다. 이를 통해 이미지의 밝기, 대비 등을 표준화할 수 있습니다. 일반적으로 다음과 같은 과정으로 진행됩니다:

  1. 평균 제거(Mean Subtraction)

    • 각 픽셀 값에서 이미지 전체의 평균 픽셀 값을 빼서 평균을 0으로 만듭니다.

    • 이를 통해 이미지의 전반적인 밝기 차이를 제거할 수 있습니다.

  2. 표준화(Standardization)

    • 평균 제거된 픽셀 값을 표준편차로 나누어 표준 정규 분포(평균 0, 분산 1)로 변환합니다.

    • 이를 통해 이미지의 대비와 스케일을 표준화할 수 있습니다.

  3. 범위 조정(Scaling)

    • 표준화된 픽셀 값을 특정 범위(예: 01 또는 -11)로 변환합니다.

    • 이를 통해 모든 이미지의 픽셀 값 범위를 일치시킬 수 있습니다.

이러한 정규화 과정을 거치면 이미지의 밝기, 대비, 스케일이 표준화되어 모델 학습에 도움이 됩니다. 특히 다양한 조명 환경이나 크기의 이미지를 사용할 때 효과적입니다.

    • 지속적인 모니터링 및 평가

    • 프로덕션 추론 데이터 활용

  • SageMaker 자동 스케일링 지원

이 문제에서 주요 키워드는 다음과 같습니다:

  • “ensemble of models”: 여러 모델의 앙상블

  • “behind a single endpoint”: 단일 엔드포인트 뒤에서 동작

  • “with minimal management”: 최소한의 관리로 구현

이를 고려했을 때, 정답으로 생각한 것은 A. AWS Lambda와 Amazon API Gateway를 사용하는 것입니다.

B와 C의 경우 AWS Deep Learning 컨테이너를 사용할 수는 있지만, 최소한의 관리로 구현한다는 요구 사항을 충족하지 못합니다.

D의 경우 단일 Amazon SageMaker 엔드포인트로는 여러 모델의 앙상블을 구현할 수 없으므로 적절하지 않습니다.

따라서 A가 가장 적절한 답변입니다. AWS Lambda와 Amazon API Gateway를 활용하면 서버리스 컴퓨팅을 통해 최소한의 관리로 앙상블 모델을 Amazon SageMaker 엔드포인트 뒤에서 동작시킬 수 있습니다.

정답 설명:
3번) Amazon CloudWatch 로그 확인

  • Amazon SageMaker 트레이닝 작업의 로그는 기본적으로 Amazon CloudWatch에 저장됩니다.

  • 따라서 CloudWatch 로그를 확인하면 작업 실패의 원인을 파악할 수 있습니다.

4번) DescribeJob API 호출로 FailureReason 확인

  • Amazon SageMaker의 **DescribeJob API를 호출하면 해당 작업의 상태와 FailureReason 등의 정보를 확인**할 수 있습니다.

  • 이를 통해 작업 실패의 구체적인 원인을 파악할 수 있습니다.

오답 설명:
1번) 트레이닝 작업 인스턴스 로그 확인

  • 트레이닝 작업이 실패했으므로, 작업이 종료된 인스턴스에 로그인하여 로그를 확인하기는 어렵습니다.

2번) AWS CloudTrail 로그 확인

  • CloudTrail 로그에는 API 호출 기록이 기록되지만, 구체적인 작업 실패 원인은 확인하기 어려울 수 있습니다.

  • 따라서 CloudWatch 로그와 DescribeJob API가 더 직접적인 디버깅 방법입니다.

따라서 이 문제의 정답은 3번과 4번 선택지입니다.

이 문제의 정답으로 “Install the sagemaker-runtime library on the web server. call invokeEndpoint from the webserver” 선택지가 적절하지 않습니다.

이유는 다음과 같습니다:

  1. 문제에서 요구하는 “minimal maintenance and latency for spiky traffic times”를 충족하지 못합니다.

  2. **웹 서버에 SageMaker runtime 라이브러리를 설치하고 직접 invokeEndpoint API를 호출하는 방식은 서버리스가 아니므로, 관리 부담과 지연 시간이 높아질 수 있습니다**.

  3. 서버리스 아키텍처를 사용하면 확장성과 내결함성이 높아져 spiky 트래픽 대응에 더 적합합니다.

따라서 더 적절한 솔루션은 다음과 같습니다:

  1. AWS Lambda와 Amazon API Gateway를 사용하여 서버리스 아키텍처를 구축

  2. Lambda 함수에서 SageMaker 엔드포인트를 호출하여 모델 추론 수행

  3. API Gateway를 통해 웹 애플리케이션에서 Lambda 함수를 호출

이 아키텍처는 서버리스로 구현되어 관리 부담이 낮고, 확장성과 내결함성이 높아 spiky 트래픽에도 효과적으로 대응할 수 있습니다.

따라서 “Install the sagemaker-runtime library on the web server. call invokeEndpoint from the webserver”는 적절한 답변이 아닙니다.
