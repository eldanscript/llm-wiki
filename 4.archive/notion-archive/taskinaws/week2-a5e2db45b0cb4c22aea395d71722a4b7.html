Modernization & MSA

Business situation

  • Pandemic 이후 Cloud 중심 인프라 및 Application 적용 속도가 2배 이상 증가

    • Application 뿐만 아니라 Analytic, AIML, IoT workload 에서도 EC2 사용하듯이 container를 사용하게 될 것

  • Business 환경 변화에 대응 → 엔터프라이즈에서는 기존 환경의 붕괴(disruption)과 새로운 변화에 50% 빠르게 대응하기 위한 현대화에 대응이 목표

  • 팬데믹 기간 동안 축적된 기술 부채에 대처하는 것이 CIO의 70%를 덮을 것이기 때문에 재정적 스트레스를 유발하고 IT 민첩성을 저해할 것 : 관련 링크

  • 2024, 25 이전에 AWS computing revenue 50% 이상을 container가 차지하게 될 것

Monolithic is Legacy, so bad?

  • Legacy는 익숙하고 안정적일 수 있음

  • MSA의 장점은 대규모의 변화에 대해 민첩하게 대응할 수 있다는 점

  • Legacy가 변화 대응에 준비가 되어 있지 않은 것인가?

  • Legacy가 관리에 있어 비용 효율적이지 않은 것인가?

  • Container 사용이 오히려 부담이 되고 장애가 될 수 있음

    • K8s를 도입하면서 업그레이드를 계획 하지 않음

    • 배포만 하고 관리하지 않음 → 기능 개선, 변화 대응 어려움

  • Kubernetes는 3개월 단위로 신규 버전 release

    • Upstream Kubernetes는 3개의 Main Version을 Maintain

    • Security Hole에 대해 latest 3개 버전에 대해 backport

  • EKS platform은 4개의 version을 유지하여 1년 3개월 정도 유지 → Kubernetes의 LTS 지원 요청

  • 현대화의 접근 방법은 변화에 능동적으로 대응하고 인프라의 의존성을 완전히 격리

  • 운영에 대한 부담을 어떻게 해소? 인프라 운영에 많으 리소스를 투입하게 되면 오히려 변화 대응이 느려짐

    • Kubernetes에 집착하기 보다는 서비스, 비지니스에 집착해야 함 → Kubernetes 도입이 목표가 아니라 서비스, 비지니스를 변화에 쉽고 유연하게 대응할 수 있게 만드는 것이 목표

  • 기능 확장, 운영 도구 증가에 대해 관리할 수 없다면 복잡도만 높이게 되고 손을 댈 수 없는 상황이 발생

    • Microservice deathstar

Great Architecture

  • Delivers Quality : 좋은 아키택쳐는 빠르게 배포, 관리, 모니터링하고, 가시성이 높으며, 피드백을 받아 개선하기가 용이한 아키텍쳐

    • Managed Service가 필요한 이유 → Orchestration Tool에 리소스를 낭비하지 않도록

  • Scale Development Teams : 개발팀이 증가할 때 신규 개발자들이 빠르게 적응할 수 있음

  • Support Future Features Naturally : 직관적으로 확장해 나아갈 수 있는 구조

  • Enables High Performance & Low Cost

Why Customers adopt containers

  • 변화에 빠르게 대응

  • Component화 하여 관리

  • 규모 확장시 빠르게 대응

  • 모든 작업의 코드 관리 및 자동화

Critical Decision

  • Design schema first for all APIs and Events

    • Consume events by default

    • 아키텍쳐가 스키마를 가지고 API와 Event를 통해서 통신하게 만듬 → MSA 구축 시 Application 별로 Component화 하는 수준의 접근을 지양

    • MSA는 Lift and Shift가 아닌 Refactoring이 필요

  • MSA는 API나 Event 단위의 소비를 위한 구조 설계이며 이 작업을 쉽게 하기 위해 사용하는 것이 Orchestration 도구임

  • Invest in automation

    • 비용, 리소스에 부담을 가지고 투자를 많이 하지 않게 되면 향후 관리에 더 많은 비용을 사용하게 됨

    • 비용 절감을 위해 Orchestration을 직접 운영할 경우 어려움 발생

      • dependency 관리가 힘듬

      • 다운타임 발생하지 않도록 유지하기 어려움

  • 다양한 테스팅 도구 사용 추천

    • Artifacr가 준비 되었을 때 이것이 Production ready 상태를 확신 할 수 있는 수준이 되어야 함

MSA Core Concept

  • Independently deployable

  • Loosely coupled → component 단위로 확장 가능

  • Highly maintainable and testable → Static Code, 사람이 개입이 없도록

  • Owned by a small team

  • Organized around business capabilities

  1. Scale cube of MSA : 서비스 컴포넌트의 규모를 정의하기에 좋은 메트릭

  2. Modularity : 모듈화 관리

  3. Data as a Service : 하나의 데이터베이스는 하나의 서비스로

Amazon ECS Overview

Amazon ECS

  • AWS 환경에서 컨테이너 애플리케이션에 대한 오케스트레이션 툴 (실행, 확장, 관리, 보호)

  • AWS 서비스와의 쉬운 연동

Architecture

Amazon ECS Objects

ECS Cluster

  • 작업(Task)이 실행되는 논리적 그룹

  • Cluster 생성 시 EC2 instance 구축 혹은 생성, 추가 instance 등록

ECS Task

  • 최소 실행 단위로 실제 컨테이너 작업 → K8s Pod

  • 하나 혹은 둘 이상의 컨테이너 묶음

  • Task Definition 기반으로 ECS Cluster의 Instance 및 Fargate에 배포

  • Task당 최대 10개 컨테이너 가능, 동일 호스트에 배치

ECS Service

  • 지정된 작업을 동시에 실행하고 작업을 지속적으로 관리 → K8s Deployment

  • 실패한 작업을 자동으로 대체 : 작업 수 유지

    • 서비스 유형 : Replica or Daemon

    • 작업 배치 전략

    • 배포 유형

      • Rolling Update (ECS에서 제어)

      • Blue/Green Update (CodeDeploy로 제어)

  • ALB를 통해 부하 분산 및 AutoScaling 적용

Task Definition

  • ECS에서 컨테이너 실행을 위한 작업 정의 필요

  • 컨테이너 이미지 맵핑을 통해 컨테이너 정의

  • 배포 타입 설정 : EC2 or Fargate

  • 작업 역할 부여 : API 요청 시 권한에 따른 동작

  • 작업 크기 설정

  • 다양한 볼륨 선택 : docker 관리 volume, 호스트 volume, EFS mount

  • App Mesh(Service Mesh), Firelens(Log Writer) 등과 통합 활성화

IAM Role

  • 호스트 권한을 상속받지 않음

  • 작업에 할당된 IAM 역할 사용

  • Fine grained role로 최소한의 권한 부여

Task Deployment Strategy

  • Binpacking

    • Host utilization을 최대한 활용하기 위해 사용

    • Container instance 수를 최소로 유지

  • Spread

    • 고가용성 혹은 분산 환경 구축을 위해 사용

    • AZ에 균등 배포 유지

  • One Task per Host

ECS Cluster

  • Cluster Management Engine : Control Plane

  • Agent Communication Service on Control Plane

Capacity Provider

  • Task가 실행 될 Infrastructure를 결정하는 전략

  • AWS Fargate

  • Amazon EC2

    • ASG : scale-in or scale-out

AWS Fargate on Amazon ECS

  • AWS가 미리 준비한 Computing node에서 Task 실행

AWS Fargate

  • Container Cluster 관리를 AWS에 위임하여 관리 업무 오버헤드 경감 → Application에만 집중

  • Container 실행에 필요한 자원 만큼 비용 지불 → 필요한 만큼 사용 및 쉬운 연동

Task CPU & Memory

Consideration
