3.3 Automate Deployment

Objectives

DevOps, 소프트웨어 릴리스 프로세스, ML 워크플로우와 CI/CD, MLOps에 대해 정리하면 다음과 같습니다:

DevOps:

  • 소프트웨어 개발(Dev)과 운영(Ops)의 협업 문화

  • 빠른 소프트웨어 릴리스와 안정적인 운영을 목표로 함

소프트웨어 릴리스 프로세스:

  • 개발, 테스트, 배포, 운영의 단계로 구성

  • 개발과 운영 팀 간 협업이 중요

ML 워크플로우와 CI/CD:

  • ML 모델 개발, 학습, 배포에 CI/CD 원칙 적용

  • 자동화된 테스트, 통합, 배포로 ML 모델의 안정성 확보

MLOps:

  • ML 모델 운영을 자동화하고 체계화하는 접근법

  • 데이터 엔지니어, ML 엔지니어, DevOps 엔지니어 등이 참여

  • ML 모델 수명주기 관리, 모델 배포, 모니터링 등을 다룸

DevOps for ML 요구사항:

  • 자동화된 ML 워크플로우

  • 모델 재학습 및 재배포 자동화

  • 로그 및 메트릭 수집, 모델 평가, 모니터링 기능

자동화된 테스팅의 이점:

  • 릴리스 주기 단축

  • 품질 향상

  • 운영 안정성 제고

SageMaker Projects의 CI/CD 지원:

  • 템플릿 기반의 프로젝트 생성

  • 코드 리포지토리, 파이프라인, 배포 자동화 등 제공

버전 관리 시스템:

  • Git, SVN 등을 통한 코드 변경 추적 및 협업

파이프라인 실행 자동화:

  • CloudWatch 이벤트, CodePipeline 등을 통한 자동 실행

AWS 서비스 활용:

  • CodePipeline, CodeBuild, CodeDeploy 등을 통한 CI/CD

  • Step Functions, SageMaker 등으로 ML 워크플로우 오케스트레이션

배포 전략 및 롤백:

  • 블루/그린, 캐나리, 다크 출시 등의 배포 전략

  • 문제 발생 시 신속한 롤백 기능 필요

이를 통해 ML 애플리케이션의 개발, 배포, 운영을 자동화하고 효율화할 수 있습니다.

DevOps Introduction

DevOps와 ML 워크플로우에 대해 정리하면 다음과 같습니다:

DevOps:

  • 개발(Dev)과 운영(Ops) 팀의 협업을 통해 소프트웨어를 더 빠르고 안정적으로 구축, 테스트, 배포하는 접근법

  • 개발자는 새로운 기능을, 운영팀은 안정적인 운영을 담당하던 전통적인 방식에서 탈피

소프트웨어 릴리스 프로세스:

  1. 소스 코드 리포지토리에 개발자가 코드 작성

  2. 코드가 빌드되어 배포 가능한 패키지로 생성

  3. 기능 및 성능 테스트 수행, 버그 수정

  4. 인프라(서버, 데이터베이스 등) 프로비저닝

  5. 스테이징/프로덕션 환경에 배포

  6. 프로덕션 환경에서 성능 및 오류 모니터링

CI/CD:

  • 지속적 통합(CI): 코드 변경 사항을 자주 공유 리포지토리에 병합하여 통합 문제를 조기에 발견

  • 지속적 딜리버리(CD): 변경 사항이 자동화된 테스트와 검증을 거치지만, 수동 승인이 필요

  • 지속적 배포(CD): 테스트를 통과하면 즉시 자동으로 프로덕션에 배포

MLOps:

  • ML 모델 개발, 배포, 운영을 자동화하고 체계화하는 접근법

  • DevOps 원칙을 ML 워크플로우에 적용

  • 데이터 엔지니어, ML 엔지니어, DevOps 엔지니어 등이 협업

이를 통해 ML 애플리케이션의 개발, 테스트, 배포, 운영 전반을 효율화할 수 있습니다.

Code Repositories

코드 리포지토리의 역할과 중요성에 대해 정리하면 다음과 같습니다:

코드 리포지토리:

  • DevOps 및 CI/CD 파이프라인의 필수적인 구성 요소

  • 코드를 중앙 집중화된 장소에 저장하고 관리하는 역할

  • 팀 간 협업, 코드 변경 추적, CI/CD 시스템과의 통합을 지원

GitHub:

  • 가장 널리 사용되는 웹 기반 코드 리포지토리 호스팅 서비스

  • 분산 버전 관리 및 소스 코드 관리 기능 제공

  • 개발자들이 협업하고 코드 리포지토리를 관리할 수 있음

DevOps for ML:

  • 코드 리포지토리를 활용하여 ML 모델 개발과 배포 과정을 자동화

  • 새로운 코드가 자동으로 빌드, 테스트, 프로덕션에 푸시됨

  • 팀 간 협업과 ML 개발 프로세스 관리를 지원

따라서 코드 리포지토리는 ML 프로젝트의 DevOps 실현을 위한 필수적인 요소입니다. 이를 통해 신속하고 안정적이며 최신 상태의 ML 모델을 개발하고 배포할 수 있습니다.

MLOps Introduction

ML 모델 호스팅과 MLOps에 대해 정리하면 다음과 같습니다:

ML 모델 호스팅의 특징

  • 복잡한 수학 방정식과 반복적인 실험 필요

  • 새로운 데이터로 인해 모델이 시간이 지남에 따라 구식이 될 수 있음

MLOps의 필요성

  • ML 모델의 개발, 배포, 운영에 특화된 프로세스와 절차 필요

  • DevOps 원칙(자동화, 모니터링, 협업)을 ML 시스템에 적용 - MLOps incorporates DevOps principles with machine learning

CI/CD와 ML 생애주기:

  • CI/CD 파이프라인을 통해 ML 모델 구축, 평가, 선택, 배포, 모니터링 자동화

  • 새로운 ML 모델 개발 및 기존 모델 업데이트 가속화

MLOps의 이점

  • 자동화된 테스트, 린팅(Linting), 릴리스를 통한 코드 품질 및 반복 속도 향상

  • 데이터셋, 모델, 데이터 드리프트 및 성능 저하 모니터링 자동화

  • 안정적이고 고성능 ML 시스템 유지

MLOps 팀의 역할

  • 데이터 엔지니어, 데이터 과학자, ML 엔지니어의 협업을 통한 ML 생애주기 관리

데이터 엔지니어

  • 데이터 수집, 정제, 처리 담당

  • ML 분석과 데이터 과학자 작업을 위한 데이터 준비

데이터 과학자

  • 모델 개발, 학습, 평가, 모니터링 담당

  • 데이터로부터 인사이트 도출

ML 엔지니어

  • 모델 배포, 프로덕션 통합, 모니터링 담당

  • ML 시스템 개발(Dev)과 배포(Ops)의 표준화

  • 안정적인 프로덕션 ML 모델의 지속적 delivery 실현

이와 같이 MLOps 팀은 데이터 엔지니어, 데이터 과학자, ML 엔지니어 등 다양한 역할로 구성됩니다. 각 팀원은 ML 모델 생애주기 전반에 걸쳐 협업하며 책임을 분담합니다.

이를 통해 안정적이고 확장 가능한 ML 시스템을 구축하고 운영할 수 있습니다.

데이터와 ML 코드의 독립성

  • 데이터 전처리와 ML 모델 코드는 독립적이지만 긴밀하게 연계

  • 두 구성 요소의 신중한 설계가 필수적

ML의 비기능 요구사항

일관성(Consistency):

  • 개발, 스테이징, 프로덕션 등 다양한 환경 간 최소한의 편차를 보장하여 모델 성능 유지

유연성(Flexibility):

  • 변화하는 요구사항에 맞춰 다양한 ML 프레임워크와 기술을 수용할 수 있어야 함

재현성(Reproducibility):

  • 과거 실험과 학습 프로세스를 재현할 수 있어 모델 신뢰성과 추적성 확보

재사용성(Reusability):

  • 다른 ML 프로젝트에서도 재사용할 수 있는 구성 요소를 설계하여 효율성과 개발 시간 단축

확장성(Scalability):

  • 증가하는 수요와 데이터 볼륨에 대응하여 컴퓨팅, 스토리지, 메모리 등의 리소스를 확장할 수 있어야 함

감사 가능성(Auditability):

  • 모든 ML artifacts에 대한 포괄적인 로깅, 버전 관리, 종속성 추적을 제공하여 투명성과 규정 준수 보장

설명 가능성(Explainability):

  • 의사 결정의 투명성과 모델 해석 가능성을 높이는 기법을 포함

이러한 비기능적 요구사항들은 안정적이고 신뢰할 수 있는 ML 시스템 구축에 필수적입니다.

ML 워크플로우와 DevOps의 차이점

추가적인 단계:

  • ML 워크플로우에는 **데이터 준비, 모델 학습 및 버전 관리, 모델 성능 모니터링 등의 추가적인 단계**가 포함됩니다.

  • 이러한 추가 책임으로 인해 ML 실무자들은 ML에 맞춤형 모범 사례를 채택해야 합니다.

배포 및 운영의 복잡성:

  • MLOps와 DevOps는 일부 유사성이 있지만, ML 모델의 복잡성으로 인해 배포 및 운영 과정에서 더 많은 주의가 필요합니다.

고유한 과제 대응 필요:

  • ML 실무자는 모델을 프로덕션으로 원활하게 전환하고 성공적으로 관리하기 위해 이러한 고유한 과제를 고려해야 합니다.

전통적인 소프트웨어 개발과 비교하면, ML 프로젝트에는 다음과 같은 추가적인 복잡성이 존재합니다:

  • 데이터 준비, 모델 학습, 성능 모니터링 등의 추가 단계

  • ML 모델의 특성으로 인한 배포 및 지속적 운영의 어려움

  • 이러한 고유한 과제에 대한 대응 필요

따라서 MLOps는 DevOps와 일부 유사성이 있지만, ML 워크플로우의 특성을 고려한 별도의 접근법이 필요합니다.

  • Data Provenance (데이터 기원 추적)

    Data provenance는 데이터의 출처, 변환 과정, 사용 이력 등을 의미합니다.

    Data provenance의 주요 개념은 다음과 같습니다:

    1. 출처(Origin):

      • 데이터가 어디에서 왔는지, 어떤 출처로부터 수집되었는지에 대한 정보

    2. 변환 과정(Transformation):

      • 데이터가 어떤 단계를 거쳐 현재의 형태로 변환되었는지에 대한 기록

    3. 사용 이력(Usage History):

      • 데이터가 어떻게 사용되었고, 어떤 용도로 활용되었는지에 대한 정보

    Data provenance를 추적하면 다음과 같은 이점이 있습니다:

    • 신뢰성 향상: 데이터의 출처와 변형 과정을 알 수 있어 데이터에 대한 신뢰성 제고

    • 재현성 보장: 데이터 처리 과정을 추적할 수 있어 실험 및 분석의 재현성 확보

    • 감사 가능성: 데이터 사용 이력 관리를 통해 규정 준수와 투명성 확보

    • 오류 추적: 데이터 문제 발생 시 변환 과정을 따라 추적하여 오류 원인 파악

    이처럼 Data provenance는 ML 프로젝트에서 데이터의 무결성, 신뢰성, 재현성을 보장하는 데 중요한 역할을 합니다.

Automating Testing in CI/CD pipelines

ML system reliability

ML 시스템의 안정성 향상을 위한 자동화된 테스팅:

자동화된 테스팅의 중요성

  • ML 모델 개발 및 배포 과정에서 자동화된 테스팅은 필수적

  • 복잡한 프로젝트일수록 수동 테스팅의 오류 발생과 확장성 문제가 증가

자동화된 테스트 유형

단위 테스트(Unit Tests):

  • 개별 함수나 메서드와 같은 작은 구성 요소를 검증합니다.

  • 각 구성 요소의 정확한 동작을 확인합니다.

통합 테스트(Integration Tests):

  • 데이터 수집, 모델 학습, 배포 등의 파이프라인 단계가 올바르게 연동되는지 확인합니다.

  • 시스템 또는 아키텍처에 따라 다른 유형의 통합 테스트를 수행할 수 있습니다.

회귀 테스트(Regression Tests):

  • 이전에 정상적으로 동작했던 부분이 변경으로 인해 문제가 발생하지 않았는지 재확인합니다.

  • 모델뿐만 아니라 전반적인 시스템에 대한 회귀 테스트가 필요합니다.

이와 같은 다양한 수준의 자동화 테스트를 통해 ML 시스템 전체에 대한 철저한 검증이 가능합니다. 단위, 통합, 회귀 테스트를 CI/CD 파이프라인에 통합하면 빠르고 신뢰성 있는 모델 개발 및 배포를 지원할 수 있습니다.

CI/CD 파이프라인의 자동화된 테스팅 이점

  • 속도: 신속한 피드백으로 개발 반복 속도 향상

  • 신뢰성: 일관된 방식으로 테스트 실행

  • 포괄성: 다양한 시나리오, 입력, 하이퍼파라미터, 지표 검증

  • 조기 오류 발견: 프로덕션 전 개발 과정에서 버그 식별

SageMaker의 자동화된 테스팅

  • 데이터, 빌드, 테스트, 배포, 모니터링 등 다양한 ML 파이프라인에 적용

  • 자동화된 테스팅을 통해 ML 워크플로우의 재현성, 협업, 운영화 지원

SageMaker Projects with CI/CD practices

  • 모델 구축부터 배포까지 전체 ML 생애주기 관리

  • 코드 리포지토리, 워크플로우 자동화 도구, 파이프라인 단계 등 제공

이와 같은 자동화된 테스팅 접근법은 ML 시스템의 안정성과 품질을 향상시킬 수 있습니다.

Version Control Systems

버전 컨트롤의 중요성:

  • GitHub과 같은 코드 리포지토리는 코드와 파일의 변경 사항을 관리하는 데 활용됩니다.

  • 팀원들이 동시에 프로젝트에 작업할 수 있도록 지원하며, 필요 시 이전 버전으로 되돌릴 수 있습니다.

  • MLOps와 CI/CD 워크플로우의 핵심 요소로, 재현 가능한 빌드와 배포를 보장합니다.

버전 컨트롤 시스템의 주요 활용 사례:

  • 협업: 팀원 간 동시 작업과 변경 사항 통합

  • 변경 추적: 누가, 언제, 왜 변경했는지 기록

  • 브랜치 및 병합: 안정적인 메인 코드와 실험적 변경 관리

  • 재현성: 모델, 데이터, 설정 변경 이력 추적

  • CI/CD 파이프라인과의 통합: 자동화된 테스트, 빌드, 배포 실행

Git 소개:

  • 분산 버전 컨트롤 시스템의 표준

  • 대용량 파일과 데이터셋에 효율적

  • AWS에서 CodePipeline, CodeBuild 등과 통합 제공

Git 기본 명령어:

  • git init: 새 Git 리포지토리 초기화

  • git clone: 원격 리포지토리의 로컬 복사본 생성

  • git add, git commit: 변경 사항 스테이징 및 커밋

  • git push, git pull: 리포지토리에 변경 사항 업로드/다운로드

  • git branch, git checkout, git merge: 브랜치 관리

이와 같은 버전 컨트롤 시스템 활용은 ML 프로젝트의 협업, 재현성, 배포 자동화에 필수적입니다.

Continuous Flow Structures

ML 모델의 지속적인 배포를 위한 자동화된 워크플로우 구현:

지속적 배포의 핵심 구성 요소:

  1. 모델 학습 및 버전 관리: 모델 변경 사항 추적 및 관리

  2. 모델 패키징 및 컨테이너화: 모델과 종속성을 표준화된 컨테이너로 패키징

  3. 지속적 통합(CI): 모델 및 구성 요소 빌드, 테스트, 검증 자동화

  4. 배포 자동화: 모델을 프로덕션 환경에 자동으로 배포

  5. 모니터링 및 관찰성: 배포된 모델 성능, 안정성, 상태 모니터링

  6. 롤백 및 롤포워드 전략: 문제 발생 시 이전 버전 복구 또는 새 버전 배포

Gitflow와 GitHub Flow:

Gitflow

  • 브랜치 전략(main, hotfix, release, develop, feature)을 활용한 구조화된 워크플로우

Gitflow 워크플로우의 주요 브랜치 역할:

  1. Main:

    • 프로덕션 준비 상태의 코드베이스를 나타내는 주 브랜치

    • 최신 안정 버전의 소프트웨어를 포함

  2. Hotfix:

    • 프로덕션 환경의 중요한 이슈를 신속히 해결하기 위한 브랜치

    • Main 브랜치에서 분기되며, Main과 Develop 브랜치에 병합됨

  3. Release:

    • 새로운 프로덕션 릴리스를 준비하기 위한 브랜치

    • Develop 브랜치에서 분기되며, 버그 수정 등의 최종 작업을 수행

  4. Develop:

    • 새로운 기능 개발 및 통합을 위한 중심 브랜치

    • 완료된 모든 기능이 병합되는 허브 역할

  5. Feature:

    • 새로운 기능 개발을 위한 단기 브랜치

    • Develop 브랜치에서 분기되며, 기능 완료 후 Develop 브랜치에 병합됨

이와 같은 체계화된 브랜칭 전략은 소프트웨어 프로젝트의 안정적인 개발과 배포를 지원합니다.

Gitflow 워크플로우의 주요 단계를 정리하면 다음과 같습니다:

  1. 새 기능 개발 시작:

    • Develop 브랜치에서 새로운 Feature 브랜치 생성

    • 기능 개발 후 Feature 브랜치에 변경 사항 커밋

  2. 기능 병합:

    • 기능 개발이 완료되면 Feature 브랜치를 Develop 브랜치에 병합

  3. 릴리스 준비:

    • Develop 브랜치에서 새로운 Release 브랜치 생성

    • Release 브랜치에서 최종 조정(버그 수정 등) 수행

  4. 릴리스 병합:

    • Release 브랜치를 Main 브랜치에 병합하고 버전 태그 지정

    • Release 브랜치를 Develop 브랜치에도 병합하여 변경 사항 통합

  5. 핫픽스 대응:

    • 프로덕션 환경의 중요 이슈 발생 시 Main 브랜치에서 Hotfix 브랜치 생성

    • 이슈 해결 후 Hotfix 브랜치를 Main과 Develop 브랜치에 병합

이와 같은 Gitflow 워크플로우를 통해 안정적이고 체계적인 소프트웨어 개발 및 배포 과정을 관리할 수 있습니다.

GitHub Flow:

  • 가벼운 브랜치 기반 워크플로우로 지속적인 통합과 배포 지원

GitHub Flow의 주요 특징과 장점을 정리하면 다음과 같습니다:

GitHub Flow의 특징:

  • 가벼운 브랜치 기반 워크플로우

  • 새로운 기능, 버그 수정 등의 변경 사항을 체계적이고 구조화된 방식으로 관리

  • 메인 브랜치에서 새로운 브랜치를 생성하여 작업 격리

  • 브랜치 생성, 변경 커밋, Pull Request 생성, 코드 리뷰, 프로덕션 배포 등의 반복적인 주기

GitHub Flow의 주요 장점:

  1. 지속적 통합 및 배포:

    • 언제든 메인 브랜치를 배포 가능한 상태로 유지할 수 있어 변경 사항을 더 쉽고 빈번하게 배포할 수 있습니다.

  2. 협업 및 코드 리뷰:

    • Pull Request 프로세스를 통해 팀 간 협업과 동료 리뷰를 장려하여 코드 품질을 보장할 수 있습니다.

  3. 유연성 및 격리:

    • 브랜치 기반 접근 방식으로 개발자들이 서로 간섭하지 않고 독립적으로 다양한 기능이나 버그 수정을 진행할 수 있습니다.

이러한 특징과 장점으로 GitHub Flow는 팀 기반 소프트웨어 프로젝트에 효과적인 워크플로우로 활용됩니다.

지속적 실행 구조 시작하기

  • 이벤트 기반 트리거를 통한 파이프라인 자동화

  • 단계별 작업 순서 및 종속성 정의

이와 같은 자동화된 배포 워크플로우를 통해 ML 모델의 빠른 반복 배포, 안정성 있는 운영을 실현할 수 있습니다.

지속적 실행 구조 구현을 위한 단계별 접근 방식:

  1. 태스크 식별:

    • 파이프라인의 개별 태스크 또는 작업 식별

    • 명확한 입력과 출력을 가지는 독립적인 태스크 정의

  2. 태스크 순서 결정:

    • 태스크 간 종속성 분석

    • 태스크 수행 순서 수립

  3. 지속적 실행 프레임워크 선택:

    • Apache Airflow, Luigi, Prefect 등의 프레임워크 검토

    • 필요 사항(사용 편의성, 확장성, 기존 인프라와의 통합 등)에 적합한 프레임워크 선택

  4. 파이프라인 정의:

    • 선택한 프레임워크를 사용하여 태스크와 종속성, 전체 워크플로우 정의

  5. 태스크 구현:

    • 각 태스크에 대한 데이터 읽기, 변환, 처리 등의 로직 작성

  6. 파이프라인 구성:

    • 태스크 스케줄링, 리소스 할당, 오류 처리 등 필요한 구성 요소 설정

  7. 테스트 및 검증:

    • 샘플 데이터를 사용하여 파이프라인 테스트 및 검증

  8. 배포 및 모니터링:

    • 프로덕션 환경에 파이프라인 배포

    • 실행 모니터링 및 로깅 구현

  9. 반복 및 최적화:

    • 파이프라인 성능 모니터링 및 필요에 따른 조정

    • 태스크 완료 시간 최적화, 새로운 태스크 추가, 전체 구조 개선 등

이와 같은 단계적 접근을 통해 신뢰성 있고 효율적인 지속적 실행 구조를 구현할 수 있습니다.

Continuous Delivery Services

AWS 클라우드에서의 애플리케이션 배포 자동화 과정:

소프트웨어 릴리스 라이프사이클:

  • 소스 코드 관리, 배포 가능한 아티팩트 빌드, 통합 테스트, 환경 배포, 성능 모니터링 등의 단계로 구성

소스에서 프로덕션까지의 도구:

  • CodePipeline, Git 리포지토리, CodeBuild, CodeDeploy 등의 AWS 서비스를 활용하여 각 단계를 자동화하고 효율화

AWS 서비스별 특징 및 사용 사례:

AWS CodeBuild:

  • 완전 관리형 지속적 통합 서비스로, 소스 코드 컴파일, 테스트 실행, 빌드 아티팩트 생성 자동화

  • 빌드 명령 지정, 병렬 빌드 실행, 사전 구성된 빌드 환경 활용 가능

  • 소스 코드 리포지토리, Jenkins 등 다른 도구와 통합

AWS CloudFormation:

AWS CodeDeploy:

  • 온프레미스 서버와 AWS 서비스(Lambda, ECS, EC2 등)에 애플리케이션을 자동으로 배포하는 서비스

  • 증분 배포, 자동/수동 롤백 등의 기능으로 빠르고 안정적인 릴리스 지원

  • 수동 프로세스를 자동화하여 동시 배포 요구 사항에 대응 가능

이러한 AWS 서비스들을 활용하면 애플리케이션 개발, 빌드, 배포 전반의 자동화를 달성할 수 있습니다.

AWS CodePipeline:

  • 다양한 AWS 서비스와 통합되어 소스에서 프로덕션까지의 파이프라인 구축

AWS CodePipeline의 주요 기능:

수동 승인 기능:

  • 파이프라인에 수동 승인 게이트를 구성하여 릴리스 프로세스를 통제할 수 있습니다.

  • 특정 사용자 또는 그룹의 승인이 필요하도록 설정할 수 있습니다.

모니터링 및 알림:

  • 파이프라인의 상태, 상세 로그, 알림 등을 제공하여 가시성을 확보할 수 있습니다.

보안:

  • 리소스 수준의 권한 설정을 지원하여, 사용자별로 파이프라인에 대한 권한(읽기 전용, 특정 단계 또는 액션 접근 등)을 세분화할 수 있습니다.

이를 통해 CodePipeline은 릴리스 프로세스에 대한 통제력, 가시성, 보안성을 제공하여 안정적이고 신뢰할 수 있는 애플리케이션 배포를 지원합니다.

Git 리포지토리:

  • 개발자들이 안전하게 Git 기반 코드 저장소를 관리할 수 있는 완전 관리형 서비스

AWS Git 리포지토리의 주요 특징:

Git 기반 버전 관리:

  • 익숙한 Git 명령어와 워크플로우를 그대로 사용할 수 있습니다.

안전한 데이터 저장:

  • end-to-end 암호화와 액세스 제어 메커니즘을 통해 코드를 안전하게 저장합니다.

확장성과 고가용성:

  • 대용량 리포지토리와 높은 트래픽을 처리할 수 있도록 설계되었습니다.

AWS 서비스와의 통합:

Best Practices for Configuring and Troubleshooting

AWS 개발자 도구 문제 해결에 대해 정리하면 다음과 같습니다:

일반적인 문제 해결 접근법:

  • 체계적인 방식으로 문제를 조사하여 근본 원인을 찾아내는 것이 중요

AWS CodeBuild 문제 해결:

  1. CloudWatch 로그 확인: 빌드 과정에서 발생한 오류 및 경고 사항을 확인

  2. 빌드스펙(buildspec.yml) 유효성 검사: 형식과 필수 명령/환경변수 확인

  3. 빌드 환경 점검: IAM 역할 권한, 리포지토리 설정, 프로젝트 구성 등 확인

  4. 네트워크 문제 확인: 네트워크 설정, 방화벽, 보안 그룹 등을 점검

  5. CloudTrail 로깅 활용: 관련 리소스 변경 내역 추적

AWS CodeDeploy 문제 해결:

  1. CodeDeploy 로그 확인: 배포 오류 및 이슈 식별

  2. CodeDeploy 에이전트 확인: 에이전트 설치 및 구성 점검

  3. AppSpec 파일 유효성 검사: 형식과 필수 구성 확인

  4. IAM 권한 확인: 배포에 필요한 리소스 접근 권한 점검

  5. 대상 EC2 인스턴스 상태 확인: 인스턴스 상태, 보안 그룹, 네트워크 연결성 등

AWS CodePipeline 문제 해결:

  1. 파이프라인 실행 내역 확인: 어느 단계에서 실패했는지 식별

  2. 실행 세부 정보 검토: 오류 메시지와 관련 정보 확인

  3. 단계별 로그 점검: 오류의 근본 원인 파악

  4. 입력 구성 유효성 검사: 소스 리포지토리 등의 설정이 올바른지 확인

  5. IAM 권한 점검: 파이프라인에 필요한 권한이 있는지 확인

이와 같은 단계적인 문제 해결 접근법을 통해 AWS 개발자 도구 관련 이슈를 효과적으로 진단하고 해결할 수 있습니다.

트래픽 이동 모드:

SageMaker의 트래픽 이동 모드에 대해 정리하면 다음과 같습니다:

한 번에 전체 이동(All at once):

  • 기존 블루 환경의 모든 트래픽을 한 번에 새로운 그린 환경으로 이동

  • 베이킹 기간 동안 CloudWatch 알람으로 그린 환경을 모니터링

  • 문제 없으면 베이킹 기간 후 기존 블루 환경 종료

캐나리(Canary):

  • 2단계로 트래픽을 이동

  • 먼저 일부 트래픽(캐나리)을 새 환경으로 이동하고 베이킹 기간 동안 모니터링

  • 캐나리 성공 시 나머지 트래픽을 새 환경으로 이동하고 기존 환경 종료

선형(Linear):

  • 사전 정의된 수의 단계에 걸쳐 점진적으로 트래픽 이동

  • 단계 수와 각 단계의 트래픽 비율을 사용자 정의 가능

  • 캐나리의 2단계에서 n개의 선형 단계로 확장하여 더 점진적이고 맞춤형 이동 가능

이러한 트래픽 이동 모드를 통해 SageMaker는 새로운 모델 버전을 점진적이고 통제된 방식으로 롤아웃할 수 있습니다.

베이킹 기간:

  • 새 환경 배포 후 모니터링 기간

  • 문제 발생 시 롤백할 수 있어 안전한 배포 보장

캐나리 배포:

  • 새 모델 버전을 일부 사용자에게만 단계적으로 롤아웃

  • 성능 확인 후 전체 배포 진행

SageMaker에서 캐나리 배포를 구현하는 단계는 다음과 같습니다:

  1. 사용자 분할:

    • 로드 밸런서를 사용하여 일부 사용자(캐나리)를 새 버전으로 보냅니다.

  2. 버전 구분 지표 설정:

    • 주요 성능 지표(KPI)에 버전 정보를 나타내는 차원을 추가합니다.

  3. 배포 성공 여부 평가:

    • 메트릭을 통해 새 버전 배포의 성공 여부를 판단합니다.

    • 이 결과에 따라 배포를 계속 진행할지 롤백할지 결정합니다.

  4. 점진적 확대:

    • 새 버전의 부하를 점차 늘려, 모든 사용자가 새 버전으로 마이그레이션되거나 완전히 롤백될 때까지 반복합니다.

이와 같은 단계적 접근을 통해 캐나리 배포를 구현하면 새 소프트웨어 버전을 점진적이고 안전하게 롤아웃할 수 있습니다.

롤링 배포:

  • 모델 버전을 점진적으로 교체하며 배포

  • 블루/그린에 비해 리소스 사용량이 적음

자동 롤백:

  • CloudWatch 알람으로 새 환경 모니터링

  • 문제 발생 시 자동으로 기존 환경으로 롤백

SageMaker의 자동 롤백 기능:

  • SageMaker의 블루/그린 배포에서 자동 롤백 기능을 제공

  • CloudWatch 알람을 사용하여 새로 배포된 그린 환경을 모니터링

  • 문제 발생 시 자동으로 기존 블루 환경으로 트래픽을 되돌림

자동 롤백 과정:

  • 블루/그린 롤링 배포 중 새로 배포된 그린 환경의 CloudWatch 지표가 알람 임계값을 초과

  • 이 경우 SageMaker가 자동 롤백을 실행하여 모든 트래픽을 기존 블루 환경으로 리디렉션

장점:

  • 새 코드 배포 시 애플리케이션 가용성을 유지하면서 위험을 최소화할 수 있음

자동 롤백 기능에 대한 자세한 내용은 “Auto-Rollback Configuration and Monitoring”에서 확인할 수 있습니다.

비용 고려사항:

  • 블루/그린, 베이킹 등의 배포는 두 환경 유지로 인한 비용 발생

  • 한 번에 전체 이동의 경우 한 환경에 대해서만 비용 발생

이와 같은 배포 전략과 모니터링 기능을 통해 SageMaker는 위험을 최소화하면서도 신뢰성 있는 모델 배포를 지원합니다.

Code Repositories Work

ML 파이프라인 구현을 위한 코드 리포지토리 활용 및 보안:

코드 리포지토리의 역할:

  • ML 파이프라인의 소스 코드, Dockerfile, 학습 스크립트, 배포 템플릿 등을 보관

  • 데이터 과학 계정 또는 온-프레미스 환경에 위치할 수 있음

Git 리포지토리:

  • 버전 관리 서비스로, 웹 콘솔을 통해 리포지토리 생성 및 관리 가능

  • 로컬 컴퓨터에 클론하여 변경 사항을 푸시할 수 있음

리포지토리 생성 및 관리:

  • 개발 PC, 콘솔, 리포지토리 서비스를 통해 다양한 작업 수행 가능

파이프라인 실행 시 리포지토리 활용:

  1. 개발자가 코드베이스에 변경 사항을 커밋 또는 푸시 (Clone or check out the repository)

  2. 리포지토리가 이벤트를 감지하고 파이프라인 실행 (Build the code)

  3. 파이프라인이 리포지토리에서 최신 코드를 가져와 처리 (Run tests)

  4. 소스 단계에서 리포지토리로부터 코드를 체크아웃 (Deploy the application)

보안 및 액세스 제어:

  • 데이터 보호: HTTPS/SSH를 통한 암호화된 통신

  • 액세스 제어: IAM 사용자 및 권한으로 인증 및 승인 관리

이와 같이 코드 리포지토리는 ML 파이프라인에 필수적인 구성 요소이며, 안전하고 통제된 방식으로 관리되어야 합니다.

Building and Integrating Mechanisms for Retraining

모델 재학습의 필요성:

  • 데이터 변화와 요구사항 변경에 따른 지속적인 모델 개선을 위해 필요

  • 새로운 데이터 또는 모델 코드 변경 시 재학습이 필요

재학습 메커니즘:

  1. 자동 재학습 파이프라인: ML 파이프라인에 재학습 단계 포함

  2. 예약 재학습: 정기적인 스케줄에 따라 재학습 수행

  3. 드리프트 감지 및 호출 재학습: 데이터 드리프트 감지 시 재학습 실행

  4. 점진적 학습: 새로운 데이터로 점진적으로 모델을 개선

  5. 실험 및 A/B 테스팅: 새 모델 버전 테스트 및 비교

재학습 시 발생하는 재앙적 망각:

  • 새로운 작업/데이터로 학습할 때 이전 지식을 잊어버리는 현상

  • 과도한 적합으로 인해 발생

재앙적 망각 해결 방법:

정규화 기반 방법:

  • 탄성 가중치 응집(EWC): 이전 작업의 중요 매개변수 보존

  • 시냅틱 지능: 매개변수 중요도를 추적하여 선택적 업데이트

재현 기반 방법:

  1. 경험 재현:

    • 이전 작업의 데이터 일부를 저장하고 현재 작업 학습 시 재현

    • 이를 통해 이전 지식 유지

  2. 생성 재현:

    • 실제 데이터를 저장하지 않고, 생성 모델로 이전 작업 데이터 합성

    • 합성 데이터를 현재 작업 학습에 활용

아키텍처 기반 방법:

  1. 점진적 신경망:

    • 새로운 작업 학습 시 모델 용량을 증가시켜 이전 작업 지식 보존

  2. 모듈러 네트워크:

    • 모델을 작업별 모듈로 분리하여, 해당 모듈만 업데이트

재연습 (rehearsal) 기반 방법:

  1. 그래디언트 에피소딕 메모리:

    • 이전 작업 데이터의 일부를 저장하고 현재 작업 학습 시 함께 사용

  2. 예시 재현:

    • 이전 작업의 대표적인 예시를 저장하고 현재 작업 학습에 활용

이러한 다양한 기법들을 통해 재앙적 망각 문제를 해결할 수 있습니다. 각 기법의 장단점과 구현 방법은 모델 아키텍처, 작업, 리소스에 따라 달라질 수 있습니다.

Configuring Inferencing Jobs

SageMaker 추론 전략과 CI/CD 파이프라인 구성에 대해 정리해보겠습니다.

추론 유형:

  • 실시간 추론: 실시간, 대화형, 낮은 지연 시간이 필요한 경우

  • 서버리스 추론: 컴퓨팅 인스턴스를 직접 프로비저닝하지 않고 실시간 추론 처리

  • 비동기 추론: 큰 페이로드 크기, 긴 처리 시간, 준실시간 지연 시간이 허용되는 경우

  • 배치 변환: 대규모 데이터셋에 대한 오프라인 추론 수행

학습과 추론의 차이:

  • 학습은 병렬 처리와 대량 배치 처리를, 추론은 단일 입력 처리를 수행

  • 학습은 더 많은 계산 및 메모리 집약적, 추론은 상대적으로 가벼움

  • 학습은 독립적 실행, 추론은 애플리케이션 워크플로우에 통합

CodePipeline 모범 사례:

  • 파이프라인 구조, 입력 데이터 검증, 버전 관리, 모니터링, 최적화 등

CodePipeline 파이프라인 구성을 위한 모범 사례:

파이프라인 단계 구성:

  • 소프트웨어 개발 수명 주기와 배포 프로세스에 맞춰 단계를 논리적이고 일관되게 구성

소스 제어 통합:

  • 파이프라인 정의와 관련 코드의 버전 관리 및 추적성을 위해 Git 등의 신뢰할 수 있는 소스 제어 시스템 통합

자동화된 테스트:

  • 단위 테스트, 통합 테스트, 보안 검사 등의 자동화된 테스트 단계 포함

  • 배포의 품질과 정확성 보장

환경 일관성:

  • 개발, 스테이징, 프로덕션 등 일관된 환경 유지

  • 배포 관련 문제 최소화

배포 전략:

  • 안전하고 신뢰할 수 있는 배포를 위해 롤백 메커니즘, 블루/그린, 캐너리 등의 배포 전략 구현

이와 같은 모범 사례를 적용하면 CodePipeline 기반의 CI/CD 파이프라인을 안정적이고 효율적으로 구축할 수 있습니다.

SageMaker 파이프라인 모범 사례:

  • 모듈화된 구조, 데이터 검증, 재현성, 로깅 및 모니터링, 병렬 처리 활용

SageMaker 파이프라인 구축을 위한 모범 사례:

파이프라인 구조:

  • 명확하고 모듈화된 구조로 설계

  • 단계별 관심사와 책임을 분리

  • 유지 관리성과 이해도 향상

입력 데이터 검증:

  • 파이프라인 단계 내에 입력 데이터 검증 체크 구현

  • 데이터 무결성과 품질 보장

버전 관리 및 재현성:

  • Git 리포지토리, SageMaker 모델 레지스트리 등을 활용한 버전 관리

  • 파이프라인 정의, 모델 아티팩트, 관련 자산의 재현성 확보

  • 롤백 및 재배포 용이

로깅 및 모니터링:

  • 실행 상태, 성능 지표, 오류/실패 사항에 대한 포괄적인 로깅과 모니터링

  • 파이프라인 실행 가시성 확보

병렬화 및 최적화:

  • SageMaker의 병렬 처리 기능 활용

  • 전체 실행 시간과 효율성 개선

이러한 모범 사례를 적용하면 안정적이고 프로덕션 준비가 된 SageMaker 파이프라인을 구축할 수 있습니다.

EventBridge 규칙 모범 사례:

EventBridge 규칙 활용:

  • SageMaker 이벤트(모델 학습 작업, 엔드포인트 상태 변경 등)를 모니터링하고 자동화된 워크플로우 실행

규칙 구성:

  • 이벤트 유형, 상호 작용 서비스, 사용 사례 등 기준으로 규칙을 논리적 그룹으로 구성

  • 규칙 구조의 명확성과 유지 관리성 보장

이벤트 필터링:

  • 관련성 있는 이벤트에만 규칙이 작동하도록 정확한 필터링 기준 적용

  • 불필요한 처리와 비용 발생 방지

이벤트 리플레이 및 보존:

  • 필요 시 과거 이벤트 분석과 문제 해결을 위한 적절한 리플레이 및 보존 정책 구성

오류 처리:

  • 오류 알림 등 규칙 처리 중 발생할 수 있는 예외와 오류를 처리하는 메커니즘 구현

모니터링 및 경고:

  • 규칙 처리의 문제와 이상을 빠르게 식별하고 대응하기 위한 모니터링과 경고 설정

이러한 모범 사례를 적용하여 EventBridge 규칙을 체계적이고 효과적으로 관리할 수 있습니다.

이러한 접근법을 통해 ML 추론 전략과 CI/CD 파이프라인을 안정적이고 효율적으로 구현할 수 있습니다.
