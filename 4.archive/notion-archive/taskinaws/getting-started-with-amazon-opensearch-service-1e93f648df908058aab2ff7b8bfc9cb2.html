Introduction to OpenSearch

  1. OpenSearch 서비스란?

    • **완전 관리형 검색 및 분석 서비스**

    • OpenSearch와 OpenSearch Dashboards를 제공

    • Elasticsearch 버전 1.5부터 7.10까지 지원

  2. OpenSearch란?

    • 오픈 소스 검색 및 분석 스위트

    • **Elasticsearch 7.10.2 버전을 기반으로 for**k됨

    • 보안, 이상 감지, 경고, 관측성 등의 다양한 기능 제공

  3. OpenSearch 서비스의 주요 기능 및 장점

    • 높은 확장성과 가용성

    • **반구조화 및 비정형 데이터 검색** 지원

    • 트레이스 분석 기능

    • 인프라 문제 진단

    • 이상 감지 기능

    • 비용 효율적

    • 고급 보안 기능

  4. OpenSearch 서비스의 문제 해결

    • 인프라 관리, 모니터링, 패치 등의 작업을 자동화

    • CloudWatch 통합으로 도메인 상태 모니터링

    • 사용자 맞춤형 구성 옵션 제공

    • 대시보드 시각화 도구 번들링

  5. OpenSearch 서비스 요금

    • 인스턴스, 스토리지, 데이터 전송 요금으로 구성

    • 예약 인스턴스 사용 시 온디맨드 대비 요금 절감

    • 스토리지 계층 활용으로 비용 절감 가능

    1. 인스턴스 요금

      • OpenSearch Service에 사용되는 Amazon EC2 인스턴스 유형에 따라 요금이 달라집니다.

      • 더 작은 인스턴스를 선택하면 요금이 저렴하고, 더 큰 인스턴스를 선택하면 요금이 증가합니다.

      • 예약 인스턴스를 선택하면 온디맨드 인스턴스보다 요금이 저렴합니다.

    2. 스토리지 요금

      • 핫 스토리지(hot storage), 울트라워밍 스토리지(UltraWarm storage), 콜드 스토리지(cold storage)에 대한 요금이 다릅니다.

      • 핫 스토리지는 가장 높은 요금이 적용되며, 콜드 스토리지는 가장 낮은 요금이 적용됩니다.

      • 데이터 액세스 패턴에 따라 스토리지 계층을 조정하면 비용을 절감할 수 있습니다.

    3. 데이터 전송 요금

      • Amazon Virtual Private Cloud(VPC) 내에서의 데이터 전송은 무료입니다.

      • 인터넷을 통한 데이터 전송에는 요금이 부과됩니다.

      • 리전 간 데이터 전송에도 요금이 부과됩니다.

What is Amazon OpenSearch?

Amazon OpenSearch Service 개요

  • 관리형 서비스로 AWS 클라우드에서 OpenSearch 클러스터를 쉽게 배포, 운영 및 확장할 수 있음

  • **OpenSearch Service 도메인**은 **OpenSearch 클러스터와 동일**하며, 사용자가 지정한 설정, **인스턴스 유형, 인스턴스 수, 스토리지로 구성**됨

    1. 1:1 대응

      • OpenSearch Service 도메인은 실제 OpenSearch 클러스터와 일대일로 매핑됩니다.

      • 다시 말해, 하나의 OpenSearch Service 도메인은 하나의 OpenSearch 클러스터를 나타냅니다.

    2. 동일한 구성 요소

      • OpenSearch Service 도메인 내에는 OpenSearch 클러스터의 모든 구성 요소가 포함됩니다.

      • 데이터 노드, 마스터 노드, 클라이언트 노드 등 OpenSearch 클러스터를 구성하는 모든 컴포넌트가 포함됩니다.

    3. 동일한 설정 및 리소스

      • OpenSearch Service 도메인에는 사용자가 지정한 설정, 인스턴스 유형, 인스턴스 수, 스토리지 리소스 등이 그대로 반영됩니다.

      • 이는 OpenSearch 클러스터의 구성 및 리소스와 동일합니다.

  • OpenSearch와 레거시 Elasticsearch OSS(최대 7.10 버전) 지원

OpenSearch Service 기능

  • 확장성: 다양한 CPU, 메모리, 스토리지 옵션, 최대 1,002개의 데이터 노드, 25PB 스토리지 지원, 비용 효율적인 UltraWarm 및 콜드 스토리지

    • AZ당 334 Hot 노드 구성 가능 → 3 AZ : 334 x 3 = 1002

  • 보안: IAM 액세스 제어, VPC 및 보안 그룹 통합, 암호화, Cognito/HTTP basic/SAML 인증, 다단계 보안 제어, 감사 로그

  • 안정성: 다중 AZ 배포, 전용 마스터 노드, 자동 스냅샷 기능

  • 유연성: SQL 지원, 사용자 정의 패키지, OpenSearch Dashboards, CloudWatch/CloudTrail 통합, S3/Kinesis/DynamoDB 데이터 수집 등

OpenSearch 서비스 vs. 자체 관리형 OpenSearch

  • OpenSearch 서비스: 인프라 관리가 필요 없음, 비용 관리가 용이, 다른 AWS 서비스와의 통합 이점

  • 자체 관리형 OpenSearch: 소스 코드 제어, 오픈 소스 선호, 멀티 클라우드 전략, 신속한 새 기능 접근

지원되는 Elasticsearch 및 OpenSearch 버전

  • Elasticsearch: 1.5부터 7.10까지의 버전 지원

  • OpenSearch: 1.0부터 2.19까지의 버전 지원

  • 최신 OpenSearch 버전 사용 권장(가격-성능, 기능, 보안 개선)

표준 및 확장 지원

  • 표준 지원 기간: 버그 및 보안 업데이트 제공

  • 확장 지원 기간: 표준 지원 종료 후 최소 12개월 동안 중요 보안 수정 제공(추가 요금 부과)

  • 확장 지원 요금은 Normalized Instance Hour(NIH) 기준으로 청구

가격 책정

  • EC2 인스턴스 사용 시간, EBS 스토리지 볼륨 크기 기반

  • AZ 간 트래픽, 샤드 재배치 트래픽, S3와의 트래픽은 요금 부과 없음

관련 서비스

  • CloudWatch, CloudTrail, Kinesis, S3, IAM, Lambda, DynamoDB 등 다른 AWS 서비스와 통합 가능

Architecture and Use Case

OpenSearch Service를 활용한 클라우드 솔루션 아키텍처 설명:

  1. OpenSearch Service의 기본 기술 개념:

    • 클러스터: OpenSearch 클러스터는 **데이터 노드**, 선택적 **리더 노드**, 실행에 필요한 **스토리지**로 구성됩니다.

    • 데이터 노드: 데이터를 저장하고 검색, 집계 등의 데이터 관련 작업을 수행합니다. 실례 스토리지 또는 EBS 볼륨을 사용합니다.

      데이터 노드의 인스턴스 유형별 Workload Type:

      1. M 인스턴스 (Balance of CPU and memory)

        • 일반적인 용도의 워크로드에 적합합니다.

      2. C 인스턴스 (High-CPU clock speeds, with trade-off of less memory)

        • CPU 집약적인 워크로드에 적합합니다.

        • **더 작은 규모의 높은 빈도의 인덱싱과 쿼리 작업에 적합** : 실시간 로그 분석, 웹 사이트 검색, 센서 데이터 분석 등

      3. R 인스턴스 (High-memory allocation)

        • **많은 메모리를 사용하는 집계 작업**에 적합 : 비지니스 인텔리전스, 기계 학습, 금융 데이터 분석 등

        • Scroll API를 사용하거나 메모리에 **큰 결과 집합을 저장**하는 워크로드에 적합합니다.

      4. I 인스턴스 (On-instance NVMe SSDs, providing exceptionally high levels of I/O throughput)

        • 매우 큰 볼륨의 데이터를 읽거나 쓰는 작업에 적합합니다.

      초기 추정 후 실제 테스트를 통해 적절한 인스턴스 유형을 선택해야 합니다. CPU 사용률이 높다면 다른 인스턴스 유형을 선택해야 할 수 있습니다.

    • 리더 노드: **클러스터 관리 작업을 수행**하지만 데이터를 보유하거나 데이터 업로드 요청에 응답하지 않습니다.

      1. 클러스터 관리 작업 수행:

        • 클러스터의 모든 노드와 **인덱스, 샤드의 상태를 추적**합니다.

        • 클러스터 **상태 변경(인덱스 생성, 노드 제거 등)이 발생하면 클러스터 상태를 업데이트**합니다.

      2. 클러스터 상태 복제:

        • 클러스터 상태 **변경 사항을 모든 노드에 복제**합니다.

        • 이를 통해 클러스터의 **일관된 상태를 유지**합니다.

      3. 클러스터 노드 상태 모니터링:

        • 클러스터의 모든 노드에 **heartbeat 신호를 보내 가용성을 모니터링**합니다.

        • 데이터 노드의 가용성을 지속적으로 체크합니다.

      4. 리더 노드 선출:

        • OpenSearch Service 도메인에는 **항상 하나의 리더 노드가 선출**됩니다.

        • 별도의 **리더 노드를 배포하지 않으면 데이터 노드 중에서 리더 노드가 선출**됩니다.

    • 문서, 필드, 인덱스: **데이터는 JSON 객체인 문서로 저장**되며, **필드는 키-값 쌍**입니다. **인덱스는 데이터의 논리적 그룹**입니다.

    • 샤드: 인덱스는 샤드라는 작은 논리적 단위로 나뉘어 노드에 분산됩니다. 샤드는 기본 샤드와 복제본으로 구분됩니다.

      1. 샤드 크기 권장사항:

        • **검색 지연 시간이 중요**한 경우: **10-30GiB 사이**의 샤드 크기 유지

        • **쓰기 집약적**인 경우(로그 분석 등): **30-50GiB 사이**의 샤드 크기 유지

      2. 샤드 크기 고려 사항:

        • 샤드 크기가 너무 크면 장애 복구가 어려워질 수 있습니다.

        • **샤드 수가 너무 많으면 CPU와 메모리 사용이 증가하여 성능 이슈가 발생**할 수 있습니다.

      3. 기본 샤드와 복제본 샤드:

        • 기본 샤드: **원본 데이터를 저장**하는 샤드입니다.

        • 복제본 샤드: 기본 샤드의 복사본입니다. **장애 극복과 요청 처리**에 사용됩니다.

        • 클러스터 노드 장애 발생 시 복제본 샤드가 기본 샤드로 승격됩니다.

      4. 샤드 배포 전략:

        • 인덱스 생성 시 적절한 샤드 수를 설정해야 합니다.

        • 나중에 샤드 수를 변경하기 어려우므로 초기 설정이 중요합니다.

        • 인덱스 크기와 쿼리 패턴을 고려하여 샤드 수를 결정해야 합니다.

      5. 모니터링 및 최적화:

        • OpenSearch Service의 모니터링 지표를 통해 샤드 크기와 수를 지속적으로 모니터링합니다.

        • **필요한 경우 인덱스 재색인 등의 방법으로 샤드 구성을 최적화**할 수 있습니다.

    • 스토리지: UltraWarm 스토리지와 콜드 스토리지를 제공하여 비용 효율적인 데이터 관리가 가능합니다.

    • 스냅샷: 클러스터의 인덱스와 상태에 대한 백업을 자동 또는 수동으로 생성할 수 있습니다.

    • Auto-Tune: 클러스터 성능과 사용량 지표를 분석하여 메모리 관련 구성 변경을 자동으로 제안합니다.

  2. OpenSearch Service의 주요 사용 사례:

    • 검색 및 개인화: 애플리케이션, 웹사이트, 데이터 레이크 카탈로그에 대한 빠른 검색 경험을 제공합니다.

    • 보안 모니터링: 로그를 중앙 집중화하여 실시간 위협 탐지 및 사고 관리를 지원합니다.

    • 애플리케이션 및 인프라 모니터링: 서버, 라우터, 스위치, 가상화 시스템의 로그와 메트릭을 수집하여 가시성을 제공합니다.

    • 옵저버빌리티 플랫폼: 로그와 트레이스 데이터를 분석하여 성능 문제의 근본 원인을 신속하게 진단할 수 있습니다.

OpenSearch Service의 보안 및 접근성 특징

  1. 접근성:

    • Amazon Virtual Private Cloud (VPC) 또는 공개 엔드포인트를 통해 접근 가능

    • VPC 엔드포인트의 경우 보안 그룹으로 네트워크 액세스 제어

    • 공개 엔드포인트의 경우 IP 주소로 액세스 허용 또는 제한 가능

  2. 보안 레이어:

    • 네트워크 레이어: 요청이 도메인에 도달할 수 있게 허용 여부 결정

    • 도메인 액세스 정책: 도메인 엔드포인트에 도달한 요청에 대한 액세스 허용/거부

    • 세부 권한 제어: 액세스 정책 통과 후 사용자 인증 및 권한 기반 요청 처리

  3. 암호화:

    • AWS Key Management Service를 통한 저장 데이터 암호화

    • 노드 간 TLS 기반 통신 암호화

    • HTTPS 통신 강제

  4. 로깅:

    • CloudWatch Logs를 통해 오류 로그, 검색 느린 로그, 인덱싱 느린 로그 제공

    • 오류, 성능, 안정성 문제 진단에 활용 가능

Amazon OpenSearch Serverless

  1. 개요:

    • 관리형 OpenSearch Service의 프로비저닝된 버전과 달리, 인프라에 대한 걱정 없이 검색 및 분석 워크로드를 실행할 수 있는 서버리스 옵션

    • 간헐적이거나 예측할 수 없는 워크로드에 적합

  2. 주요 특징:

    • 스토리지와 컴퓨팅 리소스가 분리되어 각각 독립적으로 확장 가능

    • CPU, 디스크 사용량, 메모리, 핫 샤드 상태 등의 리소스를 모니터링하고 자동으로 조정

    • 예를 들어 모니터링 워크로드에서 로깅 활동이 급증하면 인덱싱 컴퓨팅 노드를 자동으로 확장

  3. 장단점:

    • 장점: 인프라 관리 걱정 없이 검색 및 분석 워크로드 실행 가능

    • 단점: 알림, 이상 탐지, k-NN 등의 고급 기능 미지원

    • 고급 기능이 필요한 경우 프로비저닝된 관리형 클러스터를 사용해야 함

  4. 사용 사례:

    • 간헐적이거나 예측할 수 없는 워크로드

    • 인프라 관리에 대한 부담을 최소화해야 하는 경우
