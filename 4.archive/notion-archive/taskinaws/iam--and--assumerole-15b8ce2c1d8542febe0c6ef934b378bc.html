What is IAM

  • Identity and Access Management : 자격 증명과 접근 관리

  • AWS 서비스를 사용할 수 있는 자격을 인증하고 필요한 권한을 부여 하는 기능

  • 누가 (Identity) 무엇을 할 수 있는지 (Access Management) 를 결정

  • AAA

    • Authentication : 사용자를 식별

    • Authorization : 사용자가 리소스에 접근 할 수 있는지를 결정

    • Accounting : 사용자가 한 것을 추적

IAM Resources

  • IAM에 저장되는 객체

  • User / Group / Role / Policy / Identity Provider

IAM Identities

  • 식별하고 그룹화 하는 리소스 객체

  • User / Group / Role

IAM Entities

  • 인증에 사용되는 리소스 객체

  • User / Role

Principals (보안 주체)

  • AWS에 Sign-In 하고 Request 하는 person 이나 application

  • AWS 리소스에 접근 할 수 있도록 허가 받은 IAM 개체 (entity)를 의미

  • 기본 : Root User / IAM User / IAM Role

  • 확장 : Federated User / Assumed Role

Authentication

Authorization

  • Reuest context에 대해 Policy를 확인하여 결정

Policy

  • Policy는 principal entity에 대한 권한을 지정한 JSON 문서

Policy Type

Identity-based policy

💡

사용자에게 계정내의 AWS 리소스에 대한 권한 제공

  • Managed policy

    💡

    IAM identity에 연결할 수 있는 독립적인 policy

    • AWS managed policy

      • AWS에서 생성하여 관리하는 policy

      • Policy에 익숙하지 않을 경우 사용을 권고

    • Customer managed policy

      • Customer가 생성하여 관리하는 policy

      • AWS managed policy 보다 상세하게 관리 할 수 있음

      • Visual editor나 JSON policy document를 사용하여 생성

  • Inline policy

    • Single User, Group, Role에 바로 포함하여 생성, 관리 되는 policy

    • 대부분 사용을 권장하지 않음

Resource-based policy

💡

계정간 접근 (다른 계정의 사용자가 나의 리소스를 접근)을 허용하기 위해 사용

  • 지정된 Principal이 어떤 조건에서 어떤 AWS 리소스에 어떤 동작을 할 수 있는지 제어

  • Inline policy 임

Advanced policy

Granting Process

  • AWS 리소스 접근의 기본 설정은 거부 (explicity deny) : Root User는 언제나 접근 허용

  • Allow 정책이 설정되면 기본 설정을 덮어쓰고 허용 (explicity allow)

  • Organization SCP, IAM permission boundary, Session Policy가 있다면 Allow 설정을 덮어씀

  • Deny가 설정된 정책이 있다면 모든 Allow 정책을 덮어 씀 → 여러개의 정책이 있다면 모든 정책에서 allow 설정을 해야 허용이 됨

Policy 구성

IAM Role

  • IAM User와 동일한 자격 증명으로 권한에 대한 Policy를 가진다

  • IAM User와의 차이는 password나 Access Key와 같은 인증 정보 (credential)을 가지지 않는다

  • 특정 한 사람에게 만 관련되는 것이 아니라 Role이 필요한 경우 누구나 사용할 수 있게 고안 된 것

  • IAM User는 한 가지 역할을 맡아 특정 작업을 위한 다른 권한을 임시로 얻을 수 있다

IAM Role과 IAM User 선택

IAM Role

  • EC2 instance에서 실행되는 애플리케이션에서 AWS 리소스에 request 할 경우

    • 애플리케이션에 IAM User의 인증 정보를 전달하는 것 보다는 IAM Role을 부여하여 임시 자격 증명을 가지도록 하는 것이 보안상 안전

    [

    Using an IAM role to grant permissions to applications running on Amazon EC2 instances

    Applications that run on an EC2 instance must include AWS credentials in the AWS API requests. You could have your developers store AWS credentials directly within the EC2 instance and allow applications in that instance to use those credentials.

    https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-ec2.html

    ](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-ec2.html)

  • Mobile phone에서 실행되는 앱에서 AWS 리소스에 request 할 경우

    • IAM User를 만들고 Access Key를 앱에 전달하지 않고 Identity Provider (자격 증명 공급자)를 사용한다

    • Mobile 앱은 IAM Role에 연결된 policy에 지정된 권한을 가지는 임시 보안 자격 증명 (credential)을 얻게 된다

    • Identity Provider

      • Amazon Cognito

      • Web Identity Federation

        • Login with Amazon, Facebook, Google

        • OIDC (OpenID Connect) 호환 Identity Provider

  • 기업 네트워크에서 인증 받은 사용자가 다시 로그인 하지 않고 AWS를 사용할 수 있기를 원하는 경우 → User federation

    • IAM User를 만들지 않고 기업 자격 증명 시스템과 AWS 사이에 연동 관계를 설정 한다

    • 기업 자격 증명 시스템이 SAML 2.0과 호환 될 경우 사용 가능

    [

    ](https://docs.aws.amazon.com/ko_kr/IAM/latest/UserGuide/id_roles_providers_saml.html)

    • Custom proxy 서버를 생성하여 기업 자격 증명을 IAM Role로 변환한다. IAM Role은 임시 AWS 보안 자격 증명을 제공한다.

IAM User

  • IAM User는 계정에서 특정 권한을 가지는 자격 증명일 뿐이다 → 자격 증명이 필요한 모든 경우에 대해 IAM User를 만들 필요는 없음. 임시 보안 자격 증명을 활용할 수 있다.

  • AWS 계정의 사용자가 유일할 경우

    • Root User 자격 증명을 사용할 수 있지만 권장하지는 않음

    • IAM User를 생성하고 IAM User의 자격 증명을 사용하는 것이 보안 모범 사례로 권장 됨

  • User Group의 다른 사람이 AWS 계정에서 작업해야 하는데 User Group에서 사용하는 다른 자격 증명 메커니즘이 없는 경우

    • AWS 리소스에 접근해야 하는 사람 각각에 대해 IAM User를 생성하고 적합한 권한을 할당한다

    • 다수의 사용자가 자격 증명을 공유하지 않도록 해야 한다

임시 자격 증명 사용

AssumeRole

💡

일반적으로 접근 할 수 없는 AWS 리소스를 접근 하기 위해 사용할 수 있는 임시 보안 자격 증명 세트

구성

  • Access Key ID

  • Secret Access Key

  • Security Token

사용 사례

  • 사용자가 다른 AWS 계정의 리소스에 액세스 해야 할 경우

  • 일시적으로 액세스 권한을 얻는 수단으로 사용 : 예) MFA 제공

권한

  • AssumeRole에서 생성된 임시 자격 증명을 사용하여 AWS 서비스로 API 호출을 할 수 있다

  • GetFederationToken 혹은 GetSessionToken API는 예외

Trust Relationship

  • Trusting Account (리소스 소유자)

    • Access 되는 리소스를 보유하고 있는 계정

  • Trusted Account (리소스 접근자)

    • 리소스에 대해 Access가 필요한 IAM User를 보유한 계정

  • 신뢰 관계가 생성되면 Trusted Account의 IAM User 혹은 애플리케이션은 AWS STS AssumeRole API 작업을 사용할 수 있음

    • Trusted Account에 AWS 리소스를 접근할 수 있는 임시 보안 자격 증명이 제공 됨

  • External ID

    • AWS 리소스에 대한 접근 권한을 제 3자에게 부여할 때 사용

    • 리소스 소유자와 제 3자 계정 사이에 합의된 단어나 숫자를 사용할 수 있음

Cross-Account Access

  • Production 환경과 개발 환경을 격리하기 위해 여러 개의 AWS 계정을 가진 상황에서 개발 계정의 사용자가 Production 계정의 리소스에 접근할 수 있도록 역할을 설정

  • Trusting Account : Production Account

  • Trusted Account : 개발 Account

  • Production Account에서 IAM Role을 생성 : UpdateApp

  • IAM Role은 Production Account가 소유한 리소스에 접근할 수 있는 권한 policy를 가진다 → 이 policy를 trust policy라고 함

  • Trust Policy 구성

    • Principal에 Trusted Account를 입력 : Principal은 리소스에 접근할 수 있도록 허가 받은 IAM 개체를 말한다.

    • Permission Policy에 S3 bucket을 읽고 쓸 수 있는 리소스 접근에 대한 내용을 기술

    • 아래의 IAM Role은 Account 111122223333이 S3 mybucket에 R&W를 할 수 있는 권한을 허용 한다

  • 관리자는 생성된 IAM Role을 위임 받고자 하는 대상에게 공유 : Trusted Account에게 공유

    • 공유 정보는 ARN을 사용 : Account 숫자와 IAM Role 이름

    • arn:aws:iam::123456789012:role/UpdateApp

  • 관리자는 Trusted Account인 개발 계정의 구성원에게 공유된 역할 (UpdateApp)로 전환할 수 있는 권한을 부여

    • 개발 그룹에 UpdateApp Role에 대해 AWS STS AssumeRole API를 호출할 수 있는 권한을 부여하여 수행

    • 개발 계정의 모든 IAM User가 Trusting Account인 Production의 UpdateApp Role로 전환할 수 있게 됨

  • Trusted Account에 STS AssumeRole 에 대한 권한을 부여 한다

    • Resource에 Assume할 Role의 ARN을 사용한다
