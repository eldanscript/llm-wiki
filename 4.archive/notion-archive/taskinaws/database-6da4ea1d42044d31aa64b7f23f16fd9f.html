DataBase

Data Trend

  • 데이터의 규모, 속도, 다양성, 복잡성, 상호 연결성이 급격하게 증가

Database Category

Relational

  • 일관적인 구조와 고정된 스키마로 이루어진 table형 data를 위해 설계

  • ACID : Atomicity(반영 혹은 미 반영), Consitency(일관성), Isolation(고립성 - 다른 transaction 끼어들지 못함), Durability(지속성)

    • Data transaction이 안전하고 유효하게 수행 되기 위한 특성

  • ERP, CRM, 전자 상거래 등의 애플리케이션에서 transaction 로깅과 GB, TB 단위의 구조화 데이터베이스를 저장

  • Aurora

    • MySQL, PostgreSQL 호환

    • 엔터프라이즈 데이터베이스 성능 및 가용성 + 오픈 소스 데이터베이스의 단순성 및 비용 효율성

  • RDS

    • 클라우드에서 관계형 데이터베이스를 손쉽게 설치, 운영 및 확장할 수 있는 서비스

    • Aurora

    • PostgreSQL

    • MySQL

    • MariaDB

    • Oracle Databae

    • SQL Server

  • Amazon Redshift

    • 데이터 웨어하우스 쿼리를 데이터 레이크로 확장하는 클라우드 데이터 웨어하우스

Key-Value

  • 카-값 쌍의 컬렉션으로 저장, 하나 이상의 키가 인덱스에 대한 고유한 식별자 역활, 유연한 스키마, 규모와 무관하게 일관된 짧은 지연 시간, 선택적 일관성

  • 실시간 입찰, 장바구니, 제품 카탈로그, 고객 선호도, 지표, 메시지, 주문 이력과 같은 정렬 데이터 수집

  • DynamoDB

    • 규모에 관계없이 10밀리초 미만의 성능을 제공하는 서버리스 키-값 데이터베이스

    • 최종적이며 강력한 읽기 일관성

    • 하나 이상의 행에 걸친 트랜잭션에 작업에 대한 ACID 준수

    • 가장 높은 수준의 가용성과 규모 조정 탄력성을 제공

Document

  • JSON과 유사한 문서에 데이터 저장, 애플리케이션 코드에서 사용하는 것과 동일한 문서-모델 형식을 사용하여 데이터를 쉽게 저장 및 쿼리

  • MongoDB 호환, 유연성, 반구조화, 계층형, 강력한 인덱싱, 빠른 쿼리

  • 카탈로그, 콘텐츠 관리, 개인화, 모바일

  • DocumentDB

    • MongoDB 워크로드를 지원하는 문서 데이터베이스 서비스

In-memory

  • 데이터 캐싱으로 동적 데이터베이스 속도를 높여 액세스 지연 시간을 줄이고, 처리량을 늘리며, 기본 데이터베이스의 부하를 감소

  • 1msec 미만의 지연 시간, 초당 수백만 건 작업, 간단한 명령 세트, 리치 명령 지원 (Redis)

  • 캐싱, 세션 스토어, 리더보드, 지리 공간 및 실시간 분석에 유용

  • MemoryDB for Redis

    • Redis와 호환 되는 인메모리 데이터 스토어

    • 1밀리초 미만의 지연 시간 제공하며 인터넷 규모의 실시간 애플리케이션 가동

  • ElastiCache

    • 인메모리 키-값 스토어 서비스

Graph

  • 고도로 연결된 데이터 세트 내에 관계를 생성

  • 관계형 데이터 세트를 처리할 애플리케이션을 손수비게 구축하고 운영하도록 설계된 NoSQL 데이터베이스

  • SPARQL이나 Gremlin 같은 특화된 그래프 언어를 사용하여 고도로 연결된 데이터 세트를 효율적으로 탐색하는 쿼리를 구축

  • 데이터를 노드, 엣지, 속성 형태로 저장 : 노드는 레코드와 동일

  • RDF (Resource Description Framework) 그래프에서 IRI (Internationalized Resource Identifier)가 포함된 리소스로 표현됨

  • 사기 탐지 소셜 네트워킹, 데이터 계보, 지식 그래프

  • Neptune

    • 완전 관리형 그래프 데이터베이스 서비스

Time-series

  • 시간 순으로 데이터를 수집, 저장, 관리

  • 데이터는 추가만 가능하고 쿼리는 항상 시간 간격을 두고 수행

  • DevOps, 애플리케이션 모니터링, IoT애플리케이션, 산업용 텔레메트리

  • TimeStream

    • IoT 및 운영 애플리케이션용 빠른 시계열 데이터베이스 서비스

Ledger (원장)

  • 원장은 거래 내역을 시간별로 기록한다는 의미

  • 정확한 내역, 투명성, 불변성

  • 재무, 제조, 보험, HR, 급여, 소매, 공급망, 기록 시스템, 건강 관리 : 은행 거래에서 입금 및 출금 내역 추적, 보험금 청구 시 데이터 계보 확인, 공급망 네트워크의 품목 이동 추적

  • QLDB (Quantum Ledger Database)

    • 애플리케이션 데이터에 적용된 모든 변경 사항에 대해 완전하고 암호로 확인할 수 있는 기록을 제공하도록 구축된 원장 데이터베이스

    • 추가 전용 저널에 기록하여 개발자에게 전체 데이터 계보 (data lineage)를 제공

    • 블록체인, 분산 원장 기술이 아님 (Amazon Managed Blockchain) → 애플리케이션에서 모든 데이터 변경 이력이 필요 하지만 신뢰하지 않는 여러 당사자가 개입하지 않는다면 QLDB가 적합

Wide Column

  • 대규모 확장이 가능한 데이터베이스로 빠른 성능과 대량의 데이터 저장이 필요한 애플리케이션에 적합

  • 테이블에 스키마가 있고, 테이블 스키마를 정의하여 쿼리 패턴을 일치 시킴 : 조인을 사용한 테이블간 쿼리 실행은 부 적합

  • 사용자, 디바이스, 이벤트 관련 정보 저장, Cassandra 마이그레이션 (분산 NoSQL 데이터베이스)

  • 산업용 장비 관리 / 플릿 관리 / 경로 최적화, 데이터 로그, 지리적 데이터

  • Keyspaces (Managed Cassandra)

    • 확장 가능하고 가용성이 높은 관리형 Apache Cassandra 호환 데이터베이스 서비스

    • 기존 CQL (Cassandra Query Language) 코드 및 도구를 활용

  • MySQL (ver 5.6, 5.7, 8.0), MariaDB, PostgreSQL (ver 9.6.6 이상)

  • SQL Server : error, agnet log

  • Oracle : alert, trace, audit, listener, agent log

Enhanced Monitoring

3rd party Monitoring Tool

Alarm

  • Capture system and user-defined events : deadlock, access denied, comunnication erros (https://aws.amazon.com/ko/blogs/database/monitor-errors-in-amazon-aurora-mysql-and-amazon-rds-for-mysql-using-amazon-cloudwatch-and-send-notifications-using-amazon-sns/)

Performance Monitoring

  • 데이터베이스 성능을 표시하여 성능에 영향을 미치는 문제를 분석

HA

Multi-AZ vs Read Replicas

  • Multi-AZ : HA & Failover → Synchronous replicated to a standby instance in a different AZ

  • Read Replicas (https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)

    • Read scalability → Asynchronous replica (read-only instance from the snapshot)

    • Same-AZ, Cross-AZ, Cross-Region

    • Maintain the binlogs on your source instance until you have verified that they have been applied to the replica

Aurora

Architecture

Shared Storage System (Cluster Volume)

  • 전통 RDB의 Monolithic식 구조 (SQL → Transaction → Caching → Log)를 분해하여 Storage 계층을 분산 형 스토리지 시스템을 적용

    • 계층 분리를 통해 DB instance node 전체가 늦어지거나 부분 Fail로 인해 전체가 Fail 되는 문제가 없음

    • 계층을 독립적으로 확장할 수 있어 비용 효율적임

  • 전통 RDB는 page에 데이터 구성한 후 page 변경시 디스크에 Flushing → Aurora는 redo log records를 분산 스토리지 계층에 기록하고 요청 시 log record 를 page image로 구성하여 처리

DB Cluster

DB Instance

  • Primary DB instance

    • Read & Write operation

    • Cluster volume의 데이터 수정 작업을 수행

    • DB Cluster는 1개의 Primary instance만 가진다

  • Aurora Replica

    • Primary DB instance와 동일 스토리지에 연결

    • Only read operation

    • Up to 15 Replica

Cluster Volume

  • 10GB chunk 단위로 분할하고 각 6개의 복사본을 사용하여 보호 그룹에 독립적으로 복제

Quorum (정족수) Model

https://aws.amazon.com/ko/blogs/korea/amazon-aurora-under-the-hood-quorum-and-correlated-failure/

  • 3개의 가용 영역(AZ)에 6개의 데이터 복사본을 배포

  • 동기식 복제에서는 하나의 쓰기가 내구성을 가지려면 모든 복사본 확인이 필요 → 디스크, 노드, 네트워크 중 가장 성능이 낮은 요소로 지연 시간이 결정

  • 비 동기식 복제에서는 지연 시간을 낮출 수 있지만 내구성 확인 전 장애 발생 시 데이터 손실 가능

  • Aurora에서는 Quorum model을 사용

    • 읽기 세트와 Vr과 쓰기 세트 Vw 가 최소 하나의 중첩 복사본을 가져야 한다 : 세 개 데이터 복사본 존재할 경우 Vr 2, Vw 2개 필요 → 1개의 중첩 복사본 가능

    • 쓰기 쿼럼은 이전의 쓰기 쿼럼과 중첩되어야 한다 : Vw > V/2

  • Aurora에서는 위 규칙에 따라 4개의 쓰기 세트와 3개의 읽기 세트가 있는 6개 복사본 쿼럼을 사용 → 4개 복사본에 쓰기 수행하여 완료 응답을 받으면 쓰기가 완료

Global Database

Feature

  • 1개 region에 primary DB cluster를 5개 region에 읽기 전용 secondary (보조) DB cluster를 사용

  • 1초 미만의 대기 시간으로 보조 region에 데이터 복제

Pros

  • Local 대기 시간으로 Global read 구성

  • 보조 Aurora DB cluster 확장

Limitiation

  • Aurora Mult-master cluster

  • Aurora Serverless v1

  • Amazon RDS proxy

  • Aurora 내 역추적

DynamoDB

DynamoDB Accelerator (DAX)

  • DynamoDB 테이블 앞에 논리적으로 배치되는 완전 관리 캐싱 서비스

  • 쓰기 모드(Write-Through)에서 작동하며 DynamoDB와 API 호환
