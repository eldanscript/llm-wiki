Deep Dive IoT Rule Engine

MQTT

  • Publish/subcribe 기반의 메시징 프로토콜

  • 모든 메시지를 주제(topic)를 통해 전송

MQTT message

Feature

  • 주제(topic)은 여러개의 게시자 (publisher)와 구독자 (subscriber)를 가질 수 있다

  • 단일 소스는 여러 주제를 게시하고 구독할 수 있다

  • Wildcard 주제 구독 가능

    • (multi-level wildcard) : 모든 하위 트리 (sensor/# → sensor/temp, sensor/temp/room1)

      • (single-level wildcard) : 해당 트리 레벨 일치 (sensor/+/room1 → sensor/temp/room1, sensor/moisture/room1)

    • $ : AWS에서 예약하여 사용하는 주제

  • 게시자와 구독자가 분리되고 메시지 브로커를 통해 연결

  • 주제는 대,소문자 구분 (case-sensitive)

Telemetry message

  • 디바이스에서 전송되어 클라우드에 수집되는 읽기 전용 데이터

Command message

  • 원격에서 디바이스를 제어하기 위해 사용되는 메시지

MQTT communication pattern

https://docs.aws.amazon.com/ko_kr/whitepapers/latest/designing-mqtt-topics-aws-iot-core/designing-mqtt-topics-aws-iot-core.html

Point-to-point

  • One to one

  • One to many

Broadcast

  • One to many

  • Fan in

Topic Best Practice

  • 소문자, 숫자, 대시만 사용

  • 주제 레벨은 일반적인 것에서 구체적으로 (general to specific)

  • 적절한 (relevant) 라우팅 정보를 포함

  • 데이터 주제와 명령어 주제를 구분

  • Thing Name을 포함 하여 메시지 추적이 가능하도록

  • 디바이스가 multi-level wildcard를 사용하여 모든 주제를 구독하도록 하지 않음

    • IoT rule engine에서 wildcard 사용

    • single-level wildcard를 사용

Basic Ingest

  • 메시지 브로커 비용 감소

  • 예약 주제로 메시지를 전송해야 함 : $aws/rules/rule-name/optional-message-topic

Best practice

  • 추가적인 라우팅 정보를 MQTT 주제에 포함

  • 짧고 설명적인 rule name 사용

Query statement

  • Not SQL → SQL-like command

Data Type

  • Int, Decimal, Boolean, String, Array, Object, Null, Undefined

JSON extensions

  • “*”

    • SELECT * → full message data

  • “.”

    • SELECT car.tier2 → nested JSON object

Query Format

SELECT clause

  • 메시지 부분을 지정

  • select multiple components by separating them with a comma.

  • VALUE keyword : produces outputs that are not JSON objects

Example

  • Message :{ "vehicle": "truck", "speed": 38, "weight": 2000}

  • SELECT speed AS mph {"mph": 38}

  • SELECT speed AS mph, weight AS lbs

  • SELECT *, "blue" AS color {"vehicle": "truck", "speed": 38, "weight": 2000, "color": "blue"}

  • SELECT [32, 32, 32, 32] AS tirepress {"tirepress": [32, 32, 32, 32]}

  • SELECT VALUE vehicle "truck"

FROM clause

  • Rule이 트리거 되는 주제를 지정

  • When using Basic Ingest, the FROM clause is optional.

WHERE clause

  • Boolean statement

  • Rule 수행 조건

Example

  • SELECT * WHERE speed < 30 OR weight > 1000 YES

Query example

  • Message : { “vehicle”: “truck”, “speed”: 38, “weight”: 2000}

  • Query : SELECT speed AS velocity, speed - 30 AS above_limit WHERE weight < 3500 AND vehicle = ‘truck’

  • Output : {“velocity”: 38, “above_limit”: 8}

Function

  • Query내 함수 사용 가능

  • Mathematical, String

  • AWS Function : aws_lambda, machinelearning_predict

  • AWS IoT Function : get_thing_shadow, clientId, accountId, topic

  • timestamp : UTC (from Thursday, 1 January 1970)

Best Practice

  • If you are not using reserved topics and do not need to distribute messages to multiple subscribers, use Basic Ingest to send messages to the rules engine to avoid incurring messaging costs.

  • Pin yourself to one SQL-version when creating IoT rules.

  • Use the WHERE clause to filter messages that do not apply to an AWS IoT action.

  • If your commands are in JSON, reference any contextual payload metadata, such as session ID, in the SELECT and WHERE clause of the rules engine.

  • Use the topic(Decimal) rule function to augment your MQTT messages with contextual information contained in your MQTT topics. Use the timestamp() rule function to include a timestamp that correlates to the time that a message reached AWS IoT Core.

  • Use substitution templates in your actions to express variables. Substitution expressions make it easier to dynamically route to downstream IoT rule actions.

  • Always use error actions for your rules.

  • In cases where commands are sent at a high throughput rate, you can use the IoT rules engine with other AWS services to buffer data before storage. After AWS IoT Core receives a message, use AWS services, such as like Amazon Kinesis or Amazon Simple Queue Service (Amazon SQS), to buffer the message payload along with the MQTT topic the message was published to. After messages are buffered, you can run your own logic to map fields from the payload or the topic and enrich the payload with additional metadata.

  • When creating new rules, use the DynamoDBv2 action over the DynamoDB action. When you use the DynamoDB action to write data to a DynamoDB database, the entire MQTT message payload goes into one column named payload. For the DynamoDBv2 action, each attribute in the payload is written to a separate column in the DynamoDB database. Having the attributes in separate columns enables querying and sorting.

  • Automate operational activities using IoT rules.

  • To track the completion of a command or request, use the AWS IoT rules engine to store the data and status in a service, such as Amazon DynamoDB or CloudWatch metrics.

  • Use infrastructure as code by using AWS CloudFormation templates to deploy IoT rules.

Query Example

Q3)

  • When using the message broker, the FROM clause is required. When using Basic Ingest, the FROM clause is optional

Q6)

  • Topic : us11/car1/speed, us11/car2/speed, us11/car3/speed

  • car1, car2, car3 (in the topic) are the car IDs.

  • The messages contain a lot of information, such as the car model, speed, location (but not the carId).

  • Send the speed, carId, and model of the cars driving over 35 mph to Amazon S3.

  • The speed is being given in mph so rename the speed variable “mph” and store the carId as “carId”

  • SELECT speed AS mph, topic(2) AS carId, model FROM ‘us11/+/speed’ WHERE speed > 35

Q8)

  • Topic : truck/dump/height

  • message length : height

  • Store the value of the angle of the bed height as a CloudWatch metric

  • angle = cos^-1((height^2 - 325) / (-300))

  • SELECT VALUE acos((power(height, 2) - 325) / (-300)) FROM ‘truck/dump/height’

Q9)

  • Query : SELECT airbags, get(airbags, 0) AS driver FROM ‘vehicle/car1/airbags’

  • Message : {“carId”: 72849, “speed”: 28, “airbags”: [true, false, true, false]}

  • Output : {“airbags”: [true, false, true, false], “driver”: true}

Q10)

  • Input message : {“airbag1”: true, “airbag2”: false}

  • Output messge : {“airbags”: [true, false]}

  • SELECT [airbag1, airbag2] AS airbags

Q11)

  • SELECT topic(2) AS carId, encode(*, ‘base64’) AS memo FROM ‘vehicle/car2/details’ WHERE timestamp() % 12 = 0

Q17)

  • You want to write a rule query statement so that whenever the cost is greater than 50, an Amazon SNS notification is sent with the full message.

For messages with the method, “car”, calculate the cost based on gas mileage so that it would be the distance × 0.35. Otherwise, keep the cost as is

  • SELECT * FROM ‘gps/options’ WHERE CASE method WHEN “car” THEN distance*.35 ELSE cost END > 50

Q19)

  • Topic : gps/walking → {“walk”: {“distance”: 14, “time”: 27, “cost”: 0}}

  • SELECT walk.distance/walk.time AS speed FROM ‘gps/walking’

Q20)

  • Topic : gps

{ “method”: “car”, “distance”: 1.6, “time”: 9},

  • outputs all the options where the time is less than 15 minutes and stores the output as “travel”

  • SELECT (SELECT * FROM directions WHERE time < 15)) AS travel FROM ‘gps/options’
