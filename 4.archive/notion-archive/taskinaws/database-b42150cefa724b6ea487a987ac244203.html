개념에 대한 부분

  • DB transaction에서의 ACID에 대해 설명할 수 있는지?

    • DB transaction이 안전하게 수행되는 것을 보장하기 위한 성질

    • Atomacity : ensures all-or-none rule for database modifications

    • Consistency : Data values are consistent across the database

    • Isolation : Two transactions are said to be independent of one another

    • Durability : Data is not lost even at the time of server failure

  • 분산 시스템에서의 BASE에 대해 설명할 수 있는지? ACID와의 차이는?

    • Basically Available : system is guaranteed to be available, 가용성 중시

    • Soft state : state of the system may change over time, even without input, 사용자가 관리(refresh, modify)하지 않으면 Data가 expire 될 수도 있음

    • Eventually Consistency : system will become consistent over time

    • BASE는 NoSQL에 적용, ACID는 RDBMS에 사용

    • BASE는 System 전반에 대한 특성, ACID는 Transaction에 한정

    • BASE는 약한 일관성, ACID는 강한 일관성

    • BASE는 시스템 성능에 초점, ACID는 데이터 관리에 초점

    • BASE는 query 설계가 중요, ACID는 Table 설계가 중요

  • RDBMS와 NoSQL의 차이는 무엇이고 어떤 경우에 사용하면 좋을지?

    • DBMS는 사용자와 데이터베이스 사이에서 사용자의 요구에 따라 정보를 생성해주고 데이터베이스를 관리해 주는 소프트웨어라고 설명을 했습니다. 또한 기존의 RDBMS에서의 저장 방식은 SQL에 의해 저장되고 있으며 정해진 스키마에 따라 데이터를 저장하여야 합니다. RDBMS에는 DBMS앞에 R이 붙어 있습니다. 이 R은(Relational)의 약자로 RDBMS는 관계형 데이터베이스 관리 시스템을 의미합니다. 이름과 같이 RDBMS는 RDB를 관리하는 시스템이며

    • RDB는 관계형 데이터 모델을 기초로 두고 모든 데이터를 2차원 테이블 형태로 표현하는 데이터베이스입니다

    • Non-RDBMS의 총칭이다. 단순한 data를 대용량으로 저장할 수 있고 빠른 성능을 제공하는 database이다. Data model은 key:value 형태의 저장 구조를 가지며 data간의 관계는 지원하지 않는다. data를 빠르게 읽고 쓰는데 최적화 되어 있다.

    • Data 간의 관계를 정의하지 않고 peta byte급 대용량 data를 저장할 수 있다. data를 고성능 머신에 저장하는 것이 아니라 일반적인 서버 수십 대를 연결하여 저장, 처리하는 분산형 구조를 가진다. 분산형 구조를 통해 특정 서버에 장애가 났을 때에도 data 유실이나 서비스 중지가 발생하지 않는다. Table의 schema가 유동적이다.

    • NoSQL의 data 저장 구조는 Key/Value, Ordered Key/Value, Document Key/Value로 분류된다. Key안에 Column과 Value 조합으로 된 여러 개의 Field (Column Family) 개념을 적용하여 Value를 저장한다. Key field는 RDBMS의 Primary Key, Column Field는 RDBMS의 일반 data field와 유사하다. Ordered Key/Value는 내부적으로 Key를 순서로 정렬하여 저장한다. Document Key/Value는 XML,JSON,YAML과 같은 구조화된 data type을 Value로 저장하는 것으로 복잡한 계층 구조를 표현할 수 있다.

    • Redis는 Key/Value Store (KVS)를, MongoDB는 Document Key/Value를 사용한다.

    • NoSQL : Key-Value, Document, Wide Column, Graph

  • RDBMS와 NoSQL 장단점

    • RDBMS는 위에서 설명을 하였듯이 정해진 스키마에 따라 데이터를 저장하여야 하므로 명확한 데이터 구조를 보장, 각 데이터를 중복없이 한 번만 저장

    • 테이블간테이블 간 관계를 맺고 있어 시스템이 커질 경우 JOIN문이 많은 복잡한 쿼리가 만들어질 수 있습니다. 성능 향상을 위해서는 서버의 성능을 향상 시켜야하는 Scale-up만을 지원합니다. 이로 인해 비용이 기하급수적으로 늘어날 수 있습니다. 스키마로 인해 데이터가 유연하지 못합니다. 나중에 스키마가 변경 될 경우 번거롭고 어렵습니다.

    • NoSQL에서는 스키마가 없기 때문에 유연하며 자유로운 데이터 구조를 가질 수 있습니다. 언제든 저장된 데이터를 조정하고 새로운 필드를 추가할 수 있습니다. 데이터 분산이 용이하며 성능 향상을 위한 Saclue-up 뿐만이 아닌 Scale-out 또한 가능.

    • 데이터 중복이 발생할 수 있으며 중복된 데이터가 변경 될 경우 수정을 모든 컬렉션에서 수행을 해야 합니다. 스키마가 존재하지 않기에 명확한 데이터 구조를 보장하지 않으며 데이터 구조 결정가 어려울 수 있습니다.

    • RDBMS는 데이터 구조가 명확하며 변경 될 여지가 없으며 명확한 스키마가 중요한 경우 사용하는 것이 좋습니다. 또한 중복된 데이터가 없어(데이터 무결성) 변경이 용이하기 때문에 관계를 맺고 있는 데이터가 자주 변경이 이루어지는 시스템에 적합합니다.

    • NoSQL은 정확한 데이터 구조를 알 수 없고 데이터가 변경/확장이 될 수 있는 경우에 사용하는 것이 좋습니다. 또한 단점에서도 명확하듯이 데이터 중복이 발생할 수 있으며 중복된 데이터가 변경될 시에는 모든 컬렉션에서 수정을 해야 합니다. 이러한 특징들을 기반으로 Update가 많이 이루어지지 않는 시스템이 좋으며 또한 Scale-out이 가능하다는 장점을 활용해 막대한 데이터를 저장해야 해서 Database를 Scale-Out를 해야 되는 시스템에 적합합니다. 데이터 정합성이나 일관성이 최 우선 순위가 아닌 경우나 데이터가 너무 너무 많은 경우

    • 만약 서비스 구성하는데 비관계형 데이터베이스를 써야 하는 이유를 정확하게 알지 못하면 관계형 데이터베이스를 사용하는 것을 일단 추천합니다. 그리고 기존에 하나인 데이터베이스에서 영화 데이터와 시상 데이터를 찢어서 사용한다고 하면 분명히 두 테이블관 관계가 있는 것으로 보입니다. 만약에 관계형 데이터 형태인데 무리하게 NoSQL를 사용하려고 하면 분명히 나중에 후회를 할 것입니다. 만약에 특정 데이터, 예를 들어 보고 싶은 목록 리스트를 문서 형태로 만든다면(사실 이것도 영화와 사용자 정보 간에 관계가 있기 때문에 굳이 사용할 필요가…) PostgreSQL의 JSON형태로 저장하는 기능 활용하면 관계형과 비 관계형을 함께 효율적으로 사용할 수 있을 것 같네요.

실무 경험에 대한 부분

  • DB의 Index는 무엇인지?

    • RDB (Relational DataBase)는 가장 일반적인 data base이다. table이라는 data 구조를 가지며 SQL 언어를 사용하여 table에 record 단위로 data를 추출, 입력, 삭제를 수행한다.

    • DB Index는 검색 속도를 높이기 위한 Data 구조로 DB에 색인을 남기는 작업이다. Indexing 작업을 하게 되면 Query에서 속도 향상을 얻을 수 있지만 쓰기 작업에서 Index를 구성해야 하기 때문에 처리 시간이 증가하고 별도의 Storage 사용이 필요하게 된다. Index는 Key-Field 구조로 이루어져 있으며 Table에 대한 세부 정보를 가지고 있지는 않다. 대부분의 DBMS에서는 Primary Key를 자동으로 Indexing 한다.

  • 어떤 것 들이 좋은 Index 일지? 나쁜 Index 어떤 것 일지?

    • 컬럼을 정해서 설정하는 것이므로 후보 컬럼의 특징을 잘 파악해야 함

    • Cardinality : 카디널리티가 높을 수록 인덱스 설정에 좋은 컬럼 (다양성이 높은 것을 의미, 한 컬럼이 갖고 있는 값의 중복 정도가 낮을 수록 좋음)

    • Selectivity : 선택도가 낮을 수록 인덱스 설정에 좋은 컬럼

    • 활용도 : 활용도가 높을 수록 인덱스 설정에 좋은 컬럼

    • 중복도 : 중복도가 없을 수록 인덱스 설정에 좋은 컬럼

  • Shared Nothing Architecture란?

    • 각각의 node가 독립적으로 구동디고 독립적인 data를 처리 → data를 node간에 partitioning 하여 처리

    • 성능에 집중, node간 중복 데이터 처리 문제. 데이터 균등 분할의 이슈

    • Shared everything은 각각의 node가 data store를 공유 → 자원 활용에 초점

  • **Sharding에 대해 설명해 줄 수 있는지?**

    • 무공유(share-nothing) architecture를 구현하여 대규모 Database를 다수의 소규모 Database로 분할하는 기술이다.

    • Database 분할은 동일한 query에 join 되지 않은 table을 다른 host로 분할하는 방법이 일반적이다.

    • 그외에 table을 여러 host로 복사한 후 hashing algorithm을 사용해 어떤 host로 update 할지 결정하는 방법도 있다.

    • distributes a single logical database system into a cluster of machines

    • Horizontal partitioning design scheme

    • Sharding makes a database system highly scalable. The total number of rows in each table in each database is reduced since the tables are divided and distributed into multiple servers.

    • Reduces the index size, which generally means improved search performance.

    • The most common approach for creating shards is by the use of consistent hashing of a unique id in application (e.g. user id)

  • Sharding을 할 때 신경써야 할 점은?

    • application to be aware of the data location

    • Any addition or deletion of nodes from system will require some rebalance to be done in the system

    • require lot of cross node join queries then your performance will be really bad

    • knowing how the data will be used for querying becomes really important

    • wrong sharding logic may result in worse performance

    • 스키마 구조를 변경하려면 DBA가 모든 샤드에 적용

  • CDC (Change Data Capture) 서비스가 어떤 것인지 설명해 줄 수 있는지?

    • 변경된 데이터를 사용하여 동작을 취할 수 있도록 데이터를 결정하고 추적하기 위해 사용되는 여러 소프트웨어 디자인 패턴들의 모임

    • Timestamp, Version number, status on rows, Log scaning

  • ETL (Extarct, Transform, Load) 서비스가 어떤 것인지 설명해 줄 수 있는지?

  • 사용해 본 DB는? 어떤 Workload 였는지?

  • Inner Join, Left Outer Join, Right Outer Join, Full Outer Join에 대해 설명한다면

    • Inner Join : 두 테이블의 교집합

    • Full Outer Join : 두 테이블의 합집합

    • Left Outer / Right Outer Join : Table 1 혹은 Table 2의 모든 행과 나머지의 공통 행 반환
