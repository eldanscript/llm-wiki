Resiliency (복원력) - 워크로드가 인프라나 서비스의 시스템 장애를 복구하고, 컴퓨팅 리소스를 동적으로 확보하여 수요에 대응하거나, 구성 오류나 일시적 네트워크 문제와 같은 장애를 완화하는 기능을 의미

DR objectives

  • DR의 목표는 워크로드를 백업하거나 다운타임을 완전히 피하는 것

  • 워크로드의 가치에 따라 RTO와 RPO의 목표치를 결정해야 한다

RTO (Recovery Time Objective)

  • 서비스 중단과 복원 간의 허용 가능한 최대 시간

  • 수용 가능한 서비스 다운타임이 결정 된다

RPO (Recovery Point Objective)

  • 마지막 데이터 복구 지점 이후 최대 허용 시간

  • 수용 가능한 데이터 손실이 결정 된다

DR Strategy

Multi-AZ Strategy

  • 하나 이상의 AZ에 영향을 주는 단일 이벤트의 위험을 크게 감소 시킴

Multi-Region Strategy

  • 별도로 분리된 위치에 있는 여러 데이터 센터에 영향을 줄 수 있는 범위의 이벤트에 대해 비즈니스 보증을 제공

  • Multi-AZ strategy나 Hybrid strategy와 함께 사용 가능

Backup and Restore

  • RPO : in hours

  • RTO : ~ 24 hours

  • 데이터와 애플리케이션을 Point-in-time backup을 사용하여 DR 리전에 백업

  • 재해 복구 필요 시 백업 데이터를 복원

AWS Services

  • 주기적 혹은 연속적인 Snapshot 운영 → RPO가 결정 됨

    • Point-in-time recovery 지원

    • Amazon EBS, Amazon DynamoDB, Amazon RDS, Amazon Aurora DB, Amazon Redshift, Amazon Neptune

    • Amazon S3 CRR (Cross-Region Replication) : S3 버킷을 DR 리전에 비동기 방식으로 복사하며 versioning을 사용해야 복구 point를 선택할 수 있음

  • AWS Backup

    • 리소스에 대한 백업 기능을 구성, 스케쥴링, 모니터링 할 수 있는 중앙화된 위치를 제공

    • DR 복구 리전 등의 다른 리전에 대한 백업 생성

    • Amazon EBS, Amazon EC2 instances, Amazon RDS, Amazon Aurora, Amazon DynamoDB, Amazon EFS, AWS Storage Gateway volumes, Amazon FSx for Windows and Lustre

    • Amazon S3

Pilot Light

  • RPO : in minutes

  • RTO : in hours

  • 시스템의 가장 중요한 핵심 요소를 항상 실행하는 최소 버전의 환경을 DR 리전에 유지

  • 중요한 핵심 요소를 중심으로 전체 프로덕션 환경을 신속하게 프로비저닝

  • 데이터를 다른 리전에 복제하고 핵심 워크로드의 인프라 복제본을 공급

    • 데이터베이스와 오브젝트 스토리지를 지원하는 리소스는 항상 동작

    • 애플리케이션 서버와 같은 요소들은 중단 상태에서 재해 복구 장애 조치가 호출되면 애플리케이션 코드와 구성을 가지고 동작 시킴

  • 활성화된 리소스를 최소화하여 비용을 최소화 하고 핵심 인프라 요소들이 제자리에 위치하고 있어 복구 시간을 감소 시킴

  • 복구 배포시 각 리전에 핵심 인프라를 변경하면서 동시에 워크로드 구성이나 코드 변경을 배포해야 함 → IaC를 사용하여 자동화 가능

    • Full infrastructure deployment to the primary Region and Scaled down/Switched-off infrastructure deployment to DR region

AWS Services

  • DR 리전에 연속적으로 데이터 복제를 하는 것이 RPO를 줄이기 위해 가장 좋은 접근 방법임

  • Amazon S3 Replication, Amazon RDS read replicas, Amazon Aurora global databases, Amazon DynamoDB global tables

  • Amazon RDS에 장애 조치를 수행은 RDS read replica를 primary 인스턴스로 승격

    • 승격 과정에 리붓이 되며 수 분이 소요됨 (Amazon Aurora 제외)

    • Amazon Aurora global database를 사용하면 1분 이내에 승격 되며 리붓 과정이 없음

  • 축소된 규모의 핵심 인프라를 DR 리전에 배포하기 위해 CloudFormation template을 사용

    • 사전 정의한 의사 패러미터를 사용하여 조건 로직을 구현

    • EC2 인스턴스 배포에는 Golden AMI를 사용하고 이후 규모 확장에 AWS Auto Scaling을 사용

  • Amazon Route 53 혹은 AWS Global Accelerator를 통해 트래픽을 DR 리전으로 라우팅

  • AWS Elastic Disaster Recovery

CloudEndure Disaster Recovery

  • AWS Marketplace에서 이용 가능

Warm Standby

  • RPO : in seconds

  • RTO : in minutes

  • 항상 실행되는 모든 기능을 갖춘 환경의 축소된 버전을 DR 리전에 유지

  • 비즈니스 크리티컬 시스템은 완전히 복제되고 항상 실행되지만 플릿은 축소

  • 복구 시기가 되면 시스템은 프로덕션 로드를 처리하기 위해 신속하게 확장

  • Warm Standby 규모를 크게 할수록 RTO가 감소 → 전체 규모로 확대하면 Hot Standby가 됨

Multi-Region (Site) Active-Active

  • RPO : Near Zero

  • RTO : Potentially Zero

  • 워크로드가 여러 AWS 리전에 배포되고 능동적으로 트래픽을 처리

  • 사용 중인 리전 간에 사용자 및 데이터를 동기화가 필요

    • 두 개의 다른 지역 복제본의 동일한 레코드에 대한 쓰기로 인한 가능한 충돌은 회피나 처리가 필요

    • 데이터 복제는 데이터 동기화에 유용하며 일부 유형의 재해로부터 보호가 되지만 point-in-time recovery 옵션이 포함되어 있지 않으면 데이터 손상이나 파기로부터 보호되지 않음

  • 복구 시점이 되면 Amazon Route 53 또는 AWS Global Accelerator와 같은 서비스를 사용하여 워크로드가 정상인 위치로 사용자 트래픽을 라우팅

AWS Services

  • Amazon Route 53과 AWS Global Accelerator가 트랙픽을 라우팅할 엔드포인트를 결정

    • AWS Global Accelerator의 Traffic dial 의 percentage 설정

    • Amazon Route 53의 geoproximity, latency 기반 policy를 사용

  • 데이터 복제

    • Read 작업은 가까운 리전에서 진행 (read local)

    • Write global strategy

      • 모든 쓰기 작업을 단일 리전에 수행 → 리전 실패시 다른 리전을 승격

      • Amazon Aurora global database

    • Write local strategy

      • 가까운 리전에 쓰기 작업 (write local)

      • Amazon DynamoDB global tables : last writer wins reconciliation 사용

    • Write partitioned strategy

      • 파티션 키를 기준으로 특정 리전에 쓰기 작업 진행 → 쓰기 충돌 회피

      • Amazon S3 replication (bi-directionally configure)
