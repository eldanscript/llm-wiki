3.2 Create and Script Infrastructure

Base

머신 러닝 솔루션의 유지 보수, 확장성, 비용 효율성을 높이는 best practices:

  • 모듈화된 아키텍처 설계

  • CI/CD 파이프라인 구축

  • 재사용 가능한 코드 및 구성 요소 개발

  • 자동화된 테스트 및 배포 프로세스 구현

  • 모니터링 및 로깅 시스템 활용

  • 비용 관리를 위한 리소스 최적화

IaC(Infrastructure as Code)의 이점 및 사용 사례:

  • 반복 가능하고 일관된 인프라 배포

  • 코드 기반 버전 관리를 통한 변경 추적성

  • 신속한 환경 프로비저닝 및 스케일링

  • 개발 및 운영 팀의 협업 향상

  • 클라우드 인프라의 선언적 관리

CloudFormation을 통한 자동 리소스 프로비저닝:

  • 인프라와 리소스를 선언형 JSON/YAML 스택으로 정의

  • 스택 생성, 업데이트, 삭제 등의 인프라 수명 주기 관리

  • 크로스 리전 및 계정 간 리소스 배포 가능

  • 사용자 지정 리소스 유형 및 변환기 생성 가능

AWS CDK를 통한 자동 리소스 프로비저닝:

  • 개발자 친화적인 프로그래밍 언어(TypeScript, Python 등)로 인프라 정의

  • 앱 수준의 추상화를 통해 복잡한 리소스 구조 관리

  • 프로그래밍 언어 기능(반복문, 조건문 등) 활용 가능

  • 클라우드 네이티브 개발 방식과 잘 어울림

AWS CDK와 CloudFormation 비교:

  • CloudFormation은 선언형 템플릿, CDK는 프로그래밍 언어 기반

  • CloudFormation은 AWS 전용, CDK는 멀티 클라우드 지원

  • CloudFormation은 템플릿 작성 경험 필요, CDK는 프로그래밍 언어 경험 필요

  • CloudFormation은 템플릿 변환 유틸리티 필요, CDK는 프로그래밍 언어 컴파일러 활용

컨테이너 구축 및 관리:

  • 표준화된 배포 단위로 애플리케이션 패키징

  • 경량화된 운영 체제 및 종속성 관리

  • CI/CD 파이프라인과의 통합

  • 컨테이너 레지스트리 활용(ECR, Docker Hub 등)

컨테이너 개념 및 AWS 컨테이너 서비스:

  • 컨테이너화: 격리된 실행 환경 제공

  • Docker: 가장 널리 사용되는 컨테이너 플랫폼

  • AWS ECS(Elastic Container Service): 컨테이너 오케스트레이션

  • AWS EKS(Elastic Kubernetes Service): 관리형 Kubernetes 서비스

SageMaker를 통한 ML 모델 배포 및 호스팅:

  • SageMaker SDK를 활용한 모델 학습, 등록, 배포

  • 사용자 지정 컨테이너 이미지 활용

  • 실시간 추론을 위한 엔드포인트 생성

  • 배치 추론을 위한 작업 실행

Auto Scaling을 위한 지표 선택:

  • CPU 사용률, 메모리 사용률, 네트워크 I/O 등

  • 애플리케이션 성능 지표(지연 시간, 처리량 등)

  • 비용 효율성을 위한 지표(인스턴스 사용량, 스토리지 사용량 등)

SageMaker 엔드포인트 Auto Scaling:

  • 사용자 지정 스케일링 정책 정의

  • 지표 기반 자동 확장 및 축소

  • 예측 기반 스케일링을 통한 선제적 확장

  • 비용 최적화와 SLA 준수 간 균형 유지

Best Practices

AWS Well-Architected Framework은 기계 학습(ML) 솔루션을 설계하고 구성할 때 유용한 지침을 제공합니다. 이 프레임워크는 안전하고, 고성능이며, 복원력 있고, 효율적인 인프라를 갖춘 애플리케이션을 만들 수 있도록 도와줍니다. AWS Well-Architected Framework의 6개 핵심 원칙은 다음과 같습니다:

  1. 보안(Security): 환경, 데이터, 워크로드를 안전하게 유지하는 방법

  2. 신뢰성(Reliability): 중단에 강하고 신속하게 복구되는 솔루션 구현

  3. 성능 효율성(Performance Efficiency): 인프라 리소스를 효율적으로 사용하여 요구 사항 충족

  4. 비용 최적화(Cost Optimization): 예상 성능을 제공하면서도 비용을 최소화

  5. 지속 가능성(Sustainability): 환경적 영향, 특히 에너지 소비와 효율적인 리소스 사용을 고려

  6. 운영 탁월성(Operational Excellence): ML 개발 프로세스의 효율적인 운영, 가시성, 지속적 개선

이 6가지 원칙은 솔루션 아키텍처를 평가하고 확장 가능한 설계를 구현하는 일관된 접근법을 제공합니다.

예를 들어, ML 모델의 학습 및 배포 프로세스를 설계할 때 이 원칙들을 활용할 수 있습니다. 데이터 처리, 모델 개발, 모델 배포 단계에서 이 원칙들을 적용하면 도움이 됩니다.

보안 원칙은 데이터 암호화, 최소 권한 액세스 구성, 계정 및 VPC 구조 설정 등을 안내합니다. 신뢰성 원칙은 장애 허용, 데이터 백업 및 버전 관리, Checkpointing 등을 제공합니다. 성능 효율성 원칙은 데이터 통합, 적절한 EC2 인스턴스 선택, 엣지 컴퓨팅 활용 등을 안내합니다.

비용 최적화 원칙은 데이터 분석 도구 사용, 적절한 컴퓨팅 리소스 선택, Auto Scaling 구성 등을 제공합니다. 지속 가능성 원칙은 데이터 수명 주기 관리, 효율적인 하이퍼파라미터 튜닝, 에너지 효율적인 인스턴스 선택 등을 안내합니다.

마지막으로 운영 탁월성 원칙은 자동화된 ML 워크플로우 구축, 반복 가능한 프로세스 구현, 지속적인 프로세스 개선 등을 제공합니다.

이러한 AWS Well-Architected Framework의 원칙들은 ML 솔루션 설계 및 구현 전반에 걸쳐 유용한 지침이 됩니다.

Infrastructure Types

Model Building and Deployment

  1. 컴퓨팅 리소스 프로비저닝:

  3. 인증 및 권한 부여:

  4. 리소스 디프로비저닝:

    • 추론 요청 및 응답을 위한 스토리지(Amazon S3, Amazon EBS, Amazon EFS)

    • 보안 네트워킹, 모니터링, 로깅 기능 지원

Automatic Resource Provisioning

리소스 프로비저닝 자동화의 주요 이점:

  1. 인적 오류 감소:

    • 의도한 인프라 구성이 항상 적용됩니다.

    • 오류 발생 기회가 줄어들어 문제 해결이 용이해집니다.

  2. 릴리스 시간 단축:

    • 사람이 수동으로 수행하는 것보다 새 환경을 빠르게 배포하거나 리소스를 확장할 수 있습니다.

    • ML 애플리케이션이 변화하는 수요에 신속하게 대응할 수 있습니다.

  3. 규정 준수 유지:

    • 자동으로 프로비저닝된 리소스는 항상 동일한 구성으로 배포됩니다.

    • 정의된 보안 및 규정 준수 요구 사항이 각 배포에 포함됩니다.

이러한 이점을 통해 ML 애플리케이션의 배포와 관리를 효율적이고 안정적으로 수행할 수 있습니다. 인적 오류를 줄이고, 변화에 신속하게 대응하며, 규정 준수를 유지할 수 있습니다.

Infrastructure as Code

인프라스트럭처 코드(IaC)는 코드를 통해 인프라 리소스를 관리하고 프로비저닝하는 현대적인 접근 방식입니다. 수동으로 리소스를 생성하는 대신 기계 판독 가능한 정의 파일을 사용하여 인프라를 정의할 수 있습니다. IaC에는 다음과 같은 주요 구성 요소가 포함됩니다:

  1. 인프라 정의:

    • 인프라 구성 요소, 구성 및 통합을 지정합니다.

    • JSON 또는 YAML과 같은 템플릿 파일로 작성되며, CloudFormation과 같은 프로비저닝 도구로 처리됩니다.

    • AWS CDK와 같은 SDK를 사용하여 Python 또는 TypeScript 등의 프로그래밍 언어로 정의할 수도 있습니다.

  2. Shell 스크립트:

    • EC2 인스턴스와 같은 리소스를 프로비저닝할 때 인프라 작업을 자동화합니다.

    • 소프트웨어 설치, 설정 구성, 필요한 리소스 관리 등을 수행합니다.

  3. 애플리케이션 코드:

    • 인프라의 핵심 목적은 애플리케이션 코드를 호스팅하는 것입니다.

    • IaC 솔루션은 코드 저장소, 빌드, 배포 워크플로와 상호 작용합니다.

IaC에는 두 가지 주요 접근 방식이 있습니다:

  1. 선언형(Declarative):

    • 원하는 시스템의 최종 상태를 설명합니다.

    • IaC 솔루션이 이 시스템을 인프라 코드에서 생성합니다.

    • 필요한 구성 요소와 설정을 알고 있는 경우 편리합니다.

  2. 명령형(Imperative):

    • 리소스를 설정하고 원하는 상태에 도달하는 모든 단계를 설명합니다.

    • 복잡한 인프라 배포에 필요할 수 있습니다.

    • 작업 순서가 중요한 경우 유용합니다.

IaC의 주요 이점은 다음과 같습니다:

  • 코드 관리: 소프트웨어 개발 관행(버전 관리, 협업, 코드 리뷰)을 인프라 관리에 적용할 수 있습니다.

  • 반복 가능한 프로비저닝: 신뢰성 있게 인프라 리소스를 생성, 삭제, 재생성할 수 있습니다.

  • 테스트 및 실험: 모델 테스트와 벤치마킹을 위해 필요에 따라 빠르게 리소스를 프로비저닝하고 제거할 수 있습니다.

IaC tools

AWS CloudFormation:

  • 모델링, 프로비저닝, 관리를 위한 IaC 도구

  • JSON 또는 YAML 템플릿을 사용하여 AWS 및 타사 리소스를 정의하고 프로비저닝

AWS CDK(AWS Cloud Development Kit):

  • 오픈 소스 소프트웨어 개발 프레임워크

  • TypeScript, Python, Java, C# 등 익숙한 프로그래밍 언어로 AWS 리소스 정의 및 프로비저닝

  • CloudFormation 템플릿 효율적으로 생성

Terraform:

  • 다양한 클라우드 제공업체와 서비스를 지원하는 인기 있는 IaC 도구

  • 일관된 워크플로와 언어를 사용하여 여러 플랫폼 간 인프라를 관리

Pulumi:

  • 오픈 소스 IaC 도구

  • TypeScript, JavaScript, Python, Go, .NET, Java, YAML 등 일반적인 프로그래밍 언어 지원

  • 다운로드 가능한 CLI, 런타임, 라이브러리, 호스팅 서비스를 통해 클라우드 인프라 프로비저닝, 업데이트, 관리

이와 같은 IaC 도구들은 각각의 강점과 특징이 있어, 사용 사례와 요구 사항에 따라 선택할 수 있습니다.

AWS CloudFormation

CloudFormation 기본 개념:

  • CloudFormation은 AWS 및 타사 리소스를 모델링, 프로비저닝, 관리하는 IaC(Infrastructure as Code) 도구입니다.

  • CloudFormation 템플릿은 JSON 또는 YAML로 작성된 텍스트 파일로, 프로비저닝할 리소스를 정의합니다.

  • CloudFormation은 이 템플릿을 사용하여 리소스를 프로비저닝하고, 이렇게 생성된 리소스를 CloudFormation 스택으로 관리합니다.

  • 스택 내의 모든 리소스는 성공적으로 프로비저닝되어야 CloudFormation이 스택 구축을 완료합니다.

CloudFormation 템플릿 구조:

  1. Format Version: CloudFormation 템플릿 버전을 명시합니다.

  2. Description: 템플릿에 대한 설명을 제공합니다.

  3. Metadata: 템플릿에 대한 추가 정보를 제공합니다.

  4. Parameters: 스택 생성/업데이트 시 전달받을 값을 정의합니다.

  5. Rules: 템플릿 파라미터에 대한 검증 규칙을 정의합니다.

  6. Mappings: 조건부 파라미터 값을 지정하는 조회 테이블을 정의합니다.

  7. Conditions: 리소스 생성 여부 또는 속성 값을 결정하는 조건을 정의합니다.

  8. Transform: Serverless 애플리케이션을 위한 변환 정보를 지정합니다.

  9. Resources: 프로비저닝할 리소스와 속성을 정의합니다.

  10. Outputs: 스택 생성 후 출력할 값을 정의합니다.

CloudFormation 스택:

  • CloudFormation은 템플릿에 정의된 모든 리소스를 단일 단위로 관리합니다.

  • 리소스 생성에 실패하면 스택 롤백을 수행하여 부분적으로 생성된 리소스를 삭제합니다.

  • 스택을 변경할 때는 변경 사항을 검토한 후 적용합니다.

CloudFormation 아키텍처:

  • 계층형 아키텍처: 하위 계층의 출력을 상위 계층에서 참조할 수 있습니다.

  • 서비스 지향 아키텍처: 스택 간 출력 참조를 통해 리소스를 공유할 수 있습니다.

프로그래밍 방식의 스택 생성:

  • AWS CLI를 사용하여 템플릿 파일과 파라미터 값을 전달하여 스택을 생성할 수 있습니다.

  • 이를 통해 스택 프로비저닝 과정을 자동화할 수 있습니다.

CloudFormation Templates

  • Format Version: CloudFormation 템플릿 버전을 명시합니다.

  • Description: 템플릿에 대한 설명을 제공합니다.

  • Metadata: 템플릿에 대한 추가 정보를 제공합니다.

  • Parameters: 스택 생성/업데이트 시 전달받을 값을 정의합니다.

  • Rules: 템플릿 파라미터에 대한 검증 규칙을 정의합니다.

  • Mappings: 조건부 파라미터 값을 지정하는 조회 테이블을 정의합니다.

  • Conditions: 리소스 생성 여부 또는 속성 값을 결정하는 조건을 정의합니다.

  • Transform: Serverless 애플리케이션을 위한 변환 정보를 지정합니다.

  • Resources: 프로비저닝할 리소스와 속성을 정의합니다.

    • 템플릿의 필수 섹션입니다.

  • Outputs: 스택 생성 후 출력할 값을 정의합니다.

CloudFormation Stacks

CloudFormation 스택에 대한 주요 개념 정리:

  • 스택 단일 관리 단위: CloudFormation은 템플릿에 정의된 모든 리소스를 하나의 단일 단위로 관리합니다.

  • 스택 롤백 및 삭제: 리소스 생성에 실패하면 CloudFormation은 스택을 롤백하여 부분적으로 생성된 리소스를 삭제합니다.

    • 삭제에 실패한 리소스는 전체 스택이 성공적으로 삭제될 때까지 유지됩니다.

  • 스택 업데이트: 실행 중인 스택을 변경하려면 수정된 템플릿이나 새로운 입력 파라미터 값을 제공합니다.

    • CloudFormation은 변경 세트를 생성하여 기존 스택과 변경 사항을 비교합니다.

    • 사용자가 변경 세트를 검토하고 승인하면 CloudFormation이 변경을 적용합니다.

  • 계층형 아키텍처: CloudFormation 스택은 서로 종속된 여러 수평 레이어로 구성됩니다.

    • 각 레이어는 바로 아래 레이어에 의존합니다.

    • 동일 레이어 내에서는 유사한 수명 주기와 소유권을 가진 리소스를 포함합니다.

  • 스택 간 통신: 크로스 스택 참조를 통해 레이어드 또는 서비스 지향 아키텍처를 구현할 수 있습니다.

    • 한 스택의 출력을 다른 스택에서 사용할 수 있습니다.

    • 이를 통해 네트워크 리소스를 공유할 수 있습니다.

  • 프로그래밍 방식 스택 생성: AWS CLI를 사용하여 템플릿 파일과 파라미터 값을 전달하여 스택을 프로그래밍 방식으로 생성할 수 있습니다.

AWS CDK

AWS CDK 개요:

  • AWS의 IaC(Infrastructure as Code) 소프트웨어 개발 프레임워크

  • AWS CloudFormation을 위한 추상화 계층을 제공

  • 익숙한 프로그래밍 언어(Python, TypeScript, JavaScript, Java, C#, Go 등)로 클라우드 인프라 정의 가능

AWS CDK의 주요 구성 요소:

  • AWS CDK Construct Library: AWS 리소스를 나타내는 재사용 가능한 모듈식 구성 요소

  • AWS CDK Toolkit: CDK 프로젝트를 생성, 관리, 배포하는 명령줄 도구

CDK Constructs 수준:

  • L1 Constructs (CFN Resources): **CloudFormation 리소스를 직접 나타내는 저수준 구성** 요소

  • L2 Constructs: L1 구성 요소를 보완하는 추상화된 구성 요소

    • 기본값, 보일러플레이트, 연결 로직 제공

    • 리소스 작업을 위한 편리한 메서드 제공

  • L3 Constructs (Patterns): 특정 사용 사례를 위한 고수준 구성 요소

    • 전체 AWS 아키텍처를 선언적으로 정의

Constructors 재 정리

L1 Constructs (CFN Resources):

  • CloudFormation 리소스를 직접 나타내는 저수준 구성 요소입니다.

  • 모든 리소스 속성을 CloudFormation 템플릿과 동일한 수준으로 명시적으로 구성해야 합니다.

  • 예: SageMaker Endpoint 리소스 생성 시 L1 Construct인 sagemaker.CfnEndpoint를 사용합니다.

L2 Constructs:

  • L1 Construct를 보완하는 추상화된 구성 요소입니다.

  • 기본값, 보일러플레이트, 연결 로직을 내장하여 리소스 사용을 단순화합니다.

  • **리소스 작업을 위한 편리한 메서드**를 제공합니다.

  • 예: S3 Bucket과 DynamoDB Table 생성 시 L2 Construct인 s3.Bucket과 ddb.Table을 사용합니다.

L3 Constructs (Patterns):

  • 특정 사용 사례를 위한 고수준 구성 요소입니다.

  • 여러 개의 관련 리소스를 선언적으로 정의하여 전체 AWS 아키텍처를 나타냅니다.

  • 개발자는 애플리케이션 고유의 속성만 설정하면 됩니다.

  • 예: ECS Fargate 서비스 배포 시 ecs_patterns.ApplicationLoadBalancedFargateService L3 Construct를 사용합니다.

이처럼 L1, L2, L3 Construct는 점점 높은 수준의 추상화를 제공하며, 개발자의 편의성과 생산성을 높입니다. 사용 사례에 따라 적절한 Construct 유형을 선택하면 됩니다.

AWS CDK 프로젝트 구조:

  • App: CDK 프로젝트의 최상위 구성 요소

  • Stack: 특정 그룹의 관련 리소스를 정의

  • Construct: 리소스 및 리소스 그룹을 나타내는 기본 구성 요소

AWS CDK Toolkit 사용:

  • 합성(Synthesize): CloudFormation 템플릿 생성

  • 배포(Deploy): 개발 AWS 계정에 스택 배포

  • 비교(Diff): 코드 변경에 따른 배포 영향 확인

  • 삭제(Destroy): 더 이상 필요하지 않은 스택 삭제

이를 통해 CDK를 사용하면 익숙한 프로그래밍 언어로 클라우드 인프라를 선언적으로 정의하고, 자동화된 방식으로 관리할 수 있습니다.

Deploying resources with AWS CDK Toolkit

CDK 프로젝트 시작하기:

  • 프로젝트 디렉토리 생성:

    • mkdir my-cdk-app

    • cd my-cdk-app

  • CDK 프로젝트 초기화:

    • cdk init app --language typescript

    • 사용하려는 프로그래밍 언어(TypeScript, Python 등)를 지정합니다.

  • 환경 부트스트랩:

    • cdk bootstrap

    • CDK에 필요한 특별한 리소스를 생성하여 배포 환경을 준비합니다.

  • CloudFormation 템플릿 합성:

    • cdk synth

    • CDK 앱의 구성을 CloudFormation 템플릿으로 변환합니다.

    • 기존 스택을 업데이트할 때는 cdk diff로 변경 내용을 비교할 수 있습니다.

  • 리소스 배포:

    • cdk deploy

    • 합성된 CloudFormation 템플릿을 사용하여 리소스를 프로비저닝합니다.

이와 같은 워크플로를 통해 CDK를 사용하여 클라우드 인프라를 코드로 정의하고 관리할 수 있습니다.

Comparing CloudFormation and CDK

AWS의 IaC(Infrastructure as Code) 도구인 CloudFormation과 CDK의 주요 특징을 비교하면 다음과 같습니다:

작성 경험:

  • CloudFormation: JSON/YAML 템플릿 사용, 간단하지만 규모가 커질수록 관리가 어려워질 수 있습니다.

  • CDK: 프로그래밍 언어(Python, TypeScript 등) 사용, 익숙한 코딩 경험과 소프트웨어 개발 관행을 적용할 수 있습니다.

IaC 접근 방식:

  • CloudFormation: 선언형(Declarative) - 원하는 인프라 상태를 정의하면 CloudFormation이 프로비저닝합니다.

  • CDK: 명령형(Imperative) - 프로그래밍 언어로 CloudFormation 템플릿을 생성하며, 조건문 등을 사용할 수 있습니다.

디버깅 및 문제 해결:

  • CloudFormation: CloudFormation 고유의 오류 처리와 메시지 이해가 필요합니다.

  • CDK: 프로그래밍 언어의 디버깅 기능을 활용할 수 있어 문제 해결이 편리합니다.

재사용성 및 모듈성:

  • CloudFormation: 중첩 스택과 크로스 스택 참조로 모듈성을 달성할 수 있지만, 복잡성이 증가할 수 있습니다.

  • CDK: 객체 지향 프로그래밍 원칙을 적용하여 모듈화된 IaC 코드 블록을 만들 수 있습니다.

커뮤니티 지원:

  • CloudFormation: 더 오래된 도구로 광범위한 커뮤니티와 리소스가 있습니다.

  • CDK: 새로운 도구이지만 빠르게 성장하는 활성 커뮤니티가 있습니다.

학습 곡선:

  • CloudFormation: 템플릿 기반 접근법에 익숙해져야 하므로 학습 곡선이 다소 가파를 수 있습니다.

  • CDK: 프로그래밍 언어에 익숙하다면 학습이 수월합니다.

이와 같은 특징을 고려하여 조직의 요구 사항과 개발자의 선호도에 따라 CloudFormation 또는 CDK를 선택할 수 있습니다.

Amazon SageMaker Python SDK

SageMaker Python SDK의 주요 기능을 정리하면 다음과 같습니다:

ML 생애주기 태스크 정의 및 오케스트레이션:

  • SageMaker Pipeline을 사용하여 데이터 처리, 모델 학습, 모델 평가 등의 태스크를 오케스트레이션할 수 있습니다.

  • 모델 선택 시 정확도 지표와 임계값을 비교하여 모델 등록 여부를 결정할 수 있습니다.

SageMaker Pipeline 생성

  • Pipeline() 메서드를 사용하여 재사용 가능한 파이프라인을 생성할 수 있습니다.

  • 파라미터를 정의하여 파이프라인 실행 시 사용자 지정이 가능합니다.

일반적인 태스크 자동화

  • Processor 클래스를 사용하여 데이터 전처리, 모델 학습, 모델 배포 등의 태스크를 수행할 수 있습니다.

  • 전처리 작업의 경우 SKLearnProcessor를 사용하여 scikit-learn 스크립트를 쉽게 실행할 수 있습니다.

  • 이러한 태스크를 ProcessingStep과 같은 파이프라인 단계로 정의할 수 있습니다.

Preparing Data

Amazon SageMaker Processing을 활용한 데이터 전처리 자동화:

Processor 생성:

  • SKLearnProcessor 클래스를 사용하여 scikit-learn 기반의 데이터 전처리 Processor를 생성합니다.

  • 필요한 파라미터로는 scikit-learn 버전, IAM 역할, 인스턴스 유형, 인스턴스 수 등이 있습니다.

Processor 실행:

  • .run() 메서드를 사용하여 Processor를 실행합니다.

  • 전처리 스크립트(preprocessing.py)를 지정하고, Amazon S3에서 데이터를 가져와 전처리합니다.

  • 전처리 결과를 Amazon S3에 다시 저장합니다(train 데이터, test 데이터).

SageMaker Pipeline에 전처리 단계 추가:

  • ProcessingStep을 사용하여 파이프라인에 데이터 전처리 단계를 정의합니다.

  • step_args에 앞서 실행한 Processor의 .run() 메서드 호출 결과를 전달합니다.

  • 이를 통해 파이프라인 실행 시 데이터 전처리 작업이 자동으로 수행됩니다.

이와 같은 방식으로 SageMaker Python SDK를 활용하면 다음과 같은 이점을 얻을 수 있습니다:

  • Amazon S3에서 데이터를 읽어와 전처리하고, 결과를 다시 Amazon S3에 저장할 수 있습니다.

  • scikit-learn과 같은 인기 있는 ML 프레임워크를 쉽게 활용할 수 있습니다.

  • 데이터 전처리 작업을 SageMaker Pipeline의 일부로 자동화할 수 있습니다.

이를 통해 ML 모델 구축 및 배포 워크플로우를 체계적으로 관리하고 효율화할 수 있습니다.

  • 이를 통해 파이프라인 실행 시 모델 학습 작업이 자동으로 수행됩니다.

이와 같은 방식으로 SageMaker Python SDK를 활용하면 다음과 같은 이점을 얻을 수 있습니다:

  • MXNet과 같은 인기 있는 ML 프레임워크를 쉽게 활용할 수 있습니다.

  • 학습 스크립트, 하이퍼파라미터, 인프라 구성 등 학습 작업 전반을 관리할 수 있습니다.

  • 모델 학습 작업을 SageMaker Pipeline의 일부로 자동화할 수 있습니다.

이를 통해 ML 모델 구축 및 배포 워크플로우를 체계적으로 관리하고 효율화할 수 있습니다.

Deploying Models

SageMaker Python SDK를 이용한 모델 배포 자동화:

엔드포인트 구성 정의:

모델 생성:

  • MXNetModel 클래스를 사용하여 사전 학습된 모델 아티팩트를 SageMaker 모델로 생성합니다.

엔드포인트 호출:

  • 배포된 서버리스 프레디터의 .predict() 메서드를 사용하여 엔드포인트를 호출합니다.

  • 추론 데이터를 전달하면 모델이 응답을 반환합니다.

이와 같은 방식으로 SageMaker Python SDK를 활용하면 다음과 같은 이점을 얻을 수 있습니다:

  • 기존 모델 또는 새로 학습된 모델을 쉽게 배포할 수 있습니다.

  • 서버리스 구성을 통해 인프라 관리 부담을 줄일 수 있습니다.

  • 단일 API 호출로 모델 배포와 호출을 수행할 수 있습니다.

이를 통해 ML 모델 배포 과정을 자동화하고 효율화할 수 있습니다.

IaC 기반 자동화

  • 코드로 파이프라인을 정의하면 모델 구축 및 배포 인프라를 체계적으로 관리할 수 있습니다.

  • 이를 통해 반복 가능하고 자동화된 ML 워크플로우를 구축할 수 있습니다.

ML 모델 구축 파이프라인 자동화 과정:

  1. 파이프라인 코드 저장소 액세스:

    • SageMaker Python SDK로 작성한 파이프라인 코드는 코드 저장소에서 관리됩니다.

  2. 파이프라인 인프라 프로비저닝:

    • CI/CD 도구가 파이프라인 코드 변경을 감지하면 자동으로 알림을 받습니다.

    • CI/CD 도구는 코드를 가져와서 실행 파라미터를 전달하며, 파이프라인과 필요한 인프라를 구축합니다.

  3. 모델 학습:

    • 파이프라인은 전달받은 파라미터(학습 데이터, 학습 인스턴스 유형, 모델 승인 기준 등)를 사용하여 학습 단계를 수행합니다.

  4. 모델 등록:

    • 학습된 모델이 승인 기준을 충족하면 모델 레지스트리에 등록됩니다.

    • 이후 배포 파이프라인에서 해당 모델을 사용할 수 있습니다.

  5. 파이프라인 리소스 디프로비저닝:

    • 파이프라인 실행이 완료되면 CI/CD 도구가 더 이상 사용되지 않는 리소스를 정리합니다.

    • 이를 통해 유휴 리소스에 대한 비용 지출을 방지할 수 있습니다.

이와 같은 자동화된 워크플로우를 통해 다음과 같은 이점을 얻을 수 있습니다:

  • 코드 기반 인프라 관리로 일관성 있고 반복 가능한 모델 구축 과정 보장

  • CI/CD 도구와의 통합으로 자동화된 배포 및 리소스 관리

  • 모델 승인 기준 충족 여부에 따른 모델 레지스트리 등록 자동화

  • 불필요한 리소스 사용 방지를 통한 비용 절감

이를 통해 ML 모델 구축 및 배포 워크플로우의 신뢰성, 효율성, 가시성을 향상시킬 수 있습니다.

Building and Maintaining Containers

학습 컨테이너

  • 학습 작업 컨테이너에는 특정 폴더 구조가 요구됩니다.

  • 이 폴더 구조에는 학습 데이터, 모델 아티팩트, Checkpoint, 출력 등이 저장됩니다.

  • SageMaker는 환경 변수를 사용하여 AWS 클라우드 스토리지와 학습 작업 간 경로를 정의합니다.

SageMaker 학습 컨테이너의 폴더 구조 및 사용 용도를 정리하면 다음과 같습니다:

  1. /opt/ml

    • SageMaker 학습 작업에 사용되는 최상위 디렉토리

  2. /opt/ml/code/

    • 컨테이너가 실행할 스크립트(예: 사용자 정의 학습 알고리즘)가 포함된 디렉토리

  3. /opt/ml/input/

    • 학습 작업에 대한 입력 데이터가 포함된 디렉토리

    • /opt/ml/input/config/

      • 하이퍼파라미터 및 분산 학습 리소스 구성을 위한 JSON 파일이 포함

    • /opt/ml/input/data/

      • Amazon S3에서 가져온 학습 데이터 채널이 포함

  4. /opt/ml/checkpoints/

    • Checkpointing 사용 시 로컬에 저장된 Checkpoint가 포함되며, Amazon S3에 동기화됨

  5. /opt/ml/output/

    • 학습 작업의 출력 데이터가 포함된 디렉토리

    • /opt/ml/output/data/

      • 학습 작업에서 생성된 출력 데이터(output.tar.gz)가 포함

  6. /opt/ml/model/

    • 학습 작업에서 생성된 최종 모델 아티팩트(model.tar.gz)가 포함

이와 같은 표준화된 폴더 구조를 따르면 SageMaker가 학습 작업을 효율적으로 처리할 수 있습니다. 사용자는 이 구조를 준수하여 자체 컨테이너를 생성하거나 기존 컨테이너를 확장할 수 있습니다.

추론 컨테이너

  • 추론 컨테이너에는 다음과 같은 요구사항이 있습니다:

    • /opt/ml/model 경로를 포함해야 합니다.

    • 실행 가능한 컨테이너로 구성되어야 합니다.

      • ENTRYPOINT [“python”, “serve.py”]

    • 8080 포트에서 웹 서버를 실행해야 합니다.

    • /invocations와 /ping 엔드포인트를 수락해야 합니다.

    SageMaker 추론 컨테이너의 주요 구성 요소:

    serve.py:

    • 컨테이너 시작 시 실행되는 스크립트

    • nginx 웹 서버와 Gunicorn Python WSGI 인터페이스를 시작하여 추론 서버를 실행합니다.

    predictor.py:

    • 모델 로딩 및 추론 로직을 포함하는 Python 스크립트

    • Flask를 사용하여 /ping과 /invocations 엔드포인트를 제공합니다.

    wsgi.py:

    • Gunicorn 서버를 위한 래퍼 스크립트

    nginx.conf:

    • 웹 서버 구성 스크립트

    • 8080 포트에서 수신하며, /ping과 /invocations 경로의 요청을 Gunicorn 서버로 전달합니다.

    이와 같은 구성 요소들은 추론 컨테이너가 SageMaker 엔드포인트 요구사항을 충족하도록 합니다:

    • 모델 아티팩트를 /opt/ml/model 경로에서 로드할 수 있습니다.

    • 실행 가능한 컨테이너로 구성되어 있습니다.

    • 8080 포트에서 웹 서버를 실행합니다.

    • /invocations와 /ping 엔드포인트를 제공합니다.

    이를 통해 SageMaker는 추론 요청을 처리하고 응답할 수 있습니다. 이러한 표준화된 구조와 요구사항은 추론 컨테이너의 일관성과 상호운용성을 보장합니다.

컨테이너 관리

  • 컨테이너 기반 ML 애플리케이션에는 다음과 같은 관리 도구가 필요합니다:

    • 레지스트리: 컨테이너 이미지를 저장하고 배포하는 레지스트리(예: Amazon ECR)

    • 오케스트레이션: 컨테이너 배포와 관리를 자동화하는 오케스트레이션 도구(예: Kubernetes, ECS)

    • 호스팅: 컨테이너를 실행하는 호스팅 환경(예: Fargate, EC2)

이와 같은 컨테이너 관리 체계를 통해 다음과 같은 이점을 얻을 수 있습니다:

  • 애플리케이션 종속성 및 실행 환경을 표준화할 수 있습니다.

  • 지속적인 통합 및 배포(CI/CD) 파이프라인을 구축할 수 있습니다.

  • 확장성 있는 컨테이너 기반 아키텍처를 구현할 수 있습니다.

  • 다양한 AWS 서비스와 통합하여 전체 ML 워크플로우를 자동화할 수 있습니다.

컨테이너 애플리케이션 개발 및 관리 시 고려사항

컨테이너 이미지 생성:

  • 애플리케이션 코드, 런타임, 시스템 도구, 라이브러리, 설정 등을 포함하는 컨테이너 이미지를 생성합니다.

  • 이미지를 컨테이너 레지스트리(예: Amazon ECR)에 푸시하여 버전 관리합니다.

컨테이너 오케스트레이션:

  • 컨테이너의 확장, 네트워킹, 유지 관리 등을 관리하는 오케스트레이션 도구가 필요합니다.

  • AWS에서 제공하는 오케스트레이션 도구:

    • SageMaker: 모델 학습 및 배포 시 컨테이너 오케스트레이션 지원

    • Amazon ECS: 컨테이너 배포를 위한 관리형 서비스

    • Amazon EKS: Kubernetes 기반 관리형 컨테이너 오케스트레이션

컨테이너 호스팅:

  • 컨테이너를 실행할 컴퓨팅 리소스를 선택해야 합니다.

  • AWS에서 제공하는 컨테이너 호스팅 옵션:

    • AWS Fargate: 서버리스 컴퓨팅 리소스를 자동으로 할당

    • Amazon EC2: 다양한 인스턴스 유형을 사용하여 직접 관리

이와 같은 컨테이너 관리 체계를 통해 다음과 같은 이점을 얻을 수 있습니다:

  • 애플리케이션 종속성 및 실행 환경의 표준화

  • 컨테이너 배포, 확장, 유지 관리의 자동화

  • 다양한 AWS 서비스와의 통합을 통한 전체 워크플로우 관리

이를 통해 컨테이너 기반 ML 애플리케이션의 배포, 관리, 운영을 효율적으로 수행할 수 있습니다.

Auto Scaling Inference Infrastructure

SageMaker 모델 Auto Scaling 전략에 대해 정리해 보겠습니다:

Auto Scaling의 중요성

  • 추론 트래픽에 대한 적절한 compute 리소스 확보가 필요

  • 부족하면 지연 문제, 과다하면 비용 효율적이지 않음

리소스 포화 지표 파악:

  • 부하 테스트를 통해 모델 variant의 수용 한계 지점 확인

  • CPU 또는 메모리 리소스 포화 여부를 모니터링

SageMaker 모델 Auto Scaling 방식

Target Tracking Scaling Policy:

  • 목표 지표와 목표값을 지정하여 자동으로 용량을 조정

  • 예: CPU 활용률 50% 유지

Step Scaling Policy

  • 지표 임계값을 기반으로 단계적으로 확장/축소

  • 예: 인스턴스당 호출 수 50, 80 등

Scheduled Scaling Policy

  • 시간별, 요일별 등 예측 가능한 수요 패턴에 맞춰 용량 조정

  • 예: 수요 증가 예상 일정에 맞춰 확장

On-demand Scaling

  • 수동으로 인스턴스 수를 증감

  • 예: 신제품 출시, 트래픽 급증, 프로모션 등 예측이 어려운 경우

이와 같은 Auto Scaling 전략을 통해 다음과 같은 효과를 얻을 수 있습니다:

  • 요구 사항에 맞는 적절한 리소스 프로비저닝

  • 가용성 높은 추론 서비스 구축

  • 비용 효율적인 리소스 사용

SageMaker는 이러한 다양한 Auto Scaling 방식을 제공하여 ML 애플리케이션의 확장성 있는 배포를 지원합니다.

정답은 “A target tracking scaling policy adjusts the number of instances to maintain a specific metric value. A step scaling policy adjusts the number of instances based on the size of the alarm breach.”이며, 그 이유는 다음과 같습니다:

차이점:

  • Target Tracking Scaling Policy:

    • 지정된 지표 값을 유지하기 위해 인스턴스 수를 자동으로 조정합니다.

  • Step Scaling Policy:

    • 알람 위반의 크기에 따라 인스턴스 수를 조정합니다.

즉, Target Tracking 정책은 목표 지표값을 중심으로 능동적으로 리소스를 조정하지만, Step 정책은 임계값에 따라 단계적으로 리소스를 확장하는 방식입니다.

다른 대답들은 적절하지 않습니다:

  • “A target tracking scaling policy manages both scale out and scale in actions. A step scaling policy can only be used to scale out resources to meet increased demand.”은 잘못된 정보입니다. Step 정책도 수요 감소 시 축소(scale in)할 수 있습니다.

  • “A target tracking scaling policy is more complex to configure, whereas a step scaling policy is more straightforward.”은 구성의 복잡성 측면에서 차이가 있다고 볼 수 없습니다.

  • “A target tracking scaling policy uses a predefined metric, whereas a step scaling policy uses a custom metric.”은 잘못된 정보입니다. 두 정책 모두 사용자 정의 지표를 사용할 수 있습니다.

따라서 정답은 첫 번째 답변이며, 그 이유는 두 정책이 리소스 조정 방식에 차이가 있기 때문입니다.
