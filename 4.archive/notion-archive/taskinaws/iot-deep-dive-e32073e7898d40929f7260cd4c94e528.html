Application

  • CoAP (Constrained Application Protocol)

    • 제한된 노드와 제한된 네트워크를 위한 경량 메시징 프로토콜 → 저전력이며 손실이 많은 네트워크 대상

    • 클라이언트 ↔ 서버 프로토콜

      • 1:1 연결이 기본 이지만 1:N 및 멀티 캐스트도 지원

    • 비동기식 통신

      • Observe 방식 : Pub/Sub와 유사 하며 노드가 다른 노드를 관찰한다는 컨셉

      • 브로커가 없다는 점에서 MQTT와 차이가 있으며 네트워크 노드 중 하나는 Observer를 위한 메시지를 보유하고 있다는 점은 유사

    • Transport Layer (전송 계층)으로 UDP 사용

      • 비 연결 데이터그램 (IP 계층 패킷) 이기 때문에 낮은 오버헤드, 작은 패킷, 빠른 웨이크업과 전송 사이클의 특성을 가져 저전력 디바이스에 적합

      • 낮은 신뢰성은 반복적 메시징으로 보완

    • Security

      • DTLS 이용

  • MQTT on AWS

    • Version 3.1.1

    • QoS level

      • Level 0 : Sent zero or more (at most once) → 안정적인 통신 연결에서 사용되어야 함

      • Level 1 : Sent at least once and then repeatedly until a PUBACK response is received → PUBACK을 수신하여야 전송이 완료된 것으로 판단

    • Persistent session

      • Store a client’s subscriptions and message → 클라이언트가 승인하지 않은 QoS 1인 클라이언트의 구독 및 메시지가 저장

      • 연결이 끊어진 장치가 영구 세션에 다시 연결되면 세션이 재개되고 구독이 복원

      • 다시 연결하기 전에 수신되고 클라이언트에서 확인되지 않은 구독된 메시지가 클라이언트로 전송

      • Session expiration time : 1h (soft)

      • Connection inactivity (keep-alive interval) : 30 ~ 1200sec (using VPC endpoint, 230sec) → Hard Limit

Managing CA and the Chain of Trust

Using ATS

  • Generate Device Certificate and Private Key using AWS IoT

  • Use device generated or owned Private Key

    • CSR (Certificate Signing Request)을 AWS에 요청하여 사용

  • 대기업의 경우 자체 self-signed Root CA를 대체적으로 가지고 있음

Using Customer CA

  • 자체 RootCA를 가지고 Intermediate CA를 만들고 이 ICA를 사용하여 디바이스 인증서를 생성한다

  • ICA를 생성하는 과정에서 Signer CA를 AWS IoT에 등록하여 CA의 무결성을 확보해야 한다.

Using Customer CA managed by ACM (AWS Certificate Manager)

  • Customer CA는 사용하고 싶지만 PKI, CA를 관리하고 싶지 않다면 ACM 서비스를 이용

  • ACM에서 발급되는 X.509 인증서를 사용하고 이것을 생산 업체 혹은 Secure Element Vendor를 통해 제품에 투입

Install Certificate before delivered

  • JITP (Just-in-time Provisioning)

  • JITR (Just-in-time Registration)

  • MAR (Multi-Account Registration)

  • Device Certificate이 AWS IoT에 등록되어 있어 디바이스가 처음 연결될 때 AWS IoT가 인식할 수 있게 한다

  1. Provision devices with unique credentials in firmware

    1. X.509 인증서와 Private Key를 코드에 포함시켜 각 디바이스마다 다른 firmware를 생성하고 생산 단계에서 programming

    2. 디바이스 제조사가 AWS IoT에 디바이스 인증서를 사전 등록하고 이것을 각 디바이스에 직접 programming

Just in Time Provisioning (JITP)

  • 디바이스가 인증서와 개인키를 가지고 있는 경우에 사용 된다

  • 디바이스 인증서는 AWS IoT에 등록되어 있는 CA에서 사인되어 있어야 한다

  • 인증 과정

    • 디바이스가 AWS IoT에 연결하고

    • 인증서 Signature가 확인 되어야 한다

    • Provisioning template을 사용하여 Thing, 인증서, Policy를 등록 한다

    • 디바이스 제조사는 사전에 **signer CA**와 **provisioning template**을 CA에 attach 해야 한다

Just in Time Registration (JITR)

  • JITP와의 차이는 추가적인 커스텀 로직이 필요하는 것임

  • 인증 과정

    • 디바이스가 AWS IoT에 연결하고

    • 인증서 Signature가 확인되면 **인증서를 inactive 상태로 등록** 한다

    • AW IoT는 MOTT topic으로 Lifecycle 이벤트를 생성 한다 : $aws/events/certificates/registered/

    • 디바이스 제조사는 위 topic이 publish 될 때 마다 Lambda 함수가 trigger 되도록 IoT Rule을 구성해 두어야 한다

    • Lambda 함수에서는 이차 검증 작업을 수행한다

      • Allow List, 인증서 해지 목록 (Certificate Revocation List) 적용

      • 특정 사용자에 등록 하거나 추가적인 온보딩 단계를 호출 한다

      • Lambda 함수도 IoT Thing에 등록하고 Policy를 설정해야 한다

    • Lambda 함수 **실행이 완료되면 Certificate 상태를 active**로 변경

  • 디바이스의 첫번째 연결은 실패하지만 두번째 연결은 성공하는 로직을 가짐

Multi-Account Registration (MAR)

  • 디바이스가 인증서와 개인키를 가지고 있어야 한다

  • 인증서는 CA sign되어 있지만 CA가 반드시 AWS IoT에 등록되어 있을 필요는 없다

  • 디바이스 제조사는 벤더 고유 CA로 sign된 인증서를 AWS 콘솔, API, CLI 를 사용하여 등록해야 한다. 이 때 인증서는 어떤 리전이나 어떤 계정에도 등록될 수 있다

  • 인증 과정

    • 디바이스의 TLS stack은 SNI (Server Name Indicator) extension을 지원해야 한다

    • AWS IoT Core의 endpoint는 SNI string으로 전달된다

  • Use Case

    • 디바이스 provisioning을 유연하게 하고 싶을 때 사용 된다

    • AWS 계정을 sandbox, testing, production 등으로 다양하게 구성할 때 사용할 수 있다 → 이 경우 인증서는 각 계정별로 등록이 되고 디바이스는 lifecycle에 따라 다른계정으로 연결 될 수 있다

  • 디바이스를 글로벌하게 판매할 경우 인증서를 여러 AWS 리전에 등록하여 사용할 수 있다

  • 디바이스 제조사가 자체 signing CA를 가지고 있지 않고 CA를 AWS IoT에 등록할 수 없을 때

  • Mode of CA certificate registration

    • DEFAULT: register a CA certificate with a verification certificate

    • SNI_ONLY: register a CA certificate without a verification certificate

  • Registration Case

    • Only one account can register a CA in DEFAULT mode in one region.

    • Multiple accounts can register the same CA in SNI_ONLY mode in the same region. There is no limit on the number of accounts in the region where such CA is registered.

    • Multiple accounts can register the same CA in either DEFAULT or SNI_ONLY modes if these accounts are in different regions — this was possible before.

    • A CA can be in different modes across accounts. For example, one account can register it in DEFAULT mode and another account in SNI_ONLY mode.

    • In a given account, a CA can exist in only one mode. To change the mode of the registered CA, you need to delete the CA and register it again.

Fleet Provisioning

What is

  • 대량의 디바이스를 AWS IoT Core에 손쉽고 안전하게 온보딩할 수 있도록 제공되는 기능

  • 디바이스가 IoT Core에 최초 연결 시 다음의 작업을 자동으로 수행 하거나

    • 각 장치에 고유 한 디지털 ID를 안전하게 전달 합니다

    • Lambda 함수를 통해 디바이스 페이로드를 검증합니다

    • 고객의 AWS 계정에 ID를 등록합니다

    • 모든 필수 권한 및 레지스트리 메타 데이터가 있는 장치를 설정합니다

  • 새로운 자격 증명을 부여 받거나 설정을 변경

Background

  • 생산 시점에 고유한 Credential을 디바이스에 provisioning 하기 어려운 경우 사용할 수 있다 → 기술적 한계, 생산 비용, 애플리케이션 사양의 제약 등 다양한 이유가 있을 수 있다

  • 이 경우 디바이스는 고유한 Identity를 가지지 못하고 판매가 된다

  • 디바이스 고유 Credential을 Provisioning하는 방식은 2가지가 있다

    • by Trusted User

    • by Claim

Fleet Provisioning by Trusted User

  • 오직 Trusted User가 디바이스에 고유한 credential을 provision 할 수 있다

  • Mobile 애플리케이션에서 임시 인증서와 개인키를 생성하게 한다 → API 사용

  • 사전에 Trusted User API를 사용하는 Mobile 애플리케이션과 Fleet Provisioning Template이 필요하다

  • 추가 인증 과정이 필요하면 AWS Lambda 함수를 추가하여 사용할 수 있다

  • 인증 과정

    • Installer는 모바일 애플리케이션을 사용하여 AWS 인증을 진행 한다

    • Trusted User API를 사용하여 installer는 임시 X.509 인증서와 개인키를 받는다 → 유효 시간은 5분

    • 모바일 애플리케이션이 이 credential을 디바이스에 전달 한다 : BLE, WiFi, USB 등으로 연결

    • 디바이스는 AWS IoT에 연결하고

    • 전달 받은 임시 credential을 AWS CA signing된 인증서와 개인키로 교환한다

    • 이 과정에서 AWS 리소스 (Thing name, Policy, Certificate)가 설정 된다

  • Use Case

    • 높은 수준의 보안이 필요할 경우

    • 생산 체인을 신뢰할 수 없을 경우

    • 생산 체인에서 디바이스 Provisioning이 가능하지 않을 경우

Fleet Provisioning by Claim

  • 디바이스가 안전하게 credential을 받을 전송 채널을 만들 수 없거나

  • 생산 체인에서 디바이스를 customizing 할 수 없는 경우

  • 디바이스가 deploy 될 때 고유한 identity를 받을 수 있도록 한다

  • 사전에 Fleet Provisioning template과 AWS Lambda 함수를 등록해야 한다

  • Claim certificate에 대한 관리가 필요하다

  • 인증 과정

    • 디바이스 제조사는 FW에 공유되는 claim certificate을 포함시킨다 → claim certificate은 디바이스 batch 단위로 고유해야 한다

    • 디바이스가 AWS IoT에 최초 연결하면

    • claim certificate을 고유한 AWS CA signing된 X.509 인증서와 개인키로 교환한다

    • 이 때 디바이스는 고유한 token (Serial No, HW secret 등)을 AWS IoT로 전달해야 한다

    • Fleet Provisioning 서비스에서는 디바이스 고유 token 정보를 Allow List와 대조 확인한다

Transport Security

  • Encrypts the connection between the device and the broker

MQTT

  • TLS client authentication

  • AWS IoT는 TLS 프로토콜의 클라이언트 인증 모드를 사용하여 클라이언트 인증서를 인증

  • Vesion 3.1.1 support

HTTP

  • Authentication is delegated to AWS Signature V4

SNI extension

  • Require device to send the Server Name Indication extension to the TLS protocol

  • Provide the complete endpoint address in the host_name field

IoT Core Component

IoT Device Gateway

  • AWS에 연결하는 IoT 디바이스를 위한 진입점의 역할

  • 모든 활성 디바이스 연결을 관리하고 여러 프로토콜의 시맨틱을 구현하여 디바이스가 AWS IoT Core와 안전하고 효율적으로 통신할 수 있도록 지원

  • 지원 프로토콜 : MQTT, WebSockets, HTTP 1.1

IoT Registry

  • 디바이스에 대한 자격 증명을 설정하고 디바이스의 속성 및 기능 같은 메타데이터를 추적하는 기능을 가짐

  • 사물에 대한 정보는 레지스트리에 JSON 데이터로 저장

  • 일반적인 디바이스 사용 사례에서는 사물 이름을 기본 MQTT 클라이언트 ID로 사용

  • 사물의 레지스트리 이름과 사물의 MQTT 클라이언트 ID, 인증서 또는 섀도우 상태 사용 사이의 매핑을 강제 적용하고 있지는 않지만 사물 이름을 하나 선택하여 레지스트리 및 디바이스 섀도우 서비스 모두에서 MQTT 클라이언트 ID로 사용할 것을 권장

  • 디바이스에 관한 메타데이터를 저장 → 최소 7일에 한 번 이상 레지스트리 항목을 액세스 또는 업데이트하기만 하면 레지스트리에 저장된 메타데이터가 계속 유지
