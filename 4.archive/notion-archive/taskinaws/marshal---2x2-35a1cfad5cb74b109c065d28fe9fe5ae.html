<case> 

[HYBE IM New Launch Game Puzzle SVT OpenSearch Optimization ] 

- 배경
    - HYBE IM은 아티스트 '세븐틴' IP를 활용한 mobile puzzle 게임인 '퍼즐 세븐틴'을 4월에 신규 launching 하였는데 초기에 이용자가 몰리면서 
    OpenSearch로 구축한 application log 검색에서 20초 이상의 slow query 및 query timeout이 지속적으로 발생
- 액션
    - Analytics Specialist SA와 함께 고객사의 OpenSearch cluster 및 shard 구성 등에 대한 전반적인 구성을 검토하고 아래와 같이 가이드
Shard 수 구성
Shard 수는 data node의 배수이면서 AZ의 배수로 설정하는 것이Best Practice 입니다. (가용성 및 데이터와 부하의 고른 분산 목적, 참조 링크)
: 현재의 4개 data node와 5개 primary shard구성 에서는 특정 (5번째의 primary / replica shard가 위치한) data node들이 부하를 더 받게 될 수 있습니다.
Shard 크기는 현재와 같은 rolling index의 경우 상황에 따라 shard 당 10GB~50GB 정도를 일반적인 적정 크기로 권장하고 있습니다.
 
검토 하실 내용) Shard 크기와 data node 수를 고려하여Shard 수를 산정
: 예를 들어, 현재처럼 daily로 rolling 하고 하루 데이터 량을 100GB 로 가정할 경우 다음과 같이 Shard 수를 산정해 볼 수 있습니다.
Data node 수(4)의 배수이면서 AZ 수(2)의 배수 → 4의 배수
100GB / 4 = 25GB / shard 혹은 100GB / 8 = 12.5GB / shard 와 같습니다. Shard 크기를 고려하면 4개 Shard 사용이 적절할 것으로 보입니다.
실제 production 환경에서 최적화가 필요하겠 으나 4개shard 로 검토해 볼 수 있을 것 같습니다.
 
Query 시 index pattern 사용 관련
전달받은 query 관련 코드에 따르면 현재 특정 index가 아닌 다수 index 대상으로 검색을 수행하는 상황으로 추정 됩니다.
Opensearch에서는 검색 대상으로 wildcard index pattern을 받게 되면 해당 index에 데이터가 있는지 여부와 무관하게 대상 index 모두에 대해 검색 작업을 수행 합니다.
정확히는 각 index의 모든 shard에게 query를 전달 합니다.
따라서 하루 5개 shard (및 이에 대한 replica shard) 가 존재하게 되고, 이런 index가 10일 치 생성된 상태라면 5 * 10 = 50개 shard로 검색 query가 전달됨
: 필요 없는 shard로의 쿼리 전송 / 각 data node 에서의 처리를 위한 thread pool 내 thread 사용 / 무의미한 결과병합 작업 등으로 vcpu나 network, I/O 자원 낭비 등 발생하고 상황에 따라 search reject 발생도 가능
 
검토 하실 내용) 실제 데이터가 존재할 가능성 있는 index만을 대상으로 search query를 수행
각 index 보존 기간에 따라 대상 shard 수는 줄어들 수 있으나 모범 사례는 실제 데이터가 존재할 가능성 있는 index만을 대상으로 search query를 수행하는 것 입니다.
빈번하게 사용되는 기간에 대한 alias를 정의하고 (예: my-index-1week) 
매일 신규 index 생성 시 마다 해당index를 해당 alias에 추가하고, 기간이 지난 index는 alias에서 제외시키는 방식으로 자주 사용되는 검색을 지원 합니다.
더 오랜 기간에 대해서는 UI 등으로 검색 대상 기간 설정하도록 하고 해당 기간 데이터를 보유한 index만 명시적으로 검색 대상으로 전달하게 하는 것이 query 성능 개선을 위한 방법 입니다.
 
Query 관련
현재 공유해 주신 query / profile이 실제로 발생하는 “느린" query 인지에 대해서는 명확하지 않지만 이 query 를 기준으로 보면 다음과 같습니다.
index mapping 을 보면 검색의 대상이 되는 log_type에 대해 아래와 같이 정의되어 있습니다.
"log_type": {
          "type": "text",
          "fields": {
            "keyword": {
              "type": "keyword",
              "ignore_above": 256 } } }
하지만 query는 아래와 같이 subfield를 사용하지 않고 있습니다.
GET user-behavior-log-2025-04-03/_search
{
  “query”: {
    “match”: {
      “log_type”: “META_ITEM”
    } },
  “profile”: true }
이 query에 대해서는 내부적으로 아래와 같이 동작 됩니다.
log_type을 multifield로 선언했으나 검색에서 subfield를 사용하지 않았기 때문에 text type에 대한 검색 수행됨
해당 index에서 별도 analyzer / tokenizer 선언하지 않았으므로 Standard Analyzer 사용해 query 하려는 입력값(“META_ITEM”) analyze → 아마도 (“meta”, “item”) 으로 tokenize
두 개의 term (“meta” 와 “item”) 을 각각 검색 → 불필요한 분석 수행 및 더 많은 검색 & 더 많은 자원 사용
또한 정확도 측정을 위해 scoring 작업 수행 및, 상위 scoring 을 골라내기 위해 매 건 마다 상위에 속하는지 비교 작업도 함께 수행
 
검토 하실 내용) query문 변경
아래와 같은 형태로 query json이 구성될 수 있도록 하는 것이 성능 개선을 기대할 수 있습니다. 이 부분은 실제 Application에서 발생하는 query 문에 대해 확인이 필요합니다.
GET user-behavior-log-2025-04-03/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "log_type.keyword": "META_ITEM" } }
      ]
    }
  }
}
filter 문 적용은 다음의 효과를 가집니다.
score 계산을 수행하지 않고 정확히 원하는 값과 일치하는지 여부만 확인 (true / false)
또한 결과를 caching 하기 때문에 빈번한 검색에서 성능 확보에 도움
- 결과
	  - 가이드대로 shard 수 조절하여 re-indexing 하였고 이후 timeout 및 slow query가 발생하고 있지 않음

Supertone

AI 오디오 기업인 슈퍼톤은 딥러닝 기반의 음성 추출, 복제, 변환 및 가창 합성 기술을 보유한 기업으로 23년 1월에 하이브로 인수 되었습니다.

슈퍼톤은 온프렘 환경에서 딥러닝 음성 모델 연구와 학습을 진행하였고 학습된 모델 서빙 플랫폼을 Kubernetes를 사용하여 개발하고 GCP의 GKE 클러스터를 통해 배포 하고 있었습니다.

슈퍼톤은 음성 모델에 대한 추론 서비스를 글로벌 하게 제공 하고자 하며 end-to-end 서빙이 아닌 user interactive한 실시간 추론 서비스 제공을 계획하고 있습니다.

슈퍼톤이 모델 서빙을 위해 고민했던 부분은 비용과 성능을 동시에 만족 시킬 수 있는 인프라 구축이었으며 AWS로 이전 하는 것을 목표로 PoC를 진행하기로 하였습니다.

모델 학습은 아직은 온프렘에서 NVIDIA A100 GPU 서버를 통해 이루어 지고 있으며 CNN, RNN, Transformer 등을 사용하여 대략 300M 개의 패러미터를 사용하여 학습을 진행하고 있습니다.

GKE 클러스터로 제공되는 모델 서빙을 Amazon EKS로 migration 하고 Auto Scaling 및 분산 추론이 가능한 serverless framework을 구축할 예정이며 추론 인스턴스는 Inferentia2 적용을 검토할 예정 입니다.

슈퍼톤 음성 학습 모델은 여러 개의 작은 모델로 구성되어 있는데 모델 서빙 제공시 user 요구 사항에 따라 학습 모델에 대한 fine tuning이 필요하게 되고 이 부분도 AWS Tranium 인스턴스를 통해 구축하는 것도 함께 검토될 예정 입니다.

PoC 과정을 통해 AWS 환경에서의 분산 추론 플랫폼 및 production 서비스 구축을 진행할 예정이며 이후 MLOps로 확대 및 온프렘의 학습 모델의 확장과 병렬 학습등에 대해 AWS 환경으로 이전을 견인하고자 합니다.
