Session - DataLab Program

2023/3/2 - 사전 준비(Pre-lab) 1차 미팅

Attendee

  • YG : 이태영 리더, 이상철 과장(인프라 구축), 김진혁(데이터 분석), 김유빈(데이터 엔지니어)

  • AWS : 황선화 DataLab SA, 정윤지 AM, 이종우 SA

대상 선정 및 일정

  • UseCase 1 (Artist 데이터 수집 및 보고서 작성) 우선 진행

  • UseCase 2 (Weverse 데이터 추가 분석)는 차후 진행

  • 일정

    • 3/22~23로 Full Day 진행

    • AWS Training Room

    • 사전 QuickSight IMD 진행 (Half Day)

Use Case Meeting

Scope

  • 구축과 운영의 범위에 대한 구분

Biz Challenge

  • 월간/주간/분기 보고서 작성에 2인 2주 이상 공수 사용되는데 이 공수를 최소한으로 줄이고자 함

  • 빠른 의사 결정을 위해 최신 분석 결과를 확인할 수 있는 시각화 대시보드 필요

Use Case

  • Powerpoint → Apple Keynote 사용

  • 월간 보고서

    • 아래 양식은 월간 리포트의 사용 내용 (대중, 라이트, 코어)

  • 주간 보고서

    • 월간 보고서 보다는 좀더 간소화 된 데이터를 사용 (Raw 데이터를 그대로 배치하여 사용)

    • 기존 다른 부서의 정형화된 프로세스로 진행 되고 있음

  • 분기 보고서 : MariaDB외에 DB화 되지 않은 많은 데이터(excel 등)를 수동으로 취합 정리, 함축적이고 활용도가 높음 → 차후 진행

  • Build Lab Coverage

    • 월간 보고서 cover, 주간 보고서는 추가 결정

  • MariaDB 접근

    • 온프렘에 VPN으로 접근 가능

    • AWS 연결 여부는 불명확

  • Batch 작업

    • Python으로 구성

    • Java API를 제공

    • Batch 과정에서 S3에 접근하도록 수정 가능 여부 : 기술적 이슈 보다는 정책적인 결정이 필요

    • DB는 하나의 테이블로 관리

    • 다른 데이터 소스 사용 여부

  • GPU 서버에 CSV 파일을 업로드 하여 처리 : 파일 경로 추가 하여 처리

  • Python program

    • 리포트에 따라 원본 데이터를 다르게 표현하는 경우가 발생

    • DB의 crawling 된 데이터를 리포트 형태로 재 구성 : historic data 포함

    • 주간, 월간용 따로 생성

    • Output 구조 : CSV or JSON

  • 리포트 page 별로 필요한 field 값 들을 계산

  • 이전에 작업된 엑셀 파일을 활용 → Keynote에 들어갈 데이터를 추가 작업

  • 메시징 자동화 여부

    • QuickSight에서 제공되는 기능을 최대한 활용하고 추가적인 코멘트를 기재한다면 활용도가 있을 듯 함

    • Insight 기능 (한글 미 지원) 있으나 Custom 메시징 활용 가능

  • 모니터링 대상 결정

    • 케이스 별로 선정

    • DB에서는 목록이 있음

    • 아티스트 별로 query 하여 정제 : DB 데이터에 대한 Python program 과정에서 처리 (다운로드 과정 인지 확인 필요)

  • 자동화 되어 있는 부분은 없음

검토 필요 항목

  • Maria DB 서버가 AWS에 연결 가능 한지 : QuickSight에서 직접 접근 가능

  • Maria DB 처리 배치에서 AWS 서비스로 데이터 저장 : S3 or RDS 등

  • Table 구조 : query 수행 혹은 전체 데이터 단일 table에 저장

  • Program Script와 Output format sample 제공

  • 리포트 양식을 그대로 적용하기 보다는 데이터를 통해 인사이트를 확보할 수 있는 것 들을 활용하고 싶음

    • 급상승 파악 : BTS나 다른 Artist의 패턴은 다름

  • 대시 보드에서 표현 하고자 하는 항목 정리

  • 아티스트 별 데이터 선별 작업은 어디서 수행 되는지?

  • 수동 메시지 생성 부분은 입체적인 분석으로 대치하면 좋을 것으로 보임 → 필요한 항목은?

  • 시각화 대시보드에 반영하고자 하는 Idea

    • 필터 적용 (원하는 기간, 원한는 아티스트만 필터링 하여 확인)

    • 추가 시각화 하고자 하는 분석

Attendee

  • AWS : 황선화 DataLab SA, 정윤지 AM, 이종우 SA

DataLab 소개

Overall

  • 공동 engineering : 몇 개월 소요 될 수 있는 작업을 수 일내로 prototyping 할 수 있도록 지원

Build Lab

  • Architecture 구축 혹은 재 설계 → Prototype 구축

  • 3~6 주

Design Lab

  • Architecture 구축 혹은 재 설계

  • 1~3 주

Process

  • Qualification

    • Use Case Review (UCR)

  • Pre-Lab : 2 ~ 4 주

    • Architecture Concept

    • MVP & Stretch

    • Customer 준비

    • AWS 개발 환경 및 데이터 준비

  • Lab

    • Use Case & 목표 검증

    • Identify work threads

    • solution 생성 : build, demo, roadmap 완성

  • Post-Lab

    • Post-Lab 보고서 및 DLA 후속 조치

Discussion

Customer Concept

  • 최초 시각화 검토

    • 아티스트별 3개 segment에 대한 score 생성

    • SNS, Youtube, Spotify 등에서 조회한 값을 수식을 통해 score 생성 : 월 단위로 수행

  • Weverse platform의 activity log 데이터 분석 포함

    • 9개 table로 구성된 parquet 형태의 db log : write_comment, like_comment,

    • 각 table의 user_key를 이용하여 데이터 join

    • View, Like, Comment, 구매와의 관계들에 대한 관계를 파악하고 싶음

      • Weverse로 부터 파로 로 다운롣로 : FTP로 local에 저장 → GPU 서버로 전달

      • GPU 서버에서 학습 하고 있는데 메모리에 모두 loading 하는 것 때문에 이슈 → 분산 처리가 필요

CheckList Review

  • Web Crawling 수집은

    • 일 단위 batch로 수행

      • 대행 서비스를 통해 수집 → 정제된 형태의 데이터 → 내부 Maria DB에 저장

      • 원 플랫폼의 제공 API를 통해 조회 : Twitter

  • Excel to Python

    • Crawling 작업의 마지막 단계

    • DB를 API를 사용하여 file로 export

    • 내부 DB 서버는 Cloud와의 연결에는 이슈는 없을 것으로

Report

  • 현 시점 : 주별, 월별, 분기별

  • 향후 시스템 구축될 경우 일별도 가능

  • Consumer : 경영진 및 관련 실무자

Data Source

  • 내부 생성 데이터

    • 정형 : 매출/실적 데이터, ERP, YGP 실적 데어, 스마트/MPS 데이터, 글로벌 데이터(QQ) → Data Warehouse

    • 비정형 : 음원, 영상, 앨범 자켓, 포스터, 프로필 사진, 디자인 → Data Lake

  • 외부 생성 데이터

    • Crawling → MariaDB → CSV

    • Weverse : 구매 패턴 분석 중, 포스팅 수와 구매 액수 상관 관계 등의 분석

참여 인력

  • 리더

  • 데이터 분석, Python

  • 데이터 엔지니어링, Pipeline 구축

  • AWS 인프라 운영, 구축

기대 효과

  • 리포트 생성 효율화

    • Full로 2주 정도 소요 → 인력 효율적 활용

  • 구독자 대응

    • 구독자들이 정규적으로 볼 수 있는 환경 : 작성이 일정 대비 지연이 발생

    • 구독자들이 필요한 데이터 들만 조회 가능하게 하고 싶음

    • 의사 결정자들이 객관적인 근거 데이터로 사용 : 구독자들이 능동적으로 원하는 데이터를 가져갈 수 있도록
