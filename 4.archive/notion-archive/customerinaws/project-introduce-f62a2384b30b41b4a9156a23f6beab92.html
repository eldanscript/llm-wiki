Project Introduce

PL : 송요성 (Hotel 서비스 Link Cloud 과제)

개발자 : 엄태순, 이승연

M/M : 46

기간 : 21.5 ~ 21.12

기존 과제 개요

  • 광고용 Display(Signage)용 Contents 배포 및 Signage 장치 제어 솔루션

  • 서비스 방식

    • 고객이 본사에서 Contents 제작 후 MagicINFO에 Upload → Branch의 Signage Controller에 Contents 배포

  • 현재 On-prem 기반으로 개발 : WAS(Tomcat), Redis, PostgreSQL, MS SQL (2008/2012/2016)

  • AWS 상에서 Pro Service 라는 Brand Title로 사업 진행

    • On-prem solution을 AWS 이식하여 사용

      • ELB + 2 WAS + 1 Redis + 1 DB

    • 특정 고객에 dedicated된 서버

  • MagicINFO 서비스 Page : https://www.magicinfoservices.com

  • MagicINFO 서버

    • web-based tool used to manage content files and devices.

    • creates and distributes content file schedules

  • MagicINFO Key Functions

    • Media Content File Management

    • Playlist for sequential playback

    • Remote device monitoring

    • Remote display control

    • Remote software update

    • Contents file schedule creation and management

    • Message scedule creation and management

    • Event schedule creation and management

    • User Information and role management

    • Statistics

    • VideoWall

      • WMV : FHD, 30fps, 10Mbps

      • MPEG2 (MPEG-TS) : FHD, 30fps, 20

  • MagicINFO RCDS

MagicINFO Cloud

  • 현재 AWS에서 특정 고객을 대상으로 dedicated 되어 서비스 되고 있는 서비스를 Multi-tenant를 지원하는 SaaS 형태의 Global 서비스로 개발하는 과제

  • On-prem code를 Cloud용으로 전환

  • 적은 개발 공수로 큰 효과 기대

개발 검토 항목

Multi region coverage

  • 현재의 Single region service를 Multi region 서비스로 확대

    • LB + 2 WAS + 1 Redis + 1 DB

  • Mutli-region 구조가 필요 한가에 대해서도 확인 필요

    • Global Accelerator를 사용하여 Single Region Service도 가능하지 않은지

    • Contents 배포는 주당 1회 정도 (매장용 Signage 기준)

      • 10개 정도의 동영상 (몇백 M 수준)

      • Global 하게 분포된 Siganage에 distribution

  1. Global Cache

    • Multi region간 cache 동기화 : cache는 ?

    • Redis cache → Dynamo DB / Accelerator

  2. Global Database

    • Multi region간 동기화가 목적

    • Master region 종속성 있지만 (?) 그 외 region은 read replica를 사용하면 되지 않을까…

    • Aurora PostgreSQL → Global Aurora

  3. Region내의 Display가 Region내 MIS 접속

    • 현재 고정 → Route53 Geo-Location routing으로 가까운 region에서 service

  4. Multi-WAS용 Storage

    • 가장 큰 Issue

    • 2개의 WAS에 on-prem code를 그대로 사용 중 인데 WAS1에 연결된 EBS를 공유하여 사용하는 형태 : Fail-over 취약

    • Region내 EBS 공유 → FSx Storage의 Data Sync 사용하여 Multi WAS 연결 or S3

      • FSx의 Data Sync 시간이 최소 1시간 이라고 파악 → Sync 시간이 너무 긴 문제

      • Region간에 Sync 후 Sync된 File을 CDN을 통해 배포하는 방법

  5. Global Storage

    • File Storage sync와 동일 issue

    • X → DataSync 이용 Region간 FSx Data 동기화

  6. Front-End 독립 구조

    • 큰 Issue 없는 항목

    • 지원 → 독립 구조 서비스 : S3 + CloudFront

Multi tenant

  • SSO : Multi Auth Sever

    • 1대 MIS에 1대 Auth → 1대 MIS에 n대 Auth (organization) / Azure SaaS 서비스화 대응

  • Contents : Up/Down 속도 개선

    • Cloud Storage 에서 zipping, hash 추출 속도 느려 timeout 발생 → Local Storage 처리 후 Cloud Storage 이관

  • SLM/SPP

  • RC Server

    • Connection이 적은 서버로 연결 → Display-RC Server-RC Viewer 간 latency 고려 연결

    • Security 개선

  • Migration Tool 개발

Performance

  • Lambda로 서비스 분리 및 OTN 서버 연동

  • WAS를 docker로 package 하여 ECS 도입

  • CDN : Contents load 분산 및 속도 개선

    • Contnes Uplod / FW Download

  • Schedule 배포 부하 분산

    • SQS 순차 처리 → Lambda로 자동 scaling

  • Bootstraping 부하 분산

    • Throttling으로 제어 → Lambda로 자동 scaling

  • FW 배포 부하 분산

    • SQS 순차 처리 → OTN 서버로 FW 배포, Status 값 monitoring

  • Screenshot Upload

    • Tomcat 처리 → Lambda에서 thumbnail 처리 후 Upload (S3 or FSx)

  • Keep-Alive

    • Tomcat 처리 → Lambda 처리, Protocol 처리 대응

Architecture 상세 리뷰

MagicINFO client

  • Web Browser

  • Signage

Contents File Distribution

  • CloudFront 적용

  • Origin은 S3

  • S3에 contents file 및 Front End code upload 배포

Backend API

  • API Gateway + Lambda → ALB / API Gateway로 분기

  • Lambda 기능

    • WSRM protocol의 Message Body 분석 하여 API 추출 후 분기 : URL로 구분이 되지 않음

    • WSRM (Web Services Reliable Messaging) : RMS, RMD

    • Legacy Signage Model 지원을 위해 WSRM 필요

    • API Gateway + Lambda 외 다른 방안이 있다면 검토 가능

  • 1 way authentication : TLS 1.0 / 1.1 / 1.2

Backend Application

Serverless Application

  • MI Server에 부하가 많이 걸리는 기능을 Lambda로 분산 처리

  • Java language 사용B

  • Bootstraping (기기 초기화 과정) / Keep-Alive 등의 protocol 별 Lambda를 구성

  • Backend API → API Gateway → SQS(?) → Lambda → Storage (DB)

  • SQS 목적

    • DB로 Load가 물리는 것에 대한 우려 하여 SQS로 부하 분산

    • 특정 시간의 짧은 구간에 Traffic 유입에 대한 대응 필요

    • SQS에서 시간을 가지고 처리하여 DB 처리 Load 분산

ECS Application

  • 기존의 MI Server의 Backend API는 ALB를 통해 처리

  • 현재 Service 기준으로 구분하여 Container화

    • MI Server

    • DataLink Server

    • Author Server

  • Container를 위해 기존 Windows application을 Linux application으로 변경

Platform 운영

  • 고객별 Replication 되지 않음 → SaaS로 배포

  • 동일 Platform에 모든 고객이 들어오는 형태

  • 고객 별 contents 관리는 기존 Backend Application 처리

Data Storage

  • On-prem의 경우 Windows / Linux File System에 설치되는 항목들

  • AWS의 File System Storage를 이용하고자 함

  • Example) Web의 관리 tool에서 Schedule 작성 시 기본 base는 DB에 저장 후 Signage에 배포할 File이 생성 됨 → 다른 region으로 DB 및 File sync 필요

  • 같은 시간대의 region에서는 동기화 timing이 중요

  • Contents의 region간 이동에 대해서는 문제가 없는 것으로 파악 → 고객 responsibili

RDB

  • On-prem의 PostgreSQL → Aurora

  • Aurora의 Region간 동기화 기능 사용 : Region간 동기화

  • 다른 Region간 Multi-master 기능 지원 안되어 Master Write Region 지정하고 다른 Region은 Read Replica로 구성

  • 이 경우 Write / Read DB를 접속하는 Application을 구분하여 구성 하여야 하는지에 대해 의문 → 자동 처리 가능(?)

In-Memory DB

  • Redis Cache 동기화 지원이 안됨 → DynamoDB를 Cache로 구성

  • DynamoDB의 Region간 동기화 기능 사용 : DAX

  • Redis의 Region Replication 기능이 가능하여 Global data store로 사용 가능하다면 Redis 유지

  • Redis의 Async 동기화에서 Contents file 및 Information file의 sync

File System

  • 사용자 Upload Contents File과 Information File로 구분

  • Information File : MI, DataLink, Author에서 생성 배포되는 File

    • Schedule 표

    • Contents 정보

  • Multi-region을 고려하여 region간 replication이 필요하다고 판단

  • Contents 정보는 Signage device로 배포 → CDN 연동 필요

    • EFS에서 S3로 동기화 하여 CDN 배포가 필요하다고 판단

  • EFS의 DataSync 기능이 실시간 동기화 지원이 되지 않음 → Scheduling을 통한 주기적 동기화 (min 1h)

  • S3의 Data 동기화는 API call을 통해 진행 → 실시간 동기화 가능 여부

  • Schedule File Sync시 전체 Region의 동기화 필요

  • CRM 도구에서의 Contents Upload와 CDN을 통한 Contents 배포 시나리오를 구분하여 설계 필요
