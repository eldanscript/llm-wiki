Live source region에 따른 MediaLive 구축 region 선택 가이드

  • Check

    이 상황에서 AWS Elemental MediaLive를 설정할 때 고려해야 할 주요 요소들은 다음과 같습니다:

    1. 지연 시간 (Latency)

    2. 안정성 (Reliability)

    3. 비용 (Cost)

    한국 고객을 대상으로 하는 경우, 일반적으로 가장 좋은 선택은 Seoul (ap-northeast-2) 리전일 것입니다. 그 이유는:

    1. 지연 시간: 서울 리전은 한국 시청자들에게 가장 가까운 리전으로, 최소한의 지연 시간을 제공할 수 있습니다.

    2. 안정성: AWS의 서울 리전은 안정적인 인프라를 갖추고 있어, 고품질의 스트리밍 서비스를 제공할 수 있습니다.

    3. 비용: 한국 내 데이터 전송 비용이 국제 데이터 전송보다 저렴할 수 있습니다.

    하지만, 태국에서 RTMP로 송출하는 원본 스트림의 품질과 안정성도 중요한 고려사항입니다. 만약 태국과 한국 사이의 네트워크 연결이 불안정하다면, 태국과 더 가까운 리전(예: Singapore ap-southeast-1)을 중간 지점으로 사용하는 것도 고려해볼 수 있습니다.

    최종 결정을 내리기 전에 다음과 같은 테스트를 수행해보는 것이 좋습니다:

    1. 태국에서 서울 리전으로의 직접 스트리밍 테스트

    2. 태국에서 싱가포르 리전을 거쳐 서울 리전으로 스트리밍하는 테스트

    3. 각 설정에서의 지연 시간, 품질, 안정성 비교

    참고할 만한 링크:

    1. AWS Elemental MediaLive 리전 및 엔드포인트:
      https://docs.aws.amazon.com/general/latest/gr/medialive.html

    2. AWS 글로벌 인프라 리전 맵:
      https://aws.amazon.com/about-aws/global-infrastructure/regions_az/

    3. AWS Elemental MediaLive 사용 설명서:
      https://docs.aws.amazon.com/medialive/latest/ug/what-is.html

    4. AWS 네트워크 지연 시간 테스트:
      https://www.cloudping.info/

    이러한 정보와 테스트를 바탕으로 최적의 리전을 선택하실 수 있을 것입니다.

    네, 말씀하신 대로 MediaLive가 MediaPackage를 통해 CloudFront로 배포된다는 점을 고려하면, Singapore (ap-southeast-1) 리전이 더 효율적일 수 있습니다. 이에 대한 이유와 장점을 살펴보겠습니다:

    1. 원본 스트림과의 근접성:

      • 태국에서 송출되는 RTMP 스트림을 받아들이는 데 있어 Singapore 리전이 Seoul 리전보다 지리적으로 더 가깝습니다.

      • 이는 원본 스트림의 안정성과 품질 유지에 도움이 될 수 있습니다.

    2. CloudFront의 글로벌 분산:

      • MediaPackage에서 처리된 콘텐츠는 CloudFront를 통해 전 세계적으로 분산됩니다.

      • CloudFront의 엣지 로케이션들이 한국을 포함한 전 세계에 분포되어 있어, 최종 사용자에게 콘텐츠를 효율적으로 전달할 수 있습니다.

    3. 네트워크 안정성:

      • 태국-싱가포르 구간의 네트워크 연결이 태국-한국 구간보다 더 안정적일 가능성이 높습니다.

    4. 비용 효율성:

      • 데이터 전송 비용 측면에서 Singapore 리전이 더 유리할 수 있습니다.

    5. 리전 간 지연 시간:

      • Singapore에서 처리된 스트림이 CloudFront를 통해 한국 사용자에게 전달되는 시간과, Seoul에서 처리된 스트림이 전달되는 시간의 차이가 크지 않을 수 있습니다.

    6. 확장성:

      • 향후 다른 아시아 국가로 서비스를 확장할 경우, Singapore 리전이 더 중심적인 위치가 될 수 있습니다.

    그러나 최종 결정을 내리기 전에 다음 사항들을 고려해보시는 것이 좋습니다:

    • 실제 테스트를 통한 성능 비교 (Singapore vs Seoul)

    • 대부분의 시청자가 한국에 집중되어 있는지, 아니면 다른 아시아 국가들로 분산되어 있는지

    • 특정 리전 사용에 따른 규제 또는 컴플라이언스 이슈가 있는지

    참고할 만한 추가 링크:

    1. AWS Elemental MediaPackage:
      https://aws.amazon.com/mediapackage/

    2. Amazon CloudFront 주요 기능:
      https://aws.amazon.com/cloudfront/features/

    3. AWS 글로벌 인프라 센터:
      https://aws.amazon.com/about-aws/global-infrastructure/

    4. CloudFront 엣지 로케이션 목록:
      https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/LocationsOfEdgeServers.html

    최종적으로, Singapore 리전을 사용하는 것이 전반적인 성능과 효율성 측면에서 더 나은 선택일 수 있습니다. 하지만 실제 환경에서의 테스트를 통해 이를 확인하는 것이 가장 좋은 방법일 것입니다.

AWS 이종우 SA 입니다.

문의 주신 부분에 대해 다음과 같이 안내 드리니 참조 하시고 추가 문의 사항 있으시면 말씀 주십시오.

추가로 Media Streaming Lens를 통해 Media Streaming Architecture에 대한 가이드를 드리고 있어 해당 내용도 참조하시면 서비스 구축에도움이 되실 것 같습니다.

(Media Streaming 모범 사례 안내 blog link : https://aws.amazon.com/ko/blogs/tech/streaming-media-best-practices/)

1. 방송 중에 일반 사용자의 시청 및 녹화되는 구간 제한

1-1) 송출이 시작되고 나서 모니터링 후 준비 됐을 때 일반 사용자에게도 공개할 수 있는 환경

  • MediaLive로 channel을 구성하면 최초 상태는 Idle 이며 output으로 출력하고 있지 않습니다. Console에서는 Preview 화면을 제공하고 있기 때문에 수동으로 화면을 monitoring 하면서 channel 출력을 start로 전환하여 사용자에게 송출할 수 있습니다. (MediaLive Channel 생성 과정 안내 github link : https://github.com/aws-samples/aws-media-services-simple-live-workflow/blob/master/3-MediaLive/README.md)

  • Input channel에 대한 미리보기를 통해 input이 활성화 되는 시점을 판단할 수 있습니다. Elemental MediaLive의 Thumbnail preview 기능은 Input stream에 대해 thumbnail을 생성하여 볼 수 잇는 endpoint를 제공합니다. 이 기능은 시작 시점 판단 외에도 Input Stream 상태를 판단할 수 있는 monitoring 도구로도 활용할 수 있습니다. Thumbnail을 통해 송출 시점이 되면 API나 CLI를 통해 Idle 상태인 출력을 start로 전환하면 될 것 같습니다.

(MediaLive Thumbnail preview 사용 안내 blog link : https://aws.amazon.com/blogs/media/generating-input-preview-thumbnails-using-aws-elemental-medialive/)

  • MediaLive schedule 기능을 사용하여 channel 출력 시점을 설정할 수 있습니다. 특정 시점, 즉시, 특정 작업 이후 등으로 설정 가능하니 기능 참조해 보십시오. (MediaLive Schedule 기능 안내 link : https://docs.aws.amazon.com/medialive/latest/ug/working-with-schedule.html)

  • MediaPackage를 통해서도 특정 시점 부터 재생을 설정할 수 있습니다. Time-shifted viewing 기능을 검토해 보십시오. (https://docs.aws.amazon.com/mediapackage/latest/ug/time-shifted.html)

1-2)  일반 사용자도 시청 가능해지는 시점 부터 녹화 시작

  • MediaLive stream은 MediaPackage를 통해 VOD asset으로 생성이 가능합니다. MediaPackage의 harvest job을 생성하여 구성할 수 있습니다. VOD의 시작 시점은 송출 frame이 수집되는 시점 혹은 특정 시작 및 종료 시점을 지정하여 사용할 수 있습니다. (MediaPackage LTOV 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/ltov-how.html)

2. 송출자와 지리적으로 가까운 곳(안정적인 네트웍 환경을 위해)의 channel 을 할당하는 방안

  • 기본적으로 MediaLive 서비스 region과 Upstream Server가 최소한의 network hop으로 AWS network에 연결 되어야 합니다. Channel 할당은 Upstream 구성 방식에 따르는 MediaLive 내부 리소스 배포 이고 Upstream Server와 AWS 간의 networking 구성을별도로 고려하셔야 합니다.

  • Video Upstream이 최소한의 network hop과 안정적인 연결을 위해 Global Accelerator구성을 생각해 볼 수 있지만 비용에 대한 검토가 필요합니다.

  • 또 다른 연결 방법으로는 AWS Direct Conenct를 통해 Upstream Server를 AWS에 연결하고 RTMP VPC 혹은 CDI 구성을 통해MediaLive 입력을 생성할 수 있습니다. Direct Connect 비용 및 Upstream 처리를 위한 추가 VPC 혹은 CDI 구성이 필요 합니다. (AWS CDI 기능 안내 link : https://aws.amazon.com/about-aws/whats-new/2020/09/introducing-aws-cloud-digital-interface-cdi-and-input-support-in-aws-elemental-medialive/

  • Live 방송 수준에서는 Elemental Service인 MediaConnect를 이용하여 안정적인 Upstream 구성을 하거나 Elemental Link를 통해 on-prem에서의 방송 장비와의 AWS Elemental 서비스와의 안정적이고 빠른 연결을 구축할 수 있습니다.

(AWS MediaConnect Gateway 안내 blog : https://aws.amazon.com/blogs/media/connect-your-on-premises-multicast-video-network-to-the-cloud-with-aws-elemental-mediaconnect-gateway/)

3. 송출 상태 모니터링

  • CloudWatch 지표를 사용하여 관련 metric을 수집 및 시각화 할 수 있습니다. (MediaLive 및 MediaPackage에 대한 observability 구축안내 blog link : https://aws.amazon.com/ko/blogs/tech/aws-medialive-mediapackage-based-workflow-observability/)
  1.  Playback CDN URL
  • 운영자를 위한 재생 URL 은MediaPackage에서 생성되는 Preview URL을 사용하면 어떨까 합니다. Preview URL을 통해 playback 문제 여부와 이슈를 troubleshooting 할 수 있습니다.

(MediaPackage Preview 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/endpoints-preview.html)

  • 특정 시간 동안만 이용할 수 있는 기능은 MediaPackage의 Time-shifted viewing 설정을 통해 구성할 수 있습니다. Live view의 경우 Time-shifted viewing을 통해 일정 시간이 지난 live streaming에 대한 재생을 차단할 수 있습니다. 최대 14일 까지 가능합니다. (MediaPackage의 Time-shifted viewing 기능 : https://docs.aws.amazon.com/mediapackage/latest/userguide/time-shifted.html)

  • VoD 동영상 등을 고려하여 CDN URL에 대한 일정 기간 접근 제어를 한다면 CDN의 signed URL을 생성하고 expiration time을 지정하여 사용할 수 있습니다.

(CloudFront signed URL 기능 안내 link : https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)

  • 재생 URL 탈취 등의 보안 대응이 필요하다면 CDN Authorization이나 DRM, Watermarking 구성을 검토해 보실 수 있습니다.

(MediaPackage CDN Authorization 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/cdn-auth.html

Securing Media using AB watermarking 구성 안내 blog link : https://aws.amazon.com/blogs/media/securing-media-content-using-watermarking-at-the-edge/)

5. 송출자의 송출 스펙(bitrate, 해상도)에 따라 여러 MediaPackage 출력 그룹 하나만을 선택

  • 송출자의 Spec에 따라 Output을 다르게 설정한다면 별도의 MediaLive Channel을 구성해야 합니다.

  • MediaLive에서는 사용자 단말 혹은 플레이어의 사양에 따라 downstream output 해상도가 결정되는데 별도로 고정된 해상도 출력 구성을 검토하시는 이유 문의 드립니다.

  1. Channel 시작 / 종료 시간
  • MediaLive channel 구성에 따라 channel 시작 시간은 달라질 수 있습니다. Channel 시작 지연에 대해서는 Channel을 Upstream 시작전 미리 생성하여 ‘input prepare’ 상태로 유지한 후 연결하여 사용할 것을 권고하고 있습니다. 또 Standard channel로 설정하여 2개의 input을 구성하고 primary input의 연결이 지연될 경우 secondary input으로 변경하는 방법을 적용해 볼 수 있습니다.

(MediaLive input 준비 안내 link : https://docs.aws.amazon.com/medialive/latest/ug/feature-prepare-input.html)

  • 현재 시나리오가 생방송이 끝나고 즉시 다음 라이브가 연결 되어야 한다면 현재 channel 종료 전 미리 다음 channel에 대해 준비를 진행하는 것이 필요할 것 같습니다.

Answers

문의 주신 부분에 대해 다음과 같이 안내 드리니 참조 하시고 추가 문의 사항 있으시면 말씀 주십시오.

추가로 Media Streaming Lens를 통해 Media Streaming Architecture에 대한 가이드를 드리고 있어 해당 내용도 참조하시면 서비스 구축에 도움이되실 것 같습니다.

(Media Streaming 모범 사례 안내 blog link : https://aws.amazon.com/ko/blogs/tech/streaming-media-best-practices/)

1. 방송 중에 일반 사용자의 시청 및 녹화되는 구간 제한

1-1) 송출이 시작되고 나서 모니터링 후 준비 됐을 때 일반 사용자에게도 공개할 수 있는 환경

  • MediaLive로 channel을 구성하면 최초 상태는 Idle 이며 output으로 출력하고 있지 않습니다. Console에서는 Preview 화면을 제공하고 있기때문에 수동으로 화면을 monitoring 하면서 channel 출력을 start로 전환하여 사용자에게 송출할 수 있습니다. (MediaLive Channel 생성 과정안내 github link : https://github.com/aws-samples/aws-media-services-simple-live-workflow/blob/master/3-MediaLive/README.md)

  • Input channel에 대한 미리보기를 통해 input이 활성화 되는 시점을 판단할 수 있습니다. Elemental MediaLive의 Thumbnail preview 기능은Input stream에 대해 thumbnail을 생성하여 볼 수 잇는 endpoint를 제공합니다. 이 기능은 시작 시점 판단 외에도 Input Stream 상태를 판단할수 있는 monitoring 도구로도 활용할 수 있습니다. Thumbnail을 통해 송출 시점이 되면 API나 CLI를 통해 Idle 상태인 출력을 start로 전환하면될 것 같습니다.

(MediaLive Thumbnail preview 사용 안내 blog link : https://aws.amazon.com/blogs/media/generating-input-preview-thumbnails-using-aws-elemental-medialive/)

  • MediaLive schedule 기능을 사용하여 channel 출력 시점을 설정할 수 있습니다. 특정 시점, 즉시, 특정 작업 이후 등으로 설정 가능하니 기능참조해 보십시오. (MediaLive Schedule 기능 안내 link : https://docs.aws.amazon.com/medialive/latest/ug/working-with-schedule.html)

  • MediaPackage를 통해서도 특정 시점 부터 재생을 설정할 수 있습니다. Time-shifted viewing 기능을 검토해 보십시오. (https://docs.aws.amazon.com/mediapackage/latest/ug/time-shifted.html)

1-2)  일반 사용자도 시청 가능해지는 시점 부터 녹화 시작

  • MediaLive stream은 MediaPackage를 통해 VOD asset으로 생성이 가능합니다. MediaPackage의 harvest job을 생성하여 구성할 수 있습니다.VOD의 시작 시점은 송출 frame이 수집되는 시점 혹은 특정 시작 및 종료 시점을 지정하여 사용할 수 있습니다. (MediaPackage LTOV 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/ltov-how.html)

2. 송출자와 지리적으로 가까운 곳(안정적인 네트웍 환경을 위해)의 channel 을 할당하는 방안

  • 기본적으로 MediaLive 서비스 region과 Upstream Server가 최소한의 network hop으로 AWS network에 연결 되어야 합니다. Channel 할당은Upstream 구성 방식에 따르는 MediaLive 내부 리소스 배포 이고 Upstream Server와 AWS 간의 networking 구성을 별도로 고려하셔야 합니다.

  • Video Upstream이 최소한의 network hop과 안정적인 연결을 위해 Global Accelerator구성을 생각해 볼 수 있지만 비용에 대한 검토가 필요합니다.

  • 또 다른 연결 방법으로는 AWS Direct Conenct를 통해 Upstream Server를 AWS에 연결하고 RTMP VPC 혹은 CDI 구성을 통해 MediaLive 입력을생성할 수 있습니다. Direct Connect 비용 및 Upstream 처리를 위한 추가 VPC 혹은 CDI 구성이 필요 합니다. (AWS CDI 기능 안내 link : https://aws.amazon.com/about-aws/whats-new/2020/09/introducing-aws-cloud-digital-interface-cdi-and-input-support-in-aws-elemental-medialive/

  • Live 방송 수준에서는 Elemental Service인 MediaConnect를 이용하여 안정적인 Upstream 구성을 하거나 Elemental Link를 통해 on-prem에서의 방송 장비와의 AWS Elemental 서비스와의 안정적이고 빠른 연결을 구축할 수 있습니다.

(AWS MediaConnect Gateway 안내 blog : https://aws.amazon.com/blogs/media/connect-your-on-premises-multicast-video-network-to-the-cloud-with-aws-elemental-mediaconnect-gateway/)

3. 송출 상태 모니터링

  • CloudWatch 지표를 사용하여 관련 metric을 수집 및 시각화 할 수 있습니다. (MediaLive 및 MediaPackage에 대한 observability 구축 안내 blog link : https://aws.amazon.com/ko/blogs/tech/aws-medialive-mediapackage-based-workflow-observability/)
  1.  Playback CDN URL
  • 운영자를 위한 재생 URL 은MediaPackage에서 생성되는 Preview URL을 사용하면 어떨까 합니다. Preview URL을 통해 playback 문제 여부와이슈를 troubleshooting 할 수 있습니다.

(MediaPackage Preview 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/endpoints-preview.html)

  • 특정 시간 동안만 이용할 수 있는 기능은 MediaPackage의 Time-shifted viewing 설정을 통해 구성할 수 있습니다. Live view의 경우Time-shifted viewing을 통해 일정 시간이 지난 live streaming에 대한 재생을 차단할 수 있습니다. 최대 14일 까지 가능합니다. (MediaPackage의 Time-shifted viewing 기능 : https://docs.aws.amazon.com/mediapackage/latest/userguide/time-shifted.html)

  • VoD 동영상 등을 고려하여 CDN URL에 대한 일정 기간 접근 제어를 한다면 CDN의 signed URL을 생성하고 expiration time을 지정하여 사용할 수 있습니다.

(CloudFront signed URL 기능 안내 link : https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html)

  • 재생 URL 탈취 등의 보안 대응이 필요하다면 CDN Authorization이나 DRM, Watermarking 구성을 검토해 보실 수 있습니다.

(MediaPackage CDN Authorization 기능 안내 link : https://docs.aws.amazon.com/mediapackage/latest/ug/cdn-auth.html

Securing Media using AB watermarking 구성 안내 blog link : https://aws.amazon.com/blogs/media/securing-media-content-using-watermarking-at-the-edge/)

5. 송출자의 송출 스펙(bitrate, 해상도)에 따라 여러 MediaPackage 출력 그룹 하나만을 선택

  • 송출자의 Spec에 따라 Output을 다르게 설정한다면 별도의 MediaLive Channel을 구성해야 합니다.

  • MediaLive에서는 사용자 단말 혹은 플레이어의 사양에 따라 downstream output 해상도가 결정되는데 별도로 고정된 해상도 출력 구성을 검토하시는 이유 문의 드립니다.

  1. Channel 시작 / 종료 시간
  • MediaLive channel 구성에 따라 channel 시작 시간은 달라질 수 있습니다. Channel 시작 지연에 대해서는 Channel을 Upstream 시작 전 미리생성하여 ‘input prepare’ 상태로 유지한 후 연결하여 사용할 것을 권고하고 있습니다. 또 Standard channel로 설정하여 2개의 input을 구성하고 primary input의 연결이 지연될 경우 secondary input으로 변경하는 방법을 적용해 볼 수 있습니다.

(MediaLive input 준비 안내 link : https://docs.aws.amazon.com/medialive/latest/ug/feature-prepare-input.html)

  • 현재 시나리오가 생방송이 끝나고 즉시 다음 라이브가 연결 되어야 한다면 현재 channel 종료 전 미리 다음 channel에 대해 준비를 진행하는 것이 필요할 것 같습니다.
