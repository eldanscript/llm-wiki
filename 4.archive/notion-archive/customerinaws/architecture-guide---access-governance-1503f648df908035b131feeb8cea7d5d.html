  • non pem key, non ssh

  • 다수 애플리케이션 서버에 각각 필요한 OS User 생성 (ssm document 외에 다른 방안은?)

  • 접속자별 root / non root 권한구분 (예. 인프라운영팀 root 권한, 일반 사용자 non root 권한 등)

Specialist Answer

실제 인프라 운영간에 필요한 접근제어를 구현하신다면, 현재의 구성방안을 알아야 할 필요가 있습니다.

주지하시는 것 처럼 현재고객께서 AD 기반으로 인프라 + 사용자 관리를 하신다면, 가장 간단하게 AD connector를 통해서 IAM Identity center로 연동해서 AD의 파라메타를 SCIM으로 연계시키고 변수화 한 뒤, Tag 기반 정책을 활용해서 최대한 구현할 수 가 있습니다.

https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html

하지만, 이 경우에도, 기존 AD 그룹정책을 모두 구현하기가 어렵기 때문에, 일반적으로는 인프라팀은 IAM Identity Center를 통해서 인프라 자체를 관리하고,  실제 RDP로 접근해야 하는 어플리케이션 팀은 ADFS 포탈을 사용하도록 하는 Two track을 사용하시는 고객들도 계십니다.

만약, 어플리케이션 팀에서 RDP로 접속할 때 ADFS포탈 안쓰고 AWS Session Manager(fleet management)를 써서 기존 ad사용자의 권한으로 접속을 하고자 한다면, 다음 블로그도 참조할 수 있습니다.

https://aws.amazon.com/ko/blogs/mt/configuring-aws-systems-manager-session-manager-support-federated-users-using-session-tags/?utm_source=perplexity

Console login 제한 문의

내부적으로 aws 접근 제한 정책을 강화하고 있습니다.
단계적으로 적용하기 위해서 console login에 대한 이벤트를 수집해서 모니터링 하려 하는데요.

이로 인해 전체 어카운트에 event bridge 설정이 필요한 상황입니다.

  • EventPattern
    {
    “source”: [“aws.signin”],
    “detail-type”: [“AWS Console Sign In via CloudTrail”]
    }

문의사항으로 개별 어카운트에서 event bridge 설정을 하는 방법 외에 organization cloudtrail 을 통해 organization master 어카운트에서 전체 어카운트에 통합 설정이 가능한 방법이 있을지 문의드립니다.

확인해보니 organization master 어카운트에서 전체 어카운트에 cloudtrail log를 수집하고 있더라도 event bridge 에서는 해당 어카운트에 event history 에 대해서만 확인하고 있어 방법이 없을 것 같지만 혹시나 다른 방안이 있을지 궁금합니다.

  • 가이드 답변

    CloudTrail에서는 AWS Management Console sign-in events에 대한 log를 기록하고 있습니다.

    (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-aws-console-sign-in-events.html)

    그리고, CloudTrail의 Organization Event Data Stores 기능을 통해 AWS Organization의 모든 하위 account의 event를  S3에 저장할 수있습니다.

    (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-lake-organizations.html#cloudtrail-lake-organizations-update-eds )

    Event Bridge를 사용하는 목적은 CloudTrail의 Console sing-in log를 S3 외에 다른 서비스로 전달하여 모니터링 하기 위해 필요하신것으로 보입니다.

    Event Data Store에 저장된 Sign-in log를 query하여 모니터링과 연동하시는 방법도 검토 가능하실 지 궁금 합니다.

Session Manager를 통한 File Transfer

24년부터 pem 키 관리와 ssh, sftp port 를 사용하지 않기 위해서 개발자들에게 sso user 를 발급하고, session manager 를 통해 ec2 에 접근하게 하고 있습니다.
이러한 환경에서 개발자의 local pc > ec2 로 file upload 가 필요한 경우, aws 에서 가이드 하는 방법이 있을지 문의 드립니다.

중간에 s3 upload 후 ec2 에서 download 하는 방식은 다수 계정에 cross account role 과 assume role policy 생성이 필요하여 지양하고자 합니다.

  • 가이드 답변

    SSM을 통해 연결된 session에서 SSH에 대한 tunneling을 생성하여 scp 명령으로 local pc file을 업로드 할 수 있습니다.

    이 경우 SSH connection을 형성되지만 EC2 instance에 별도로 SSH port를 open 하지는 않고 SSM session을 활용 합니다.

    이 경우에도 User에 대한 Session Manager에 대한 권한 설정이 필요 하여 Role 생성에 대한 번거로움은 S3 사용과 동일할 것으로보입니다.

    이 방법이 적합 하시다면 아래의 CLI 환경에서 설정하는 가이드를 참고하십시오.

    https://github.com/qoomon/aws-ssm-ec2-proxy-command#prerequisits

    1. AWS CLI Session Manager Plugin 설치

    2. User의 IAM에 권한 설정

    3. SSH Proxy Command (aws-ssm-ec2-proxy-command.sh) 다운로드

    4. Local PC의 ssh config에 SSH Proxy Command 명령어 추가

    host i-* mi-*

    IdentityFile ~/.ssh/id_rsa

    ProxyCommand ~/.ssh/aws-ssm-ec2-proxy-command.sh %h %r %p ~/.ssh/id_rsa.pub

    StrictHostKeyChecking no

    1. SSH 연결 시험

    ssh <INSTACEC_USER>@<INSTANCE_ID>

    1. SCP 명령어를 사용하여 file upload

    scp localfile <INSTACEC_USER>@<INSTANCE_ID>

    추가로 ec2-instance-connect:SendSSHPublicKey 명령을 사용하여 특정 user에게 만 권한을 허용하는 방법도 가이드 하고 있으니참고 하십시오.

What is SSM

AWS Systems Manager는 다양한 기능을 제공하며, 이를 카테고리별로 나누어 설명하겠습니다.

기능 카테고리

노드 관리

  • Fleet Manager: 서버 플릿의 전체 상태와 성능을 글로벌하게 볼 수 있는 기능

  • Compliance: 비준수 리소스 탐지

  • Patch Manager: 패치 자동화

  • Session Manager: EC2 인스턴스 연결 및 관리

  • Run Command: 원격으로 관리형 인스턴스 구성

  • Distributor: 소프트웨어 패키징

애플리케이션 관리

  • Application Manager: 애플리케이션 및 클러스터 관리

  • AppConfig: 애플리케이션 구성 관리 및 배포

변경 관리

  • Change Manager: 변경 요청 관리 및 승인

  • Automation: AWS 리소스에 대한 자동화 작업 수행

  • Maintenance Windows: 패치 적용을 위한 유지 보수 기간 설정

인스턴스 및 노드

  • Hybrid Activations: 하이브리드 환경의 VM 설정

공유 리소스

  • Documents: Systems Manager가 수행할 수 있는 작업을 정의하는 사전 구성된 문서

운영 관리

  • Incident Manager: 인시던트 관리 및 해결

  • OpsCenter: 운영 문제 중앙 집중식 관리

  • Explorer: AWS 리소스에 대한 통합 대시보드

모니터링

  • Parameter Store: 구성 데이터 관리 및 암호화

  • State Manager: 인스턴스의 원하는 상태 정의 및 유지

제한사항

  1. 동시 실행 자동화: 각 AWS 계정은 최대 100개의 자동화를 동시에 실행할 수 있습니다. 적응형 동시성을 활성화하면 최대 500개까지 증가할 수 있습니다[3].

  2. Application Manager의 애플리케이션 수: 최대 100개의 애플리케이션을 Application Manager에 추가할 수 있습니다[3].

  3. Parameter Store 제한:

    • 표준 파라미터: 최대 10,000개

    • 고급 파라미터: 최대 100,000개

    • 파라미터 값 크기: 표준 4KB, 고급 8KB[3]

  4. Patch Manager 제한:

    • AWS 계정당 패치 기준: 50개

    • 패치 기준당 패치 그룹: 25개[3]

  5. Remote Desktop 세션 제한:

    • 최대 세션 시간: 60분

    • 동시 세션 수: AWS 계정당 리전당 5개 (최대 25개까지 자동 승인 가능)[3]

  6. 드래그 앤 드롭 기능 부재: AWS Systems Manager는 직관적인 드래그 앤 드롭 인터페이스를 제공하지 않습니다[4].

이러한 기능과 제한사항을 고려하여 AWS Systems Manager를 효과적으로 활용할 수 있습니다.

SSM RBAC

AWS Systems Manager의 Session Manager를 사용하여 RBAC(Role-Based Access Control)을 구성하는 방법은 다음과 같습니다:

IAM 정책 및 역할 설정

  1. 사용자 그룹 생성: 각 역할에 맞는 IAM 사용자 그룹을 생성합니다.

  2. IAM 정책 생성: 각 그룹에 대한 세분화된 권한을 정의하는 IAM 정책을 생성합니다.

  3. 정책 연결: 생성한 정책을 해당 그룹에 연결합니다.

EC2 인스턴스 태그 지정

  1. EC2 인스턴스에 태그 추가: 예를 들어, “Environment”: “Production”, “Role”: “WebServer” 등의 태그를 지정합니다.

  2. IAM 정책에 태그 조건 추가: 특정 태그가 있는 인스턴스에만 접근할 수 있도록 정책을 구성합니다.

Session Manager 설정

  1. Session Manager 기본 설정 구성: AWS Systems Manager 콘솔에서 Session Manager 설정을 구성합니다.

  2. 로깅 활성화: CloudWatch Logs 또는 S3 버킷에 세션 활동을 로깅하도록 설정합니다.

  3. 세션 제한 설정: 필요한 경우 세션 시간 제한, 최대 세션 수 등을 설정합니다.

IAM 정책 예시

이 정책은 “Environment”: “Production”과 “Role”: “WebServer” 태그가 있는 EC2 인스턴스에만 Session Manager 세션을 시작할 수 있도록 허용합니다.

MFA 강제 적용

IAM 정책에 MFA 조건을 추가하여 추가적인 보안을 구현할 수 있습니다.
