AWS IAM and Kubernetes

AWS IAM Authenticator

  • Kubernetes의 **RBAC 권한을 AWS IAM을 통해 제어할 수 있도록 해주는 도구**.

  • 기존에 AWS 상에서 권한 관리를 하고 있었다면 이를 그대로 Kubernetes API 서버로 가져와 Kubernetes에서의 Role을 엮어줄 수 있다. 예를 들어 DevOps 팀의 IAM Role은 kubernetes-admin 권한을 부여하되, 개발팀의 IAM Role에는 개발용 네임스페이스에만 접근 권한을 부여할 수 있다.

  • git project page : https://github.com/kubernetes-sigs/aws-iam-authenticator

💡

AWS IAM과 Kubernetes의 RBAC간 Mapping

RBAC Authorization

Users in Kubernetes cluster

  • Service accounts와 Normal User의 2개 category로 구분 된다

  • Service accounts (sa)

    • Pod에서 실행되는 process를 위한 계정

    • namespace에 할당 된다. 각 namespace에 default sa가 자동으로 생성된다.

    • 각 pod는 하나의 sa에 연결되지만 여러 pod가 동일한 sa를 사용할 수 있다.

    • Service account 생성은 간단하며 cluster user가 특정 작업을 위해 생성할 수 있다.

  • User accounts

    • human을 위한 계정

    • 전역을 대상으로 고려된다. 클러스터의 모든 네임스페이스에 걸쳐 이름이 고유해야 한다.

    • 기업 DB로 부터 동기화될 수 있으며, 새로운 user account를 생성하려면 특별한 권한이 필요하고 복잡한 비즈니스 프로세스에 연결된다.

Normal User

  • Normal user는 API 호출을 통해 추가 할 수 없음

  • 클러스터의 인증 기관(CA)이 서명한 유효한 인증서를 제공한 사용자는 인증 된 것으로 간주 된다.

    • Cert의 ‘subject’ 필드로 확인

    • 예 : openssl req -new -key jbeda.pem -out jbeda-csr.pem -subj “/CN=jbeda/O=app1/O=app2”

    • username : jbeda, 소속 Group : app1, app2

  • RBAC는 식별된 user에게 resource에 대한 operation 권한이 있는지 확인 한다.

Service Accounts

  • Kubernetes API로 관리되는 users

  • API server에서 자동으로 생성 되거나 API call을 통해 수동으로 생성

  • Secrets에 credential set으로 저장된다.

  • Secret은 pods에 mount 되어 in-cluster 프로세스가 Kubernetes API와 통신 할 수 있게 한다.

IAM role for cluster

Cluster 생성 시

  • EKS cluster를 생성하는 IAM user(혹은 role)는 자동으로 system:masters 권한을 가진다.

  • Control plane의 RBAC configuration이 권한을 부여 한다.

  • EKS cluster 생성 후 configmap

    • aws-auth

    • coredns

    • cp-vpc-resource-controller

    • extension-apiserver-authentication

    • kube-proxy

    • kube-proxy-config

aws-auth ConfigMap

  • EKS cluster에 접근할 수 있는 IAM user(혹은 role)를 구성하는 config map 파일

  • 수동으로 aws-auth 생성하기

  • aws-auth-cm.yaml
  • apply aws-auth
  • Edit aws-auth

EKS console access 권한 부여 하기

💡

aws-auth ConfigMap에 IAM user(role)을 EKS cluster에 binding

  1. AWS IAM user (role) 확인

    • Credential에서 작업을 호출하는 데 사용되는 IAM user(role)에 대한 세부 정보를 반환 : Permission 없이 사용 가능한 CLI 명령어

    • Cloud9의 CLI에서 AWS command 호출 시 eksworkshop-admin role을 통해 접근 : Cloud9 EC2 instance에 assumed 된 administrator role

    • EKS cluster는 이 권한으로 생성이 되었음

  2. IAM ARN 확인

    • AWS Cloud9 개발 환경에 대한 member 정보를 확인 : AWS Console에 Login한 사용자

    • EKS Console을 이 사용자 정보로 접근하므로 EKS cluster에 접근할 수 있는 권한을 부여해야 함

  3. Identity mapping 생성

    💡

    Console user가 Kubernetes resource에 대한 API를 access 할 수 있어야 한다. 이미 Kuberenetes API access 권한을 가진 identity에 mapping을 하면 됨

    • 현재 IAM user(role)의 aws-auth ConfigMap 확인

    • cluster를 지정하여 mapping 하므로 다른 cluster는 조회되지 않는다.

    • kubectl 확인
    • Binding할 Role의 ARN을 가져 온다

    • 확인된 Role을 Cluster의 Service Account에 Binding

      • usergroup - system:masters

      • username - admin

  4. Mapping 확인

    • eksctl 확인

      • ClusterRole admin에 IAM role/Admin mapping
    • kubectl 확인

NameSpace

Default namespaces

default

  • 다른 네임스페이스가 없는 오브젝트를 위한 기본 네임스페이스

kube-system

  • 쿠버네티스 시스템에서 생성한 오브젝트를 위한 네임스페이스

kube-public

  • 자동으로 생성되며 모든 사용자(인증되지 않은 사용자 포함)가 읽기 권한으로 접근할 수 있다.

  • 주로 전체 클러스터 중에 공개적으로 드러나서 읽을 수 있는 리소스를 위해 예약되어 있다.

  • 이 네임스페이스의 공개적인 성격은 단지 관례이지 요구 사항은 아니다.

kube-node-lease

  • 클러스터가 스케일링될 때 노드 하트비트의 성능을 향상시키는 각 노드와 관련된 리스(lease) 오브젝트에 대한 네임스페이스
