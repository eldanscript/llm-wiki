MC2-06-02-2020

[Shadowing - 2020.6.2]
SS) 예산 초과의 우려가 있음. 제작년 부터 진행. 최적화 중. 시스템 규모가 커질 가능성이 있음. 대상 서비스가 갤럭시 코어만 되어 있는데 컨텐츠 서비스를 여러개를 하기 때문에 개인화에 대한 요구사항이 많아 져서 확대 가능성. 스토어내에서 국가 확대도 있지만 대상 서비스 확대 로드맵이 있음. 미 확정 상태.
AWS) CE, Display가 앱 스토어에서 상호 협력 되는 구조가 될 가능성이 있는지? VD에서 헬스 관련 서비스를 앱으로 하여 구현한 것을 최근에 광고.
SS) 갤럭시 스토어가 TV까지 확장되지는 않음. TV에 별도 스토어가 있음. TV내에도 여러 개의 서비스가 있고 모바일에도 여러 개의 서비스가 있는데 개인화가 적용된 서비스가 거의 없음. 갤럭시 스토어 정도임. 개인화에 대해 중요하게 생각하고 전략적으로 확대할 가능성이 높음. 대상 서비스를 확대할 수도 있고, 각 서비스에서 개인화를 준비할 수 있지만 추천 시스템에 대한 요구 사항이 많아지고 있음.
AWS) amazon.com에서도 개인화 서비스를 제공하고 있지만 수 많은 고객사가 유사 혹은 다른 종류의 비지니스를 하고 있으며 본사의 서비스팀에서 서포트를 한 사례가 많이 있어 유사한 사례를 찾아 공유해 드리는 것에 문제가 없을 것 같다. 문제 정의만 정확히 해 주시면 됨
SS) 추천 시스템을 domain specific한 부분과 general한 부분으로 나눌 수 있을 것 같은데, 1년전에 generalize된 솔루션인 personalize로 PoC를 해 보았는데 필요한 부분을 적용하는데 제약 사항이 몇가지가 있었음. 갤럭시 스토어 서비스 서버 아키텍쳐의 제약 사항을 받쳐 주기에는 실시간으로 추천 리스트를 제공하는게 아니라 배치 형태로 돌려야 하고 배치 형태로 쓸 경우에는 많은 규모의 사용자에 대해 미리 준비를 해야 하는데 제약이 있음. domain specific한 부분과 general한 부분, data, model, output이 나올 때 까지의 ranking, filtering 관련 모듈등에 대해 설계를 어떻게 하는지 참고가 되면 좋을 것 같음
AWS) 비지니스의 종류는 다르지만 풀어야 될 문제는 유사. Large Scale 규모로 추천하는 사례들이 있음
SS) personalize를 사용하는게 아니라 in/out solution을 설계하고 범용 추천 엔진을 만든것?
AWS) personalize를 사용하거나 sagemaker를 사용한 경우가 있음. Sagemaker로 단순한 PoC 정도, 23일 내에 가능한 것들은 글로벌에서 서포트가 가능하고 커스터마이징에 대해서는 이미 아키텍쳐를 빌드했던 커스터머가 많이 있어 사례를 찾아 공유가 가능
SS) 컨셉 개념에서의 구현 가능성은 알고 있지만 실제로 진행하는 과정에서 어떤 문제가 있었고, 어떤 제약이 있어서 실패를 한 적이 있는지에 대한 사례가 있으면 도움이 될 것 같음. 그걸 기준으로 자체적으로 가능할 지 AWS의 도움을 받아야 할 지 판단할 수 있을 것 같음. 성공 사례 보다는 domain specific한 부분을 어떻게 해결 했는지에 대한 참고가 있으면 좋을 것 같음
AWS) 다른 고객사에서도 trial and error를 겪으며 진행했고 그 부분을 지원했기 때문에 큰 문제가 없음. 어떤 domain 인지?
SS) 컨텐츠 비지니스. 미디어 (비디오, 뮤직), 뉴스 등.
AWS) sagemaker는 bra팀에서 지원. 정의석 부사장님과도 빅스비 관련하여 1:1 화상 미팅을 진행. 본사 레벨에서 서비스 팀 지원 문제 없음
SS) Mobile AD및 Runestone 팀 과도 교류를 지원하고 있음. 광고팀은 스케일과 real-time 문제가 큰 것 같고, 저희는 quality control을 어떻게 하느냐가 중요한 문제임. 사용자가 불만족 스러운 추천 결과가 안 나오게 하기 위해 해결할 문제가 많고, 경험도 부족.
AWS) 유사 사례가 많아 큰 문제가 없을 것으로 보임
AWS) 개인화라는 큰 주제를 가지고 3개팀을 묶어서 온라인 세미나를 지원하고 그 안에서 필요한 부분을 세분화하여 팀별로 도와드리는 것을 기획해 보도록 하겠음.
AWS) 192개의 인스턴스 내용은?
SS) 3개 국가로 나누어져 있고 그 안에는 하나의 배치가 Collaborative Filtering을 사용하는 것도 있고 DNN을 쓰는 것 등으로 segmentation하여 나누어 짐. 개인화 뿐만 아니라 그룹화, clustering하여 컨텐츠별로 묶는 추천도 있음.
AWS) 학습 시간보다 추론 시간이 많이 걸리는 게 데이터 건 수의 차이인지? 모델이 여러 개를 동시에 하는 것인지?
SS) 데이터 건 수의 차이임. 식별하는 개인 기준으로 6천만 명 정도임. Training set은 그것보다 적게 하고 있음. 일 주일에 한번 서베이 하는 것으로 머신을 최대한 잘 활용하는 것으로 시간을 나누다 보니 학습은 30시간 정도로 충분. 건 수로는 50만 정도 됨. 50만으로 5천만건을 추론
AWS) 50만의 산정 기준은? 마케팅을 동의한 고객, 임직원 제외 등의 로직 등…
SS) label data를 가지고 있는 전체를 training data로 사용하고 있는데 생각보다 sparse가 높음. 예를 들면 개인화 추천은 PCVR base로 하는 모델인데 다운로드를 한 기록을 가지고 있는 유저를 다 카운트 해 보면 50만 명정도 되는 것임.
SS) 1년 기간 동안 어떤 컨텐츠에 대한 interaction이 있는 기록을 모아 보면 한 50만건 정도 발생. 추가 필터링은 하지 않고 있음. 전체 갤럭시 컨텐츠를 놓고 보면 훨씬 많지만 컨텐츠 특성별로 짤라서 하고 있음. 폰트, 게임, 테마와 같이. 이러다 보니 수가 줄고 있음
AWS) label의 기준은?
SS) game은 구매, 다운로드로 theme는 다운로드 후 적용하고 30분 이상 지나면 positive feedback (fit?) 으로 봄. Matrix Factorization model은 이렇게 함. MLP (deep learning) model의 경우는 헤비함. Feedback이 없는 데이터들을 사용자들을 implus하는 용도임. Trainning은 훨씬 짧고 positive feedback이 있는 사용자가 훨씬 적기 때문에, 그리고 cold start하는 사용자의 경우가 훨씬 많기 때문에 그 사용자들을 대상으로 MLP model을 구동시킴. Feature가 상당히 많음. 27개 정도임. 이것으로 사용자가 컨텐츠를 선호 할 것이냐 말 것이냐를 logistic regression으로 확인하는 model임.
AWS) Deep Learning을 쓴다면 Neural NF를 쓴다는 것인지?
SS) model이 2개임. 하나는 완전히 MLP model이고 다른 하나는 Neural MF 임. Neural MF는 feedback이 있는 사용자 대상이고, MLP는 cold start 하는 부분
AWS) 일반적인 tableau 기법 적용하는 모델인지 아니면 wide and deep learning이나 중간에 embedding 하는 것인지?
SS) wide and deep base 임. 어프로치에 참고. 사용자 demographic과 컨텐츠 특성 2개를 가지고 예측
AWS) MF는 factorization machine이라고 보면 되는지?
SS) tensor flow로 구현되어 있고 기존 MLP와 matrix factorization의 2가지를 concatrate하여 결과를 만듬. KPI로 엔디시즈를 사용하고 있는데 앤디시즈 기준으로는 제일 좋음. Personalize와도 비교해 봤는데 더 괜찮음. Pre-training기법을 사용. 컨텐츠 특성을 인지적으로 BERT를 하던지 cateogrization을 하는 방법도 있겠지만 embedding vector를 그대로 다른데서 학습한 것을 가져다가 쓰는 방법도 있음
AWS) pre-trainning은 직접 학습한 것인지 기존에 있는 것을 사용한 것인지?
SS) 기존에 있던 것에 컨텐츠 특성에 따라 좀더 학습한 경우도 있음 혹은 다른 데서 학습한 사용자 embedding vector를 가져다 쓰는 경우도 있음. 다른 곳에서 학습한 것을 가져다 사용해도 성능은 좋았음
AWS) GPU-Utilization이 4, 2, 2, 2%로 나누어져 있는 이유는?
SS) 인스턴스의 GPU 개수가 4개인데 각각 나온 값임. 최대치임. 실제 학습하고 있을 때 찍은 값임.
AWS) Utilization이 높지는 않은데 학습 시간이 많지 않아 infra에서 병목 현상이 있어 보임. 추론 시간이 많이 걸리는 것 같은데 주 단위로 100시간이 넘기 때문에 추론 하는데만 5일 정도 걸린다는 것인데.
AWS) 인플러스 할 때 방법이 처음에 데이터를 받았을 때 pre-processing 한 다음에 infrastructure 쪽을 call 하여 결과를 받는 식으로 진행. 추천을 한다고 하면 데이터를 입력해야 인플러스가 되는데 그러면 사전 전처리가 필요함. 그런 전처리를 해서 시간이 오래 걸리는 것인지? 순수하게 인플러스 콜만 했는데 오래 걸리는 것인지?
SS) 후자임. 인스턴스 정보 제공하고 같이 볼 것.
AWS) 추론을 하나의 인스턴스에서 수행하고 있는지?
SS) 국가별로 나누어서 함. 한국 인스턴스, 미국 인스턴스와 같이 나눔. P3.rcf라고 적힌 neural network의 경우는 4대로 나누어 진행하고 있음. AWS) hyper param tuning은 어떤 것이 필요하다고 한 것인지?
SS) DNN 같은 경우 parameter 개수가 27개 정도 된다고 했는데 이것도 50여가지에서 추려낸 것인데 더 개선시킬 방법이 있는 것인지? 실제 hyper parameter는 초반에 manual로 test를 하여 찾은 것임.
AWS) 비정형 데이터는 어떤 것들이 있는지?
SS) 데이터 모듈이라고 하여 pre-processing하는 비정형 데이터를 정형화 시키고 정형 데이터도 filter out하는 부분이 따로 있음. 2년전에 EC2에 직접 셋업하고 tensor flow 설치하여 구축. 이 후 AMI 사용하고 그 뒤에 sagemaker 나올 때 쯤 상품화 버전이 나와서 운영하고 있는 것임. 개선할 포인트는 있음. 모델 tuning이나 hyper parameter 최적화는 별도로 과제를 하고 있음.
AWS) tensor flow version은?
SS) 1.7.0
AWS) 2.0 업그레이드 할 생각은?
SS) 시도는 해 보았는데 잘 돌지 않는 부분이 있음. 패키지와 호환성이 맞지 않는 것이 있음. 처음 시작할 때 sagemaker와 같은 managed service가 있었으면 좋았을 것 같음.
AWS) production과 dev를 이원화 하여 운영하고 있는 것인지? Hyper parameter나 network test와 같은 것을 dev 단에서 나누어서 사용하는지?
SS) 그렇게 하고 있음. 2년 전에 상품화 한 후 model과 data의 품질이 어느 정도 추천 결과에 대해서 담보를 하지만 비지니스 영역과 만나면, 이것, 저것에 대한 변경 요구가 많음. 랭킹 로직이나 필터링 로직에 대해 많은 시간을 사용하게 됨. 상품화 하여 동작하게 되면 다른 것에 리소스를 쓰게 됨. 서비스 목적에 맞게 하다 보니… 작년에는 greedy 알고리즘을 가지고 다른 것을 하기도 하고 그 동안 상품화 버전은 유지가 되고 있었음. 최근에 model optimization 관련 하여 올 1월 부터 시작되었고 dev 인스턴스에서 학습, 추론, model 개선, hyper parameter tuning하여 어제 role out하여 A/B test 들어감. 성능은 어떻게 나올 지 잘 모름. 일주일안에 결과를 낼 수 있는지도 매우 중요.
AWS) 코드는 python 사용?
SS) 그러함.
AWS) docker 기반으로 하는지?
SS) 사용 안 함. 처음에 인스턴스 3, 4대 이렇게 시작하던 것이고 코드 변경이 빈번하고 인력도 부족하여 엄두를 내지 못함
AWS) 사용 리전은?
SS) 아일랜드 (더블린) 하나만 사용. 최종적으로 serving은 mysql 사용하여 최대한 속도를 유지하도록 만들고 추천 결과는 batch로 만들고 있어서 성능상에 큰 문제는 없고 아일랜드 리전에 대부분의 serving하는 서버 - 갤럭시 스토어 같은 것들이 같이 있어야 하여 거기에 맞춰저 있음.
AWS) batch로 결과를 뽑아 낸 후에 upload 시켜 놓고 주기적으로 그것을 update하는 방식을 사용하고 있는 것?
SS) 맞음
AWS) 전체 인력은?
SS) 시작은 7명 이었고 그 중에 모델이 23명, 나머지는 데이터 사이언스와 데이터 엔지니어 업무를 반반 나누어서 하고 있음. 명확한 경계가 있지는 않음
AWS) 협업시 소스 코드 관리는 시스템 구축이 되어 있는지?
SS) 퍼퍼스 사용 하고 있음. Github 사용 하지 않음
AWS) Github를 사용하는 수요가 늘어가고 있지 않은가?
SS) tool은 익숙한 것을 사용하자는 주의임. 6개월 정도 리서치 하며 build하여 만들어 낸 것이어서 사실 많이 사용될지 몰랐는데 생각보나 성능이 잘 나와서 많이 사용되고 있음. 급하게 만든 것이 없지 않아 있는 상태임. Conceptual한 architecture는 나쁘지 않다고 생각함. 다만 이것을 구현하고 deploy하는 과정에서는 경험 사례나 업무를 한 사람이 없음. 그래서 나름대로 했는데 부수적인 것 들, 운영/관리의 용이성 들은 skip하고 간 것임.
AWS) 동작하는 모델은 만들어진 상태인데 그 이후의 상품에 대한 고민 사항들이 있는 것 인지?
SS) 아직은 괜찮음. Docker를 사용한다고 하면 그것을 관리하는 사람이 또 있어야 함. 지금은 퍼퍼스에서 코드를 pull하여 밀어 넣는 batch를 만들어 둔 상태임. 인스턴스 병렬화 되어 있고, training set, inference set 나누어 각 인스턴스로 배포하는 것도 구현한 상태여서 운영에 큰 문제는 없음. 물론 이 과정에 사고가 날 가능성이 있는 miss point가 있음. 인력이 더 있으면 이런 부분에 투자할 생각은 있음. 내부적으로 논의 중.
AWS) 데이터 image 관리는 하는지?
