Meta-data of Instance

To get metadata of an EC2 instance when connecting via SSH, you can use the ec2-metadata command or curl commands to the instance metadata endpoint.

  1. Connect to your EC2 instance using SSH.

  2. Use the command to view all available metadata categories:

    ec2-metadata

  3. To fetch a specific metadata, use the command along with the metadata path:

ec2-metadata instance-id
  1. Alternatively, you can use curl commands directly to the instance metadata endpoint at 169.254.169.254:
curl http://169.254.169.254/latest/meta-data/

curl http://169.254.169.254/latest/meta-data/instance-id
  1. The AWS documentation provides more details on the supported metadata paths and usage examples for Linux, Windows and other platforms.

Token Processing

When you queried the metadata of an EC2 instance, you received a 401 unauthorized error. This typically occurs when using version 2 of the EC2 Instance Metadata Service, which requires authentication.

To fix this, you need to obtain a token and pass it with the metadata request. The steps are:

  1. Generate a signature for the request using your AWS credentials. You can use the AWS CLI command for this.

    aws sts get-caller-identity

  2. Make a POST request to the IMDSv2 token endpoint at with the signature.

    http://169.254.169.254/latest/api/token

  3. The response will contain a token.

  4. Pass this token in the ‘X-aws-ec2-metadata-token’ header for subsequent GET requests to the instance metadata endpoints like .

    http://169.254.169.254/latest/meta-data/

  5. The token expires after 15 minutes, so you may need to periodically refresh it by repeating steps 1-3 if making metadata requests over a longer period.

Refer to the AWS documentation on Instance Metadata Service Version 2 for detailed examples on generating and using the authentication token.

EC2 Spot Instance

Get Spot

When you request a Spot instance, you do not set the cost directly. Amazon EC2 sets the Spot price based on supply and demand for EC2 spare capacity in each Availability Zone.

Some key points about Spot instance pricing:

  • You pay the Spot price that is in effect at the time your Spot instance is running, billed per second.

  • You can optionally specify a maximum price, but it is recommended to leave this blank to pay the current Spot price. Specifying a maximum does not increase your chances of getting capacity.

  • The Spot price fluctuates based on supply and demand. You never pay more than the current Spot price, even if you specified a higher maximum price.

  • If your Spot instance is interrupted, you are charged either for the seconds used or the full hour, depending on operating system and who interrupted it.

For the most accurate pricing details, it is best to refer to the EC2 documentation or pricing pages on the AWS website. The pricing models can vary over time based on AWS’s costs and capacity availability.

Get enough capacity

There are a few ways to get Spot instances fast with enough capacity:

  1. Use EC2 Auto Scaling with Spot instances. Auto Scaling will maintain the desired capacity and automatically request more Spot instances when existing ones are interrupted.

  2. Use EC2 Fleet with the capacity-optimized allocation strategy. This analyzes real-time capacity data to launch Spot instances in Availability Zones with most available capacity, reducing the chances of errors.

  3. Specify multiple Spot capacity pools. EC2 can find the most cost-effective capacity across pools using Auto Scaling, Fleet or Spot Fleet.

  4. Leave the maximum price blank when requesting Spot instances. This allows you to pay the current Spot price without interruptions due to price fluctuations.

  5. Consider using containerized workloads which are easier to redistribute in case of interruptions. Services like ECS, EKS make it simpler to run containerized jobs on Spot capacity.

  6. Refer to the EC2 documentation for best practices on using Spot instances. Things like instance types, purchase options, interruption behaviors need to be configured appropriately for your use case

Spot instance interruption

Spot instances are maintained as long as available capacity exists in the Spot capacity pool. However, Amazon EC2 may need the capacity back and can interrupt your Spot instance with a two-minute warning notice.

Some key points about Spot instance availability:

  1. Spot instances are subject to interruption when EC2 needs the underlying hardware resources. The interruption notice provides a chance to save work and request new Spot capacity.

  2. Factors like instance type, Availability Zone and time of day affect capacity availability. Certain configurations may have lower interruption risks.

  3. You can use features like Spot Instance interruption monitoring, EC2 Auto Scaling or Spot Fleet to maintain availability despite interruptions. Auto Scaling can quickly request replacement Spot instances.

  4. Fixed duration Spot instances called Spot blocks are less likely to be interrupted but still have a small risk in rare cases of capacity needs.

  5. For the most accurate details on Spot instance behavior, billing and best practices, refer to the EC2 documentation pages on the AWS website.

Spot instances are started on spare Amazon EC2 capacity that is available. However, if EC2 needs the underlying hardware resources back to support other customers, your Spot instance may be interrupted with a two-minute notification. There are a few reasons why a Spot instance could be interrupted:

  1. EC2 receives a new on-demand instance request that requires the physical hardware your Spot instance is running on.

  2. EC2 needs to perform hardware maintenance, such as software/security updates or hardware repairs, on the physical server hosting your Spot instance.

  3. There is a surge in demand that increases the Spot price above your maximum price. This can cause your Spot request to be cancelled.

To maintain availability despite interruptions, you can use features like Spot Instance interruption monitoring, EC2 Auto Scaling or Spot Fleet. These allow requesting replacement Spot instances automatically
when interruptions occur. You can also choose stop or hibernate options instead of terminating instances on interruption.

Refer to the EC2 documentation for more details on Spot instance interruption behaviors and best practices for using Spot capacity reliably. The documentation is the most accurate source of information.

Node Termination Handler

you can get notified of Spot interruptions using the AWS Node Termination Handler. Here are a few ways:

  1. The Node Termination Handler allows you to specify a termination behavior of STOP or HIBERNATE for Spot instances. This keeps the instance in a stopped or hibernated state instead of terminating it on
    interruption.

  2. You can write scripts or code that gets executed by the Node Termination Handler during interruption. This allows you to take actions like notifying other services, saving state, or requesting replacement
    instances.

  3. The handler metadata provides details of the interruption like the instance ID and reason code. Your scripts can parse this metadata to identify interrupted Spot instances.

  4. You can also integrate the handler with other AWS services like SNS or Lambda for notification. For example, publishing to an SNS topic on interruption that triggers a Lambda function.

  5. The AWS documentation provides tutorials on testing Spot interruptions using the Node Termination Handler and Fault Injection Service (FIS). This can help validate your application’s ability to handle interruptions.

Cost Optimization

Reserved Instances can provide greater savings than Savings Plans, but Savings Plans provide more flexibility. Some key differences:

  1. Reserved Instances require a 1-year or 3-year commitment to a specific EC2 instance type, region, platform and tenancy. This limits flexibility if your usage changes. Savings Plans do not have this limitation.

  2. Reserved Instances offer savings of up to 72% but only apply to the committed instance configuration. Savings Plans savings are up to 66% for Compute Savings Plans and up to 72% for EC2 Instance Savings Plans.

  3. With Savings Plans, you can change instance types, regions, platforms etc and still receive discounts. This provides more flexibility to adapt to changing infrastructure needs.

  4. Reserved Instances provide capacity reservations to ensure availability of the committed instances. Savings Plans do not offer this.

EC2 Connection

The main differences between EC2 Instance Connect and SSH client connection are:

  1. EC2 Instance Connect allows you to connect to your EC2 instances securely through the browser without having to manage SSH keys. It pushes a one-time SSH key to the instance for connecting.

  2. With SSH client connection, you need to have an SSH key pair configured for the instance and the private key locally to authenticate.

  3. EC2 Instance Connect uses the Instance Connect API to manage the SSH connection securely, while SSH client connection establishes a direct SSH tunnel between your local machine and the instance on port 22.

  4. EC2 Instance Connect supports Linux instances, while you can use SSH client connection to connect to Linux, Windows and other OS instances.

  5. For SSH client connection, you need to ensure the security group allows inbound access on port 22 from your IP and there is no firewall blocking it. With EC2 Instance Connect, connection is proxied and no
    special port or firewall configuration is required.

Some common errors when using SSH client connection include connection timeout if security group or network ACL does not allow port 22 access, or connection refused if no SSH service is listening on the
instance.

The main difference between EC2 serial console and EC2 instance connect is:

EC2 serial console allows you to connect to the serial port of a running EC2 instance directly from the AWS Management Console using a browser-based terminal window. You can troubleshoot boot issues or
access the instance when you don’t have SSH access.

EC2 instance connect allows you to establish an SSH connection to your instance programmatically using the AWS CLI or SDKs. With instance connect, you push your SSH public key to the instance. Then you use your private key to SSH into the instance within 60 seconds through the serial console service endpoint before the public key is removed.

Some key aspects:

  • EC2 serial console provides a simple browser-based terminal window to connect. EC2 instance connect requires using SSH and CLI/SDK commands.

  • With EC2 serial console, AWS manages the connection for you through the console. With instance connect, you must use your own SSH key to connect programmatically.

  • EC2 serial console allows one live connection at a time. Instance connect removes the public key after 60 seconds, so you can connect multiple times.
