Access Management using IAM Policy

To manage access to different S3 buckets per user, I would recommend using IAM policies. Here are a few options:

  1. Create individual IAM users for each person who needs access to S3. Attach a policy to each user granting access only to the relevant bucket(s).

  2. Use bucket policies or access point policies to restrict access to specific buckets or prefixes (folders) within buckets based on the IAM principal making the request. You can scope the policies to allow access only to particular users or groups.

  3. Leverage AWS Directory Service for Microsoft Active Directory (AD) to sync your on-premises users and groups to AWS. Then you can attach IAM policies to the AWS AD groups to scope access to particular S3 resources.

  4. If you need very granular access down to the object level, you can also use S3 access control lists (ACLs) to grant read/write permissions on individual objects. However, most customers find that bucket/access point policies and IAM policies meet their needs.

The key is to scope permissions as narrowly as possible by user or group. This allows managing access control even if you have thousands of users while maintaining security and compliance.

S3 Access Grant

When controlling access to S3 buckets, an access grant refers to granting access permissions to specific identities like IAM users or groups to access particular S3 resources like buckets, prefixes or objects.

Some common ways access can be granted include:

  1. Using IAM policies to grant permissions to IAM users or roles to access S3 buckets and objects. This is one of the most common and flexible ways to manage access.

  2. Leveraging S3 access control lists (ACLs) to grant permissions on individual objects within buckets.

  3. Defining bucket policies or access point policies to control access based on conditions like source IP addresses or request headers.

  4. With S3 access points, access can be granted by attaching custom access policies to each access point to define permissions for that access point independently of the bucket policy.

  5. Temporary access can also be granted using techniques like query string authentication where pre-signed URLs are generated granting time-limited access to objects.

S3 Access Grant with IAM Identity Center

When controlling access grant to S3 buckets with IAM Identity Center, you have the following capabilities:

  1. You can synchronize users and groups from your identity source like Active Directory, Ping, Okta etc to IAM Identity Center.

  2. Create S3 Access Grants in the AWS Region associated with your IAM Identity Center to define permissions to S3 resources like buckets, prefixes or objects.

  3. The grants can be assigned to the users and groups synced from your identity source using their GUIDs. For example:

aws s3control create-access-grant --grantee GranteeType=DIRECTORY_USER,GranteeIdentifier=83d43802-00b1-7054-db02-f1d683aacba5

  1. This allows managing permissions to thousands of users while maintaining security and compliance as the actual permissions are scoped based on group memberships.

  2. The user identity gets logged with all S3 access, enabling easy auditing of who accessed what resources.

  3. You can also use the IAM Identity Center APIs to lookup user/group GUIDs or manage access to other applications integrated with IAM Identity Center based on group permissions.

S3 Access Grant to the users signed in with external IdP (Okta)

Yes, you can apply Amazon S3 access grants to users signed in from an external identity provider like Okta. Here are the basic steps:

  1. Configure Okta as an external identity provider in IAM Identity Center. This will link user identities in Okta to the corresponding user profiles in Identity Center.

  2. Create S3 access grants in the usual way by specifying the grantee type as DIRECTORY_USER and providing the user’s GUID from Identity Center.

  3. The user’s GUID can be retrieved from Identity Center using CLI commands like list-users or get-user-id.

  4. When a user signs in via Okta, they will get assigned the permissions defined in the S3 access grant associated with their Identity Center user profile using the GUID.

  5. This allows centrally managing access to S3 buckets for users authenticated through an external IdP like Okta while controlling object-level permissions using S3 access grants.

For more details on configuring Okta as an IdP in Identity Center or using the Identity Store APIs, refer to the AWS documentation pages on IAM Identity Center and S3 access grants.

GetFederationToken vs AssumeRoleWithSAML

GetFederationToken and AssumeRoleWithSAML both allow you to temporarily delegate access to AWS resources to third-party users or applications. However, there are some key differences:

  1. GetFederationToken is used to generate temporary security credentials for a federated user or application that can be used to make API calls to any AWS service. AssumeRoleWithSAML allows assuming an IAM role by passing SAML assertions from an identity provider, and the credentials returned will have permissions of that IAM role.

  2. With GetFederationToken, you have more control over permissions by passing session policies that further restrict access. With AssumeRoleWithSAML, permissions are determined by the IAM role being assumed.

  3. AssumeRoleWithSAML provides a way to federate user identities via SAML. GetFederationToken does not have identity federation capabilities.

To manage SSO user access to S3 buckets, AssumeRoleWithSAML would be more suitable as it allows integrating user identities via SAML. You can create IAM roles with different permission policies for S3 access. The SAML response from the identity provider can then map users to appropriate IAM roles based on claims/attributes.
