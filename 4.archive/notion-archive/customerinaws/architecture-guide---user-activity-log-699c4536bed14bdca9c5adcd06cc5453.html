Decision Point

Redshift Serverless/Spectrum vs Athena

  • Point 1 (Vote 0)

Redshift Spectrum may provide a more stable querying experience compared to Athena. Redshift Spectrum is a good choice for running complex queries on huge data while Athena’s strength is running adhoc queries fast.

For queries that are closely tied to a Redshift data warehouse, you should lean towards Redshift Spectrum. Spectrum makes it easier to join data on S3 with data in Redshift, and to load those results into a Redshift table. If you are willing to pay more for better performance, lean towards Redshift Spectrum.

A key difference between Redshift Spectrum and Athena is resource provisioning. In the case of Athena, AWS automatically allocates resources for your query. You do not have control over resource provisioning. Thus, performance can be slow during peak hours. When using Spectrum, you have control over resource allocation, since the size of resources depends on your Redshift cluster. Thus, if you want extra-fast results for a query, you can allocate more computational resources to it when running Redshift Spectrum.

  • Point 2 (Vote 6)

Athena uses Presto. It is mainly used to run ad-hoc queries against a variety of standard data formats, including CSV, JSON, ORC, Avro, and Parquet. It uses Data Catalog to store information and schemas. Athena relies on pooled resources provided by AWS to return query results.

From the cost perspective, for Redshift Serverless, customer pays separately for the compute and storage. They pay for the Redshift Processing Units (RPUs) duration in seconds when the data warehouse is in use like querying or loading data. They will also pay for data stored in Amazon Redshift-managed storage and storage used for snapshots, whereas for Athena they are charged based on the amount of data scanned by each query with a 10MB minimum per query. Amazon Athena queries data directly from Amazon S3. So there are no additional storage charges for querying your data with Athena

With Redshift serverless you will have more control over price/performance

  • Point 3 (Vote 2)

Cost dimensions

  • In Redshift Serverless, customers pay per query and define how many resources (RPU) they want to give to Redshift, and then pay for the duration of each query.

  • In Athena, customers pay for the amount of data scanned during the query.

Data format

  • Redshift Serverless stores data in a proprietary and efficient format inside RMS (Redshift Managed Storage). Customers do not have direct access to this data and cannot process it with other engines.

  • Athena can read open file formats such as Parquet, ORC, JSON, and Avro that are stored in S3. This means you can use Athena with Glue or EMR to process the same data.

Resource control

  • In Athena, customers do not control the resources allocated during query execution.

  • In Redshift Serverless, you can allocate between 32 and 512 RPU.

Data Source

  • To use Redshift Serverless, you must first load data into Redshift (unless you use Spectrum).

  • Athena can read directly from S3.

Different Syntax

  • Redshift is based on PostgreSQL.

  • Athena for SQL uses Trino and Presto with full standard SQL support (Trino is the open-source distributed SQL query engine for big data, formerly known as PrestoSQL)

  • Athena for Apache Spark supports Python and allows you to use Apache Spark

To summarize, it’s important to consider where their data is currently located, the type of queries they wish to run (adhoc, used with BI tools, etc.), and to run a POC for both Redshift Serverless and Athena to determine which cost-performance works best.

Point 1 (Vote 0 - https://answers.amazon.com/posts/301635

There are two different facets to your question 1. Compute 2. Storage

  1. For computation i.e transforming the data after it arrives in to your Data platform, services like Glue and EMR are best suited. Customers generally run spark workloads on Glue or EMR for performing this computation and the subsequent results are stored either in S3 Datalake or Redshift for further analytics. If your customer has lot of
    complex computations, I’d highly recommend following this approach instead of performing those computations on SQL engines like Athena/Presto/Redshift

  2. For data storage and consumption, as @gonher mentioned above, depending on the use-case you would store the transformed data in S3 datalake and choose Athena or Presto on EMR for adhoc analytics. For performing any complex BI/Reporting, you would store the data on Redshift.
