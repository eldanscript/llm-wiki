CDC

Binlog

When using AWS DMS for CDC replication from Amazon Aurora to target databases, there are a few key points regarding using CDC:

  1. Enable binary logging on the Aurora database instance being used as the source. DMS reads the binary logs to capture changes made to the source database.

  2. The Aurora instance must be the primary/writer instance. Read replicas are not supported as sources for CDC.

  3. DMS will replicate ongoing changes captured in the binary logs to the target database. This allows keeping the source and target databases synchronized as changes are made on the source.

  4. You can validate that changes are being replicated properly by monitoring the DMS task and checking the target database for the replicated changes. DMS also has validation options to check for data mismatches between the source and target.

  5. Refer to the AWS documentation on using Aurora as a DMS source for more details on binary logging configuration and other requirements for CDC replication from Aurora.

Aurora MySQL CDC feature

The FULL LOAD AND CDC feature in AWS Database Migration Service (DMS) allows you to migrate your existing database content along with ongoing changes in a continuous and near-real-time manner. 1(https://aws.amazon.com/blogs/database/how-aws-dms-handles-open-transactions-when-starting-a-full-load-and-cdc-task/)

Here are some key aspects of this feature:

  • FULL LOAD: DMS first performs a one-time full load of the entire source database content, schema, and data to populate the target. This ensures the target is fully initialized.

  • CDC: After the full load is complete, DMS transitions to capturing ongoing CHANGE DATA CAPTURE (CDC) - tracking all insert, update, delete operations on the source database in real-time.

  • CONTINUOUS REPLICATION: The captured changes are continuously replicated to the target database so that it remains in sync with the source as changes occur on an ongoing basis. This keeps the target database up-to-date.

  • LOW IMPACT: The CDC process has minimal impact on the source database performance as it works by reading the transaction logs/change streams without interfering with the source workload.

  • BI-DIRECTIONAL: Some engines also support bidirectional replication between the source and target databases for high availability configurations.

Let me know if you need any clarification or have additional questions!

Sync latency

When replicating large amounts of data from an Aurora database to S3 in real-time using AWS Database Migration Service (DMS), there are a few things you can do to help achieve lower latency:

  • Use larger DMS replication instance types that have more vCPUs, memory, and network bandwidth. For dozens of terabytes of data, consider the r5.24xlarge, r5.metal, or larger instance types.

  • Add more replication instances/tasks and shard the data being replicated across them. This allows parallelizing the replication workload.

  • Compress or partition large tables so they transfer more efficiently over the network. DMS supports compression formats like gzip.

  • Make sure the Aurora database and target S3 bucket reside in the same AWS Region as the DMS replication instance to minimize network latency.

  • Monitor the DMS task metrics like replication lag/latency. Scale up instances proactively if lag grows to avoid spikes in latency.

Proper sizing of DMS resources and optimizing the data transfer process can help achieve replication latencies as low as a few seconds, even for very large datasets. Let me know if you have any other questions!

BP for latency

Here are some best practices to help reduce latency and ensure data consistency when replicating from an Amazon Aurora database to Amazon S3 using AWS Database Migration Service (DMS):

  • Use larger DMS replication instances for higher throughput. The r5.24xlarge or r5.metal instance types can help achieve lower latency for large datasets.

  • Monitor the replication task for latency/lag metrics and scale up the instance proactively if lag grows over time. This prevents latency spikes from task backlogs.

  • Compress or partition large tables for efficient transfer over the network between Aurora and S3. DMS supports compression formats.

  • Keep Aurora and S3 in the same AWS Region and VPC for lowest possible network latency during replication.

  • Prioritize replicating critical or high-write tables first to minimize replication lag on important data.

  • Check DMS logs and Aurora endpoints regularly for any errors that could cause inconsistencies. Resolve issues promptly.

  • Consider adding more replication tasks/instances and sharding data for parallel replication streams if latency reduction is critical.

Proper sizing and optimization of the DMS replication process, along with monitoring replication performance metrics closely, can help achieve consistent, low-latency data transfer from Aurora to S3 for analytics or other use cases. Let me know if you have any other questions!

Limitation in Aurora MySQL

BLOCKLIST

When replicating data from an Amazon Aurora MySQL database to Amazon S3 using AWS Database Migration Service (DMS), the BLOCKLIST data type is not directly supported.

BLOCKLIST is a non-standard MySQL data type that stores a set of values in a string. DMS currently only supports standard MySQL data types for replication tasks.

For a BLOCKLIST column, DMS will typically convert the values to strings during replication. So the individual values within each BLOCKLIST string would be preserved as comma-separated strings in the target data format like CSV or JSON.

However, the BLOCKLIST data type itself would not be maintained. The target data store would simply see it as a standard VARCHAR column containing comma-separated strings.

While not ideal, the actual values within each BLOCKLIST are at least preserved as strings for downstream analytics. Let me know if you have any other questions!

Schema evolution

When replicating data from an Amazon Aurora MySQL database to Amazon S3 using the AWS Database Migration Service (DMS) full load and CDC features, it’s important to handle schema evolution appropriately to maintain consistency as the database schema changes over time. 1(https://docs.aws.amazon.com/whitepapers/latest/migrating-databases-to-amazon-aurora/migration-using-aurora-read-replica.html)

Some best practices for supporting schema changes include:

  • Use DMS schema validation to detect changes during full load. This allows DMS to skip invalid records or pause the task for resolution.

  • For CDC, configure the replication task to ignore errors on invalid columns so it doesn’t stop capturing changes. This prevents lag but won’t replicate new columns.

  • Pause CDC replication temporarily when making major schema changes. Allow the full load to populate the new schema before resuming CDC.

  • Consider versioning tables by adding a timestamp or version column when making changes. This helps analytics queries handle different schemas.

  • The DMS migration task and target database should be designed to support schema changes via stored procedures or other automation.

Let me know if you have any other questions! Proper handling of schema evolution is important for maintaining a consistent replicated dataset in S3 over the long term.

Schema Validation

When replicating data from a source database to S3 using AWS Database Migration Service (DMS) with full load and CDC, there are a few ways to configure schema validation so that it does not impact the replication task if the source schema changes: 1(https://aws.amazon.com/blogs/database/cross-account-amazon-aurora-postgresql-and-amazon-rds-for-postgresql-migration-with-reduced-downtime-using-aws-dms/)

  1. Set the “Ignore validation errors” option to true on the DMS replication task. This will allow changes to be replicated without pausing the task due to validation errors.

  2. Temporarily stop the DMS task before making schema changes on the source database. Allow a new full load to complete, then resume CDC replication. This ensures the target schema is updated first.

  3. Use DMS schema validation only during initial load replication, and disable it for ongoing CDC replication by setting the “Turn on validation” option to false after the full load completes.

Proper change management is important as well. Making schema changes directly on the target database instead of the source can avoid validation conflicts with DMS. Monitoring DMS logs can also help detect and resolve any validation errors promptly to minimize replication lag or failures. Let me know if you have any other questions!
