EKS Hybrid Nodes

https://aws.amazon.com/ko/blogs/korea/use-your-on-premises-infrastructure-in-amazon-eks-clusters-with-amazon-eks-hybrid-nodes/

Amazon EKS Hybrid Nodes는 온프레미스 및 엣지 인프라를 Amazon EKS 클러스터에 노드로 연결할 수 있게 해주는 새로운 기능입니다. 이를 통해 고객들은 다음과 같은 이점을 얻을 수 있습니다:

  1. 클라우드와 온프레미스 환경 전반에서 Kubernetes 관리 통합 및 애플리케이션 실행: EKS Hybrid Nodes를 사용하면 클라우드와 온프레미스 환경 전반에서 일관된 운영 관행과 도구를 활용할 수 있습니다.

  2. Kubernetes 컨트롤 플레인 관리 책임 오프로드: 고객이 온프레미스 하드웨어를 사용하면서도 Kubernetes 컨트롤 플레인 관리 책임은 AWS EKS에 위임할 수 있습니다.

  3. 온프레미스 워크로드 용량 보존: 기존 온프레미스 하드웨어를 활용하면서 EKS의 확장성과 가용성을 활용할 수 있습니다.

EKS Hybrid Nodes를 사용하기 위해서는 AWS Site-to-Site VPN, AWS Direct Connect 등을 통해 온프레미스 환경과 AWS 사이의 하이브리드 네트워크 연결이 필요합니다. 또한 AWS IAM Roles Anywhere 또는 AWS Systems Manager를 통해 하이브리드 노드를 EKS 컨트롤 플레인에 인증해야 합니다.

온프레미스 노드를 EKS 클러스터에 연결하는 과정은 다음과 같습니다:

  1. EKS 클러스터 생성 시 하이브리드 노드 옵션 활성화

  2. 하이브리드 노드 IAM 역할 및 EKS 클러스터 액세스 권한 설정

  3. 온프레미스 호스트에 EKS Hybrid Nodes CLI(nodeadm) 설치 및 구성

  4. 호스트를 EKS 클러스터에 등록

이렇게 등록된 하이브리드 노드는 EKS 콘솔에서 확인하고 관리할 수 있습니다. 하이브리드 노드는 고객이 직접 관리해야 하며, EKS Hybrid Nodes CLI를 활용해 소프트웨어 업데이트 및 Kubernetes 버전 업그레이드를 수행할 수 있습니다.

전반적으로 EKS Hybrid Nodes를 통해 고객은 온프레미스와 클라우드 인프라 전반에 걸쳐 Kubernetes 환경을 통합하고 운영할 수 있는 유연성을 확보할 수 있습니다.

  1. nodeadm은 Amazon EKS Hybrid Nodes를 사용하기 위해 온프레미스 호스트에 설치해야 하는 CLI(Command-Line Interface) 도구입니다.

    1. AL2023 introduces a new node initialization process nodeadm that uses a YAML configuration schema.

  2. nodeadm을 사용하여 온프레미스 호스트에 EKS Hybrid Nodes를 설치하고 구성하는 과정은 다음과 같습니다:

① 각 온프레미스 호스트에 nodeadm을 설치합니다. 이때 AWS Systems Manager 하이브리드 활성화 또는 IAM Roles Anywhere 인증 정보를 함께 제공해야 합니다.

$ nodeadm install 1.31 --credential-provider <ssm, iam-ra>

② 설치 과정에서 nodeadm이 자동으로 필요한 구성 요소(SSM Agent, kubelet, kubectl, CNI 플러그인 등)를 호스트에 설치합니다.

③ 각 호스트의 nodeConfig.yaml 파일을 생성하여 EKS 클러스터 정보(이름, 리전), 하이브리드 노드 IAM 역할, AWS Systems Manager 또는 IAM Roles Anywhere 인증 정보를 설정합니다.

④ 호스트에서 nodeadm init 명령을 실행하여 EKS 클러스터에 노드를 등록합니다.

  1. nodeadm 외에 다음과 같은 다른 도구를 사용할 수 있습니다:

  • AWS CLI: EKS 클러스터를 생성하고 하이브리드 노드 옵션을 활성화할 때 사용할 수 있습니다.

  • eksctl: EKS 클러스터 생성 및 관리를 위한 CLI 도구로, 하이브리드 노드 구성을 지원합니다.

  • AWS CloudFormation: 인프라 코드로 EKS 클러스터와 하이브리드 노드 구성을 정의할 수 있습니다.

AWS IAM Roles Anywhere

https://aws.amazon.com/ko/blogs/security/extend-aws-iam-roles-to-workloads-outside-of-aws-with-iam-roles-anywhere/

IAM Roles Anywhere의 주요 기능:

  1. AWS 외부에서 실행되는 워크로드에 대해 IAM 역할 사용 가능

  • AWS 외부(온프레미스 서버, 컨테이너 등)에서 실행되는 애플리케이션도 IAM 역할을 사용할 수 있게 해줌

  • 이를 통해 장기 AWS 자격 증명(액세스 키, 시크릿 키) 관리가 필요 없어짐

  1. PKI 기반의 인증 및 권한 부여

  • 온프레미스 워크로드가 X.509 인증서로 자신을 인증

  • IAM Roles Anywhere는 인증서 발급 기관(CA)을 신뢰 앵커로 등록하여 인증 과정 수행

  • 인증 후 IAM 역할 세션 생성, 임시 AWS 자격 증명 제공

사용 방법:

  1. IAM Roles Anywhere 구성 (관리자)

  • 신뢰 앵커(CA) 생성

  • IAM 역할 및 신뢰 정책 구성

  • IAM Roles Anywhere 프로필 생성

  1. 온프레미스 워크로드에 인증서 프로비저닝 (인프라 관리자)
  • X.509 인증서 및 개인 키를 온프레미스 워크로드에 설치
  1. IAM Roles Anywhere 사용 (애플리케이션 개발자)

  • AWS SDK의 자격 증명 프로세스 기능을 사용하여 인증서로 임시 AWS 자격 증명 획득

  • AWS CLI에 자격 증명 프로세스 구성

이렇게 IAM Roles Anywhere를 통해 AWS 외부 워크로드에서도 IAM 역할 기반의 안전하고 편리한 AWS 서비스 액세스가 가능합니다.

  • 구성 설명

    • 이 YAML 파일은 Karpenter의 NodePool 리소스를 보여줍니다. Karpenter는 Kubernetes 클러스터에서 자동으로 노드를 관리하는 오픈소스 프로젝트입니다.

    주요 내용은 다음과 같습니다:

    1. 메타데이터: NodePool의 이름, 생성 시간, 리소스 버전 등이 포함됩니다.

    2. spec: NodePool의 실제 구성이 정의됩니다.

      • disruption: 노드 디스럽션 정책을 설정합니다. 예를 들어 동시에 제거할 수 있는 노드 수를 제한할 수 있습니다.

      • template: 노드의 실제 구성을 정의합니다.

        • expireAfter: 노드의 최대 수명을 설정합니다.

        • nodeClassRef: 노드 클래스를 참조합니다. 이는 노드의 기본 구성을 정의하는 Karpenter 리소스입니다.

        • requirements: 노드에 대한 요구사항을 정의합니다. 예를 들어 인스턴스 유형, CPU/RAM 등을 지정할 수 있습니다.

        • taints: 노드에 설정된 테인트를 정의합니다.

        • terminationGracePeriod: 노드 제거 시 유예 기간을 설정합니다.

    3. status: NodePool의 현재 상태를 보여줍니다.

    이 YAML 파일을 변경하여 NodePool 구성을 업데이트할 수 있습니다. 예를 들어 spec.template.spec 부분을 수정하면 노드 구성을 변경할 수 있습니다. 변경 후 kubectl apply -f <파일명>.yaml 명령으로 업데이트할 수 있습니다.

    주의할 점은 Karpenter는 자동으로 노드를 관리하므로, 구성을 수동으로 변경할 경우 Karpenter와 충돌할 수 있다는 것입니다. 따라서 NodePool 구성을 변경할 때는 Karpenter의 동작을 잘 이해하고 변경해야 합니다.

Node Auto Repair

  • EKS Auto Mode의 Node Auto Repair 기능은 다음과 같은 노드 문제를 자동으로 해결합니다:

    1. Ready 상태 문제: 노드가 Kubernetes 클러스터에 준비되지 않은 상태(Ready 상태가 아님)인 경우, Node Auto Repair가 자동으로 노드를 교체합니다.

    2. kubelet 응답 없음: 노드의 kubelet 프로세스가 응답하지 않는 경우, Node Auto Repair가 자동으로 노드를 교체합니다.

    3. 가속기(accelerator) 오류: 노드의 GPU, Inferentia 등 가속기 장치에서 오류가 발생하는 경우, Node Auto Repair가 자동으로 노드를 교체합니다.

    4. 네트워킹 문제: 노드의 네트워크 인터페이스가 실행되지 않거나 작동하지 않는 경우, Node Auto Repair가 자동으로 노드를 교체합니다.

    5. 스토리지 문제: 노드의 스토리지 관련 문제(예: XFS 클러스터 크기 작음)가 발생하는 경우, Node Auto Repair가 자동으로 노드를 교체합니다.

    이러한 문제가 감지되면 Node Auto Repair는 자동으로 노드를 코드온(cordon)하고 새 노드로 교체합니다. 이를 통해 클러스터의 가용성을 높이고 운영 중단을 최소화할 수 있습니다.

    단, Node Auto Repair는 DiskPressure, MemoryPressure, PIDPressure와 같은 문제는 자동으로 해결할 수 없습니다. 이런 경우에는 수동 개입이 필요합니다.

  • Kubernetes 클러스터에서 노드를 코드온(cordon)하는 것은 해당 노드에 새로운 Pod 예약을 금지하는 작업입니다. 코드온(cordon) 동작의 주요 내용은 다음과 같습니다:

    1. 스케줄링 금지: 코드온된 노드에는 새로운 Pod가 예약되지 않습니다. 즉, 해당 노드에 더 이상 새로운 워크로드가 배포되지 않게 됩니다.

    2. 기존 Pod 동작 유지: 코드온된 노드에 이미 실행 중인 Pod는 계속 동작합니다. 이미 배포된 워크로드는 계속 실행됩니다.

    3. 노드 드레이닝: 노드가 코드온되면 클러스터 관리자는 해당 노드에서 실행 중인 Pod를 다른 노드로 이동시킬 수 있습니다(노드 드레이닝). 이를 통해 노드를 제거하거나 교체할 수 있습니다.

    4. 노드 테인트: 코드온된 노드에는 자동으로 node.kubernetes.io/unschedulable=true 테인트가 추가됩니다. 이 테인트는 새로운 Pod가 해당 노드에 예약되지 않도록 합니다.

    이와 같이 코드온 동작은 문제가 있는 노드에 새로운 워크로드가 배포되는 것을 막고, 노드 교체 작업을 진행할 수 있게 해줍니다. EKS Auto Mode의 Node Auto Repair 기능은 이러한 코드온 동작을 활용하여 노드 문제를 자동으로 해결합니다.

  • EKS Auto Mode의 Node Auto Repair 기능은 문제가 있는 노드를 자동으로 교체하는 것이 핵심입니다. 그러나 단순히 노드를 교체하는 것만으로는 근본적인 문제를 해결하기 어렵습니다. Node Auto Repair는 다음과 같은 방식으로 문제가 있는 노드 구성을 해결합니다:

    1. 로그 분석: Node Auto Repair는 노드의 로그를 지속적으로 분석하여 다양한 문제를 감지합니다. 이를 통해 문제의 근본 원인을 파악할 수 있습니다.

    2. 문제 유형 분류: 감지된 문제는 유형별로 분류됩니다. 예를 들어, 네트워킹 문제, 스토리지 문제, 커널 문제 등으로 구분됩니다.

    3. 자동 수정 조치: 문제 유형에 따라 자동 수정 조치가 적용됩니다. 예를 들어, 네트워킹 관련 문제가 감지되면 노드를 자동으로 교체하고, 스토리지 문제가 감지되면 노드의 파일 시스템을 재구성합니다.

    4. 재발 방지 대책: 자동 수정 조치 후에도 동일한 문제가 반복적으로 발생하면, Node Auto Repair는 근본 원인을 해결하기 위한 대책을 수립합니다. 예를 들어, 특정 인스턴스 유형의 노드에 문제가 발생하는 경우 해당 인스턴스 유형 사용을 제한하는 등의 방안을 적용합니다.

    이와 같은 방식으로 Node Auto Repair는 문제가 있는 노드를 자동으로 교체하고, 동시에 근본적인 문제를 해결하기 위한 조치를 취합니다. 이를 통해 클러스터의 안정성과 가용성을 지속적으로 높일 수 있습니다.

Cluster DNS

  • 각 노드에 클러스터 DNS 서버를 배포하는 것은 기존 Kubernetes 클러스터의 DNS 구조와 비교했을 때 다음과 같은 장점이 있습니다:

    1. 낮은 latency:

      • 기존에는 중앙 집중식 DNS 서버를 사용했기 때문에 클러스터 내의 모든 DNS 쿼리가 중앙 서버로 전달되어 latency가 높았습니다.

      • 각 노드에 DNS 서버를 배포하면 노드 내부에서 DNS 쿼리를 처리할 수 있어 latency가 크게 낮아집니다.

    2. 확장성 향상:

      • 중앙 집중식 DNS 서버는 클러스터 규모가 커지면 성능 병목 현상이 발생할 수 있습니다.

      • 노드 단위로 DNS 서버를 배포하면 클러스터 규모에 관계없이 일관된 DNS 성능을 보장할 수 있습니다.

    3. 가용성 향상:

      • 중앙 집중식 DNS 서버에 장애가 발생하면 전체 클러스터의 서비스 검색이 불가능해집니다.

      • 각 노드에 분산된 DNS 서버를 사용하면 특정 노드 장애 시에도 다른 노드의 DNS 서버를 통해 서비스 검색이 가능합니다.

    4. 빠른 서비스 검색:

      • 각 노드의 DNS 서버는 클러스터 내부의 서비스 정보를 실시간으로 캐싱하기 때문에, 서비스 검색 속도가 빠릅니다.

      • 이를 통해 애플리케이션의 빠른 서비스 발견과 연결이 가능합니다.

    종합적으로 볼 때, 노드 단위 DNS 서버 배포 방식은 Kubernetes 클러스터의 DNS 성능, 확장성, 가용성을 크게 향상시킬 수 있는 장점이 있습니다.

  • Kubernetes 클러스터에 각 노드에 DNS 서버를 배포할 때, DNS lookup table의 정보를 최신으로 유지하는 것이 중요합니다. 이를 위해 다음과 같은 방법을 사용할 수 있습니다:

    1. 동적 서비스 검색 업데이트:

      • Kubernetes 아피 서버에서 서비스, Pod, 엔드포인트 등의 변경 사항을 지속적으로 모니터링합니다.

      • 변경이 감지되면 각 노드의 DNS 서버에 실시간으로 정보를 업데이트합니다.

    2. 청크 업데이트:

      • 대량의 서비스 변경이 발생하면 청크 단위로 데이터를 업데이트합니다.

      • 이를 통해 DNS 서버의 부하를 줄이고 업데이트 효율성을 높일 수 있습니다.

    3. 캐싱 전략 활용:

      • DNS 서버는 서비스 정보에 대한 TTL(Time To Live) 기반 캐싱을 활용합니다.

      • TTL을 최적화하여 동적 변경 사항을 적절히 반영할 수 있도록 합니다.

    4. 증분 업데이트:

      • 전체 서비스 목록을 업데이트하는 것이 아니라, 변경된 부분만 증분적으로 업데이트합니다.

      • 이를 통해 업데이트 처리 비용을 최소화할 수 있습니다.

    5. 배경 프로세스 활용:

      • 각 노드의 DNS 서버는 백그라운드에서 정기적으로 API 서버의 정보를 동기화합니다.

      • 이를 통해 실시간 변경 사항뿐만 아니라 지연된 변경 사항도 처리할 수 있습니다.

Karpenter의 기능과 동작 원리에 대한 종합적 분석

쿠버네티스 클러스터의 자원 관리 분야에서 혁신적인 접근 방식을 제시하는 Karpenter는 AWS가 개발한 오픈소스 기반의 고성능 노드 프로비저닝 시스템입니다. 2020년 11월 첫 출시 이후 지속적인 진화를 거쳐 2025년 현재 프로덕션 환경에서 안정적으로 운영될 수 있는 수준의 성숙도를 갖추었으며[3], 기존 Cluster Autoscaler(CA)의 아키텍처적 한계를 극복한 설계로 주목받고 있습니다. 본 보고서는 Karpenter의 핵심 기능과 내부 동작 메커니즘을 다층적으로 분석합니다.

1. 아키텍처 설계 철학

1.1 그룹리스(Groupless) 아키텍처

Karpenter의 근본적인 혁신은 EC2 Auto Scaling Group(ASG)에 대한 종속성 제거에 있습니다. 기존 CA가 ASG를 통해 노드 그룹 단위로 확장을 관리했던 방식과 달리, Karpenter는 EC2 Fleet API를 직접 활용하여 인스턴스 유형/가용 영역/구매 모델(on-demand/spot)을 유연하게 선택합니다[4][8]. 이로 인해 사용자는 단일 ASG 템플릿으로 다양한 인스턴스 패밀리(c, m, r 시리즈 등)를 동시에 활용할 수 있으며[1], 실제 워크로드 요구사항에 최적화된 인스턴스 선택이 가능해집니다.

1.2 JIT(Just-In-Time) 프로비저닝

Karpenter의 노드 생성 프로세스는 평균 40초 이내로 완료되는 초고속 동작 특성을 보입니다[1][7]. 이는 kube-scheduler의 스케줄링 루프 주기(기본 1분)보다 빠른 반응 속도로, pending 상태의 파드 발생 시 즉각적인 대응이 가능합니다. 내부적으로는 Kubernetes API 서버의 워치 메커니즘을 활용해 Unschedulable 이벤트를 실시간 감지하며[11], 프로비저닝 결정에서 EC2 인스턴스 기동까지의 전체 과정을 단일 컨트롤 플레인이 관리합니다[9].

2. 핵심 기능 메커니즘

2.1 동적 노드 프로비저닝

Karpenter의 노드 생성 로직은 3단계 의사결정 프로세스로 구성됩니다[13]. 첫째, 스케줄링 실패 파드의 리소스 요청사항(resource requests), 노드 셀렉터(nodeSelector), 어피니티(affinity), 톨러레이션(toleration) 등을 종합적으로 분석합니다[10]. 둘째, 가능한 인스턴스 유형 후보군을 생성한 후 비용 최적화 알고리즘을 적용해 최적의 인스턴스 유형을 선택합니다[12]. 마지막으로 EC2 Fleet API를 통해 선택된 인스턴스의 프로비저닝을 실행합니다.

2.2 자동 노드 통합(Consolidation)

Karpenter v0.34.0부터 도입된 Spot-to-Spot Consolidation 기능은 클러스터 내 리소스 사용 효율을 극대화합니다[1]. 시간 경과에 따라 워크로드의 리소스 사용 패턴이 변화하면, 기존 노드의 사용률을 분석해 더 작은 인스턴스 유형으로 마이그레이션하거나 다수의 노드를 단일 노드로 통합합니다. 이 과정에서 노드의 퇴거(eviction)는 Kubernetes의 graceful termination 절차를 준수하며[3], 파드의 디스럽션 버짓(disruption budget) 설정을 고려합니다.

2.3 노드 라이프사이클 관리

Karpenter는 생성된 노드에 대해 TTL(Time-To-Live) 기반의 자동 만료 정책을 적용합니다. 기본값인 720시간(30일) 이후에는 노드를 강제로 교체함으로써 보안 패치 적용과 AMI 업데이트를 자동화합니다[1][8]. 또한 노드 풀(NodePool) 단위로 disruption 정책을 설정하여 언더유틸라이제이션(underutilization) 발생 시 자동 회수 기능을 활성화할 수 있습니다[1].

3. 성능 최적화 전략

3.1 병렬 스케줄링 메커니즘

Karpenter는 kube-scheduler와의 협력 모드를 통해 스케줄링 성능을 극대화합니다[13]. 노드 생성 단계에서 파드의 스케줄링 제약 조건을 사전에 분석하여, 노드가 Ready 상태가 되는 즉시 파드를 바인딩하는 최적화된 워크플로를 구현합니다[7]. 이로 인해 기존 CA 대비 평균 60% 이상 빠른 파드 배치가 가능하며[12], 특히 배치 처리 워크로드에서 두드러진 성능 향상을 보입니다.

3.2 인스턴스 유형 최적화 알고리즘

Karpenter의 인스턴스 선택 알고리즘은 다중 목표 최적화(Multi-Objective Optimization) 기법을 채택합니다. 리소스 적합도(resource fit), 비용(cost), 가용성 영역 밸런싱(zone balancing) 요소를 종합적으로 평가하여 Pareto 최적점을 찾아냅니다[10]. 사용자는 NodePool CRD를 통해 인스턴스 카테고리(c, m, r 시리즈), vCPU 개수, 메모리 크기 등의 제약 조건을 유연하게 설정할 수 있습니다[2].

4. 운영 관리 기능

4.1 다중 노드 풀 전략

프로덕션 환경에서는 워크로드 유형별로 전용 노드 풀을 구성하는 것이 일반적입니다. 예를 들어 GPU 가속이 필요한 AI 워크로드용 노드 풀과 범용 컴퓨팅용 노드 풀을 분리하여 관리할 수 있습니다[9]. 각 노드 풀에는 고유한 테인트(taint)와 레이블(label)을 부여함으로써 파드의 스케줄링 정확도를 제어합니다.

4.2 통합 모니터링 체계

Karpenter Controller는 Prometheus 메트릭을 노출하여 클러스터 운영자에게 실시간 인사이트를 제공합니다. 주요 지표로는 karpenter_nodes_created(노드 생성 횟수), karpenter_nodes_terminated(노드 종료 횟수), karpenter_pods_disrupted(파드 중단 횟수) 등이 포함됩니다[10]. CloudWatch와의 통합을 통해 Auto Scaling 이벤트의 추적 및 경고 설정이 가능하며, Audit 로그를 통해 관리자 작업 이력의 감사(audit) 기능을 강화합니다.

5. 보안 및 거버넌스

5.1 IAM 최소 권한 원칙

Karpenter는 AWS 환경에서 IRSA(IAM Roles for Service Accounts)를 통해 EC2, SSM, CloudFormation 등의 서비스 접근 권한을 관리합니다[2][8]. 노드 프로비저닝을 위한 IAM 정책은 최소한의 권한(EC2:RunInstances, EC2:TerminateInstances 등)으로 제한되며, AWS Organizations의 SCP(Service Control Policy)와 연동하여 리전/인스턴스 유형 제한 정책을 적용할 수 있습니다.

5.2 노드 격리 정책

보안 강화를 위해 Karpenter가 생성한 노드에는 기본적으로 EKS 최적화 AMI가 적용되며[3], SSM 에이전트가 사전 설치된 상태로 배포됩니다. 노드 접근 제어는 Security Group 조건부 부여 방식을 통해 구현되며, 네트워크 정책은 Calico나 Cilium 같은 CNI 플러그인과 연동하여 마이크로세그멘테이션을 강화합니다[12].

결론

Karpenter는 현대적 클라우드 네이티브 환경의 요구사항을 충족시키기 위해 설계된 차세대 오토스케일링 솔루션입니다. 그룹리스 아키텍처와 JIT 프로비저닝 메커니즘을 통해 기존 Cluster Autoscaler 대비 3배 이상의 확장 속도 개선을 실현했으며[4][8], Spot 인스턴스와의 깊은 통합을 통해 컴퓨팅 비용을 최대 90% 절감할 수 있습니다[1][10]. 다만 운영 복잡도 증가와 멀티 클라우드 지원 미비 등의 과제는 여전히 존재하지만, 지속적인 커뮤니티 기여와 AWS의 적극적인 투자로 기술 성숙도가 빠르게 개선되고 있습니다.

향후 과제로는 하이브리드 클라우드 환경 지원 확대, GPU 인스턴스의 동적 프로비저닝 최적화, 서버리스 컴퓨팅 서비스(예: AWS Fargate)와의 통합 강화 등이 예상됩니다. 클라우드 운영팀은 Karpenter의 도입을 통해 인프라 관리 부담을 획기적으로 감소시키는 동시에 애플리케이션의 안정성과 비용 효율성을 동시에 개선할 수 있을 것으로 기대됩니다.
