RDS

Autoscale

When RDS storage autoscaling scales up the storage size, it increases the storage in increments of either 5GB or 10% of the currently allocated storage size, whichever is greater.

Some key points about RDS storage autoscaling:

  1. After manually increasing the storage size, there is a storage optimization process that takes 6 hours to complete before any further modifications can be made.

  2. During this optimization period, even if the free storage drops below 10%, autoscaling cannot trigger another increase.

  3. The free storage percentage reported may remain low until after the optimization completes.

  4. To avoid reaching a storage-full state, you can monitor free storage using CloudWatch and set alarms. Turning on autoscaling also helps handle unpredictable workloads.

  5. For more details on storage autoscaling, monitoring and troubleshooting storage issues, refer to the AWS documentation on RDS and CloudWatch.

Replication

The replication time for an RDS database between Availability Zones (AZs) within the same region depends on the amount of data and database write workload. Here are some key factors:

  1. For small or medium databases, replication across AZs usually completes within a few minutes.

  2. For very large production databases, it may take 30 minutes or more to complete, depending on the IOPS provisioned.

  3. The replication is asynchronous to provide low latency for database writes. So there may be some lag between the primary and standby database.

  4. You can monitor the replication lag in the RDS console under the “Performance” section for the database. AWS also provides CloudWatch metrics for replication lag.

  5. In rare cases, if the database has an unusually high write workload, the replication may take longer.

  6. Factors like network issues could also potentially impact the replication time.

I’d recommend checking the AWS documentation for more details on RDS replication, performance insights, and best practices to optimize replication times. Let me know if you have any other questions!

Read Replica vs Standby Replica

The main differences between a read replica and standby replica on Amazon RDS are:

  1. A read replica is used for scaling reads across multiple database instances in different Availability Zones or regions. All read replicas are accessible and can handle read queries to improve performance and
    availability.

  2. A standby replica is used for high availability of the primary database instance. It is maintained asynchronously behind the scenes within the same region and Availability Zone as the primary. The standby is automatically promoted if the primary fails.

  3. Database upgrades are applied to the primary instance first, and then replicated to the read replicas. For a standby replica, upgrades are applied directly by Amazon RDS for high availability of the primary
    instance.

  4. Read replicas allow for cross-region replication whereas standby replicas are always within the same region and Availability Zone for high availability of the primary in case of AZ failures.

  5. You can manually promote a read replica to become a standalone database instance. A standby is automatically managed and promoted by Amazon RDS for high availability of the primary.

Standby Replica

A standby replica on Amazon RDS does not work synchronously. Here are some key points about how standby replicas work:

  • The standby replica is maintained asynchronously behind the scenes within the same region and Availability Zone as the primary database instance.

  • Updates to the primary are replicated to the standby, but there may be some lag between the primary and standby.

  • In the event of a failure of the primary instance, AWS will automatically promote the standby replica to become the new primary so that database operations can resume quickly.

  • You cannot directly access the standby replica - it exists purely for high availability of the primary instance. Only the primary can handle read and write operations.

  • Asynchronous replication is used to minimize latency for writes to the primary database versus using synchronous replication which would introduce additional latency.

You are not charged separately for the standby replica on Amazon RDS. The standby is automatically maintained by AWS to provide high availability for the primary database
instance. You are only charged for the primary database instance based on:

  1. Database instance type (e.g. db.t3.micro) and number of hours it is running

  2. Storage space provisioned for the database

  3. IOPS provisioned if using a Provisioned IOPS storage

  4. Data transfer fees if accessing the database from outside the AWS network

The standby replica is maintained behind the scenes by AWS to enable fast failover if the primary instance fails. It exists solely to provide high availability and you cannot directly access the standby.

For exact pricing details of Amazon RDS, please refer to the AWS documentation or pricing pages. Pricing varies based on database engine, instance type, region etc. AWS also offers reserved instances for
discounted hourly rates with 1-3 year commitments.
