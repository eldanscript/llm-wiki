Session - GameLift

Introduce Session @October 17, 2024

Customer Workload information - Pre QnA via email

1. 게임에 대한 간략한 소개 부탁드립니다. 이름, 장르 등과 함께 특징적인 사항을 알려주시면 될 것 같습니다.

  • 싱글/멀티가 융합된 멀티플레이 로그라이크 (최대 16인)

2. 게임의 서비스 대상 국가는 어떻게 되나요? 각 국가별 예상 사용자 규모는 어떻게 되나요? 각 서비스를 단일 서비스로 나가나요? 국가별로 나눠서 나갈 계획이신가요?

  • 현재 계획상 단일 서비스로 구성 예정입니다.

3. 게임의 아키텍처는 대략 어떻게 생각하는지 다이어그램 형태로 작성해주실 수 있을까요?  전체 아키텍처가 어렵다면, 매치메이킹, 데디케이티드 게임 서버, 백엔드 데이턴 전송과 관련된 GameLift 와 FlexMatch 와 관련된 부분의 아키텍처만으로도 충분합니다. 미팅 시 구두로 아키텍처를 설명해주셔도 괜찮습니다.

  • 아키텍처는 현재 수립중이라 미팅 시 구두로 설명 드리겠습니다.

4. 게임 백엔드, 데디케이디트 게임 서버 등에 사용하는 OS 는 어떤 건가요? 

  • 백엔드: Linux   - 데디 게임서버: Unity / Linux

5. 게임 클라이언트와 데디케이디트 게임 서버의 경우 어떤 게임 엔진을 사용 중인가요? 또는 커스텀 개발을 하시나요?

  • Unity

6. 게임 모드의 종류는 어떻게 되나요? 데디케이티드 게임 서버의 경우 프로세스 시작 시가 아니라 매치메이킹 이후에 매치의 정보를 바탕으로 게임 모드를 선정할 수 있나요?

  • 아니오

7. 각 게임 모드 별 게임 시간은 어느 정도 예상하시나요?

  • 20분 ~ 1시간

8. 각 게임 모드 별 성능 테스트는 어떻게 진행하실 예정인가요?

  • 계획 수립 예정입니다.

9. 일일 게임 사용자 수요에 따른 백엔드의 각 서비스별 스케일링은 어떻게 하실 예정인가요?

  • 아키텍처 결정 시점에 계획 수립 예정입니다.

10. 매치메이킹 대상은 어떤 기준으로 그룹화하여 매치메이킹을 진행하시나요?

  • 되도록 가까운 지역의 유저들을 그룹화 하고자 합니다.

11. 매치메이킹의 기준은 무엇으로 하시고자 하나요?

  • “레벨” 기준으로 매치메이킹 합니다.

12. 사용자가 게임 도중에 나가고 다른 사용자가 난입하는 등의 게임 시작 이후에 사용자 변화가 가능한가요?

  • 도중에 나가는 것은 가능하지만, 난입은 불가능합니다.

13. 사용자의 레이턴시 문제는 어떻게 해결하실 생각인가요? 로비를 나누나요? 매치메이킹에서 그룹화하실 생각인가요? 가속 서비스를 쓰실 예정인가요?

  • 현재 구체적인 계획이 없습니다. GameLift 베스트 프랙티스 를 참고 할 예정입니다.

14. 게임 클라이언트와 아웃게임, 인게임 등 각각의 백엔드 서비스 연결에는 어떠한 프로토콜을 쓰시나요?

  • 인게임: UDP

  • 아웃게임: websocket

15. 게임이 원활하게 진행되기 위해서는 네트워크 레이턴시가 어느 정도 선에서 보장되어야 하나요?

  • 현재 최소 보장 레이턴시 목표는 없습니다.

16. 데디케이디드 게임 서버와 다른 백엔드 서비스 (데이터베이스 연결, 로그 수집 등)의 연결은 어떻게 설계하고 계신가요?

  • GameLift 연동을 진행 하며 토폴로지를 구성 할 예정입니다.

17. 게임 백엔드 서비스의 로그 (특히 데디케이티드 게임 서버) 는 어떻게 수집하고 어디에 쓰실 예정인가요?

  • 백엔드 서비스: Kinesis 기반 Stream 서비스를 이용 할 예정입니다.

  • 데디케이티드 게임 서버: 현재 미정입니다.

18. 게임 클라이언트의 각종 정보 (레이턴시, 오류 로그 등) 는 어떻게 수집하실 생각인가요?

  • 현재 진행 예정입니다.

19. 데디케이티드 게임 서버의 크래시 정보는 어떻게 수집하실 생각인가요?

  • 현재 진행 예정입니다.

GameLift 서비스 소개

  • 세션 기반 멀티 플레이어 게임을 위한 관리형 서비스

    • 멀티 플레이어를 위한 맵 등의 동일 리소스 구축, 사용

    • 플레이어간 매치

  • Dedicated game server 적용 시 어려움

    • Auto Scaling이 어려움

    • 게임 서버 특성 상 빈번할 수 있는 크래쉬 발생 시 복구 재 시작

    • 글로벌 서비스 : 유저는 어떻게 그룹화, Match Making 구축은 어떻게?

  • 주요 Features

    • Game server provisoning

    • Low latency

    • HA : Multi region support

    • Flexibility : Fleet 구성 (server instance 단위로 확장 배치), FlexMatch (Match making), FleetIQ (저렴한 비용의 인스턴스 구축에 집중)

Builds

  • 서버 프로세스에 Game Lift SDK를 연동하여 고객이 직접 빌드

    • C++, C#, Go, Unreal plugin, Unity Plugin

  • 빌드한 아티팩트를 압축 파일로 만들어 GameLift에 Upload

    • aws gamelif upload-build 사용을 권장

    • S3 upload 하고 GameLift에 지정하는 작업을 한 번에 수행

SDK 연동

  • 게임 서버 instance에 agent가 GameLift 서비스 시작

    • Process가 SDK 초기화 → ProcessReady → OnHealthCheck

  • Match making 서비스 흐름

    • onStartGameSession → ActivateGameSession → Game Client에서 connect → GameLift Service에서 AcceptPlayerSession → Game Client에서 Disconnect → GameLift Service에서 RemovePlayerSession

  • 단일 Process가 단일 GameService를 담당하도록 구현 되어 있음

Fleet

  • EC2 instance의 집합

    • instance type

    • 하나의 instance에 몇 개의 GameLift Process를 구성할 것인지 설정

  • Multi-region Fleet 구성을 통해 글로벌 배포가 가능

    • 단일 build upload로 여러 region fleet에 배포 가능 : 작업 효율성

  • Fleet Events

    • 게임 서버에서 발생하는 이벤트를 모니터링

    • Crash, SDK 상태, Timeout

    • AWS Event 서비스와 연동되어 있지 않기 때문에 pooling 방식으로 조회해야 함

    • 초기 Fleet 구성 시 상태 확인에 유용

  • Game Sessions

    • 실시간으로 session 상태 확인 기능 제공

    • Player 정보도 제공하며 고객에 따라 별도로 구축하여 사용하기도 함

  • Spot Fleet

    • Spot instance 사용하여 비용 최적화

    • Linux & Window

    • onProcessTerminate notification으로 instance의 interruption 대비

      • Dead by daylight 경우 spot instance 중단으로 인한 문제는 없었다고 함

      • spot 2개, on-demand 1개로 시작하는 것을 권장

      • generation이나 type을 다르게 하여 여러개를 구성하는 것을 권장

    • Spot 가용량 부족할 경우 on-demand instance로 전환

Scaling Option

  • Target based auto scaling

    • Service의 Process는 미리 생성되어 대기하고 있는 상태로 제공 : cold start로 인한 지연을 없도록 하기 위함

    • 활성화 되지 않음 Service Process는 buffer로 구성되며 여유을 가지도록 비율을 지정하여 사용

  • Rule based auto scaling

  • Limit 설정으로 min/max instance 수 제한

    • Multi-region의 경우 region별 다르게 설정도 가능

GameLift Anywhere

  • 고객 장비에서 GameLift 서비스를 구축

  • 고객이 직접 Anywhere fleet을 생성한 후 GameLift Fleet으로 구성 등록

  • 개발 서버를 등록하여 테스트 하는 방식으로 많이 활용 가능 : 개발자 PC에 GameLift Anywhere 구동하여 시험 진행

    • Linux의 경우 Fleet 구동 시간이 10분 정도로 줄어들긴 했지만 개발의 편의성을 위해 Anywhere가 유용

    • 개발 환경을 위한 Anywhere script 들도 많이 생성되어 공유되어 있음

Alias

  • 다른 Build version을 Alias로 연결하여 이전 version을 점차적으로 Fleet Queue에서 제거 : Blue/Green 배포처럼 사용 가능

Queue

  • 많은 Fleet들이 Queue에 존재하며 게임 세션을 적합한 Fleet에 배치

  • 사용하지 않을 수 있지만 여러 문제가 발생할 수 있음

  • Player latency를 가장 먼저 판단, next는 가격 (Spot → OnDemand) : Spot 이 없을 경우를 고려하여 on-demand fleet 구성을 권장

  • Multi location fleet 사용 권장 - 별도로 region별 fleet을 수동 구성할 필요가 없음

  • 장애 대응을 위해 backup queue 구성

  • 대기열 지연 시간 정책을 구성하여 배제하도록 함 : 사용자 경험 우선

Client

  • Backend에서 API를 사용하기 위해 사용하는 기능

  • AWS SDK 연동 사용

FlexMatch

  • MatchMaking 지원

  • 팀 구성 지원

  • Latency matching 가능 : 완화 정책도 지원

  • Match making은 다양한 구성 방식이 있어 참고하여 직접 개발 적용

GameLift Architecture

  • Backend Services

    • Lobby, 인증 등의 고객의 직접 구축 영역

    • GameLift에 Match Making 요청

  • Match Making 요청은 GameLift Queue로 들어오고 가장 적합한 Fleet으로 사용자를 배치

  • Matching된 사용자의 Instance 접속 정보를 Game client에 제공

  • Global한 match making pool이나 Region별 match making pool 구성

QnA

  • 최적의 지연 시간을 제공하는 알고리즘은?

    • AWS EC2 endpoint의 http 연결하여 리전별 latency를 측정 : heuristic하게 리전별 지연 시간 정보를 함께 queue에 전달하여 fleet을 결정

  • Match making 시스템 중 user 등급을 전달하여 matching이 가능한가?

    • match making의 json 항목에 MRR, Level, Map 등의 속성을 전달하여 판단하게 함

    • player 속성, team, 판단 기준 (근거리 등)

    • match making 구성에 대한 sample을 제공

  • Matching이 되지 않아 timeout 발생할 경우 어떻게 처리할 것인지?

    • 설정 된 난이도에 해당이 되지 않아 timeout이 발생할 경우 expansion rule을 구성하여 허용 범위를 확장하여 적용하거나

    • Timeout이 발생할 경우 다른 pool로 배치하는 처리를 추가 구현

  • 지연 시간으로 Region 선택 시 어떤 사용자를 기준으로 하는지?

    • matching pool의 사용자 평균 지연 시간을 사용

  • Matching Rule은 AWS에서 관리하여 업데이트가 되는가?

    • 고객이 직접 설정하여 변경해야 함

  • Spot Interrupt 발생 시 2분이 보장되는가?

    • 보장이 되지는 않음, 지표를 통해 확인 필요

  • Fleet instance는 고객 VPC에 생성되는가?

    • GameLift가 관리하는 VPC에서 별도로 관리됨

    • Backend와 연결하여 private 서비스를 구성 하기를 원한다면 어려움이 있을 수 있음

      • Game 결과를 S3로 저장하게 하고 경로 정보만 backend에 전달하여 backend가 처리

      • Cat Log 등은 Fleet 내부에 저장하고 일정 단위로 S3에 저장하여 동일하게 처리

      • IM의 경우 KDS를 통해 Log 스트림을 처리 예정

  • 한 instance에 하나의 process를 생성해야 하는가?

    • vCPU당 process 한 개 생성을 권장

  • vCPU당 여러 개의 process를 구성할 수 있는가?

    • 8 vCPU에 20개 이상 process 구성한 케이스도 있지만 game 특성에 따라 다름

    • 모니터링을 통해 확인이 필요

  • Process를 사전 loading하여 지원 되는데 game mode나 map등이 다르면 다른 fleet으로 만들어 놓아야 하는가?

    • 다른 fleet으로 구성하여 미리 생성하는 것을 권장

    • 동적 map을 사용할 경우 적용이 어려울 수 있으며 이 경우 Fleet IQ 사용을 권장

    • Fleet에 다양한 instance type, class를 사용하게 될 경우 alias를 통해 그룹화 하여 사용할 수 있음

  • Fleet의 process에서 session이 끝나면 process를 종료해야 하는가?

    • 재사용이 가능하지만 종료하고 재 시작하는 것을 권장하고 있음

  • Match making에서 team 분배를 조정이 가능한가?

    • Match rule set 설정을 통하여 가능 : skill, level 등에 대한 기준 수립하여 반영 필요

  • Spot instance를 사용하면서 상위 ranker는 on-demand를 제공하는 전략을 사용할 수 있는가?

    • Match maker 구성 시 on-demand fleet을 사용하도록 설정하여 가능

    • Match maker는 여러 개를 구성하고 queue는 하나로 생성하여 사용하는 것이 일반적인 패턴

  • Auto Scaling 구성 시 시간대 별 사용자 패턴을 반영하여 구성 추천을 주는 것이 있을지?

    • 제공되는 기능은 없으며 운영 상황을 모니터링하여 사용할 것을 권장

    • 초반에는 일반적으로 30% buffer 구성을 권장하며 작은 instance type을 사용하면서 buffer를 여유있게 구성하고 일부 기간 운영 결과를 바탕으로 구성을 업데이트

    • 큰 instance를 사용하여 spot로 우선 배치 하였는데 장기간 사용으로 문제가 발생하거나 interruption이 발생하는 경우는 어떻게 되는가?

      • 사용 type에 대한 spot instance에 문제가 있다면 다른 fleet을 사용하여 배치에서 제외되도록 함

      • 긴 게임 시간으로 인해 오랜 기간 사용되는 instance의 경우에는 recycle을 통해 관리 가능

    • GameLift의 다른 사용 용도는 없는지?

      • MMORPG의 경우 체험용 Lobby로 사용하는 경우가 있었으나 권장하지는 않음

      • Game Streaming 서비스에서 활용하는 경우가 있었음

    • EC2 instance에 여러 세션이 할당될 경우 port 할당 등은 어떻게 되는가?

      • 고객사가 할당 정책등을 정하고 GameLift에 지정해 주어야 함

    • 사용자 케이스를 고려할 때 적합한 구성은?

      • 작은 size로 시작하는 것을 권장 : 4x large

      • 규모가 커질 경우에는 큰 size instance를 적용하여 관리 포인트를 감소
