kubectl vs eksctl

Kubectl and eksctl are both useful tools for managing Kubernetes clusters, but each has a different purpose and usage: 1(https://medium.com/@michael_10187/kubernetes-kops-step-by-step-example-alternatives-ece60dcdcb26)

  • Kubectl is a universal command line tool for managing Kubernetes clusters. It can be used to interact with any Kubernetes cluster, whether it is provisioned on-premises, in the cloud, or using a managed service like EKS. Common tasks include deploying applications, debugging pods/services, viewing logs, and more. 2(https://aws.amazon.com/blogs/opensource/eksctl-eks-cluster-one-command/)

  • Eksctl is a specialized tool built specifically for Amazon EKS. It simplifies and automates the process of creating EKS clusters on AWS, managing the underlying infrastructure like VPCs and IAM roles. Eksctl handles the initial cluster setup and integration with AWS services in one command. 3(https://joachim8675309.medium.com/kubernetes-eks-with-eksctl-26eb7386cf8a)

  • After the EKS cluster is created with eksctl, you would use kubectl to interact with and manage that cluster on an ongoing basis. Things like application deployments, upgrades, scaling etc. are all done with kubectl.

  • Eksctl is only needed during the initial cluster creation and setup. For day to day cluster operations, the universal kubectl tool would be used instead of eksctl once the EKS cluster exists.

So in summary - use eksctl to easily create EKS clusters on AWS, and then use kubectl to operate and manage applications running on that EKS cluster going forward. Let me know if any part needs more clarification!

Cluster

Default Setting

When you run the eksctl create cluster command without specifying a nodegroup configuration in a YAML file, eksctl will provision a default managed nodegroup with a minimum of 2 nodes. 1(https://stackoverflow.com/questions/77400563)

The key things to note are:

  • A nodegroup named after the cluster name will be created, with a default instance type of t3.medium.

  • The minimum node count for the managed nodegroup will be 2, with no specific maximum set.

  • Additional configuration like desired capacity, max size etc. will use eksctl’s default values.

  • This allows you to quickly bootstrap a basic EKS cluster with nodes for development/testing purposes without needing a YAML file. 2(https://community.aws/content/2Z18R1xBAeJbKyigk6oB1mxDYPb/creating-a-eks-cluster-1-24-version-from-scratch-using-eksctl)

  • For production usage, you typically want more control over node sizing/capacity which requires specifying a nodegroup resource in a cluster YAML file.

So in summary - running eksctl create cluster without a YAML will provision a minimum of 2 nodes in a default managed nodegroup for your EKS cluster. Let me know if you need any clarification or have additional questions!

CoreDNS

CoreDNS in Kubernetes is deployed as a pod. Some key points: 1(https://dev.to/onai254/understand-networking-in-kubernetes-3lo7)

  • CoreDNS provides DNS services to other pods in the cluster by acting as the cluster DNS server.

  • It is packaged as a Kubernetes pod specification which is scheduled and runs on the cluster just like application pods.

  • The CoreDNS pod runs a CoreDNS process internally which listens on port 53 to serve DNS queries from other pods in the cluster.

  • Kubernetes deploys one or more CoreDNS pods to provide highly available and scalable DNS services across the cluster.

  • CoreDNS pods can be managed, scaled and upgraded just like other application pods using Kubernetes APIs and controllers.

So in summary, while CoreDNS provides daemon-like DNS services, it is implemented and runs as a special application pod inside the Kubernetes cluster rather than as a standalone daemon process. Let me know if any part needs more explanation!

Ingress

When using Ingress in Kubernetes, you do need to have a Service object defined for each backend that the Ingress routes traffic to. Here are a few key points: 1(https://yuminlee2.medium.com/kubernetes-ingress-a7d29927fa15)

  • The Ingress controller (like Nginx or Traefik) needs to know how to route traffic to the backend workloads/pods. It does this by querying the Service objects.

  • Each path defined in the Ingress spec needs to reference an existing Service by name. So the Service needs to exist before the Ingress can be created.

  • The Service provides load balancing, DNS lookups etc for the pods in its selector. So without a Service, there would be no way for the Ingress controller to know how to reach the pods.

  • You can define multiple paths in an Ingress to route to different Services. But each Service being routed to must already exist.

So in summary - while Ingress allows defining routing rules independently of Services, you cannot use Ingress without having the corresponding Service objects defined first. The Services provide the bridge for Ingress to locate and reach the actual pods/backends.

Ingress vs ALB

There are a few key differences between Kubernetes Ingress resources and Application Load Balancers (ALB) on AWS: 1(https://docs.aws.amazon.com/eks/latest/userguide/alb-ingress.html)

  • Ingress is a Kubernetes object that manages external access to Kubernetes services, providing load balancing, SSL termination and name-based routing. It is implemented by an Ingress controller like Nginx.

  • An ALB is a network load balancer managed by AWS that operates at the application layer (layer 7) of the OSI model. It can handle HTTP and HTTPS traffic. 2(https://aws.amazon.com/blogs/containers/a-deeper-look-at-ingress-sharing-and-target-group-binding-in-aws-load-balancer-controller/)

  • Ingress provides routing at the Kubernetes API level, while ALB provides routing at the networking level in AWS.

  • When using an ALB with EKS, the AWS Load Balancer Controller integrates Kubernetes Ingresses with ALBs behind the scenes. This allows Ingresses to dynamically configure ALBs.

  • ALBs can also be used independently without Ingress to load balance EC2 instances or IP addresses. Ingress always requires backing Kubernetes services.

  • Features like path-based routing, SSL offloading and load balancing are provided by both - but Ingress defines them at the Kubernetes level while ALB implements them at the AWS networking level.

So in summary - Ingress is a Kubernetes abstraction while ALB is an AWS networking load balancer, but they work together when using the AWS Load Balancer Controller with EKS.

No, the AWS Load Balancer Controller does not replace the Kubernetes Ingress controller. Both work together to provide load balancing capabilities for Kubernetes applications on EKS. 1(https://docs.aws.amazon.com/eks/latest/userguide/aws-load-balancer-controller.html)

The Ingress controller is a Kubernetes component that manages external access to Kubernetes services. It provides load balancing, SSL termination and name-based routing for incoming traffic. 2(https://community.aws/tutorials/navigating-amazon-eks/eks-cluster-load-balancer-ipv6)

The AWS Load Balancer Controller integrates the Kubernetes Ingress resource with Application Load Balancers (ALBs) in AWS. It automates the creation and management of ALBs when Ingresses are created or modified. 3(https://aws.amazon.com/blogs/containers/a-deeper-look-at-ingress-sharing-and-target-group-binding-in-aws-load-balancer-controller/)

So the Ingress controller defines the load balancing rules and configuration at the Kubernetes API level, while the AWS Load Balancer Controller implements those rules by dynamically configuring ALBs in AWS.

The Ingress controller is still required to define the routing rules, while the AWS Load Balancer Controller handles the integration with AWS to provision and manage the actual load balancers behind the scenes. They work together to provide load balancing for applications on EKS clusters.

There are some key differences between role-based access control (RBAC) in Kubernetes and Identity and Access Management (IAM) roles in AWS: 1(https://aws.amazon.com/eks/features/)

  • RBAC in Kubernetes controls access within the Kubernetes cluster only. It defines permissions for users and services to access and manage Kubernetes API resources like pods, deployments, etc. 2(https://docs.aws.amazon.com/eks/latest/userguide/access-policies.html)

  • IAM roles in AWS control access to AWS services and resources outside the Kubernetes cluster, like EC2 instances, S3 buckets, Lambda functions etc.

  • Kubernetes RBAC roles are defined within the cluster using Role and ClusterRole objects. IAM roles are defined in AWS IAM and attached to AWS principals like users, groups or EC2 instances.

  • When using EKS, IAM roles are associated with Kubernetes RBAC roles through the aws-auth ConfigMap. This maps IAM principals to users and groups in Kubernetes for cross-service access control.

  • Kubernetes RBAC roles are scoped to namespaces by default. IAM roles have cluster-wide scope in EKS for all namespaces. Cross-namespace access in Kubernetes requires additional configuration.

So in summary - RBAC controls access within the Kubernetes cluster API resources, while IAM roles manage access to AWS services and resources outside the cluster through principals like users and EC2 instances. The two systems integrate on EKS for a unified access model.

No, a Network Load Balancer (NLB) does not require an Ingress resource to route traffic to Kubernetes services. An NLB can be used on its own to load balance traffic at the transport layer (layer 4) without needing Ingress. 1(https://repost.aws/questions/QUh_s9ZuRPTj-SM3eAWQjbyw/how-to-make-eks-ingress-with-alb-partly-private)

Some key points:

  • NLB is a layer 4 load balancer that routes traffic based on IP addresses and ports only. It operates at the transport layer independently of Ingress. 2(https://repost.aws/questions/QUUUSB2hICQs6lY84kfNoKcQ/connect-nlb-with-alb-security-group)

  • Ingress is a layer 7 load balancer that routes traffic based on hostnames and paths. It requires Kubernetes Services to route to pods.

  • When using just an NLB, it can route directly to pod IPs/ports without needing Ingress or Services in between.

  • However, Ingress provides additional features like hostname-based routing, SSL termination etc. So NLB is often used with Ingress for full functionality.

  • The AWS Load Balancer Controller can integrate NLB with Ingress resources automatically when both are used together with EKS.

So in summary, while Ingress isn’t strictly required, NLB alone can load balance traffic to pods without Ingress. Ingress provides additional routing rules when needed.
