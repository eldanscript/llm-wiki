Performance 향상 검토

네, Lambda 함수에서 동시성(concurrency) 설정을 통해 접속자가 몰리는 경우에 대응할 수 있습니다. 하지만 이 설정만으로는 서비스 대응 지연을 완전히 해결하기 어려울 수 있습니다. 다음과 같은 방법들을 고려해 볼 수 있습니다:

  1. 동시성 제한 설정:
    Lambda 함수의 동시성 제한을 설정하여 동시에 실행되는 함수 인스턴스의 수를 제어할 수 있습니다. 이를 통해 과도한 리소스 사용을 방지하고 안정성을 확보할 수 있습니다.

  2. 예약된 동시성:
    특정 Lambda 함수에 대해 예약된 동시성을 설정하여 해당 함수가 항상 일정 수준의 동시 실행 용량을 확보하도록 할 수 있습니다.

  3. 비동기 호출:
    Lambda 함수를 비동기적으로 호출하여 즉시 응답을 반환하고, 실제 처리는 백그라운드에서 진행하도록 할 수 있습니다.

  4. 큐 시스템 활용:
    SQS(Simple Queue Service)와 같은 큐 시스템을 사용하여 요청을 버퍼링하고 순차적으로 처리할 수 있습니다.

  5. API Gateway와 통합:
    API Gateway의 스로틀링 기능을 활용하여 과도한 요청을 제한할 수 있습니다.

  6. 오토 스케일링:
    Lambda는 기본적으로 오토 스케일링을 지원하지만, 필요에 따라 다른 AWS 서비스와 결합하여 더 세밀한 스케일링 전략을 구현할 수 있습니다.

  7. 성능 최적화:
    Lambda 함수 자체의 성능을 최적화하여 처리 시간을 단축시키는 것도 중요합니다.

  8. 캐싱 전략:
    자주 요청되는 데이터에 대해 캐싱을 적용하여 반복적인 계산이나 데이터베이스 쿼리를 줄일 수 있습니다.

이러한 방법들을 조합하여 사용하면 접속자가 몰리는 상황에서도 보다 효과적으로 서비스 대응 지연을 관리할 수 있습니다. 다만, 완벽한 해결책은 없으며 애플리케이션의 특성과 요구사항에 맞춰 적절한 전략을 선택해야 합니다.

Amazon Bedrock의 LLM(Large Language Model) 사용 시 과도한 요청으로 인한 비용 증가를 방지하기 위해 다음과 같은 방법들을 고려할 수 있습니다:

  1. 요청 제한 (Rate Limiting):

    • API Gateway나 애플리케이션 레벨에서 요청 제한을 구현하여 단위 시간당 처리할 수 있는 요청 수를 제한합니다.

    • 이를 통해 갑작스러운 트래픽 증가로 인한 과도한 API 호출을 방지할 수 있습니다.

  2. 토큰 버킷 알고리즘:

    • 각 사용자나 애플리케이션에 대해 토큰 버킷 알고리즘을 구현하여 일정 시간 동안 사용할 수 있는 요청의 총량을 제한합니다.

  3. 캐싱 전략:

    • 자주 요청되는 쿼리에 대한 결과를 캐시하여 중복 요청을 줄입니다.

    • Amazon ElastiCache나 DynamoDB와 같은 서비스를 활용할 수 있습니다.

  4. 배치 처리:

    • 가능한 경우, 여러 개의 작은 요청을 모아 하나의 큰 배치 요청으로 처리합니다.

    • 이는 API 호출 횟수를 줄이고 효율성을 높일 수 있습니다.

  5. 비용 모니터링 및 알림:

    • AWS Budgets를 설정하여 Bedrock 사용량과 비용을 모니터링합니다.

    • 특정 임계값을 초과할 경우 알림을 받도록 설정합니다.

  6. 사용량 분석 및 최적화:

    • CloudWatch 로그와 메트릭을 활용하여 사용 패턴을 분석합니다.

    • 불필요하거나 중복되는 요청을 식별하고 최적화합니다.

  7. 모델 선택 최적화:

    • 작업에 적합한 가장 효율적인 모델을 선택합니다.

    • 더 작은 모델로도 충분한 경우, 큰 모델 대신 작은 모델을 사용하여 비용을 절감합니다.

  8. 프롬프트 엔지니어링:

    • 효율적인 프롬프트를 설계하여 불필요한 토큰 사용을 줄입니다.

    • 명확하고 간결한 지시를 통해 모델의 출력을 최적화합니다.

  9. 사용자 인증 및 권한 관리:

    • 인증된 사용자만 API에 접근할 수 있도록 합니다.

    • 사용자별로 사용량 제한을 설정합니다.

  10. 오프라인 처리:

    • 실시간 처리가 필요하지 않은 작업의 경우, 배치 작업으로 처리하여 피크 시간대의 부하를 분산시킵니다.

  11. 요청 필터링:

    • 불필요하거나 중복된 요청을 필터링하여 처리하지 않도록 합니다.

  12. 사용량 예측 및 계획:

    • 과거 사용 패턴을 분석하여 future 사용량을 예측합니다.

    • 예측된 사용량에 기반하여 리소스와 비용을 계획합니다.

이러한 방법들을 조합하여 구현하면 Amazon Bedrock LLM 사용 시 과도한 비용 발생을 효과적으로 관리할 수 있습니다. 또한, 정기적인 모니터링과 최적화를 통해 장기적으로 비용을 절감할 수 있습니다.

DynamoDB를 Provisioned 모드로 사용할 때 사용량 급증에 따른 용량 설정은 매우 중요합니다. 적절한 용량 설정을 하지 않으면 성능 저하나 불필요한 비용 발생의 원인이 될 수 있습니다. 다음은 확인해야 할 주요 사항들입니다:

  1. 읽기/쓰기 용량 단위 모니터링:

    • CloudWatch를 통해 ConsumedReadCapacityUnits와 ConsumedWriteCapacityUnits 메트릭을 모니터링합니다.

    • 프로비저닝된 용량에 근접하거나 초과하는 경우를 주시합니다.

  2. 스로틀링 이벤트 확인:

    • ReadThrottleEvents와 WriteThrottleEvents 메트릭을 모니터링합니다.

    • 이 값들이 증가하면 현재 용량이 부족하다는 신호입니다.

  3. 액세스 패턴 분석:

    • 시간대별, 요일별 사용 패턴을 분석합니다.

    • 피크 시간대와 평균 사용량을 파악합니다.

  4. 항목 크기 및 분포:

    • 저장되는 항목의 평균 크기와 크기 분포를 확인합니다.

    • 특정 파티션 키에 데이터가 집중되는지 확인합니다.

  5. 쿼리 성능:

    • 자주 실행되는 쿼리의 성능을 모니터링합니다.

    • 느린 쿼리가 있다면 인덱스 추가 등의 최적화를 고려합니다.

  6. Auto Scaling 설정:

    • Auto Scaling을 활성화하여 동적으로 용량을 조정할 수 있습니다.

    • 적절한 최소/최대 용량과 목표 사용률을 설정합니다.

  7. 버스트 용량 활용:

    • 일시적인 트래픽 증가에 대비해 버스트 용량을 효과적으로 활용합니다.

  8. 예약 용량 고려:

    • 예측 가능한 워크로드의 경우, 예약 용량을 구매하여 비용을 절감할 수 있습니다.

  9. TTL(Time to Live) 설정:

    • 오래된 데이터를 자동으로 삭제하여 스토리지 비용을 절감하고 성능을 유지합니다.

  10. 글로벌 테이블 고려:

    • 지리적으로 분산된 사용자가 많다면 글로벌 테이블을 고려하여 지연 시간을 줄입니다.

  11. DAX(DynamoDB Accelerator) 사용 검토:

    • 읽기 작업이 많은 경우 DAX를 사용하여 캐싱을 통해 성능을 향상시킬 수 있습니다.

  12. 비용 최적화:

    • AWS Cost Explorer를 사용하여 DynamoDB 관련 비용을 분석하고 최적화 기회를 찾습니다.

  13. 애플리케이션 로직 검토:

    • 애플리케이션에서 불필요한 읽기/쓰기 작업을 하고 있지 않은지 검토합니다.

  14. 주기적인 용량 리뷰:

    • 정기적으로 용량 설정을 리뷰하고 필요에 따라 조정합니다.

이러한 요소들을 종합적으로 고려하여 DynamoDB의 용량을 설정하고 조정해야 합니다. 사용량 급증에 대비하여 Auto Scaling을 설정하고, 지속적인 모니터링과 최적화를 통해 성능과 비용 효율성을 유지하는 것이 중요합니다.

1 DCU(DynamoDB Capacity Unit)의 용량은 읽기와 쓰기 작업에 따라 다르게 적용됩니다. 2023년 4월 기준으로 제공된 정보를 바탕으로 설명드리겠습니다:

  1. 쓰기 용량 (Write Capacity Unit, WCU):

    • 1 WCU = 초당 1KB 크기의 항목에 대한 1회 쓰기 작업

    • 즉, 1 DCU는 초당 1KB 크기의 항목에 대해 1회의 쓰기 작업을 수행할 수 있습니다.

  2. 읽기 용량 (Read Capacity Unit, RCU):

    • 강력히 일관된 읽기(Strongly Consistent Read)의 경우:
      1 RCU = 초당 4KB 크기의 항목에 대한 1회 읽기 작업

    • 최종적 일관된 읽기(Eventually Consistent Read)의 경우:
      1 RCU = 초당 8KB 크기의 항목에 대한 2회 읽기 작업

    따라서, 1 DCU는 다음과 같은 읽기 작업을 수행할 수 있습니다:

    • 강력히 일관된 읽기: 초당 4KB 크기의 항목에 대해 1회 읽기

    • 최종적 일관된 읽기: 초당 8KB 크기의 항목에 대해 2회 읽기

주의사항:

  • 항목 크기가 이보다 크거나 작을 경우, 필요한 용량 단위는 비례하여 조정됩니다.

  • 예를 들어, 6KB 크기의 항목을 쓰려면 6 WCU가 필요합니다.

  • 트랜잭션 읽기/쓰기 작업의 경우 일반 작업의 2배의 용량이 필요합니다.

이러한 용량 단위 개념을 이해하고 적절히 프로비저닝하는 것이 DynamoDB의 성능 관리와 비용 최적화에 중요합니다. 실제 애플리케이션의 사용 패턴과 데이터 크기를 고려하여 필요한 DCU를 산정해야 합니다.

네, 맞습니다. Amazon Bedrock의 Knowledge Base에 대한 기본 API 요청 제한(throttling limit)은 초당 5회(5 RPM, Requests Per Minute)로 설정되어 있습니다. 이 제한은 2023년 말 기준 정보이며, AWS의 정책 변경에 따라 달라질 수 있습니다.

이 제한으로 인해 사용량이 많아질 경우 응답 속도 저하나 요청 실패가 발생할 수 있습니다. 이를 해결하기 위한 몇 가지 방법을 제안드리겠습니다:

  1. AWS 지원팀에 문의:

    • AWS Enterprise 또는 Business 지원 계획이 있다면, AWS 지원팀에 연락하여 제한 증가를 요청할 수 있습니다.

    • 일반적으로 AWS는 고객의 사용 사례와 필요성을 검토한 후 제한을 조정해줄 수 있습니다.

  2. 캐싱 구현:

    • 자주 요청되는 쿼리에 대한 응답을 캐시하여 Knowledge Base API 호출을 줄입니다.

    • Amazon ElastiCache나 DynamoDB를 사용하여 효과적인 캐싱 계층을 구현할 수 있습니다.

  3. 요청 큐잉:

    • 요청을 큐에 넣고 처리하는 방식을 구현합니다.

    • Amazon SQS를 사용하여 요청을 버퍼링하고, 제한에 맞춰 처리할 수 있습니다.

  4. 클라이언트 측 스로틀링:

    • 애플리케이션 레벨에서 요청 속도를 제한하여 API 제한을 초과하지 않도록 합니다.

    • 토큰 버킷 알고리즘 등을 사용하여 구현할 수 있습니다.

  5. 배치 처리:

    • 가능한 경우, 여러 개의 작은 요청을 모아 하나의 큰 요청으로 처리합니다.

    • 이는 API 호출 횟수를 줄이는 데 도움이 될 수 있습니다.

  6. 비동기 처리:

    • 사용자 요청을 즉시 처리하지 않고 백그라운드에서 처리하는 방식을 고려합니다.

    • 사용자에게는 요청이 접수되었다는 응답을 주고, 실제 처리는 비동기적으로 수행합니다.

  7. 로드 밸런싱:

    • 여러 Knowledge Base 인스턴스를 사용하여 부하를 분산시킵니다.

    • 각 인스턴스에 대해 별도의 API 제한이 적용될 수 있습니다.

  8. 우선순위 큐:

    • 중요한 요청에 우선순위를 부여하여 처리합니다.

    • 덜 중요한 요청은 나중에 처리하거나 캐시된 결과를 사용합니다.

  9. 오프라인 처리:

    • 실시간 처리가 필요하지 않은 작업의 경우, 배치 작업으로 처리하여 피크 시간대의 부하를 분산시킵니다.

  10. 모니터링 및 최적화:

    • CloudWatch를 사용하여 API 사용량을 모니터링하고, 병목 현상을 식별합니다.

    • 사용 패턴을 분석하여 지속적으로 최적화합니다.

이러한 방법들을 조합하여 사용하면 API 제한으로 인한 성능 저하 문제를 상당 부분 해결할 수 있습니다. 또한, AWS의 정책 변경이나 새로운 기능 출시를 주시하며, 더 나은 해결책이 제공되는지 지속적으로 확인하는 것이 좋습니다.

Amazon Bedrock Knowledge Base의 응답 성능 향상에 대한 AWS 공식 문서나 기술 블로그는 2023년 4월 기준으로 제한적이었습니다. Bedrock이 비교적 새로운 서비스이기 때문에, 시간이 지남에 따라 더 많은 자료가 제공될 것으로 예상됩니다.

그러나 일반적인 AWS 서비스 최적화와 AI/ML 워크로드 관리에 대한 유용한 리소스들이 있습니다. 이들을 참고하여 Bedrock Knowledge Base의 성능 향상에 적용할 수 있는 아이디어를 얻을 수 있습니다:

  1. AWS Bedrock 공식 문서:

    • https://docs.aws.amazon.com/bedrock/

    • 기본적인 사용 방법과 모범 사례를 제공합니다.

  2. AWS AI/ML 블로그:

    • https://aws.amazon.com/blogs/machine-learning/

    • 최신 AI/ML 관련 기술과 사례 연구를 다룹니다.

  3. AWS 아키텍처 센터:

    • https://aws.amazon.com/architecture/

    • 다양한 워크로드에 대한 참조 아키텍처를 제공합니다.

  4. AWS Well-Architected Framework:

    • https://aws.amazon.com/architecture/well-architected/

    • 성능 효율성을 포함한 5가지 핵심 요소를 다룹니다.

  5. AWS re:Invent 세션:

    • https://reinvent.awsevents.com/

    • Bedrock 관련 세션을 검색하여 최신 정보와 사례를 확인할 수 있습니다.

  6. AWS 파트너 네트워크 블로그:

    • https://aws.amazon.com/blogs/apn/

    • AWS 파트너들의 구현 사례와 인사이트를 제공합니다.

  7. AWS 솔루션 라이브러리:

    • https://aws.amazon.com/solutions/

    • 다양한 워크로드에 대한 최적화된 솔루션을 제공합니다.

  8. AWS Compute Blog:

    • https://aws.amazon.com/blogs/compute/

    • 서버리스 및 컴퓨팅 최적화 관련 정보를 제공합니다.

이러한 리소스들을 정기적으로 확인하면서, Bedrock과 Knowledge Base에 특화된 성능 최적화 가이드가 발표되는지 주시하는 것이 좋습니다. 또한, AWS 지원팀이나 솔루션 아키텍트와 직접 상담하여 구체적인 사용 사례에 대한 조언을 받는 것도 도움이 될 수 있습니다.

API Gateway와 SQS를 사용하여 Amazon Bedrock Knowledge Base의 응답 속도를 안정적으로 유지하기 위한 구성 방법을 설명드리겠습니다:

  1. 전체 아키텍처 개요:
    API Gateway -> Lambda -> SQS -> Lambda -> Bedrock Knowledge Base

  2. 상세 구성:

    a. API Gateway 설정:

    • REST API 또는 HTTP API를 생성합니다.

    • 요청을 처리할 Lambda 함수와 연결합니다.

    • 필요에 따라 사용량 계획(Usage Plans)을 설정하여 클라이언트별 제한을 관리합니다.

    b. 첫 번째 Lambda 함수 (요청 처리):

    • 클라이언트 요청을 받아 유효성을 검사합니다.

    • 요청 데이터를 SQS 큐에 전송합니다.

    • 클라이언트에게 요청이 접수되었다는 응답과 함께 요청 ID를 반환합니다.

    c. SQS 큐 설정:

    • 표준 큐를 생성합니다 (처리 순서가 중요하다면 FIFO 큐 고려).

    • 메시지 보존 기간, 가시성 타임아웃 등을 적절히 설정합니다.

    d. 두 번째 Lambda 함수 (큐 처리):

    • SQS 큐에서 메시지를 폴링합니다.

    • Bedrock Knowledge Base API를 호출하여 실제 쿼리를 처리합니다.

    • 처리 결과를 데이터베이스(예: DynamoDB)에 저장합니다.

    e. 결과 조회 API:

    • 클라이언트가 요청 ID로 처리 결과를 조회할 수 있는 별도의 API 엔드포인트를 구현합니다.

  3. 구현 세부 사항:

    a. 비동기 처리:

    • 클라이언트 요청을 즉시 SQS로 전달하고 응답을 반환하여 빠른 응답 시간을 유지합니다.

    b. 배치 처리:

    • SQS에서 메시지를 배치로 처리하여 Bedrock API 호출 횟수를 최적화합니다.

    c. 재시도 로직:

    • SQS의 가시성 타임아웃과 재드라이브 큐를 활용하여 실패한 요청을 관리합니다.

    d. 캐싱:

    • API Gateway에서 캐싱을 활성화하여 동일한 요청에 대한 응답 속도를 향상시킵니다.

    • 결과 데이터베이스 앞에 ElastiCache를 두어 빈번한 조회 요청을 최적화합니다.

    e. 오토 스케일링:

    • Lambda 함수의 동시성 설정을 조정하여 부하에 따라 자동으로 확장되도록 합니다.

    f. 모니터링 및 알람:

    • CloudWatch를 사용하여 전체 파이프라인의 성능을 모니터링합니다.

    • SQS 큐 길이, Lambda 실행 시간, API Gateway 지연 시간 등에 대한 알람을 설정합니다.

  4. 최적화 전략:

    a. 우선순위 처리:

    • 중요도에 따라 여러 SQS 큐를 사용하여 우선순위별로 처리합니다.

    b. 동적 폴링:

    • 큐의 부하에 따라 Lambda 함수의 폴링 빈도를 조절합니다.

    c. 예측적 스케일링:

    • 과거 사용 패턴을 분석하여 예상 부하에 맞춰 사전에 리소스를 확장합니다.

    d. 결과 캐싱:

    • 자주 요청되는 쿼리 결과를 캐시하여 Bedrock API 호출을 줄입니다.

이러한 구성을 통해 API Gateway와 SQS를 활용하여 Bedrock Knowledge Base의 응답 속도를 안정적으로 유지하면서, 동시에 시스템의 확장성과 안정성을 확보할 수 있습니다. 실제 구현 시에는 워크로드의 특성과 요구사항에 맞게 세부적인 조정이 필요할 수 있습니다.

API Gateway의 Usage Plan은 API 사용을 제어하고 모니터링하는 강력한 기능입니다. 이를 통해 API 소비자의 액세스를 관리하고, 사용량을 제한하며, API 키를 생성할 수 있습니다. 다음은 Usage Plan에 대한 자세한 설명입니다:

  1. 주요 기능:

    • API 키 관리

    • 스로틀링 제한 설정

    • 할당량 관리

    • 사용량 모니터링

  2. API 키:

    • 각 클라이언트에 고유한 API 키를 발급합니다.

    • API 키를 통해 클라이언트를 식별하고 사용량을 추적합니다.

    • 여러 Usage Plan에 하나의 API 키를 연결할 수 있습니다.

  3. 스로틀링 제한:

    • 초당 요청 수(requests per second, RPS)를 제한합니다.

    • 버스트(일시적 급증) 제한을 설정할 수 있습니다.

    • API, 스테이지, 메소드 수준에서 제한을 설정할 수 있습니다.

  4. 할당량:

    • 특정 기간 동안의 총 API 호출 수를 제한합니다.

    • 일, 주, 월 단위로 설정 가능합니다.

    • 할당량 초과 시 추가 요청을 거부합니다.

  5. 모니터링:

    • CloudWatch와 통합되어 사용량 메트릭을 제공합니다.

    • API 키별, 메소드별 사용량을 추적할 수 있습니다.

  6. 설정 방법:

    • AWS 콘솔, CLI, 또는 SDK를 통해 설정 가능합니다.

    • API 생성 후 “Usage Plans” 섹션에서 구성합니다.

  7. 단계별 설정:
    a. Usage Plan 생성
    b. 스로틀링 및 할당량 설정
    c. API 스테이지 연결
    d. API 키 생성 및 연결

  8. 고급 기능:

    • 여러 API 스테이지를 하나의 Usage Plan에 연결 가능

    • 동적 스로틀링을 위한 토큰 버킷 알고리즘 사용

    • 사용자 지정 헤더를 통한 API 키 전달 지원

  9. 사용 사례:

    • 프리미엄/기본 티어 API 액세스 관리

    • 파트너별 API 사용량 제한 및 모니터링

    • 무료 평가판 사용자 관리

  10. 모범 사례:

    • API 키를 안전하게 관리하고 정기적으로 순환

    • 적절한 스로틀링 제한을 설정하여 API 과부하 방지

    • 정기적으로 사용량을 모니터링하고 분석

  11. 제한 사항:

    • HTTP API에는 현재 Usage Plan을 직접 적용할 수 없음

    • 일부 고급 인증 방식(예: OAuth)과 함께 사용 시 추가 구성 필요

  12. 비용:

    • Usage Plan 자체에 대한 추가 비용은 없지만, API 호출 및 데이터 전송에 대한 일반적인 API Gateway 요금이 적용됩니다.

Usage Plan을 효과적으로 활용하면 API의 안정성을 높이고, 비용을 관리하며, 다양한 고객 요구사항에 맞는 맞춤형 API 액세스 정책을 구현할 수 있습니다. 특히 Amazon Bedrock Knowledge Base와 같은 리소스 집약적인 서비스를 사용할 때 Usage Plan은 과도한 사용을 방지하고 공정한 리소스 분배를 보장하는 데 매우 유용합니다.

API Gateway의 HTTP API 타입에서는 안타깝게도 Usage Plan을 통한 rate limiting을 직접 사용할 수 없습니다. Usage Plan은 REST API 타입에서만 지원되는 기능입니다.

하지만 HTTP API에서도 rate limiting을 구현할 수 있는 몇 가지 대안이 있습니다:

  1. AWS WAF (Web Application Firewall) 사용:

    • HTTP API와 통합하여 rate limiting을 구현할 수 있습니다.

    • IP 주소 기반의 rate limiting 규칙을 설정할 수 있습니다.

    설정 방법:

    1. AWS WAF 콘솔에서 새 웹 ACL 생성
2. Rate-based rule 추가 (예: 5분당 100개 요청으로 제한)
3. API Gateway HTTP API와 웹 ACL 연결

  2. Lambda Authorizer 사용:

    • 커스텀 인증 및 권한 부여 로직을 구현합니다.

    • DynamoDB나 Redis 같은 데이터 스토어와 함께 사용하여 요청 횟수를 추적하고 제한할 수 있습니다.

  3. 백엔드 서비스에서 구현:

    • API Gateway 뒤에 있는 Lambda 함수나 EC2 인스턴스에서 rate limiting 로직을 구현합니다.

    • Redis나 DynamoDB를 사용하여 요청 횟수를 추적할 수 있습니다.

  4. Amazon CloudFront와 Lambda@Edge 사용:

    • CloudFront를 API Gateway 앞에 배치하고, Lambda@Edge를 사용하여 rate limiting을 구현합니다.

    • 이 방법은 글로벌 rate limiting이 필요할 때 유용합니다.

  5. 서드파티 API 관리 도구 사용:

    • Kong, Tyk 등의 API 관리 도구를 사용하여 rate limiting을 구현할 수 있습니다.

    • 이들 도구는 EC2 인스턴스나 EKS 클러스터에서 실행할 수 있습니다.

HTTP API에서 rate limiting을 구현할 때는 이러한 방법들 중 하나 또는 여러 개를 조합하여 사용할 수 있습니다. 선택은 애플리케이션의 요구사항, 예상 트래픽, 구현의 복잡성, 비용 등을 고려하여 결정해야 합니다.

AWS WAF를 사용하는 방법이 가장 간단하고 직접적인 해결책일 수 있지만, 더 세밀한 제어가 필요하다면 Lambda Authorizer나 백엔드 서비스에서의 구현을 고려해볼 수 있습니다.
