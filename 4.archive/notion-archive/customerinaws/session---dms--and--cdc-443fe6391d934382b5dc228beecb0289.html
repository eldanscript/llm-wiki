RDBMS의 Scalability 한계

데이터를 저장하고 분석하기 위해서 RDBMS를 사용하는 경우, 데이터가 많아지게 되면, RDBMS를 사용하기 어려워 진다.

RDBMS의 경우, 대체로 Primary-Replica 방식으로 구성되어 있고, 주로 1대의 Primary로 Write 요청을 모두 처리하고, Read 요청은 Primary와 여러 대의 Replica에서 처리

많은 양을 데이터 읽기는 Replica 추가로 대응 가능 : Scale-Out

쓰기 요청이 늘어날 경우 Primary의 물리적인 장비 사양을 높여서 대응 : Scale-Up → 무한히 Scale-Up할 수 없기 때문에 사실상 확장성에 제한

분산 파일 시스템 (S3, HDFS)은 데이터를 여러 대의 Storage Node에 나눠서 저장하고, 데이터를 조회하고 분석하는 Query 엔진이 분리

데이터 양이 늘어나거나 또는 Read/Write 부하가 늘어나는 경우에 Query 엔진과 Storage Node를 각각 Scale-Out 하는 방식으로 처리

Data Lake 구축

데이터 분석 시스템을 구축할 때, RDBMS 대신에서 분산 파일 시스템을 이용해서 많은 양의 데이터를 저장하고, 분석할 수 있도록 데이터 레이크를 사용

일반적인 데이터 레이크의 아키텍처는

CDC 데이터 (CRM, ERP 등의 RDBMS), Event Streams (Web Log, IoT 데이터) 등의 다양한 데이터를 실시간으로 수집하는 Stream Storage와

Stream Storage 데이터를 데이터 레이크에 저장하기 위한 Stream Delivery 서비스를 사용

Data Lake에 저장된 데이터를 가공해서 Data Warehouse 넣어서 비즈니스 분석을 하기도 하고,

비즈니스 목적에 맞게 가공된 데이터나 분석 결과로 Data Mart를 구축해서,

이후에 데이터 분석 또는 AI/ML과 같은 작업을 할 때 활용

RDBMS vs Distributed Object Storage

RDBMS

  • 데이터베이스의 테이블을 대체로 파일단위로 저장하고 테이블 내에 레코드는 변경 가능

  • Insert는 물론 Update, Delete 가능

  • 레코드를 Update했을 때, 업데이트 이전 버전과 업데이트 이후 버전의 레코드가
    동시에 존재하지 않고, 업데이트 이후 최신 버전의 레코드가 테이블에 존재

  • Transaction 처리가 가능

S3 (Distributed Object Storage)

  • 하나의 Object를 여러 노드에 분산해서 저장하고, 한번 저장된 Object내의 일부 데이터를 변경할 수는 없음.

  • Object내의 일부 데이터를 변경하고 싶은 경우, Object 전체를 변경

  • 불변의 Object를 저장하는 방식으로 사실상(Practically) Insert 연산만 가능

  • 전체 Object를 새로운 Object로 교체하거나, 새로운 Object를 추가해서 변경 전과 후의 버전이 동시에 존재

  • Transaction 처리가 어려움

CDC Update/Delete

PK1이라는 Primary Key를 가지고 있는 RDBMS의 레코드가 Object1.parquet 파일로 저장된 후

동일한 데이터를 RDBMS에서 업데이트 하는 경우, updated-object12.parqeut 파일로 별도로 S3에 저장

S3를 이용해서 RDBMS 처럼 Update와 Delete를 처리 하려고 할 때 가능한 방식은?

  • View Table

    • SQL statement 결과로 만들어지는 virtual table

    • 물리적으로 data를 저장하지 않음

    • 복잡한 query를 단순화 하거나

    • 데이터 접근을 제한 하거나

    • 원본 table 변경 없이 data를 특정 형식으로 표시하고자 할 때 사용 가능

  • Table Format

    • Tabular form으로 표시 되거나 저장되는 데이터 구조 혹은 layout

    • 열과 행의 데이터에 대한 물리적, 시각적 구조를 다룬다

    • 데이터를 어떻게 serialize 하거나 파일로 저장할 것 인지 다룬다

    • Schema나 Column 정의, 데이터 type, 데이터 entity 사이의 관계를 다룬다

View Table 기반 UPSERT - Merge on Read

Insert되는 데이터와 Update또는 Delete되는 데이터를 분리해서 저장

데이터를 읽을 때, Update와 Delete된 내용을 merge해서 읽는 방식으로 처리

Insert 데이터와 Update/Delete 데이터를 묶어서 View를 생성 하고 Data read 시점에 Merge-On-Read 방식으로 2개의 데이터를 읽어서 처리

Amazon Athena로 Logical View 테이블을 생성

S3 데이터를 Amazon Redshift와 같은 Data Warehouse에 Load한 후에 Materialized View를 만들어서 처리

Logical View vs Materialized View

View table 구성

  • insert 되는 데이터를 저장하는 Orginal table과

  • update 또는 delete된 데이터의 변경분을 저장하는 Delta table

  • 생성된 view를 위해서 별도의 데이터 저장 공간을 주지 않음

View table query

  • Logical view : view_table을 생성할 때 사용했던 방식으로 쿼리로 대체 → original_table과 delta_table에서 데이터를 읽는 쿼리도 대체

  • Materialzied view : 쿼리가 재작성되는 것이 아니라, view_table에 있는 데이터를 직접 읽음

  • view를 위한 별도의 데이터 저장 공간이 생성되고 view 생성 시 사용된 데이터와 별개로 저장

Logical View 단점

원본과 변경분의 데이터를 분리해서 저장할 수 있도록 아키텍처를 구성 → 복잡한 아키텍처

Merge-On-Read를 해야 하기 때문에, Read 쿼리가 복잡하

View 테이블을 관리 해야 하는 운영 부담

변경분의 데이터를 보관하고, 주기적으로 Merge & Compaction을 수행하는데 추가 비용이 발생

Read 시점에 원본과 변경분의 데이터를 merge해서 데이터를 읽기 때문에 실시간 데이터 분석 및 처리가 어려움

Materialized View 단점

원본과 변경분의 데이터를 자동으로 주기적으로 merge 해서 별도로 저장하기 때문에 Logical View 단점이 해소

지속적으로 늘어나는 데이터를 모두 Materialized View에 저장하기 어려움

Streaming Ingestion

Redshift내의 테이블들에 대해서 실시간 변경 사항을 반영해서, 데이터를 조회하고, 분석하고 싶은 경우 활용

Amazon Kinesis Data Streams 또는 MSK 에서 데이터를 읽기 위해서 Redshift 내에 Streaming Table 생성

추가 또는 변경되는 데이터를 Kinesis Data Streams 또는 MSK에 넣어주면, Redshift Streaming Table을 통해서 읽음

기존에 데이터를 저장된 Permanent Tables과 Streaming Table로 Materialized View를 생성

Materialized View에 주기적으로 자동으로 데이터를 업로드를 할 수 있도록 설정하여 실시간으로 변경된 데이터가 반영된 최신 데이터를 Materialized View를 이용해서 읽을 수 있도록 함

Merge & Compaction

S3를 이용해서 View를 생성해서, Insert와 Update/Delete를 동시에 처리하는 경우 Update또는 Delete되는 변경 데이터가 계속 증가

시간이 지날 수록, 데이터를 읽는 시점에 변경된 데이터를 읽기 위해서 아주 오래전에 변경된 시점의 데이터까지 읽어와야 하는 경우가 발생하여 Merge할 데이터가 많아져서 Merge-On-Read 성능 감소 발생

주기적으로 변경분의 데이터를 원본 데이터를 합쳐서 변경 history를 짧게 유지하는 것이 좋음

변경 history를 짧게 유지하는 경우, 원본 데이터와 merge된 변경 데이터는 삭제가 가능하기 때문에 변경분 데이터를 항상 일정한 크기로 유지 가능

Table Format

Data Lake 내의 파일들을 관리하는 방법 → S3를 마치 RDBMS 처럼 사용

분산 파일 시스템의 파일 들 내 데이터의 변경 이력을 관리

데이터가 저장된 파일 자체를 저장하는 **동시에 파일의 변경 이력을 별도로 저장**

**변경 데이터**를 원본 데이터와 **같은 위치에 저장**하고 **변경 이력을 따로 저장**

  • Git 소스 변경 관리와 동일 - 데이터를 읽을 때, Commit log을 반영해서 최신 데이터를 읽을 수 있는 방식

Transactional S3 like RDBMS

RDBMS Write

  • binlog에 먼저 변경 사항을 기록 하고 데이터베이스 테이블을 저장하는 파일에 데이터를 적고, 인덱스를 업데이트

RDBMS Read

  • 인덱스에서 읽고자 하는 데이터의 위치를 찾아서 데이터가 있는 파일에서 필요한 데이터를 읽음

Transactional S3

  • Insert, Update, Delete 데이터를 S3의 데이터 디렉터리에 저장

  • Insert, Update, Delete와 같은 변경 이력을 commit log 디렉터리에 저장

  • 데이터를 읽을 때, commit log에서 변경 이력을 확인 한 후 최신 데이터를 데이터 디렉터리에서 찾아서 전달

Open Table Format

  • Apache Hudi

  • Apache Iceberg

    • Snapshot 추적을 위한 meta data

    (1) 데이터를 Partitioning해서 저장한 경우에 Partition에 대한 정보

    (2) 데이터의 스키마 변경 추적을 위한 Schema 정보

    (3) 데이터의 저장 포맷 (Parquet 또는 AVRO)

    (4) 데이터의 저장 위치, 즉 S3의 위치 정보를 저장

    (5) 기타 데이터 관리에 필요한 통계 정보

  • Delta Lake

    • 10 commits (every 10 commits) 될 때마다 checkpoint 파일을 생성

    • 그 시점에 Delta Lake 테이블의 변경 사항들을 모아서 한번에 저장

    • checkpoint 파일만 읽어도 충분하기 때문에, Read 성능을 높일 수 있음

  • Schema evolution : dataset을 다시 쓰지 않고 구조를 변경

Debezium and AWS Database Migration Service (DMS) CDC (Change Data Capture) are both popular solutions for capturing and replicating data changes, but they cater to different needs and environments. Here’s a comparison of the two based on various aspects:

Purpose and Use Cases

Debezium is an open-source distributed platform for change data capture. It’s designed to monitor and record row-level changes in your databases so that applications can respond to data changes in real-time. Debezium is often used for data replication, data integration, and building event-driven architectures.

AWS DMS CDC is part of the AWS Database Migration Service that supports ongoing replication to keep source and target databases in sync. While it can serve similar purposes as Debezium in terms of data replication and integration, it is specifically optimized for migrating databases to AWS services and facilitating real-time replication to AWS targets.

Architecture

Debezium operates by deploying connectors for various database systems (like MySQL, PostgreSQL, MongoDB, and others) within a Kafka Connect cluster. This architecture leverages Apache Kafka’s ecosystem for scalability and fault tolerance.

AWS DMS CDC works by connecting to the source database, capturing changes, and then applying these to the target database or service. It is a managed service that abstracts much of the operational complexity and is deeply integrated with other AWS services.

Supported Databases

Debezium has a specific set of source databases it supports based on the connectors available. As of my last update, this includes popular databases like MySQL, PostgreSQL, MongoDB, SQL Server, and Oracle.

AWS DMS CDC supports a broad range of source and target databases, including but not limited to Amazon Aurora, MySQL, PostgreSQL, MariaDB, Oracle, SAP ASE, SQL Server, and MongoDB. It also supports targets like Amazon S3 for data lake scenarios.

Deployment and Management

Debezium requires setting up and managing a Kafka cluster (or using a managed Kafka service) and deploying Debezium connectors. This approach offers flexibility but requires more setup and operational effort.

AWS DMS CDC is offered as a managed service, significantly reducing the operational overhead. AWS handles the infrastructure, scaling, and maintenance. However, this ease of use comes with less flexibility compared to a self-managed solution like Debezium.

Cost

Debezium is free and open-source, but you’ll incur costs related to the infrastructure it runs on, such as Kafka clusters and the databases themselves. If you use managed services for Kafka or databases, those costs apply.

AWS DMS CDC charges are based on the compute resources used and the amount of data transferred. While the service simplifies many aspects of CDC, costs can scale with usage, especially for large-scale or high-throughput scenarios.

Scalability and Reliability

Debezium’s scalability and reliability largely depend on the underlying Kafka infrastructure. Kafka’s robustness and scalability can handle high volumes of change data, making Debezium suitable for large-scale environments.

AWS DMS CDC is designed to be highly available and scalable, with AWS managing the underlying infrastructure. The service is built to scale and handle significant workloads, providing a turnkey solution for many replication needs.

In summary, the choice between Debezium and AWS DMS CDC depends on specific project requirements, existing infrastructure, scalability needs, budget, and preference for managed services versus self-managed components. Debezium offers flexibility and is well-suited for Kafka-centric architectures, while AWS DMS CDC provides a simplified, managed solution, especially for AWS-centric migrations and integrations.
