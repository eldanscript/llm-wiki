AWS DMS

What is AWS Database Migration Service(AWS DMS)

  • 관계형 데이터베이스, 데이터 웨어하우스, NoSQL 데이터베이스 및 기타 유형의 데이터 스토어를 마이그레이션할 수 있는 클라우드 서비스

  • 복제 소프트웨어를 실행하는 AWS 클라우드의 서버

    • 소스 및 대상 연결을 생성하여 데이터를 추출할 위치와 데이터를 로드할 위치를 AWS DMS에 지시

    • 서버에서 실행되는 태스크를 예약하여 데이터를 이동

    • 테이블 및 관련 프라이머리 키가 대상에 없는 경우 이러한 항목을 생성하거나 대상 테이블을 직접 생성

How to Migrate

  • 소스 데이터 인프라 검색 : DMS Fleet Advisor

    • On-prem or other cloud Microsoft SQL Server, MySQL, Oracle 및 PostgreSQL

  • 대상 엔진으로 변환 : DMS Schema Conversion

    • 소스 스키마를 자동으로 평가한 후 새로운 대상 엔진으로 변환

    • AWS Schema Conversion Tool(AWS SCT)을 로컬 PC에 다운로드하여 소스 스키마를 변환

  • 데이터 마이그레이션 : AWS DMS

    • 지속적인 변경 사항을 복제하여 소스와 대상을 동기화 상태로 유지

    • 마이그레이션을 한 번 수행

Transfer Aurora DB to S3

Yes, AWS Database Migration Service (DMS) can be used to transfer data from an Amazon Aurora database to Amazon S3. Here are the basic steps: 1(https://aws.amazon.com/blogs/big-data/migrate-your-existing-sql-based-etl-workload-to-an-aws-serverless-etl-infrastructure-using-aws-glue/)

  1. Install the AWS DMS agent on an EC2 instance that has access to both the Aurora database and the target S3 bucket. 2(https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/postgresql-s3-export.html)

  2. Create a DMS replication instance and specify the EC2 instance as the replication endpoint.

  3. Create a DMS replication task and specify the Aurora database as the source endpoint and S3 as the target endpoint. You’ll need to provide credentials for DMS to access both.

  4. Run the replication task which will migrate the full database and keep it in sync. DMS can replicate **the entire database, individual schemas, tables, or columns** as needed.

  5. DMS will replicate the data changes and store them as files in the S3 bucket. The file format can be JSON, CSV or other formats. You can also define prefixes and folders in S3.

So in summary, yes AWS DMS provides a fully managed way to replicate data from an Amazon Aurora database and keep it in sync with files stored in an S3 bucket. This can be useful for backups, analytics workloads, and other use cases requiring data movement between Aurora and S3.

RealTime transfer Amazon Aurora to S3

To replicate an Amazon Aurora database to S3 in real-time, there are a few options:

  1. Use Aurora Global Databases. This allows you to replicate the Aurora database across multiple AWS regions with typically under one second of latency. The data changes are captured in the primary region and replicated to the secondary regions.

  2. Export Aurora database snapshots directly to S3. You can schedule automated, incremental snapshots of the Aurora database cluster and have them exported to a S3 bucket.

  3. Set up CDC (change data capture) replication from Aurora to S3 using tools like Qlik Replicate. This allows capturing data changes from the Aurora database in real-time and replicating them to tables in other databases including Aurora PostgreSQL or storing in files in S3.

The best option would depend on your specific requirements like whether you need real-time global replication, need to replicate to S3 only or to other databases as well. AWS documentation has more details on setting up these different replication methods between Aurora and S3.

There are a few different options for replicating data from an Amazon Aurora database to Amazon S3 in real-time: 1(https://aws.amazon.com/blogs/big-data/migrate-your-existing-sql-based-etl-workload-to-an-aws-serverless-etl-infrastructure-using-aws-glue/)

  • Use AWS Database Migration Service (DMS) to set up continuous replication from Aurora to S3. DMS can replicate entire databases, schemas or tables as changes occur. The data changes are written to S3 as they happen. 2(https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/WhatsNew.html)

  • Implement change data capture (CDC) on Aurora using trigger-based logging of DML statements. Use AWS Lambda to read the WAL (write ahead log) and write the changed records to S3. This provides near-real-time replication.

  • Leverage Aurora’s native replication capabilities. Configure an Aurora read replica and have an AWS Lambda function copy the transactional logs from the replica to S3. This replicates changes with minimal latency.

  • For Aurora PostgreSQL, use logical replication and have AWS DMS consume the replication slots and write the changes to S3. This provides real-time replication without impacting the source database. 3(https://aws.amazon.com/blogs/big-data/create-an-apache-hudi-based-near-real-time-transactional-data-lake-using-aws-dms-amazon-kinesis-aws-glue-streaming-etl-and-data-visualization-using-amazon-quicksight/)

The best option depends on your specific requirements around latency, workload impact, and whether you need to replicate the entire database or just changes. DMS provides a simpler managed solution, while custom approaches may offer lower latency replication depending on your use case.
