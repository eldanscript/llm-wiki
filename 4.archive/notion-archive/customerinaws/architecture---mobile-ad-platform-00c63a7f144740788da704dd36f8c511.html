  • 기존 API Server 에서 In-memory로 사용하던 것을 Redis

  • Partner 사의 사용량에 따라 용량 산정이 어려움

  • Linux Message Queue가 Java 적용이 어려워 Kafka 도입 예정

  • Log 보관을 위해 별도 EC2 기반의 Analysis Log 분석 서버 구축

  • Daily 50억 건의 input과 outbounding 150억 건 존재 → DB connection에 부담 → Cache layer에

  • DB Scaling MySQL Server

  • DB Cache 내용

    • 광고 기준 데이터는 연결 정보, 매체 정보 등의 변경 부분이 낮은 데이터를 보관

  • Traffic 예상 치

    • Request : 월 100억 수준 → 확장

  • Log data traffic

    • 100억 건에 대해 300 ~ 400억 건 수준의 로그 발생

    • 실시간 log stream 분석 →

  • Kafka 데이터

    • 일부 서비스에만 적용하고 있던 것을 전체로 확대

    • Risk 하지만 Traffic을 많이 먹는다

    • C-code 기반 application 에서

    • Data Retenton : 1 day

    • 광고 거래에 대한 이력 정산과 과금 정보 : 로그 보관을 안전하게 가져가려고 함

  • Analytics 분석 서비스

    • r5.2xlarge : 기존 C-code에서 Java로 변경하면서 1대에서 확장될 가능성이 있음

  • 데이터 수집 주기 → 3분 단위 : transaction data가 대부분이고 비용 정산 등이 batch 성으로 가능
