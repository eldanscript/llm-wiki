AWS Infra 구성 고려

  • VPC 구성

    • EKS cluster 구동

    • Public subnet : Istio gateway 등의 외부에서의 접근 가능한 서비스들 배포

    • Private subnet 구성 : VPN으로 private 한 접속 가능하도록 구성할 예정

  • Networking

    • **VPC Peering과 Transit Gateway 비교 안내 제공**

    • VPC Peering

      • 동일 Region내 소규모 VPC간 inter-connection에 사용

      • AZ간 data transfer 비용 없음

      • Bandwidth : No limit

    • Transit Gateway

      • 대규모 VPC에 대한 full mesh connection에 사용

      • Transit 연결당 시간당 0.05+처리된데이터1GB당0.02

      • Bandwidth : 50Gbps (VPC 당)

  • Certification

    • ACM으로 이동

  • S3

    • Model check point를 DBC라는 tool을 통해 관리

    • Meta 정보는 github로 versioning

    • File은 S3 bucket에 저장

    • 배포시 DBC의 특정 check point가 특정 version을 S3에서 download

    • 이런 배포 방식에서 **private 연결을 통해 internet traffic 비용을 절감** 하고자 함 : Data Transfer cost 안내 blog link (https://aws.amazon.com/blogs/architecture/overview-of-data-transfer-costs-for-common-architectures/)

      • **Interface와 Gateway type 비교**

    • AWS PrivateLink 요금

      • Interface type

        • 1GB당 0.01(데이터처리요금)+1h당0.01 (AZ별 Endpoint 사용 요금)

        • Bandwidth : 10Gbps (AZ 당)

      • Gateway type

        • 동일 region 기준으로 data transfer 비용 없음

        • DX, VPN enpoint, VPC peering 연결 미 지원

    • Type selection guide : blog link (https://aws.amazon.com/ko/blogs/architecture/choosing-your-vpc-endpoint-strategy-for-amazon-s3/)

  • File Storage

    • Checkpoint 기반으로 GB 단위의 artifact를 가져와야 함

    • 현재 NAS 기반으로 구성이 되어 있어 Elastic내 ESS로 옮길 예정

    • Cloud Storage bucket → S3 Object Storage

    • Data Sync를 통해 S3 object를 EFS로 동기화 하여 사용

    • Artifact registry → ECR 및 Code Artifacts

    • Docker repository를 ECR로 migration 할 경우 일괄 작업 방법이 가능한지 확인 필요ec

  • Memory Store

    • ElastiCache로 migration

  • Node

    • GKE(Google Kubernetes Engine) node pool을 EKS의 node group으로 설정

    • Node group에 Fargate 적용 하고자 함

      • Amazon EKS에 Fargate 적용 : 가이드 링크 (https://docs.aws.amazon.com/ko_kr/eks/latest/userguide/fargate-getting-started.html)

      • **제약 사항에 대한 확인 필요** : managed node, ALB support, daemonset 미 지원, PV 및 volume 제공하지 않음

      • GPU instance 지원 가능 여부 : ECS에서만 Fargate에 GPU instance 사용 가능 (확인 필요)

      • CPU instance : Knative, Istio, 서브 나노

    • Warm pool 구성

      • Container image에 대한 빠른 loading을 위해 warm pool을 구성하여 image를 사전 download

    • Image fast loading - rolling update or autoscaling

      • ECR에 container image update → Event Bridge → Lambda → EFS에 container image download

      • Faster pulls for AWS Fargate

      • ECS speed up task launch (AWS 가이드 link)

      • AWS Fargate increase task launch (AWS blog link)

  • AutoScaling

    • Karpenter : EKS Best Practice Guide link (https://aws.github.io/aws-eks-best-practices/karpenter/)

    • Warm pool

      • Workshop : https://ec2spotworkshops.com/efficient-and-resilient-ec2-auto-scaling/lab1/100-launch-from-warm-pool.html

      • EKS Provisioner features for warm pool : https://github.com/keikoproj/instance-manager/blob/master/docs/EKS.md

  • Event Driven Application

    • Knative

  • Observability

    • Logging, Monitoring : cluster 내부에 배포

  • Model Serving

    • 단일 모델로 서빙되는 방식이 아닌 여러 개의 모듈 조합으로 서빙이 되는 구조 : ResNet 등과 같은 방식

    • Modular화 되어 있는 여러 모델 모듈이 복합적으로 연결 되면서 inference가 수행 됨

    • 복합적으로 연결 되어 가면서 inference가 될 수 있기 때문에 MRG(?)를 통해 모델을 미리 부분적으로 정의해 두고 pre-loading 된 상태에서 inference 제공

      • Multi instance : 고 사양 instance에 15개 까지의 모델을 넣고 정적으로 추론 서빙 (container 1, 2, 3, 4, …. )

      • Multi endpoint

      • Multi model : 동적으로 모델 이동, Cold start 존재 (A10 instance 사용 시 대략 50개 정도 동시 로딩 가능)

      • 초거대 모델등의 분산 추론에 사용되는 DeepSpeed를 SageMaker에서 관리형으로 사용할 수 있음 (AWS Blog link)

      • Single instance or Multi instance

    • AWS에서의 multi model serving 방법에 대해 정리 및 논의 필요

  • Security

    • GKE IAP (Identity-Aware Proxy) → 동일 AWS service는 없음
