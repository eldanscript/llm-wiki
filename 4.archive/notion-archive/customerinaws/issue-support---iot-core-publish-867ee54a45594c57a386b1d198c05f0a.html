Service Team Analysis & Recommendation

  • Service team log analysis report

    • Based on the Service log, I could see that the publishIn.ClientError was not due to any of the previous reasons I stated, i.e PacketID being reused, or Message Size beyond 128KB,

    • However, those errors were being reported due to the **publish being made due to the client Not being connected to AWS IoT**

  • Service team recommendation

    • **confirm the connectivity** before the Publish is being made, which will ensure that there is an existing connection (already connected, or initiated again) before the Publish is being made

  • Same packet ID

    • When a publish is being made from an MQTT client, a Packet ID is assigned to the packet

    • Once the Publish is made, the same packet ID can be re-used by the publishing library to publish a new message.

    • However, before the message is published successfully to the broker. (Publish made, and PUBACK processed), a message (say M1) is considered to be in-flight.

    • If subsequent publishes are being made (say M2) during the in-flight time of the M1 message with the same Packet ID, then the M2’s Publish will be rejected with the ClientError due to reusing the same packet as an in-flight message

Support Team Recommendation (in chime call)

  • QOS 0 messages are sent by the message broker at the rate of ~10K messages per second.

    • So for a specific topic, if there are 20K subscribers, the message broker will take 2 seconds to publish to all the subscribers.

  • On the other hand QOS 1 messages are published by broker at a rate of ~1K messages per second

    • So for 20K subscribers to a topic, the messages will be sent in 20 seconds.

  • As a short term solution

    • you can publish messages in QOS 0 to have a temporary relief from the latency, however as QOS 0 doesn’t ensure delivery of the messages, any disruptions.

    • in the subscriber’s network will simply drop the messages and not retry the messages to the subscribers.

  • As a long term solution, you will need to re-architect the application by implementing topic sharding.

    • Publishing to numerous topics in one go, and having the subscribers subscribe to multiple different topics.

    • This will ensure that you can scale the application according to the growth of subscribers.

    • That way, if you use QOS 1 and publish to 10 topics with 1000 subscribers each.

      • The resultant throughput will be 10K messages per second, as the broker will publish the message to the topic at the rate of 1000 message/second. (10 topics X 1000/topic).

  • While the long term solution will need alteration of the application’s publishing logic as a whole, you can prioritise the same with the development team accordingly. As this needs additional expertise regarding implementation of the architecture at scale. You can definitely reach out to our Solution architect team who are the experts in designing resilient architectures for the customer use cases. You can reach out to them via our Sales team [1] or one of the AWS Partner Network team [2]. I have also reached out to your Solution Architect internally to discuss about the way forward.

  • Temp workaround : QoS level 0 → 1로 변경

    • QoS 1을 사용한 이유 : message 유실을 방지

  • Long term : Topic Sharding

Publish

  • Mechanism : 2 Publisher in MQTT broker

    • PublishIn : Publisher → Broker

      • When making QOS 1 Publish, the Broker sends out Acknowledgement for the Publish for the Publisher (That is before sending this forward to the Subscriber).

    • PublishOut : Broker → Subscriber

      • The broker then sends the message out to the subscribers using the same QOS gets the acknowledgement for its own.

    • Publisher does not interact with the Subscriber directly, and interacts only with the broker, and vice versa

    • In a multiple subscriber environment is called a fan-out mechanism, where the broker spreads the message accross multiple subscribers (and publisher is not aware about the existence of multiple subscribers)

Support Case Status

=======

AWS IoT

=======

(1) PublishIn-ClientError 값이 지속적으로 발생하고 있으며 payload 관련 로그가 필요합니다.

  • Client error는 한 개 이상의 메시지 payload가 MQTT 메시지 브로커에서 제공하는 limit에 충족하지 못하게 될 경우 발생합니다.

  • PublishIn.ClientError 관련하여 Throttle 혹은 Connection Error 현상을 겪으셨을 수도 있습니다.

(여기서 PublishIn.ClientError = 0 이 이상값입니다.)

  • 모든 시간대별로 Client Error 이벤트가 발생하고 있으며, 메시지를 Publishing 하는동안 Auth/Server 에러 현상은 확인되지 않았습니다. 이는 메시지를 publish 하는 어플리케이션 메커니즘에 문제가 있을 수 있습니다.

  • 메시지 브로커 한도치(connect, client id size, un-acknowledged publish-ins, etc)는 Client Error 메트릭 속성값에 영향을 주지 않습니다.

(2) AWS IoT 서비스의 Payload는 128KB를 초과할 수 없으며 이는 고정된 할당량이며 증설은 불가능합니다.

[+] https://docs.aws.amazon.com/ko_kr/general/latest/gr/iot-core.html#message-broker-limits

(3) 멀티미디어 파일을 전송하는 경우 다른 방법으로 서비스 구성을 하는 방향으로도 고려하실 수 있습니다.

이와 관련하여 메시지 PayLoad 용량 정보를 요청하였으며, 소스코드에서 확인하실 수 있듯이 AWS IoT를 통해 직접적으로 미디어파일을 전송하지 않고 S3 Key값 정보를 전달하는 방식으로 설계되어 있습니다. 그렇기에 Payload가 128KB를 초과할 가능성은 낮을 것으로 보일 것으로 AWS측에 전달하였습니다.

관련하여 내부팀으로 전달한 에러로그파일 코드파일에 대하여 분석 진행중에 있는 것으로 전달받았습니다.
