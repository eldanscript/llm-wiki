Summary

How do I restrict access to AWS from a particular set of corporate IPs/CIDRs?

In general, it is better to advocate against this style of thinking
(the castle & moat is dead) and controls of this nature provide more
of an illusion than real security - as these restrictions don’t
actually change the fact that AWS service endpoints are public. That
said, if a customer is really bent on doing this, the best way to solve
it is to:

  1. Ensure that all AWS access is only via IAM federation from a single SAML IdP.

  2. Ensure that SAML IdP is only accessible from the desired corp network.

  3. Limit the role session duration to an acceptable balance between
    usability and this policy (noting that within the session duration, the
    user could essentially disconnect from the corp LAN & be anywhere).

This imperfectly achieves the outcome indirectly, but is the best solution IMHO. Please refer to a POC of this solution here.
For completeness, aws:sourceIP restrictions may seem like a logical way
to implement this, however blanket (vs. tactical) use of this condition
key will break many service calls where an AWS service operates on your
behalf (from it’s OWN CIDR space). See What is a data perimeter? for more details.

  • Use Case 1: an employee from corporate network using their personal credentials to login to their personal AWS account via the AWS Console and upload sensitive data to their own AWS resources.

  • Use Case 2: someone logging in from non-corporate network using corporate credentials can access AWS console to access sensitive data from unapproved locations.

Customer Apply

SCP Condition Key

  • SCP is a gatekeeper and checks this HTTP requests with provided policies in AWS organizations

  • There are two types of parameters, called “Condition Keys”,

  • SCP can check: global and service level.

  • Global condition keys are generic data associated with a request, such as username, principaltype, mfa and many
    more, here is the full list.

  • Service level condition keys are on the service level, i.e. “ec2:InstanceType” for EC2 or “s3:x-amz-server-side-encryption” for S3.
