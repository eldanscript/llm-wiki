Parameter Store

Glue Python scripts can access parameters stored in AWS Systems Manager Parameter Store.

The getResolvedParameters() function can be used to retrieve and resolve job parameters set in multiple places like the job definition, run configuration etc.

Parameters from Systems Manager can be accessed by specifying the full ARN of the parameter in the job definition or run configuration.

For example:

import boto3
import sys
from awsglue.utils import getResolvedOptions

# Resolve parameters
params = getResolvedOptions(sys.argv, {"ssm": "/my-parameter"})

# Access parameter value
param_value = params["ssm"]

This allows Glue jobs to leverage managed, secure parameters without needing to hardcode sensitive values in job code or definitions. Refer to the AWS documentation for more details on using getResolvedParameters() and accessing different parameter sources.

Container Application Log - APM

X-Ray does not directly insert request IDs to pods running on EKS. However, it can trace requests made to applications running as containers on EKS.

Here are the key things to know:

  1. The X-Ray daemon needs to be deployed as a sidecar container alongside the application container.

  2. The application code needs to be instrumented using the X-Ray SDK to generate trace segments and send them to the daemon.

  3. The daemon will collect these segments and send them to the X-Ray service for analysis.

  4. Traces will show the flow of requests through the application containers and any underlying AWS services called out.

  5. Annotations can be added to traces to include request IDs or other context from the application level.

Sources

[1] Logging X-Ray API calls with AWS CloudTrail - AWS X-Ray

[2] Amazon API Gateway active tracing support for AWS X-Ray - AWS X-Ray

[3] AWS X-Ray concepts - AWS X-Ray

Athena Table Update

If the schema of the Parquet data stored in S3 is changed, Athena will not be able to query it correctly due to a mismatch between the data schema and the table schema defined in the Glue Data Catalog.

To resolve this, you have a few options:

  1. Run a Glue crawler to update the table schema in the Data Catalog.
    This will synchronize the schema based on the new Parquet file schema.

  2. Manually alter the table schema in Athena using ALTER TABLE commands
    to modify the table definition and match the new Parquet schema.

  3. Drop and recreate the table if the schema change is significant. This ensures the table schema fully matches the data schema.

  4. Use CAST functions in Athena queries to explicitly convert columns to the expected data types, if the mismatch is due to type incompatibilities like different timestamp formats.

It’s important to keep the Glue Data Catalog schema and actual data schema in sync. Running periodic crawlers or using DDL commands after schema changes can help avoid query failures due to schema mismatches.
