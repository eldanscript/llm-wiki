Answers

IoT Core Rule-Engine Timestamp Update

  • Amazon Timestream으로 데이터를 저장하는 IoT Rule Engine을 구성할 때 생성하는 SQL 문에 timestamp field를 업데이트 하여 사용할 수 있습니다. Timestamp field를 지정하지 않으면 Rule Engine에서 Timestream으로 ingest 하는 시점의 값이 기록 됩니다. (관련 기능 안내 페이지 링크)

  • Timestamp field는 time-to_epoch 또는 parse_time 함수를 사용하여 Unix Epoch이나 timestamp string을 사용할 수 있습니다.

  • Rule Engine을 위한 SQL-like query를 생성할 때 IoT Topic의 payload에 지정된 Unix Epoch time 값을 읽어와서 parse_time 함수를 사용하여timestamp string으로 변환하고 timestamp field에 업데이트 하도록 구성하면 될 것으로 보입니다.

  • IoT SQL function reference 참조 링크 : https://docs.amazonaws.cn/en_us/iot/latest/developerguide/iot-sql-functions.html

Answers on Answers

My Questions

  • IHAC that built Timestream in eu-central-1 region and query from the Java application in ap-northeast-2 region. When they query around 2500 data, it took around 10 ~ 6 seconds. Customer use Java v1 SDK. To ignore network latency between region, they did the query in eu-central-1 and it took around 3 seconds.
    My question is that

    1. The query time for 2500 data seems to be long in the same region, how to optimize the query time?

    2. How to reduce the query time across the region.

Answers

  • Ad 2) The most important thing to know here is that TS will paginate the result automatically on either 1MB result size or maxRows defined. With a large number of dimensions that could actually mean that only a few records are returned per page - so that sums up to many roundtrips. Seeing an extra cost of 7sec between local / cross region (SEO - FRA: 250ms Ping RTT) - that makes for about 20-30 pages. Making sure to use the AWS network (peering + endpoints) might bring that down a little bit - but as physics is always right, we are rather limited here.

  • Ad 1) query tuning in the first place (3 seconds). Timestream is optimized for analytical not transactional workloads - TS is not single/two digit latency like DDB. Having said that how much data is scanned? Assuming you have looked already at all the Best Practices (here) - how many records do you have in the table? If you are still using the v1 SDK I would expect also that you do not use MULTI measures yet. In this case, the dimensions on the result set are repeated for every measure - that brings up the number of pages. MULTI measures (here) are a significant performance booster. Otherwise as it says in the query best practice, limit the data scanned and data returned as good as possible. TS beeing serverless might also take a bit longer if after a long period without queries many complex queries are fired - it will take time to scale out.

Optimizing the Query

Timestream Query operation

  • TS는 query 결과를 1MB 크기 혹은 지정된 maxRows 값으로 페이징 (paginate) 한다

  • 따라서 많은 dimension을 가지고 있을 경우 page당 조회되는 record 수가 적을 수 있고 이로 인해 전체 record를 조회 하는데 많은 수의 roundtrip이 생길 수 있다.

  • 7초 정도의 시간이 걸린 이유는 대략 20~30 page로 결과가 나왔을 것으로 보인다.

  • TS는 transactional 보다는 analytical workload용도로 최적화 되어 있다.

  • Java V2 SDK의 MULTI measure를 사용하면 성능 향상 가능 → FleetWise에서 MULTI measure write를 하고 있을 것으로 보임. query에서 추가적으로 할 수 있는 것은 없어 보임

Query 시간 단축을 위한 제언

  1. Paging 수를 최소화 하여 Region간 Roundtrip을 최소화

  2. Query 작업에 대한 best practice

    1. 필요한 measure (actual record at a point in time) 와 dimension (attribute of meta-data, name + value) 이름으로만 query : 불필요한 data 스캔을 감소 시켜 query 성능을 개선

    2. SELECT와 WHERE 절에 지원되는 built-in 함수를 사용하여 data 연산 작업은 Timestream에서 처리 하도록 함

    3. 가능하다면 approximate 함수를 사용

  3. 자주 사용되는 query pattern은 Scheduled query를 생성하여 cache화
