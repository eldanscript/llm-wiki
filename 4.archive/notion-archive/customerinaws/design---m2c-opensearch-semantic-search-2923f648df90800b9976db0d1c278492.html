Feature Summary

주요 개념

기존 검색의 한계

  • 전통적인 검색 엔진은 단어 대 단어 매칭(lexical search)에 의존하여, 추상적인 쿼리에 대해 관련 결과를 놓칠 수 있습니다

  • 정확한 키워드 매칭이 없으면 의미적으로 관련된 문서를 찾기 어려웠습니다

Semantic Search의 장점

  • 대규모 언어 모델을 활용하여 dense vector embeddings를 생성

  • 단어 간의 맥락과 관계를 포착하여 검색 정확도를 향상시킵니다

  • 의미 기반 검색을 통해 사용자 의도를 더 잘 이해합니다

핵심 기능

간편한 구현

  • 몇 번의 클릭만으로 텍스트 필드를 sparse vectors로 인코딩 가능

  • 복잡한 ML 인프라 관리 없이 정교한 검색 기능 구현

  • 사전 훈련된 sparse model 사용으로 커스텀 fine-tuning 불필요[1]

언어 지원

  • 영어 전용 옵션

  • 다국어 옵션 지원[1]

하이브리드 검색

  • Lexical search와 semantic search 기능을 결합

  • Sparse vectors를 통해 의미 정보를 인코딩하면서도 단어 대 단어 매칭 제공

  • Dot-product를 통해 하이브리드 lexical-semantic 매칭 구현[3]

세부 동작 방식

데이터 처리 프로세스

  1. 데이터 수집(Ingestion) 단계

    • 데이터가 수집되는 동안 자동으로 처리

    • 텍스트 필드를 학습된 연관성을 기반으로 sparse vectors로 확장[1]

  2. 벡터 생성

    • 사전 훈련된 sparse model이 텍스트를 분석

    • 의미적 정보를 포함하는 sparse vector embeddings 생성

    • 각 토큰(단어)에 가중치 부여[3]

  3. 검색 실행

    • 쿼리와 대상 문서 모두 sparse vectors로 변환

    • 높은 가중치를 가진 토큰들 간의 dot-product 계산

    • Blended score를 통해 관련성 높은 결과 반환[3]

아키텍처 특징

  • Amazon S3를 primary data storage로 사용

  • Indexing과 search 컴포넌트가 분리된 cloud-native 아키텍처

  • 자동 스케일링으로 워크로드 수요에 따라 OCU(OpenSearch Compute Units) 조정[4]

설정 방법

블로그에서 제공하는 단계별 가이드 포함:[1]

  • 필요한 권한 설정

  • 인덱스 생성

  • Automatic semantic enrichment 활성화

  • 예제 쿼리 실행

사용 시 고려사항

최적 사용 사례

  • 대부분의 검색 사용 사례에서 검색 관련성을 크게 향상

  • 의미 기반 검색이 필요한 애플리케이션

  • RAG(Retrieval Augmented Generation) 구현[1]

제한사항

  • 매우 긴 문서에는 최적이 아닐 수 있음

  • 로그 분석 워크로드에는 적합하지 않을 수 있음[1]

비즈니스 가치

  • 비용 효율성: 복잡한 ML 인프라 관리 불필요

  • 빠른 구현: 최소한의 설정으로 semantic search 구현

  • 향상된 사용자 경험: 더 정확하고 관련성 높은 검색 결과 제공

  • 확장성: Serverless 아키텍처로 자동 스케일링

비용

  • $0.24 per OCU per hour : When not in use, no Semantic Search OCUs are charged

  • 45 MB (11.1 million input tokens) of English content or 30 MB (7.3 million input tokens) of multi-lingual content

아키텍처 계층 구조

1. 네트워크 계층

  • VPC가 모든 가용 영역에 걸쳐 확장 [7]

  • 프라이빗 서브넷에 OpenSearch 노드 배치

  • 퍼블릭 서브넷은 NAT 게이트웨이나 로드 밸런서용으로 활용 [1]

2. 보안 계층

  • 보안 그룹: ALLOW 규칙만 포함하여 허용된 트래픽만 통과 [8]

  • 네트워크 ACL: ALLOW/DENY 규칙 모두 지원하여 추가 보안 제공 [8]

  • 다중 보안 계층으로 심층 방어 구현 [9]

3. 접근 제어 계층

  • VPN 또는 프록시를 통한 접근 제어

  • 트랜짓 게이트웨이를 통한 하이브리드 연결

  • IAM 정책과 연동된 세밀한 권한 관리

아키텍처 설계 모범 사례

서브넷 분리 전략:

  • 퍼블릭 서브넷: 인터넷 게이트웨이 연결, 로드 밸런서 배치 [1]

  • 프라이빗 서브넷: OpenSearch 클러스터 노드 배치

  • 격리된 서브넷: 중요 데이터용 (인터넷 연결 없음) [10]

보안 강화 방안:

  • 애플리케이션 계층별 서브넷 분리 [11]

  • AWS Network Firewall 통합

  • NAT 게이트웨이를 통한 아웃바운드 트래픽 제어 [11]

주요 고려사항

설계 시 고려사항:

  • 초기 설계가 중요 (VPC 간 이동 불가)

  • 가용 영역별 서브넷 배치로 고가용성 확보

  • IP 주소 범위 계획 (예: 10.0.0.0/16 VPC, 10.0.1.0/24 서브넷) [4]

운영 관리:

  • 보안 그룹과 네트워크 ACL의 계층적 보안 적용

  • 라우트 테이블을 통한 트래픽 흐름 최적화

  • VPC 엔드포인트를 통한 AWS 서비스 연결 최적화

이러한 아키텍처를 통해 OpenSearch Service는 높은 보안성과 네트워크 격리를 제공하면서도 필요한 서비스 간 연결성을 유지할 수 있습니다.

Security - FGAC

Fine-Grained Access Control 개요

Fine-Grained Access Control은 Amazon OpenSearch Service의 세 번째이자 최종 보안 계층으로, 데이터에 대한 세밀한 접근 제어를 제공합니다.[1] 네트워크 계층과 도메인 접근 정책을 넘어서 클러스터, 인덱스, 문서, 필드 수준까지 보안을 적용할 수 있습니다.

  • 규정 준수: 금융, 의료 등 규제 산업에서 필수적인 데이터 보호 요구사항 충족

  • 감사 및 모니터링: 세밀한 접근 로그 및 권한 추적 가능

기존 클러스터 FGAC 활성화 절차

1. 사전 준비사항:

  • 도메인 백업 및 스냅샷 생성

  • 유지보수 시간대 계획

  • 마스터 사용자 계정 준비 (IAM 또는 내부 DB)

2. 활성화 단계:

AWS Console → OpenSearch Service → Domains → [도메인 선택]
→ Actions → Edit security configuration
→ Fine-grained access control 체크박스 활성화
→ 마스터 사용자 설정 → 변경사항 저장

3. 활성화 후 작업:

  • 사용자 역할 및 권한 매핑 설정

  • 인덱스별 접근 권한 구성

  • OpenSearch Dashboards 테넌트 설정

주요 고려사항

운영상 고려사항:

  • 서비스 중단: 블루/그린 배포로 인한 일시적 중단 불가피

  • 복잡성 증가: 권한 관리 및 문제 해결 복잡성 증가 [1]

  • 성능 영향: 권한 검사로 인한 미미한 성능 오버헤드

  • 비용: 추가 관리 노드 필요 시 비용 증가 가능

보안 강화 효과:

  • 데이터 유출 위험 최소화

  • 내부자 위협 대응 강화

  • 규정 준수 요구사항 충족

  • 감사 추적성 향상

권장사항

FGAC 활성화를 권장하는 경우:

  • 프로덕션 환경의 민감한 데이터 처리

  • 여러 팀이 동일한 클러스터 공유

  • 규제 산업 (금융, 의료, 정부) 운영

  • 외부 사용자 접근이 필요한 경우

단계적 접근 방법:

  1. 개발/테스트 환경에서 먼저 테스트

  2. 비즈니스 영향이 적은 시간대에 활성화

  3. 점진적 권한 적용 및 모니터링

  4. 사용자 교육 및 문서화 완료

FGAC는 OpenSearch Service의 핵심 보안 기능으로, 기존 클러스터에서도 활성화 가능하지만 신중한 계획과 준비가 필요합니다.

2. IAM 정책 기반 제어:

  • 특정 IAM 사용자/역할에게 OpenSearch 도메인 접근 권한 부여

  • 해당 권한이 있으면 모든 인덱스에 대한 모든 작업 가능

  • 세밀한 인덱스별 권한 제어 불가능

주요 차이점 및 제한사항

FGAC 미설정 시 제한사항:

  • 전체 접근 또는 차단: 도메인 접근 권한이 있으면 모든 인덱스 접근 가능

  • 사용자별 세밀한 제어 불가: 팀별, 역할별 인덱스 분리 어려움

  • 감사 추적 제한: 누가 어떤 인덱스에 접근했는지 세밀한 추적 어려움

  • 멀티 테넌시 불가: 여러 팀이 동일 클러스터 사용 시 데이터 격리 어려움

FGAC 설정 시 장점:

  • 인덱스별 권한: 로그 인덱스는 운영팀만, 분석 인덱스는 데이터팀만 접근

  • 작업별 제한: 읽기 전용 사용자, 쓰기 권한 사용자 구분 가능

  • 필드 수준 보안: 민감한 필드 숨김 또는 마스킹

  • 문서 수준 필터링: 부서별 데이터만 보이도록 설정

실제 운영 시나리오

FGAC 미설정 환경:

개발자 A (IAM 권한 있음) → 모든 인덱스 접근 가능
- logs-prod-* 인덱스 (운영 로그)
- analytics-* 인덱스 (분석 데이터)
- user-data-* 인덱스 (사용자 데이터)

FGAC 설정 환경:

개발자 A (analytics 역할) → analytics-* 인덱스만 접근
운영팀 B (ops 역할) → logs-prod-* 인덱스만 접근
관리자 C (admin 역할) → 모든 인덱스 접근

권장사항

FGAC 미설정이 적합한 경우:

  • 단일 팀이 사용하는 개발/테스트 환경

  • 모든 사용자가 동일한 권한이 필요한 경우

  • 간단한 로깅 용도로만 사용

FGAC 설정이 필요한 경우:

  • 여러 팀이 동일 클러스터 공유

  • 민감한 데이터 포함

  • 규정 준수 요구사항 존재

  • 세밀한 접근 제어 필요

결론적으로 FGAC를 설정하지 않아도 인덱스 작업은 가능하지만, IAM과 도메인 접근 정책에만 의존하게 되어 세밀한 권한 제어가 어려워집니다. 프로덕션 환경에서는 보안과 관리 효율성을 위해 FGAC 사용을 강력히 권장합니다.

  • 낮은 레이턴시 (벡터 검색만 수행 시)

단점:

  • 구축 복잡도 높음 (ML 모델 배포, 파이프라인 구성 필요)

  • 임베딩 모델 선택 및 관리 필요

  • 인덱싱 파이프라인 직접 구현 필요

  • 의미 기반 검색 가능 (“행복한 표정”)

  • 검색 결과 리스트 반환 (기존 방식과 유사)

  • 응답 시간: 0.5-1초 (벡터 검색만)

  • LLM 답변 생성 시 추가 구현 필요

| 비용  | 높음 ($$$) | 중간 ($$) |

| 커스터마이징  | 제한적 | 자유로움 |

| 검색 방식  | RAG 기반 답변 생성 | 벡터 유사도 검색 |

| 응답 형태  | 자연어 답변 | 검색 결과 리스트 |

| 기존 인덱스 활용 | 어려움 | 용이함 |

| 하이브리드 검색  | 제한적 | 완벽 지원 |

4. 추천 의견

현재 상황을 고려한 추천:

OpenSearch ML Connector 방식을 추천합니다. 이유는:

  1. 기존 인프라 활용: 이미 lexical 검색이 구현되어 있어, 동일 인덱스에서 하이브리드 검색 구현 가능

  2. 비용 효율성: 미디어 분석 시스템은 대량의 메타데이터를 다루므로 Bedrock 호출 비용이 급증할 수 있음

  3. 정확도: lexical + semantic 하이브리드 검색이 단순 벡터 검색보다 정확

  4. 유연성: 얼굴 인식, 객체 탐지 등 기존 분석 결과와 통합이 용이

단계별 구현 전략:

Phase 1: 벡터 검색 기반 구축 - SageMaker에 임베딩 모델 배포 (예: sentence-transformers) - OpenSearch k-NN 인덱스 설정 - 인제스트 파이프라인에 벡터 생성 추가 Phase 2: 하이브리드 검색 구현 - lexical + semantic 스코어 조합 - 검색 결과 리랭킹 Phase 3 (선택): 대화형 기능 추가 - 필요 시 Bedrock LLM으로 답변 생성 - 검색 결과를 컨텍스트로 활용

Bedrock Knowledge Base는 이런 경우 고려:

  • 빠른 POC가 필요한 경우

  • 대화형 인터페이스가 핵심 요구사항인 경우

  • 개발 리소스가 제한적인 경우

  • 비용보다 출시 속도가 중요한 경우

현재 프로젝트 문서를 보면 복잡한 미디어 분석 파이프라인이 구축되어 있으므로, 세밀한 제어가 가능한 ML Connector 방식이 장기적으로 더 적합할 것으로 판단됩니다.
