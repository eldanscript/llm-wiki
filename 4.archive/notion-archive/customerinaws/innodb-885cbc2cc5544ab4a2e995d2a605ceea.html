  • ds2 , ra3 운영 환경에서 L0는 제외되어 있음

  • 전체 cluster의 resource가 queue의 benefit을 가져가지 못하고 있는 것으로 보임

  • batch가 resource를 사용하고 있음 → cpu가 100을 유지

  • cluster를 분리하거나 node 수를 늘리는 방법을 생각할 수 있음

  • mstr 전용으로 cluster를 작게 만들어서 test를 수행

  • mstr을 빠르게 하려면 전용 queue를 생성

    • 조회용, batch용 cluster 분리

  • ds2 8xlarge → ra3.4xlarge 4 node를 통해 batch 성능을 향상

  • mstr은 ra3.x plus 2 node와 같이 다른 cluster를 구성해서 분리하고 query queue를 할당

실시간 batch

  • MSTR용 cluster :

    • L1, L2를 조회시 분리된 cluster의 endpoint에 접근

    • Redshift data sharing 기능을 설정하여 2개의 cluster간 data 공유 → data 적재는 현재 cluster에 유지

    • 2개의 cluster간에 동일한 schema를 사용해도 되는지? → share할 경우 schema의 이름을 data를 제공하는 cluster를 지정

    • 사용 방법에 대해 안내 제공

  • 고정된 data에 대해서는 B cluster에 저장하여 추가된 공간을 낭비하지 않고 활용

  • Materialized View를 B cluster에 저장하여 활용

  • 잘 안 변한다는 의미는? daily, hourly batch의 경우

    • B cluster는 computer만 활용하게 되는데 주기적으로 summary 하거나 잘 변화지 않는 data를 저장 하여 성능 향상에 적용

    • Data Sharing은 DB link의 개념

  • Cluster 추가와 node 추가의 차이는?

    • node 추가의 경우 신규 cluster

    • 사용 방법은 동일

    • 전체 queue에 concurrent하게 thread를 50개 가능 → cluster를 증가하면 +50 되는 이점이 있을 수 있음

  • Cluster 증가에 대해서는 비용 대비 효과를 판단

  • 현재 concurrent level은 30개 : 메모리 사용량이 전체 slot 수로 나누어 짐 → query 시작 전 slot을 지정 → 작업이 많아지는 경우 slot을 추가

  • Query 동작 시점의 metric 확인 필요

Concurrency Scaling

  • 내부적으로 cluster가 생성되어 지원 되는 것임 : select 위주 query에 대응 (reInvent에서 DML 까지 확장)

  • slot이 full 되었다면 사용하는 것인지?

  • concurrency 사용 기준 : short query가 intensive workload에 밀리는 경우에 대응하기 위해 사용할 수 있음
