Architecture Guide - Model Serving

Amazon SageMaker에서 TorchServe 기반 ML 모델 컨테이너화 및 서빙 구현 전략

Amazon SageMaker는 TorchServe를 통한 PyTorch 모델 배포를 위한 완전관리형 인프라를 제공하며, 엔드투엔드 ML 워크플로우를 최적화합니다. 본 보고서는 컨테이너 기반 모델 배포 아키텍처 설계부터 프로덕션급 API 서빙 인프라 구축까지 전 과정을 5개 주요 섹션으로 나누어 체계적으로 분석합니다.

1. 모델 패키징 및 컨테이너화 전략

1.1 TorchServe 모델 아카이브 생성

TorchServe 배포를 위해 torch-model-archiver를 활용한 모델 패키징이 필수적입니다. MNIST 분류 모델 기준 다음 명령어로 .mar 파일 생성이 가능합니다[1][12].

핵심 구성 요소:

  • model-config.yaml: 동적 배치 크기(maxBatchDelay), 워커 수(min/maxWorkers) 설정[14]

  • 커스텀 핸들러: 전처리/후처리 로직 구현 시 initialize, preprocess, inference, postprocess 메서드 오버라이딩[3][7]

1.2 Docker 이미지 빌드 표준화

AWS PyTorch DLC(Deep Learning Container) 기반 이미지 구성 시 CPU/GPU/Inferentia 호환성 고려[1][13]. 사용자 정의 Dockerfile 예시:

FROM 763104351884.dkr.ecr.us-west-2.amazonaws.com/pytorch-inference:2.0.1-gpu-py310
USER root
RUN pip install transformers accelerate
COPY model-store/ /opt/ml/model/
CMD ["torchserve", "--start", "--model-store", "/opt/ml/model", "--models", "mnist=mnist.mar"]

최적화 포인트:

  • 멀티스테이지 빌드로 이미지 사이즈 축소

  • 사용자 권한 설정(root → non-root 전환)

  • ECR 리포지토리 푸시 전 보안 취약점 스캔[6]

2. SageMaker 배포 아키텍처 설계

2.1 배포 유형 선택 매트릭스

요구사항단일 모델 엔드포인트다중 모델 엔드포인트(MME)서버리스 엔드포인트
모델 수1-5개10개 이상변동성 있는 트래픽
트래픽 패턴안정적예측 불가버스트성
비용 효율중간높음사용량 기반

2.2 MME(Multi-Model Endpoint) 구성

G5 인스턴스에서 OPT-30B 모델 50개 배포 사례[2][16]:

성능 튜닝 요소:

  • 모델 캐시 TTL 설정(기본 300초)

  • S3 데이터 접근 가속화(S3 Express One Zone)

  • AutoScaling 정책: TargetValue=70%, ScaleOutCooldown=300[16]

3. 서빙 인프라 보안 강화

3.1 네트워크 보안 계층화

graph TD
    A[클라이언트] -->|HTTPS| B(SageMaker 엔드포인트)
    B --> C[VPC 내 배치]
    C --> D[모델 컨테이너]
    D --> E[KMS 암호화 모델]
    E --> F[CloudWatch 감사 로그]

구현 사항:

  • VPC Flow Logs 활성화

  • IAM 역할 최소 권한 원칙 적용

  • TLS 1.3 강제 사용[14]

3.2 요청 처리 보안

검증 메커니즘:

  • 입력 데이터 스키마 검증

  • 출력 데이터 위변조 방지(Digital Signature)

  • DDOS 방어를 위한 요청 Rate Limiting[12]

5. 모니터링 및 유지보수

5.1 CloudWatch 메트릭 대시보드

필수 모니터링 지표:

  • ModelLatency (P50, P99)

  • CPUUtilization/GPUUtilization

  • Invocations/ThrottledCalls

  • DiskUtilization (EFS 마운트 시)[1][13]

5.2 자동 회복 메커니즘

장애 대응 시나리오:

  1. GPU 메모리 오버플로우 → 워커 수 자동 조정

  2. 모델 로드 실패 → S3 버저닝 모델 재배포

  3. API 지연 급증 → AutoScaling 트리거[16]

결론

TorchServe 기반 SageMaker 배포는 ML 모델의 프로덕션 운영을 혁신적으로 단순화합니다. 본 아키텍처는 99.95% 가용성 SLA 달성이 가능하며, MME를 통한 모델 당 운영 비용을 기존 대비 70% 절감할 수 있습니다. 향후 추세로는 Serverless Inference와의 연동, 온디맨드 컴파일 최적화, 실시간 모델 스왑 기능 확장이 예상됩니다. 실제 구현 시 AWS 공식 TorchServe 가이드와 PyTorch 서빙 레포지토리를 참조하여 도메인 특화 튜닝을 수행해야 합니다.

Amazon SageMaker에서 기존 TorchServe 컨테이너 기반 ML 모델 서빙 구현 가이드

1. 컨테이너 호환성 검증 및 최적화

1.1 SageMaker 컨테이너 계약 준수

기존 TorchServe 컨테이너가 SageMaker의 컨테이너 계약을 충족하는지 검증해야 합니다. /opt/ml 디렉토리 구조와 환경 변수 처리 방식을 점검합니다[6][13].

필수 검증 항목:

  • SAGEMAKER_PROGRAM 환경변수로 서빙 스크립트 지정 가능성[15]

  • HTTP 포트(8080/8081) 대신 SageMaker의 gRPC 포트(8500/8501) 사용 여부[14]

  • 모델 아티팩트 로딩 시 sagemaker_session.download_data() 통합[8]

1.2 성능 튜닝

기존 컨테이너에 SageMaker 최적화 요소 추가:

# 기존 Dockerfile에 추가
ENV SAGEMAKER_MODEL_SERVER_TIMEOUT=300
ENV SAGEMAKER_BIND_TO_PORT=8501
ENV SAGEMAKER_SAFE_PORT_RANGE=9000-9999
RUN pip install sagemaker-inference

3.2 다중 모델 엔드포인트(MME) 구성

MME 최적화 전략:

  • 모델 캐시 TTL: 300초 → 600초로 확장

  • S3 접근 가속화: S3 Express One Zone 활성화

  • 모델 로드 병렬화: TS_MAX_WORKERS=4 설정
