Q2. Capcity Provider Reservation

Q2-1. Capacity Provider Reservation 속성값 이해 확인의 건

공식문서/Blog 내용을 참조하여 Capacity Provider Reservation 특성에 대하여 이해한 내용을 바탕으로 정리해보았습니다.

만약 정정/추가 할 부분이 확인되시면 피드백 부탁드리겠습니다.

  1. ECS CAS는 AWS Auto Scaling에 의지한다.

  2. CAS는 ASG에 scaling plan을 생성하는데 여기서 target tracking scaling policy 방식이 적용된다.

  3. Scaling policy는 CapacityProviderReservation 의 CW 메트릭을 이용하는데, 이는 어플리케이션 수요에 맞게 알아서 ASG의 용량을 조절해주는 역할을 한다.

  4. CapacityProviderReservation은 기본적으로 아래와 같이 정의된다. (이제, CapacityProviderReservation 을 줄여서 CPR이라고 명명) 여기서 M은 사용자의 운영 상황에 맞도록 정의해야 한다.

  1. CPR 설정값을 기준에 부합하도록 ECS CAS는 EC2 개수를 조절하는 역할을 수행한다. 여기서 CPR 설정값은 운영자가 직접적으로 설정해야 하는 속성값이다.

Case 1. CPR = 100으로 설정하는 경우 (Blog 사례)

[+] https://aws.amazon.com/ko/blogs/containers/deep-dive-on-amazon-ecs-cluster-auto-scaling/

운영에 필요한 EC2 개수와 동작중인 EC2 개수와 동일하므로 별도의 Scaling 메커니즘이 발현되지 않는다.

  1. M < N 인 경우:

필요한 EC2 개수보다 동작중인 EC2 개수가 적으므로 Scale-Out 메커니즘이 발현된다.

  1. M > N 인 경우:

필요한 EC2 개수보다 동작중인 EC2 개수가 많으므로 Scale-In 메커니즘이 실행될 수 있다.

Case 2. CPR = 50으로 설정되는 경우

M = N인 경우, 운영에 필요한 EC2 개수는 충족하나 동작중인 인스턴스의 개수만큼 예비 인스턴스를 구비한다.

  • 예를 들어 서비스 운영에 필요한 인스턴스가 2대인 경우, 2대의 예비 인스턴스를 추가로 구비한다.

  • 예비 인스턴스에서는 Task가 별도로 할당되지 않은 상태이다

Q 2-2. Auto Scaling에서 제공하는 Warm pool과 ECS CPR < 100으로 설정하여 구성되는 예비 인스턴스 차이점에 대한 문의

ECS CPR < 100 으로 생성하여 구성된 예비 인스턴스들은 EC2 Auto Scaling에서 제공하는 Warm pool 기능을 활용하여 구성된 부분일까요?

아니라면 EC2서비스가 아닌  ECS 자체적으로 Warm pool 기능이 별도로 존재하는 것일까요?

[+] https://aws.amazon.com/about-aws/whats-new/2022/03/amazon-ecs-supports-warm-pools-amazon-ec2-auto-scaling/

Amazon ECS supports Amazon EC2 Auto Scaling warm pools. A warm pool is a group of pre-initialized Amazon EC2 instances ready to be placed into service. Whenever your application needs to scale out, Amazon EC2 Auto Scaling uses the pre-initialized instances from the warm pool rather than launching cold instances, allows for any final initialization process to run, and then places the instance into service.

Q 2-3. 예비 인스턴스 비용

윗 그림에서 CAS를 통해 생성된 예비 인스턴스 경우, 예비 인스턴스 임에도 불구하고 EC2 비용과 동일하게 청구되는지 궁금합니다.

또한, Running Task가 0으로 표기 되는데, 기존 EC2 + ECS 비용이 EC2 비용으로만 청구가 되는 부분으로 이해해도 되는지 궁금합니다.

CAS can estimate a lower bound on the optimal number of instances to add based on the instance types that the ASG is configured to use, and use that value for M. In other words, you will need at least M more instances to run all of the provisioning tasks. Q3-2. Managed Scale-Out behaviour 관련 질의

[+] https://aws.amazon.com/ko/blogs/containers/deep-dive-on-amazon-ecs-cluster-auto-scaling/

Calculate M as the minimum value within each task group and maximum value of those across all task groups.Finally, require that N + minimumScalingStepSize =< M <= N + maximumScalingStepSize. (These two parameters are defined in the capacity provider configuration).

N + minimumScalingStepSize =< M <= N + maximumScalingStepSize. 설정에서 5 <= M <= 10이 되는 경우를 생각해 보겠습니다. 이때, Scale-Out 메커니즘이 발현되는 경우 5~10 값 범위에서 어느 값으로 M이 산정이 되는것일까요?

또한, Min/Max ScalingStepSize 커스텀설정 활용한 사례가 있다면 공유해주시면 감사하겠습니다.

Q 3-3. Scaling-in Alarm 설정 가능 여부

CAS를 활용시 15분동안 CPR * 90% 미만을 유지할 시 Scale-In 메커니즘 실행이 되어지는 것으로 보여지는데, 언제 다시 Spike 성의 유입이 될지 모르는 상황이기에 낮은 자원 사용량을 2시간 가량 유지되는 경우 Scale-In 메커니즘이 발현되도록 커스텀하게 설정하고 싶습니다.

15분이라는 속성값을 커스텀하게 설정가능 여부와 더불어 CAS와 상충되지 않게 이를 실현시킬 수 있는 방안이 있다면 안내부탁드리겠습니다.

💡 Scale-in considerations
[+] https://docs.aws.amazon.com/AmazonECS/latest/developerguide/cluster-auto-scaling.html#managed-scaling-scalein
Consider the following for the scale-in process:
• When there are no running non-daemon tasks, Amazon ECS container instances are considered available for scale in.
• CloudWatch scale-in alarms require 15 data points (15 minutes) before the scale-in process for the Auto Scaling group starts. After the scale-in process starts until Amazon ECS needs to reduce the number of registered container instances, the Auto Scaling group sets the DesireCapacity value to be greater than one instance and less than 50% each minute.
• When Amazon ECS requests a scale-out (when CapacityProviderReservation is greater than 100) while a scale-in process is in progress, the scale-in process is stopped and starts from the beginning if required.

1 ECS Cluster Auto Scaling  (CAS) 와 Capacity Provider

  • 이전에는 ECS에서 직접EC2 인스턴스를 scaling 하는 방법이 없었고CAS가 제공되면서EC2 인스턴스에 대해서 Auto Scaling Group (ASG)을 통해 관리할 수 있게 되었습니다. 이 기능은Capacity Provider를 통해 가능합니다.

  • Capacity Provider는 ECS Cluster와 ASG의 연결(link)를 제공하며, Cluster의 컴퓨팅 용량을 관리할 수 있도록 다양한 실행 방법을 구성하여 관리 할 수 있습니다.

  • Capacity Provider의 구현 목표는 다음과 같습니다.

    • Task를 구동하기에 충분한 컴퓨팅 용량이 없다면 ASG을 통해 인스턴스를 추가 (scale-out) 해야 한다.

    • Daemon task를 제외한 어떤 task의 동작에 지장을 주지 않는다면 인스턴스를 제거 (scale-in) 해야 한다.

    • 고객은 ASG에 대한 모든 권한 (인스턴스 수, scaling policy, 인스턴스 타입 설정 등…) 을 유지하여야 한다.

  1. CAS의 Scaling Logic

  • ASG에서 적합한 (right) 인스턴스 수를 유지하기 위해 CAS는 CapacityProviderReservation metric을 사용합니다.

    • CapacityProviderReservation metric은 이미 구동하고 있는 인스턴스 수 (N)와 필요한 인스턴스 수 (M)의 비율로 정의 되며Q2-1에 설명주신 내용이 맞습니다.

  • 인스턴스에 필요한 수 (M) 값에 대한 추론

    • M의 값은 task를 모두 provisioning 하기 위한 최적 (optimal)의 수가 되어야 하지만 더 크거나, 더 작지 않고 딱 정확한 수를 예측 하는 것은 불가능 합니다.

    • CAS는 ASG가 사용하도록 구성된 인스턴스 유형을 기반으로 추가할 최적의 인스턴스 수의 하한선을 추정하고 이 값을 M에 사용 합니다.

    • ASG에서 단일 인스턴스 유형을 사용할 경우의 M 값 추정

      • Provisioning task를 동일한 리소스 요구 사항을 갖도록 그룹화

      • 각 그룹별로 binpack 배치를 사용할 경우의 필요한 인스턴스 수를 계산

    • ASG에서 여러 인스턴스 유형을 사용할 경우의 M값 추정

  • 기능이 없었고 ECS 외부에서 별도의 ASG에 수동으로 scaling policy를 설정하여 Cluster의 컴퓨팅 인스턴스의 확장, 축소를 관리했습니다. 이후 ECS에 Capacity Provider를 제공하여 ECS에서도 ASG의 scaling policy를 관리할 수 있도록 하였습니다.

  • 2022년 5월에 ECS의 Capacity Provider에 대한 기능 업그레이드가 있었습니다. (신규 기능 안내 블로그)

  • 새로 업그레이드 된 기능은 Capacity Provider와ASG에 대한 통합 입니다. ASG의 scaling policy에 의존하지 않고 target-tracking scaling policy를 통해 Cluster 컴퓨팅 용량을 관리 할 수 있도록 하였습니다.

전반적으로 ECS Capacity Provider에 대한 기능을 상세하게 파악하시고 잘 정리하여 질문 주셔서 매우 감사 드립니다.
이미 상세한 내용에 대해 파악을 하고 계시는데 문의 주신 내용에 대해서 아래 부분 참조 하시고 추가 논의 필요한 부분에 대해 말씀 주십시오.

1 ECS Cluster Auto Scaling (CAS) 와 Capacity Provider
• 이전에는 ECS에서 직접EC2 인스턴스를 scaling 하는 방법이 없었고CAS가 제공되면서EC2 인스턴스에 대해서 Auto Scaling Group (ASG)을 통해 관리할 수 있게 되었습니다. 이 기능은Capacity Provider를 통해 가능합니다.
• Capacity Provider는 ECS Cluster와 ASG의 연결 (link)를 제공하며, Cluster의 컴퓨팅 용량을 관리할 수 있도록 다양한 실행 방법을 구성하여 관리 할 수 있습니다.
• Capacity Provider의 구현 목표는 다음과 같습니다.
o Task를 구동하기에 충분한 컴퓨팅 용량이 없다면 ASG을 통해 인스턴스를 추가 (scale-out) 해야 한다.
o Daemon task를 제외한 어떤 task의 동작에 지장을 주지 않는다면 인스턴스를 제거 (scale-in) 해야 한다.
o 고객은 ASG에 대한 모든 권한 (인스턴스 수, scaling policy, 인스턴스 타입 설정 등…) 을 유지하여야 한다.
2. CAS의 Scaling Logic
• ASG에서 적합한 (right) 인스턴스 수를 유지하기 위해 CAS는 CapacityProviderReservation metric을 사용합니다.
o CapacityProviderReservation metric은 이미 구동하고 있는 인스턴스 수 (N)와 필요한 인스턴스 수 (M)의 비율로 정의 되며Q2-1에 설명주신 내용이 맞습니다.
• 인스턴스에 필요한 수 (M) 값에 대한 추론
o M의 값은 task를 모두 provisioning 하기 위한 최적 (optimal)의 수가 되어야 하지만 더 크거나, 더 작지 않고 딱 정확한 수를 예측 하는 것은 불가능 합니다.
o CAS는 ASG가 사용하도록 구성된 인스턴스 유형을 기반으로 추가할 최적의 인스턴스 수의 하한선을 추정하고 이 값을 M에 사용 합니다.
o ASG에서M 값 추정 방식
 Provisioning task를 동일한 리소스 요구 사항 별로 그룹화
 각 그룹별로 최소 수량을 추정하기 위해 binpack 배치 경우에 대한 필요 인스턴스 수를 계산
 인스턴스 수량 계산에는 vCPU, memory, ENI, ports, GPU와 함께 task 배치 제한도 고려 됩니다.
 최종 M의 값은 N + minimumScalingStepSize, N + maximumScalingStepSize 의 범위를 벗어 나지 않아야 합니다. ScalingStepSize는 Capacity Provider에 설정하는 값으로 scaling out 시 한번에 증가 시키는 instance 개수 입니다. 기본 값은 1 입니다. 여기서 범위를 벗어 나지 않는다는 의미는 산정된 M을 이 범위에서 새로 산정이 되는 것이 아닙니다. M은 최소 수량으로 결정이 된 것이고 만약 ScalingStepSize 범위를 벗어 나게 된다면 M의 값이 N+minimumScalingStepSize나 N+maximumScalingStepSize로 대체 된다고 생각하면 됩니다. (Q3-2 문의 내용)
 M값 산정은 binpack 배치 전략을 사용하기 때문에 cpu나 memory 자원을 기준으로 산정하게 됩니다. distinctInstance와 같은 Placement Containt 를 사용하면 해당 조건을 고려하여 인스턴스에 대해 예상치를 산정하게 됩니다. Spread를 CAS에서 관리하는 혼합하게 하는 부분은 가능 합니다. CAS에서는 최소 인스턴스 유지를 위해 binpack을 기본으로 사용하지만 spread를 혼합하게 되는 경우는
o 추정된 M의 값이 필요한 provisioning task를 모두 커버하지 못한다면 남은 task는 pending 상태를 유지하다 다음 scaling 진행에서 처리되게 됩니다. 적합한 M의 값이 추정된다면 한번의 scaling 진행으로 task를 provisioning 할 수 있게 되므로 전체 서비스 수요를 좀더 빠르게 cover할 수 있게 된다고 보시면 됩니다.
• Target Tracking Scaling Policy
o CAS에서는 M의 값을 산정한 후 ASG에 target tracking scaling policy를 추가 하여 컴퓨팅 인스턴스를 scaling 하게 됩니다.
o Target tracking scaling policy는 cloudwatch로 수집된 metric을 통해 설정된 CapacityProviderReservation 값을 유지하기 위해 scaling-out 이나 scaling-in 을 수행합니다.
o CapacityProviderReservation 값이 100 이하로 설정된다면 (over provision capacity) M의 값이 N보다 큰 경우로 (M-N) 값은 유휴 자원이 되게 됩니다.
o CapacityProvider에서 target capacity 를 50으로 설정했고 현재 동작중인 N이 2개라면 CapacityProviderReservation 값을 유지 하기 위해 CAS는 scaling-out을 수행하여 2개의 추가 인스턴스가 생성되게 됩니다.
o 예비 인스턴스 (Free Capacity)는 수행되는 task가 없지만 running state의 인스턴스 입니다. 문의 주신 Q2-3에 답을 드리면 예비 인스턴스에 대해서는 비용이 청구 됩니다. 그럼에도 예비 인스턴스를 사용하게 되는 이유는 인스턴스가 준비되어 있기 때문에 로드 증가에 따른 task provisioning이 빠르게 완료될 수 있다는 점 입니다. ECS는 비용이 청구되지 않기 때문에 예비 EC2 인스턴스의 비용만 청구됩니다.
