Architecture Guide - OpenSearch Discussion

Summary from Sungil

agent: Packetbeat, Telegraf, filebeat

→ 로그스태시 → 필터링으로 데이터 뽑아내는 작업 후 → OpenSearch 적재

문제점: 대시보드에서 timerange를 길게 하는 경우 점점 느려짐

원인:

  • 데이터 검색 요청건수, 데이터 조회 range 증가는 속도에 영향을 미치는 작업이 맞습니다.

    • 하나의 대시보드 내에 차트가 많을 수록 검색 api 요청이 증가하므로 소요시간이 증가합니다.

    • range를 늘릴 수록 scan 해야하는 샤드(segment) 수가 늘어나면서 소요시간이 증가합니다.

가능한 해결방법:

  • 데이터 노드의 scale up 또는 scale out

  • 인덱스 롤업 (절대적인 데이터 사이즈를 줄임)

    • https://docs.aws.amazon.com/ko_kr/opensearch-service/latest/developerguide/rollup.html

    • https://opensearch.org/docs/latest/im-plugin/index-rollups/index/

    • 외부 링크 - 개념 참고용

      • https://www.elastic.co/guide/en/elasticsearch/reference/7.10/data-rollup-transform.html

      • https://www.elastic.co/blog/how-to-create-manage-and-visualize-elasticsearch-rollup-data-in-kibana

  • 대시보드당 차트수 줄이기 또는 대시보드를 여러 개로 분리하기

  • 기타 모범사례 기반으로 튜닝하기

    • 샤드 전략 개선

      • 일반적으로 로그 검색의 샤드 당 사이즈는 30~50GiB 입니다. 이것을 출발점으로 잡고 최적의 사이즈를 찾으시면 좋습니다.

        • https://docs.aws.amazon.com/ko_kr/opensearch-service/latest/developerguide/bp.html#bp-sharding-strategy

    • 참고할만한 모범사례 : https://docs.aws.amazon.com/ko_kr/opensearch-service/latest/developerguide/bp.html#bp-perf

  • slow logs 활용하기

    • https://repost.aws/ko/knowledge-center/opensearch-troubleshoot-slow-logs

    • 대시보드 내 특정 차트가 문제일 수 있습니다.

    • 정확하게는 차트를 불러오기 위한 검색쿼리 튜닝이 필요할 수 있습니다.

    • 이 경우 slow logs를 사용하여 튜닝 포인트를 찾습니다.

    • 유튜브 영상 뒷 쪽의 검색 쿼리 튜닝 참조

  • 사용하지 않는 인덱스는 삭제 또는 close하시는 것이 성능 향상에 도움이 됩니다.

고객이 수행하신 개선작업

  • 캐싱 서비스를 앞단에 둠

    • 대시보드는 엔진에 api로 통신하므로, 고객이 직접 생성하신 캐싱 서비스는 실질적인 도움이 되지 않습니다.

    • 현재 문제의 핵심은 많은 데이터에 많은 요청을 하고 있는 것으로 생각됩니다.

  • 데이터 전처리

    • 키워드 타입의 필드로 따로 분리하시는 작업은 OpenSearch 내부 또는 OS 레벨의 캐싱을 가능하게 해서성능에 도움이 될 수 있습니다.

  • 대시보드의 탭을 나눠서 차트를 분산시킴

    • 탭이라고 말씀해주셔서 세션시에는 대시보드를 분산시켰다고 이해하고 말씀드렸습니다.

    • 탭을 어떻게 구현하셨는지에 따라 다를 수 있는데, 성능을 향상 시키기 위해서는 엔진으로 요청되는 절대적인 검색 요청의 숫자가 줄어야 합니다.

    • 탭을 구성하셨다고 하더라도, 대시보드 클릭시에 모두 호출하게 되어있는 구조라면 성능의 향상을 기대하기 어렵습니다.

    • 대시보드 단위로 분산하시면 페이지를 열 때 절대적인 api 요청을 줄여 성능을 향상시킬 수 있습니다.

참고

  • 현재 cpu 사용률이 증가하는 문제가 있으므로 다음을 고려하세요

    • https://repost.aws/ko/knowledge-center/opensearch-troubleshoot-high-cpu

    • 데이터 노드 선택시, c6g 타입을 고려해보시는 것도 좋습니다.

  • 성능 향상을 위해 최신 버전의 인스턴스 타입과 OpenSearch 버전의 업그레이드를 고려하십시오.

  • 가능한 샤드 allocation을 직접 시도하시 마십시오, 샤드 갯수와 노드 수, az의 배수의 데이터 노드수 등을 잘 정의하시면 알아서 샤드가 분배됩니다.

    • 데이터 노드의 경우 현재 16대가 있는데, 3az를 사용중이라면 3의 배수로 하시는 것이 좋습니다. 15대 또는 18대로 변경하시는 것을 추천드립니다.

    • https://docs.aws.amazon.com/ko_kr/opensearch-service/latest/developerguide/bp.html#bp-sharding-strategy

  • 공부가능한 워크샵

    • https://catalog.us-east-1.prod.workshops.aws/workshops/f0213896-4dd9-494a-89c5-f7886b45ed4a/ko-KR

  • 키워드, 텍스트 학습 링크

    • 직접적인 링크 공유를 드리기 어려워서 구글에서 “elastic 가이드북”이라고 찾아보시면 한글로 잘 정리된블로그가 있습니다. 여기서 참고해보시면 개인적인 학습에 도움이 되시리라 생각합니다.

Meeting @May 3, 2023

Cost Estimation

  1. Check if the cluster is right sized - Monitor CPU/JVMMP/Free Storage metrics and see if the cluster is overprovisioned(eg - <30% CPU). If so, you can scale down the instance type/reduce number of nodes.
  2. If this is a log analytics workload, where logs are stored for compliance reasons, customers could use ultrawarm and move the data to ultrawarm node where compute and storage are decoupled and cost is significantly less for ultrawarm nodes - https://aws.amazon.com/opensearch-service/pricing/

OpenSearch domain sizing

  • https://docs.aws.amazon.com/opensearch-service/latest/developerguide/sizing-domains.html

  • Index type 구분

    • Long-lived index : 소스 데이터의 변화를 주기적으로 업데이트 하게 되는 경우. 문서, 검색 데이터 등

    • Rolling index : 임시 인덱스 세트로 계속 유입되는 데이터. log 분석, 시계열 처리, 클릭 스트림 분석 등의 경우

  • Source data 크기 산정

    • 주요 기간에 생성된 데이터의 양에 보존 기간을 곱하여 산정. 시간당 200MB 로그가 생성될 경우 하루 4.7GB 생성되고 보존 기간이 2주일 경우 66GB 데이터 생성

    • Replica 수 반영 : 1 → x 2

    • Indexing overhead 반영 : 10% → x 1.1

    • OpenSearch 서비스 overhead 반영 : 15% ~ 20% → x 1.15 or x 1.2

  • Instance type

    • c5.xlarge → c6.xlarge (cost saving)
