Lift and Shift

나온소프트 그룹웨어/ERP AWS EC2 Lift and Shift 마이그레이션 가이드

1. 마이그레이션 개요

Lift and Shift 방식은 애플리케이션 코드를 변경하지 않고 온프레미스 환경에서 AWS 클라우드로 워크로드를 빠르게 이전하는 전략입니다[1]. 제공된 인벤토리 리스트를 기반으로 나온소프트의 그룹웨어와 APLUS ERP 시스템을 AWS EC2로 효율적으로 마이그레이션하기 위한 단계별 가이드를 제공합니다[2]. AWS Application Migration Service(MGN)를 활용하면 복잡한 수동 프로세스를 최소화하고 전체 서버를 자동으로 복제하여 마이그레이션 과정을 간소화할 수 있습니다[3].

2. 인프라 분석 및 계획

2.1 현재 인프라 구성 분석

제공된 인벤토리 리스트를 분석한 결과, 다음과 같은 서버 구성이 확인되었습니다[4]:

  • 그룹웨어 시스템: 개발서버 1대, 운영서버 2대(active-standby), 메신저/이미지변환 서버 1대, DB 서버 2대(active-standby)

  • ERP 시스템: 개발서버 1대, 운영서버 2대(active-standby), DB 서버 2대(active-standby)

  • 운영체제: 모든 서버가 Rocky Linux 8.6/8.10 기반

  • 애플리케이션: Apache, Tomcat, MariaDB, PostgreSQL 등 구성

2.2 AWS 인프라 계획

온프레미스 환경의 서버 사양을 기반으로 AWS EC2 인스턴스 유형을 선택해야 합니다[5]. 인벤토리 분석 결과에 따른 권장 EC2 인스턴스 유형은 다음과 같습니다[6]:

  • 그룹웨어 서버(48 vCore): m5.12xlarge 또는 c5.12xlarge (CPU 사용률이 낮으므로 m5 계열 권장)

  • 그룹웨어 DB 서버(48 vCore): r5.12xlarge (메모리 최적화 인스턴스)

  • ERP 서버(16/32 vCore): m5.4xlarge 또는 c5.4xlarge

  • ERP DB 서버(16 vCore): r5.4xlarge (메모리 최적화 인스턴스)

스토리지 구성은 EBS 볼륨을 사용하여 온프레미스 환경과 유사하게 구성할 수 있습니다[7].

3. AWS Application Migration Service(MGN)를 활용한 마이그레이션

3.1 사전 준비 단계

  1. AWS 계정 및 IAM 설정

    • AWS 계정 생성 및 필요한 권한을 가진 IAM 역할 설정[2]

    • AWS MGN 서비스에 필요한 권한 부여[2]

  2. 네트워크 연결 설정

    • 온프레미스와 AWS 간 안정적인 네트워크 연결 구성(AWS Direct Connect 또는 VPN)[1][8]

    • 적절한 대역폭 확보 (데이터 크기와 마이그레이션 일정 고려)[2]

  3. AWS MGN 초기화

    • AWS 콘솔에서 Application Migration Service 초기화[2]

    • 복제 설정 템플릿 구성[2]

3.2 마이그레이션 실행 단계

  1. 소스 서버에 복제 에이전트 설치

    • 각 소스 서버에 AWS MGN 복제 에이전트 설치[2]

    • Linux 서버용 설치 명령어 실행[2]

  2. 초기 데이터 복제

    • 에이전트 설치 후 초기 데이터 복제 시작[2]

    • 복제 상태 모니터링 및 문제 해결[2]

  3. 테스트 및 검증

    • 테스트 인스턴스 시작 및 구성 검증[2]

    • 애플리케이션 기능 테스트 수행[2]

  4. 전환 계획 및 실행

    • 전환 일정 수립 및 다운타임 최소화 계획[1]

    • 최종 전환 실행 및 검증[2]

4. 데이터베이스 마이그레이션 전략

4.1 MariaDB 마이그레이션 (그룹웨어)

그룹웨어 시스템의 MariaDB는 다음과 같은 방법으로 마이그레이션할 수 있습니다:

  1. AWS MGN을 통한 전체 서버 마이그레이션

    • 서버 전체를 복제하여 데이터베이스 포함 마이그레이션[2]

    • 기존 설정 및 구성 유지[2]

  2. 고가용성 구성 설정

    • EC2 인스턴스에서 MariaDB Galera Cluster 구성으로 고가용성 확보[9]

    • EBS Multi-Attach 기능을 활용한 단일 AZ 내 고가용성 구성[10]

    • 기존 active-standby 구성 유지를 위한 설정[11]

4.2 PostgreSQL 마이그레이션 (ERP)

ERP 시스템의 PostgreSQL 데이터베이스는 다음과 같은 방법으로 마이그레이션할 수 있습니다:

  1. AWS MGN을 통한 전체 서버 마이그레이션

    • 서버 전체를 복제하여 데이터베이스 포함 마이그레이션[2]

    • 기존 설정 및 구성 유지[2]

  2. 네이티브 PostgreSQL 도구를 활용한 마이그레이션

    • pg_dump 및 pg_restore 도구를 사용한 데이터베이스 마이그레이션[12]

    • 기존 active-standby 구성 유지를 위한 설정[12]

5. 스토리지 및 백업 전략

5.1 스토리지 구성

인벤토리 리스트에 기반한 스토리지 구성 방안은 다음과 같습니다[7]:

  1. 루트 볼륨: gp3 EBS 볼륨 (OS 및 애플리케이션용)

  2. 데이터 볼륨:

    • 그룹웨어: io2 또는 gp3 EBS 볼륨 (2TB /gwstore 볼륨)

    • ERP: io2 또는 gp3 EBS 볼륨 (데이터 저장용)

  3. 고성능 요구사항: 높은 IOPS가 필요한 데이터베이스 서버는 io2 EBS 볼륨 권장[7]

5.2 백업 전략

AWS 환경에서의 효과적인 백업 전략은 다음과 같습니다[13]:

  1. AWS Backup 서비스 활용

    • 자동화된 백업 일정 설정[13]

    • 백업 보존 정책 설정 (인벤토리 리스트 기준 1년)[4][13]

  2. 다중 리전 재해 복구 계획

    • 백업 데이터의 다중 리전 복제 구성[13]

    • 리전 장애 시 신속한 복구 가능[13]

  3. 스냅샷 수명 주기 관리

    • 비용 최적화를 위한 스냅샷 수명 주기 정책 설정[13]

    • 백업 데이터 암호화 적용[13]

6. 네트워크 및 보안 구성

6.1 VPC 및 서브넷 구성

AWS 환경에서의 네트워크 구성은 다음과 같이 설계할 수 있습니다[8]:

  1. VPC 설계

    • 프라이빗 서브넷에 애플리케이션 및 데이터베이스 서버 배치[8]

    • 퍼블릭 서브넷에 로드 밸런서 및 배스천 호스트 배치[8]

  2. 보안 그룹 구성

    • 서버 유형별 적절한 보안 그룹 설정[8]

    • 최소 권한 원칙에 따른 네트워크 액세스 제어[8]

6.2 고가용성 구성

인벤토리 리스트에 나타난 active-standby 구성을 AWS 환경에서도 유지하기 위한 방안은 다음과 같습니다[11][10]:

  1. 다중 가용 영역 배포

    • 서버를 여러 가용 영역에 분산 배치하여 가용성 향상[10]

    • 자동 장애 조치 메커니즘 구성[11]

  2. 로드 밸런서 활용

    • Application Load Balancer 또는 Network Load Balancer를 통한 트래픽 분산[1]

    • 상태 확인을 통한 장애 서버 자동 감지[1]

7. 마이그레이션 실행 계획

7.1 단계별 마이그레이션 계획

전체 시스템을 한 번에 마이그레이션하는 것보다 단계적으로 진행하는 것이 위험을 최소화할 수 있습니다[2]:

  1. 1단계: 개발 환경 마이그레이션

    • 그룹웨어 개발서버 및 ERP 개발서버 마이그레이션[4][2]

    • 기능 검증 및 문제점 파악[2]

  2. 2단계: 비핵심 시스템 마이그레이션

    • 메신저/이미지변환 서버 마이그레이션[4][2]

    • 기능 검증 및 문제점 파악[2]

  3. 3단계: 핵심 시스템 마이그레이션

    • 그룹웨어 운영서버 및 DB 서버 마이그레이션[4][2]

    • ERP 운영서버 및 DB 서버 마이그레이션[4][2]

    • 전체 시스템 통합 테스트[2]

7.2 마이그레이션 테스트 및 검증

마이그레이션 후 시스템 검증을 위한 테스트 계획은 다음과 같습니다[2]:

  1. 기능 테스트

    • 모든 애플리케이션 기능이 정상 작동하는지 확인[2]

    • 사용자 시나리오 기반 테스트 수행[2]

  2. 성능 테스트

    • 마이그레이션 전후 성능 비교[2]

    • 필요시 인스턴스 유형 조정[14]

  3. 장애 복구 테스트

    • 장애 상황 시뮬레이션 및 복구 절차 검증[2]

    • 백업 및 복원 기능 테스트[13]

8. 마이그레이션 후 최적화

8.1 비용 최적화

AWS 환경에서의 비용 최적화 방안은 다음과 같습니다[14]:

  1. 인스턴스 크기 최적화

    • 실제 사용량에 기반한 인스턴스 크기 조정[14]

    • 4주 동안 CPU 및 메모리 사용률이 40% 미만인 경우 인스턴스 다운사이징 고려[14]

  2. 예약 인스턴스 활용

    • 안정적인 워크로드에 대해 예약 인스턴스 구매로 비용 절감[14]

    • 사용 패턴에 따른 적절한 예약 인스턴스 유형 선택[14]

8.2 운영 최적화

AWS 환경에서의 효율적인 운영을 위한 방안은 다음과 같습니다[1][2]:

  1. 모니터링 및 알림 설정

    • CloudWatch를 활용한 시스템 모니터링 구성[1]

    • 주요 지표에 대한 알림 설정[1]

  2. 자동화 구성

    • 인프라스트럭처 코드화(IaC)를 통한 환경 관리[15]

    • 자동 확장 그룹 설정으로 부하에 따른 자동 확장/축소[14]

  3. Rocky Linux 최적화

    • AWS MGN의 CentOS에서 Rocky Linux로의 변환 기능 활용 (필요시)[16]

    • AWS 환경에 최적화된 설정 적용[16]

10. 결론

제공된 인벤토리 리스트를 기반으로 AWS Application Migration Service(MGN)를 활용한 Lift and Shift 방식의 마이그레이션 계획을 수립하였습니다[1][2]. 이 계획은 현재 온프레미스 환경의 구성을 최대한 유지하면서 AWS 클라우드의 이점을 활용할 수 있도록 설계되었습니다[1]. 단계적인 마이그레이션 접근법과 철저한 테스트를 통해 위험을 최소화하고 성공적인 마이그레이션을 달성할 수 있습니다[2]. 마이그레이션 후에는 AWS의 다양한 서비스와 기능을 활용하여 시스템의 가용성, 확장성, 보안성을 더욱 향상시킬 수 있을 것입니다[3].
