Query Timeout

Issue)

  1. OLAP 솔루션 MSTR 에서 리포트 조회할 때 1분가량 로딩되다가 조회조건에 대한 결과값을 받기 전 504 Timeout 오류 발생

  • 현재 MSTR 솔루션의 Time설정값은 => ‘요구 시간 초과’ 설정은 300초 로 설정 되어 있음

  • 그래서 MSTR 상에서 504오류를 뱉어내는 상황은 아니라고 판단됨

  • 의심되는 사항 : AWS 의 ELB 설정값이 기본 60초로 되어 있다고 하나 직접 확인한 부분은 아님, 구글링해서 찾은 내용 => AWS 내부 설정값 확인 필요함

  1. Timeout 발생시점 Redshift 로그확인결과 15일은 오류로 뱉어냄, 16일은 정상수행됨
  1. 11/16 09:02~ Redshift 프롬프트 실행쿼리

  • 2021.11.16 09:02 (KR시간) 정상수행됨

  • 시작시간 = 2021-11-16 00:01:55 종료시간 = 2021-11-16 00:03:58 (time laps = 2분 3초)

  1. 11/15 08:18~ Redshift 프롬프트 실행쿼리

  • 2021.11.15 08:18 (KR시간) 쿼리 실패

  • 시작시간 = 2021-11-14 23:17:58 종료시간 = 2021-11-14 23:18:12 (time laps = 14초)

💡

11/15 발생했을 때는 Redshift에서 쿼리에 오류유형으로 뱉어냈었는데
11/16 발생했을 때는 15일보다는 수행시간이 좀 길어졌지만 Redshift 로그상에서는 정상수행으로 찍히고 timeout이 발생했습니다

참고

  • select a13 xxxx → time laps 1분 이하

  • 오전 8시30분~10시 30분 사이 배치 스케줄이 가장 많이 돌아가는 상황

상황 정리

  • 오전 8시 30분 이전에 Redshift 프롬프트 timeout 에러 발생

    • 다른 시간 대 발생 오류는 없는지?

    • 오류 발생 시 Redshift Log가 있는지?

  • Prompt query를 batch 명령과 별도로 실행 하였는지?

    • batch 실행 부하 영향?

  • ELB timeout 기본 값? ELB 에서 timeout 오류가 발생하면 504 오류를 Reply 하는가?

    • ELB_500x metric을 통해 확인할 수 있음

  • TimeOut 값을 Application 구성에 따라 조정 필요하며 너무 길게 설정하면 전체 응답 성능에 영향을 줄 수 있으므로 적절한 고려가 필요

전달해 주신 내용들을 바탕으로 다음과 같이 현황과 개선 포인트에 대해 정리해 보았습니다.

현재 이슈에 대해서는 이미 전달 드린 대로 ALB Idle timeout값 조정으로 504 timeout에 대한 조치가 가능하며

좀더 근본적인 대책으로는 Batch Job의 영향을 최소화 하기 위한 Queue 분리가 좋을 것으로 보입니다.

향후 Batch Job Scheduling 변경을 위한 강건한 워크로드 구성에 대해서는 좀더 논의를 진행하며 개선 포인트를 구체화 시켜야 할 것 같습니다.

[ 현황]

  1. BI Application인 MSTR을 통해 크게 2종류의 쿼리 수행

  1. 리포트 실행 시 프롬프트 리스트를 가져오기 위해 수행되는 쿼리 : 기준 정보 테이블에 수행하는 쿼리로 100여개의 조회 조건을 가져오며 수행 시간은 통상10초 이내로 처리.  (Short Query Type)

  2. 프롬프트 실행 시 수행된 조회 조건으로 실제 데이터를 로드 하는 쿼리 : 대용량 테이블에 수행하는 쿼리로 대량의 결과 데이터가 반환 되며 수행 시간은 1분 이상 소요.

  1. 리포트 실행 시WEB 서비스에서 504 Error가 발생

  1. 리포트 실행이Batch Job 수행 시간에 요청될 경우 2분 이상 소요되면서 504 Timeout Error 발생.

  2. Batch Job은 하루 3회 각 3시간 정도의 시간 동안 수행.

  3. 향후 Batch Job Scheduling 간격을 hourly로 변경할 예정.

  1. MSTR에서 Redshift 쿼리 수행 시 오류 발생

  1. 504 Error 발생 시 프롬프트 쿼리에 대한 실패 로그 발생.

  2. AWS Support Team 확인 결과 Redshift 에서는 오류가 발생 하지 않았으며 MSTR과 Redshift간 TCP keep-alive 유지에 대한 설정 확인 필요.

[개선 포인트]

  1. 리포트 실행 시 504 Error 발생

  1. WEB  서비스 인스턴스 (Lena)와 ALB간의 Idle Timeout 값이 MSTR의 DW (Redshift) 응답 대기 시간 (300초) 이상으로 설정하여 ALB와 WEB간의 연결 상태 유지.

  2. 프롬프트 실행 요청에 대한 응답 처리를 Async 방식으로 구성 하여 MSTR 응답 대기 시간에 영향 받지 않고 WEB 인스턴스와 ALB간 연결을 유지 하도록 변경. 이 경우에는 ALB Idle Timeout 조정 필요 없음.

  1. 프롬프트 리스트 조회 작업 시간 지연 발생

  1. 현재 단일 작업 Queue로 구성 되어 있으며 프롬프트 처리 요청이 Queue에 대기하고 있는 Batch Job 이 처리 될 때까지 대기 하면서 발생하는 것으로 추측 됨.

  2. WLM에서 Batch Job 처리 Queue와 프롬프트 처리 Queue를 분리하여 구성하여 Batch Job  수행 영향을 최소화. (WLM Queue 구성 변경 실습 예제)

  1. TCP keep-alive 값 설정 ( TCP/IP 설정 관련 추가 문의에 대한 답변 입니다)
  1. /etc/sysctl.conf에 값을 저장하는 것은default가 아닌 지정 값을 부팅 이후에도 계속 사용할 수 있도록 유지하기 위해서 이며 default 값을 유지 한다면 별도로 값을 저장할 필요는 없음.
  1. Redshift Workload 최적화를 위해 아래의 항목들에 대한 검토가 필요하며 다음 링크를 통해 개별 항목들의 상세한 내용을 확인할 수 있습니다.

  1.  Query 수행 상태에 대한 metric 모니터링 및 Redshift Advisor 권장 사항 확인

  2. Batch Job 간격을 줄이기 위해 Batch 작업 수행 시간에 대한 분석

  3. 주요 Query에 대해  Explain 명령어로 실행 계획 분석 및 지연 발생 가능 요소 검토

  4. WLM 구성 최적화
