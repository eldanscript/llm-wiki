Demand-Driven Context (DDC): 에이전트 실패를 통한 일관된 지식베이스 구축 방법론

IKEA 스태프 소프트웨어 엔지니어 Raj Navakoti가 AI Engineer Europe 워크숍(2026-05-05)에서 발표한 방법론. 기업 AI 도입이 88%에 달하지만 가치 창출이 6%에 그치는 근본 원인을 institutional knowledge(암묵지)의 비구조적 monolith 상태로 진단하고, 에이전트 실패를 통해 지식 격차를 탐지·큐레이션하는 ‘풀(pull)’ 방식의 지식 관리 사이클을 제시한다.

핵심 문제: 기업 지식의 Monolith 구조

  • AI/에이전트의 실패 지점: 에이전트는 추론·코드생성에 뛰어나지만 기업 고유 암묵지(institutional knowledge)에서 반복 실패한다 — 영화 ‘Memento’의 기억상실 비유로 설명
  • 지식 monolith 구성 비율:
    • 20% outdated (예: last_updated_1997.pdf)
    • 20% unreliable (예: final_real_final.doc)
    • 10% duplicated (예: copy_of_copy.xlsx)
    • 40% tribal knowledge — 문서화되지 않은 채 사람만 아는 지식 (파이차트에서 절반 가까이 차지)
  • 기존 retrieval 계층의 한계: RAG·MCP·지식그래프는 ‘푸시(push)’ 방식 — 데이터가 비결정적이고 검증되지 않음. MCP/RAG를 10~20개 구축해도 monolith 자체가 깨지지 않으면 소용없다
  • 핵심 비유: legacy monolith를 microservice로 전환하듯 지식도 쪼개야 한다

DDC 방법론: Pull 전략의 6단계 사이클

PROBLEM → AGENT FAILS → CHECKLIST → FILL GAPS → CURATE → SUCCEEDS
(반복, 사이클당 30~60분)

동작 원리 (신입사원 온보딩 비유)

  1. PROBLEM: 에이전트에 실제 업무 문제를 부여 (Jira 인시던트, 버그 티켓 등)
  2. AGENT FAILS: 에이전트가 institutional knowledge 부재로 실패
  3. CHECKLIST: 실패 원인 분석 → 부족한 지식 항목 체크리스트 생성
  4. FILL GAPS: 사람이 체크리스트 기반으로 그 격차만 채움
  5. CURATE: 에이전트가 채워진 지식을 재사용 가능한 구조화 컨텍스트 블록으로 큐레이션
  6. SUCCEEDS: 동일 문제 재시도 성공 → 다음 사이클로

TDD와의 유사성

  • 실패하는 테스트(문제)를 먼저 주고 실패 원인(gap)에 맞춰서만 지식을 채우는 접근
  • 불필요한 지식 사전 적재 없이 수요(demand)가 발생한 시점에만 지식 추가

결과물 저장 구조

GitHub 저장소 권장

  • PR/리뷰 프로세스가 내장되어 여러 팀·에이전트의 동시 기여 충돌 관리
  • 구조화된 엔티티를 버전 관리 가능한 파일로 저장

메타모델 (Meta Model)

13개 엔티티 타입:

  • Systems, APIs, Platforms, Processes, Business Events
  • Data Models, Data Products, Teams, Personas, Capabilities
  • Offerings, Business Jargon, Tech Jargon

관계 예시 (relationships.yaml):

  • 메타모델은 필수가 아니지만 에이전트가 지식베이스를 ‘지도’처럼 탐색하게 해주는 강력한 부가 요소

DDC의 전체 파이프라인 위치

CONTEXT (Confluence/Jira/SharePoint/GitHub/Slack)
  'messy, tribal, outdated'
    ↓
  DDC (Extract/Curate) — 'the missing piece'
    ↓
  CURATED BLOCKS ('structured, agent-ready')
    ↓
  RETRIEVAL (RAG/Graph RAG/MCP/API)
    ↓
  AGENT (Skills/Hooks/Rules/Specs)
    ↓
  ROI ('Domain-expert reasoning. Not just code — business delivery.')

80/20 법칙 적용

  • 문서의 20%만 실제로 유용 → 그 20%를 캐시처럼 컨텍스트 블록에 담음
  • 나머지 80%는 링크로만 남겨 필요 시에만 접근
  • 지식베이스 건강도 예시:
    • APIs: 89 clean / 47 stale / 23 incomplete / 11 missing / 2 tribal
    • Processes: 8 clean / 5 stale / 12 incomplete / 15 missing / 19 tribal (취약 영역)

한계 및 비판

  • DoS 위험: 팀원들에게 지속적 질문 공세가 부담이 될 수 있음 (발표자도 동의)
  • 최신성 보장 불가: 최신 정보가 항상 옳다는 보장 없음 → 최신 수정일 기반 필터링과 duplicate 플래깅으로 일부 완화
  • 유지보수 비용: 지식 엔티티 지속 관리 필요
  • 코드-문서 소스오브트루스 충돌: 코드와 문서 간 진실의 원천이 충돌할 때 판단 기준 필요

전략적 시사점

  • 에이전트 실패 = 지식 격차 탐지 신호: 실패를 회피하지 않고 적극 활용해 지식베이스를 구조화
  • 수요 기반 큐레이션: 미리 모든 문서를 벡터화하는 대신, 실제로 필요한 지식만 엔티티로 추출 → 유지보수 비용 절감
  • DDC ≠ RAG 대체: DDC는 RAG 앞단의 ‘큐레이션 레이어’ — 기존 retrieval 인프라를 대체하지 않고 보완
  • GitHub as Knowledge Infra: 코드 협업 인프라를 지식 협업에도 재활용 — 리뷰·버전 관리 공짜로 확보
  • Agent-Context-Engineering과의 교차: 두 방법론 모두 ‘에이전트가 context 부족으로 실패하는 문제’를 다루지만, DDC는 지식 큐레이션 레이어에, Polygraph는 세션 기억 및 멀티 레포 컨텍스트에 초점
