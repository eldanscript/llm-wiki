LLM 메모리를 프로그램 분석으로 바꾼 Lemmalog

Jordy Zomer가 취약점 리서치용 LLM 에이전트의 고질적 문제(이미 틀렸다고 확인한 가설을 몇 시간 뒤 다시 꺼내거나, 전제가 깨졌는데 결론은 그대로 믿는 현상)를 프로그램 분석 문제로 재정의하고, Datalog 엔진 Lemmalog로 해결한 사례 연구 (pwning.systems, 2026-08-28).

핵심 통찰

  • 문제 재정의: “기억”이 아니라 “지금 뭐가 참인지 유지하기(truth maintenance)“가 핵심이다 — 관찰이 바뀌면 그로부터 파생된 결론도 자동으로 무효화되어야 한다.
  • 구조적 동형: 공격자가 객체를 제어한다 → 그 객체가 커널 객체를 가리킨다 → 공격자가 커널 객체를 제어한다 — 이 추론 체인이 프로그램 분석과 LLM 에이전트 메모리 유지 모두에 동일하게 적용된다.
  • 벡터DB의 한계: 벡터DB 기반 메모리는 “과거에 뭘 말했는지”는 잘 찾지만 “지금 뭐가 참인지”는 유지하지 못한다.
  • 사실 철회(retraction)의 복잡성: 결론 하나가 여러 독립된 근거로 지지될 수 있어, 근거 하나가 사라져도 다른 근거가 남아 있으면 결론은 유지돼야 한다.
  • Provenance(근거 추적): 의존성 추적의 부산물로 “왜 그렇게 결론 내렸는지”를 소급 추적할 수 있다 — 근거가 없는 결론은 유지 상태(state)에 속하지 않은 것으로 구분된다.
  • 시간 사실(temporal facts): 유효 구간(validity interval)을 붙여 시간에 따라 달라지는 값을 모순 없이 표현한다 — 예: viable(primitive_a) [10:14, 12:37) → not_viable(primitive_a) [12:37, ...).
  • 이중 메모리 구조: 최종 결론은 “연역적 상태(사실·규칙·시간·근거·철회)“와 “일화적 메모리(퍼지 컨텍스트·의미 검색·원문)” 두 레이어를 함께 쓰는 구조 — 양자택일이 아닌 상호 보완.

Lemmalog 아키텍처

컴파일러 3단계에 비유:

단계역할특성
프런트엔드 (LLM)자연어·코드·디버거 출력 → 구조화된 사실(fact)확률적
중간표현·분석 엔진 (Lemmalog)사실 → 규칙 적용 → 의존성 추적 → 유지 상태결정론적
백엔드 (LLM)유지된 상태 → 자연어 설명·다음 실험 제안·행동 수행확률적

Lemmalog 지원 기능: 증분 평가(incremental evaluation)·철회(retraction)·근거 추적(provenance)·시간 사실(temporal facts)·집계·개체 동일성 해소·하이브리드 검색·요구 기반 질의(demand-driven query)·MCP 서버.

  • 토큰 절감: 질의당 Full Context ~104,000 토큰 vs Lemmalog ~2,700 토큰 (약 38배 절감)

  • 개선 이력: 최초 F1 0.226 → 개체 해소·날짜 정규화·어간 처리·거부 로직 수정 → 0.463

디버깅 인사이트

  • LongMemEval F1 0.371 급락 사건: 102문항 중 32건이 거부 — “근거에 없으면 거부하라” 지시를 모델이 집계·비교 질문에도 확대 적용했기 때문
  • 어간 처리 버그: 복수형 어간 처리기가 4글자 이하 단어(owns→own)를 처리하지 못해 카운트 관련 사실이 관련성 필터에서 전부 누락 → 수정 후 F1 0.463까지 회복
  • LoCoMo 개선 출처: 대부분의 성능 향상이 Datalog 엔진 자체가 아니라 프런트엔드(추출 파이프라인) 개선에서 발생 — 개체 동일성 해소, BM25+그래프+임베딩 혼합 검색 전환 등

추출 설정

  • 추출 단계: Claude Sonnet 4.6 (청크·파일 캐시로 대화당 1회 과금)
  • 평가: 각 벤치마크 표준 리더·저지 모델 그대로 사용
  • 비교 대상: PropMem, SimpleMem, OpenClaw, Hindsight, Graphiti, Memory-R1
