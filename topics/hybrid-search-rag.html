하이브리드 서치 — RAG 검색 최적화의 시작

Doug Turnbull(softwareDoug)이 Hamel Husain 채널에서 발표한 하이브리드 서치 실전 가이드. 렉시컬 검색(lexical)과 벡터 검색(vector)을 결합하는 방법론과 실무 설계 원칙을 다룬다.

핵심 내용

  • 하이브리드 서치 정의 — 렉시컬 검색(순수 문자열 매칭)과 벡터 검색(임베딩 기반 통계적 유사도)을 결합한 검색 아키텍처
  • 임베딩의 역할과 한계 — 임베딩은 문서 전체를 아우르는 좋은 1차 후보군(first-pass retrieval) 제공에 탁월하지만, 정확한 이름 매치나 속성 매치는 쿼리 이해(query understanding) 후 부스트/재랭킹으로 보완 필요
  • 임베딩 생성 원칙 — 제목만이 아닌 설명까지 concat하여 임베딩 생성 필수. text_concatted = product_name + ' -- ' + product_description
  • Two-Tower 임베딩 — 짧은 쿼리와 긴 문서가 같은 유사도 공간에 매핑되어야 함(two-towerable). 이를 만족하는 임베딩 모델 선택이 중요
  • 프리필터링(Prefiltering)이 핵심 — 벡터DB의 진짜 경쟁력은 HNSW 알고리즘 자체가 아니라 벡터 유사도 계산 이전에 얼마나 잘 프리필터링할 수 있는가
  • RRF의 한계 — Reciprocal Rank Fusion은 두 검색 시스템 품질이 비슷할 때만 유효하며, 최종 목표가 아닌 임시방편으로 간주. ‘RRF is Not Enough’ 블로그 참고
  • Candidate Arm 병렬 아키텍처 — 여러 개의 candidate arm(렉시컬 필터+벡터 정렬, 순수 벡터, 카테고리 필터, 이미지 임베딩, 순수 렉시컬 스코어 등)을 병렬로 뽑아 합친 뒤 상위 레이어에서 부스팅·재랭킹
  • ‘두 개의 top K’ 원칙 — 필터링된 top100뿐 아니라 순수 벡터 매치 top100도 UNION ALL로 함께 가져와야 원하는 후보를 놓치지 않음
  • 포스트필터링 경계 — 포스트필터링은 안전망으로만 사용. 초기 단계에서 결과 대부분을 걸러내는 것은 비효율적

하이브리드 서치 파이프라인 구조

쿼리 이해(Query Understanding)
  └─ 속성 파싱 (색상·브랜드·카테고리 등)
  └─ 필터 vs 부스트 결정

Candidate Arm (병렬)
  ├─ Arm A: 렉시컬 매치 + 벡터 정렬 (프리필터)
  ├─ Arm B: 전체 term 매치
  ├─ Arm C: 카테고리 필터
  ├─ Arm D: 이미지 임베딩
  └─ Arm E: 순수 렉시컬 스코어

Merge & Rerank
  ├─ 부스팅 (상품명 인덱스 매치 가산점 등)
  ├─ 재랭킹 (cross-encoder 등)
  └─ 포스트필터 (안전망)

쿼리 이해와 설계 난점

  • 색상·브랜드명 등 속성을 파싱해 필터로 켤지 부스트로 처리할지 결정하는 것이 어려운 설계 포인트
  • Chicken-and-Egg 문제: 승격시키려는 후보가 애초에 1차 후보군에 있어야 부스트가 의미 있음
  • 필터 적용 시 재현율(recall) 저하 위험 → ‘두 개의 top K’ 패턴으로 보완

평가 방법

  • 골든 데이터셋 없을 때: ‘Pepsi-Coke 챌린지’(블라인드 사이드바이사이드 비교)로 변화된 쿼리 표본을 팀에 노출시켜 체크
  • 평균 NDCG보다 tail 분포: 소수 쿼리를 의도대로 크게 개선하고 나머지는 거의 안 변한 경우가 전체 NDCG를 조금 올리고 분산이 큰 경우보다 안전
  • RAG의 검색 품질 관대함 경계: RAG는 응답 지연에 관대해(텍스트 스트리밍 중 시간을 벌 수 있어) 부실한 검색 설계도 눈감아주는 경향. 경계 필요
