적응형 소프트웨어 배포: 파이프라인의 종말

Sky Valley Ambient Computing 공동창업자 Iris ten Teije가 AI Engineer World’s Fair 2026(2026-07-07)에서 발표한 개념. 코드 생성 비용이 0에 수렴하면서 ‘하나의 버전, 모두에게’라는 소프트웨어 배포의 근본 전제가 무너지고 있으며, 스템(Stem) + 사용자별 디버전스(Divergence) 구조가 그 대안이라는 주장이다.

발표 개요

  • 발표자: Iris ten Teije (공동창업자, Differ / Sky Valley Ambient Computing)
  • 공동창업자: Noam (JFrog 최초 엔지니어, 파이프라인 설계 당사자)
  • 발표자 배경: 핀테크 10년 경력, 디지털 뱅크 초기 합류·스케일업·엑싯
  • 행사: AI Engineer World’s Fair 2026 (2026-07-07)
  • 원본 영상: https://www.youtube.com/watch?v=bRnoEpoK5m4

핵심 주장: 파이프라인은 왜 만들어졌나

기존 전제의 해부

  • 기존 CI/CD 파이프라인 전체는 단 하나의 전제 위에 서 있다: 소프트웨어는 한 곳에서 만들어져 얼어붙은(frozen) 아티팩트로 모두에게 동일하게 배포된다
  • 이 전제는 기술적 필연이 아닌 경제적 타협이었다 — 올바른 변경을 만드는 데 숙련된 인력의 수 시간~수 일이 필요했기 때문에 생긴 방식
  • ‘하나의 버전, 모두에게’는 누가 의식적으로 선택한 결정이 아니었다 — 개인화 버전이 선택지에 없었을 뿐이다

전제가 무너지는 이유

  • AI 코딩 에이전트로 인해 정확한 변경을 만드는 비용이 0에 수렴 → 개발과 배포를 분리할 이유가 사라짐
  • 코드를 배포하는 것이 실행하는 것만큼 저렴해지면, 개발과 배포의 경계 자체가 소멸한다

개인화 소프트웨어 수요의 3가지 선례

슬라이드 캡션: ‘THE DEMAND IS OLD. THE RATIONING CHANGED.’

#사례의미
01전문 서비스 (Forward Deployed Engineer)‘맞춤의 가격’ — 수십 년간 기업들이 개인화 소프트웨어에 프리미엄을 지불해 온 증거
02Dotfiles’수요가 새어나오다’ — 개발자들이 직접 환경을 커스터마이징한 수십 년간의 역사
03Excel’프로그램이 아닌 기판(substrate)’ — 사용자가 스스로 맞춤화하는 소프트웨어의 원형

Differ의 아키텍처: 스템 + 디버전스

핵심 구조

  • 스템(Stem): 하나의 캐노니컬 베이스라인 소프트웨어
  • 디버전스(Divergence): 사용자별로 격리·불변·롤백 가능한 개인화 레이어
    • 각 디버전스는 한 사용자 컨텍스트로 blast radius 제한
    • 개별 롤백 가능 → 전체 시스템 영향 없이 특정 사용자 상태만 되돌리기 가능
    • 검사(inspect) 가능 → 무엇이 바뀌었는지 추적 가능

자동 관찰-대응 메커니즘

  • 시스템이 사용자 행동을 관찰(observe) → 패턴 감지 → 코드 변경으로 적응
  • 예시: Quick actions panel was never opened — 0 interactions across 214 sessions → 패널 삭제, 320px 콘텐츠 공간 확보 (자동 코드 diff 생성)
  • 개발자는 결제·인증 등 특정 영역을 ‘적응 금지(no-adapt boundary)‘로 설정 가능

Acme CRM 데모 요약

  • 사용자(Priya)의 CRM 사용 패턴 자동 학습:
    • ‘Warm Intro Path’ 자동 생성 (Cold → Priya → Wei Zhang)
    • 반복적으로 스킵하는 필드(Close date) 자동 제거
    • ‘Relationships by priority’ 뷰로 자동 재구성
  • 결과: ‘This is Priya’s CRM now.’ + ‘Replay from baseline’ 롤백 버튼 제공

5가지 하드 챌린지

챌린지설명Differ의 접근
계보(Lineage)버전 번호 대신 변경 이력 그래프 추적그래프 쿼리 기반 계보 추적
정확성(Correctness)스템 + 모든 디버전스 조합에 대한 테스트디버전스별 독립 테스트
데저러빌리티(Desirability)변경이 실제로 개선인지 지표로 검증사용자 행동 지표 연동
자율성 vs 통제시스템이 너무 자율적이면 신뢰 이탈신뢰 획득 후 점진적 승인 완화
조율(Coordination)코드가 아닌 ‘의도·결과’를 머지의도 기반 조율 레이어

핵심 통찰: 코드 생성 자체는 이미 쉬워진 ‘쉬운 80%’. 진짜 어려운 부분은 관측성·검증·조율이며, 이것이 Differ가 만드는 사업의 본질이다.

Differ 전체 아키텍처

슬라이드 캡션: ‘GENERATION GOT CHEAP. COORDINATION GOT HARD.‘

INPUTS
  ├── AI Generation
  ├── Agent Runtime
  └── User Context
         ↓
    [DIFFER]
  ├── Adaptations
  ├── Versioning
  ├── Delivery
  └── Coordination
         ↓
OUTPUTS
  ├── UI
  ├── Behavior
  ├── Agent Surface
  └── Dev Surface

전략적 시사점

  • 소프트웨어 배포 패러다임 전환: 다음 20년은 ‘모두에게 같은 버전’이 아닌 ‘각자에게 맞는 최선의 버전’을 안전하게 배포하는 시대
  • 브리틀함의 원인 재정의: AI가 코드를 생성해서 불안정한 것이 아니라, 경계 없는 뒤엉킨 단일 아티팩트 구조 때문 → 구조적 분리가 해법
  • 에이전트 런타임의 역할: 소프트웨어가 실행 중에도 계속 진화하려면 에이전트 런타임이 배포 인프라의 일부가 되어야 함
  • 관측성이 핵심 인프라: 코드 생성보다 관찰(observe)·검증(verify)·조율(coordinate) 역량이 더 중요한 경쟁 요소로 부상
