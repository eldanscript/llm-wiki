없앤 라벨 3개 (2026-08-25)

개인 · 생활 · 계정-보안 — 주제가 아닌 성격 기반이라 축이 달랐고, 애매한 것이 흘러들어 분류된 것처럼 보이는 문제 제거.

사람이 만든 개인/Colleague·개인/Personal 하위 라벨은 부모가 사라져 자동 판정이 안 되므로 PROTECTED_SUBLABELS에 직접 등록해 보호.

아카이브행 판정 순서

rules.is_archive_bound(sender, subject) — classify() 보다 먼저 실행. 순서가 곧 우선순위.

① 전 직장 도메인인가        → 예: 절대 아카이브 안 함 (급여·퇴직·세무 기록 보호)
② 제목 앞머리에 광고 표기    → 예: 아카이브
③ 갈래표가 광고·일회성·뉴스레터 → 예: 아카이브
④ 손으로 확정한 광고 발신자   → 예: 아카이브
⑤ 기존 보관 패턴            → 예: 아카이브
그 밖                      → 라벨을 붙여 받은편지함

①이 맨 앞인 이유: 실제로 전 직장 메일 22통이 갈래표 미등록만으로 보관 처리된 사고 발생 → 선제 예외 처리로 해결.

제목 광고 표기 패턴

공백 제거 후 앞머리만 검사 — Re: (광고)...는 미해당. 정보통신망법이 강제하는 발신자 자기표식이므로 예외적으로 제목 키워드 룰을 허용.

갈래별 정의

  • 광고 — 상품·서비스 판매, 할인, 프로모션, 회원 혜택
  • 일회성 — 인증코드·로그인 알림·영수증·배송·예약 확인·약관 변경
  • 뉴스레터 — 정기 구독물 중 읽을 값이 없는 것 (채용 알림, 상품 소식, 강좌 추천)
  • 보존 — 사람·업무·법률·금융 기록, 그리고 기술 읽을거리

기술 읽을거리는 보존

alphasignal·McKinsey·바이라인·Medium·GlobalSpec·OpenCV 등 40곳은 뉴스레터가 아닌 보존. 한때 뉴스레터로 묶었다가 매일 읽는 것이 받은편지함에서 사라진 교훈으로 분리.

한 갈래 안에 성격이 다른 것이 섞이면, 그 갈래에 건 규칙은 반드시 한쪽을 잘못 다룬다.

  • 갈래표에 없는 발신자는 라벨을 받는다 — 처음 보는 곳은 사람이 한 번 확인 후 갈래표에 편입
  • 코드가 아닌 데이터 파일로 관리: 2천 곳 이상 목록은 계속 자라고, 판단 코드와 자라는 데이터를 분리해야 유지 가능

메일 수명 정책

도착 처리 (2시간마다)

08:10 ~ 22:10 두 시간 간격 8회, 1회 최대 30통. 대상: in:inbox -in:chats newer_than:2d.

├─ 아카이브행  →  라벨 없이 Raingent/Archive, 받은편지함에서 내림
└─ 그 밖       →  라벨·중요도·할 일을 붙이고 받은편지함에 남김

중요도 4 이상이거나 할 일이 있으면 텔레그램·Slack으로 통지.

매일 23:30 daily-sweep 4단계

① 라벨 없는 받은편지함 메일 처리 — 아카이브행이면 Archive, 아니면 라벨 부착
② 하위 라벨이 있으면 부모 라벨 제거
③ Raingent/Archive에서 180일 경과 → 휴지통 (별표 제외)
④ Notion 할 일 카드 보관 (완료 30일 뒤)

분류 학습과 갱신 원칙

결정 원장

state/ledger/YYYY-MM.jsonl — 실행마다 한 줄 기록.

  • src 필드: rule · llm · archive 중 어느 경로가 판단했는지
  • why 필드: 어느 규칙이 맞았는지 명시 (“규칙이 금융이라 했다”만으로는 어느 줄을 고칠지 알 수 없음)
  • 라벨 실제 부착 후에만 기록 — 부착 전 기록 시 실패와 성공이 구분 불가
  • 원장을 LLM 프롬프트에 직접 붓지 않음 — 집계는 코드, LLM에는 결론만 전달
  • LLM 호출은 늘지 않는다 — 판단은 이미 끝났고 값만 기록
  • 하루 39통 기준 연 6.4 MB (한 줄 468바이트)

갱신 절차

  1. Raingent/미분류 큐 확인 — 유일한 사람 검토 큐
  2. 발신자 갈래 판단
  3. cleanup/sender-categories.json 갱신
  4. (필요 시) sync_to_rule.py 실행 — 규칙 변경 시 기존 라벨 상태를 새 규칙에 맞춤

교정 회수 (python -m gmail_triage.corrections)

원장의 판단과 Gmail 현재 라벨을 비교. 다른 것 = 사람의 교정. 세기만 하고 고치지 않는다 — 무엇을 고칠지는 사람이 정한다.

--days 21        며칠치를 볼까
--min-count 3    발신자별 이 횟수 이상만 제안 (한 번은 우연, 세 번은 규칙)

네 가지를 본다: 라벨바뀜 · 보관됨 · 꺼내짐 · 지워짐.

다음 단계 — 자동 제안·승인

원장 vs Gmail 현재 라벨 주기적 비교 → 불일치 누적 → 규칙 변경 제안 → 사람 승인 후 반영. 기준이 자동 반영되면 잘못된 분류가 학습되어 굳는 피드백 루프 위험 차단.

도구: "이 발신자를 광고로 옮기자. 근거는 지난 3주간 교정 5건"
사람: 승인 / 거절

승인 큐(~/agent-home/queue/approvals/)의 첫 소비자 — 되돌리기 어려운 행동을 사람 결정으로 넘기는 구조.

일괄 처리 5단계 규칙

2026-08-25 세 건의 사고(전 직장 도메인 오분류·집계 누락·뉴스레터 갈래 과폭)에서 도출:

① 대상 수집 (읽기만)
② 목록을 사람에게 보여주고 확인
③ 복구용 기록 파일 생성 (이게 먼저 쓰이지 않으면 실행 중단)
④ 1통 시험 → 결과 확인, 실패 시 즉시 중단
⑤ 나머지 실행

②가 오늘 세 사고를 다 잡았다.
